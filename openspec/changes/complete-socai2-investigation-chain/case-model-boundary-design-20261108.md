# Case 模型环节设计与验证方案

2026-11-08 建立，2026-11-09 更新。承接已完成的 A/I 接入及用户确认的[模型设计原则](design.md#12-18按环节目标设计模型调用的共同原则2026-11-08)。第 10 节的 C1/C3 已完成本地接入，尚未部署；第 11 节继续设计 Deep/C6 交接并核对保存原件。本稿各节的候选、历史实测和已实施范围分别说明，不把离线复核当作新模型执行。

## 1. 每一步必须产生什么

Case 的目标是在既定案件范围内，结合告警原件、已有判断及必要补查，给出有依据的案件判断、影响和下一步。成员归并已经由上游确定；下面的“行为联系”用于分析事实关系，不重新审批事件归并或改变成员目录。

| 环节 | 业务目标 | 模型必须给出的判断 | 程序负责的产物 |
| --- | --- | --- | --- |
| C1 材料准备 | 固定本轮要调查谁、什么时间、哪些版本 | 无模型调用 | 冻结成员、原材料、有效 A/I、人工反馈、比较基线及来源映射 |
| C2 背景查询 | 按现有策略取得可用背景 | 无模型调用 | 实际查询请求、回执、返回行、来源和限制；不把查空写成无风险 |
| C3 主分析 | 说明目前支持什么解释，关键证据还缺什么 | 初步整体解释、事实/推断/未决发现、问题答案、相关领域及补查计划 | 短号映射、校验、保存；按真实工具目录和剩余资源安排后续 |
| C4 直接查询 | 执行已有明确绑定的补查 | 无额外模型决策 | 执行已选 binding，保存原返回和实际状态；查询完成不表示问题已解答 |
| C4 Deep | 解决一个指定问题 | 选一个可用查询，或给出有依据的答案，或明确无法确认及缺口 | 限定对象/时间、去重、执行和预算；不会自行扩大范围 |
| C5 图生成 | 表达已有证据中的对象与关系 | 无新增模型调用 | 图及来源引用；图连通本身不证明因果或影响 |
| C6 最终交付 | 综合新增证据，形成此次案件判断 | 最终结论、适用范围、影响、与所选历史结论的变化、必要建议和未决项 | 原合同装配、状态、原子保存、报告渲染、图/证据/成员关联 |

当前默认执行链是 C3 → 按需 C4 → C5 → C6。四领域共用 C3 一次调用；`C3.reanalysis` 有独立入口，但不是默认链额外必经的一次调用。C6 已承担补查后的综合，不再为“写一份报告”追加模型调用。

依据：[执行器](../../../services/api/app/socai2/baseline_executor.py)、[C3 合同](../../../services/api/app/socai2/baseline_analysis_contract.py)、[Deep 合同](../../../services/api/app/socai2/baseline_deep_contract.py)、[C6 合同](../../../services/api/app/socai2/baseline_delivery_contract.py)。

## 2. 现状缺口与最小推进范围

[已有离线核对](../../../docs/operations/evidence/case-boundary-design-20261108-01/current-audit.json)包含 3 份历史 Case 请求，以及两份云审计和一份邮件材料的纯函数投影。本次继续核对其 3 份快照和 15 份源码/配置指纹，均与该回执一致；没有把历史请求称为当前在线实测。

| 已确认现状 | 影响 | 候选处理 |
| --- | --- | --- |
| C1 已冻结有效 I 的 8 条发现和 2 个待核问题，模型视图只取摘要、结论、限制 | Case 缺少直接交接的关键发现和问题，需从其他材料重新推理 | 按明确路径交接发现/问题，保留原文、原范围、引用及 `prior_analysis` 角色 |
| 旧标量投影对样本中的云审计/邮件材料提取到 0 字段 | 已有业务字段可能未通过这条原件路径传入 | 从冻结完整材料按结构映射；先验证覆盖，再去掉后台信息 |
| C3 主用户材料中 `program_facts` 为 7,778 字节 | 管理字段、来源结构和业务事实混排 | 业务需要的时间、对象、等级、回执转短句；完整管理账本留程序侧 |
| Deep 合并所选问题材料和整案基础视图 | 单问题仍可能携带大量无关背景 | 按计划范围、来源依赖和业务块选择材料，不用关键词删减原文 |
| 历史 C6 紧凑输出的 `analysis` 占 79.11% | 再次生成成员、六问、四领域、发现和计划，输出成本较高 | 先明确最终复核职责；输入接入验证后再比较完整输出与显式复核方案 |

“投影 0 字段”不等于整个 Case 提示为空；标题、前序判断等还可能提供信息。“占 79.11%”也不等于这些内容都无用。第一轮候选优先改 **C3 的材料输入和映射**，暂保原业务输出的七类职责，避免同时改输入覆盖、问题体系和最终交付而无法判断影响来源。

## 3. C3 输入：按业务块呈现，原件与判断分开

每次请求由任务指令、业务材料、可选工具及输出 Schema 组成。后台账本单独保存，不作为一大段 JSON 再交给模型。

| 业务块 | 冻结来源与必要内容 | 处理原则 |
| --- | --- | --- |
| 本轮范围 | `Context.scope`、成员目录、Case 有值说明 | 给成员短号、必要对象和调查窗口；Case/Run/租户 UUID、版本、hash 留程序侧 |
| 告警事实 | C1 绑定的 `alert_materials.raw_json/raw_text`，以及原采集说明 | 按业务结构呈现活动、主体、目标、时间、action/outcome、协议、检测依据；保留原始正文及来源角色 |
| 当前 A 分诊 | `Context.alerts.<id>.triage`，沿当前可用性判断 | 保留判定、理由和影响判断的限制，标为历史分析；旧正文编号不变成本轮证据编号 |
| A 实际查询 | 同一采用 A 的 `source_run_id` 对应已保存请求/回执/结果 | 与已有 A 分析分开呈现。先冻结并验证所属关系，不查询“最新一次”替代原回执；查空/失败/跳过按实际区分 |
| 当前 I 诊断 | `Context.incidents.<id>.diagnosis.summary`、`.diagnosis.conclusion/findings/limitations`、`.open_questions` | 逐条带入发现和待核事项，不只保留摘要；不得把 I 的判断升级为原始观察 |
| 人工确认 | 冻结反馈、已采用任务版本及明确结果范围 | 正文保留，身份/时间/适用对象按已有字段给出；未提供授权不等于无授权 |
| C2 背景 | 本 Run 保存的工具返回及实际回执 | 按记录类型和角色组织，原记录与附带旧判断分开；同一记录多字段不算独立证据 |
| 必要限制 | 原材料缺失、前序不可用、来源未接、真实截断/省略 | 只显示影响当前判断的短说明；不显示 `included/omitted` 等后台统计 JSON，也不把材料已发送当已分析 |
| 可选工具 | 本 Run 实际可用能力及绑定 | 写清用途、返回内容、适合解决的问题与限制；用短绑定号选择，不输出 SQL 或自行编参数 |

字段规则复用 A/I 已验证的结构遍历和文本呈现思路，但 **不能直接把 I 的输入包装交给 Case 或导入旧裁剪结果再称完整材料**。Case 使用自己的配置和适配入口，沿冻结材料取值，完整保留数组层次、原字段路径及来源映射；遇到包含点号等不可寻址键，沿现有策略保留完整上层对象，不拼造路径。

省略规则按已知结构定义：空字符串/null、后台身份/版本、重复管理信息可退出模型视图；`0`、`false`、有业务意义的空列表、未知非空业务字段保留。业务用户名、云账号、邮件消息标识或会话标识可能有取证意义，不能用“字段名包含 id”统一删除。非空说明、历史分析和人工正文不由程序概括或纠错。

### I → Case 的范围与引用

- 继续采用 `diagnosis_usable` 的当前条件，不把失败、过期或未采用诊断默认为有效结论。若以后引入失败 I 的有效片段，须另行声明片段验证及用途，本稿不自动放宽。
- 一个发现的声明范围取它自己的 `scope`，不能对每条发现统一套用整个事件成员。事件超出 Case 时，同时记录原事件/发现范围与当前案件交集；模型不能据此把案件外成员纳入本次结论。
- `statement`、`limitations`、`support/counterevidence`、待核问题正文和适用范围均保留。原引用只有在冻结目标真实可解析、且本次确实显示相应材料时，才映射为本轮可引用来源；否则保留来源限制，不制造直接依据。
- 领域关注 A2 时可引用涉及 A1/A2/A3 的相关发现，发现仍保持原范围。领域相关性与每条主张实际覆盖的成员分别校验。
- 若接入同 A 回执需要扩充 C1 快照 JSON，应版本化并同步输入新鲜度检查；旧快照按旧版本读取，不能凭空补回执。本方案不需要改表设计。

涉及：[C1 冻结](../../../services/api/app/socai2/baseline_context.py)、[当前视图](../../../services/api/app/socai2/baseline_model_view.py)、[来源成员映射](../../../services/api/app/socai2/model_input_view.py)、[I 结构遍历](../../../services/api/app/socai2/incident_model_boundary.py)。

## 4. C3 输出：明确初步判断，先保留有下游用途的七类内容

不能直接照搬告警五字段。当前七类输出各有使用者，第一轮候选保留业务职责，通过短编号和内容边界减少复写；字段命名和可选性在候选 Schema 中再固定。

| 当前内容 | 要模型输出什么 | 下游用途及程序边界 |
| --- | --- | --- |
| `summary` | 一份明确的初步整体解释，说明目前支持/不能确认什么 | 后续分析背景；不是最终结案结论，不复写工具调用记录 |
| `members` | 每个成员的分析状态、简短评述、支持依据或限制 | 成员覆盖和最终交付所需；程序只给短号并恢复 UUID，不能替模型填“已分析” |
| `findings` | 事实、推断或未决发现，范围、支持/反证、必要替代解释 | 问题、领域、图和最终判断的基础；保留跨成员真实范围 |
| `questions` | 六类既有问题的明确答案/无法确认原因及依据 | 供 C4 和 C6 使用；程序提供问题目录，模型不重写问题文本 |
| `domains` | 身份、云、钓鱼、内部威胁的适用性、关注成员和相关发现 | 保持现有领域工件；它们是分析方向，不是四次模型调用或四个工具 |
| `conflicts` | 哪些判断冲突，已解决还是未解决，依据是什么 | 供后续核查和 C6 复核；无冲突返回空数组 |
| `followups` | 缺什么证据、解决哪个问题、查询/Deep/图/人工、对象范围及优先级 | 程序执行计划；已有明确绑定时直接查询，不为执行它再加一次 Deep |

六类现有问题为原始事实、行为联系、行为性质、授权、影响及未决/覆盖。覆盖问题中的实际查询状态由程序给出，模型只分析仍影响判断的缺口；行为联系问题不成为重新归并事件的要求。此次不直接删除目录，若后续要调整数量，需核对 C4 路由及 `results.questions` 的读取兼容。

保留本轮成员/来源/对象/绑定短号。Finding 的本地编号可用于同一答案内交叉引用；后台 UUID、来源工件位置及版本由程序恢复。输出适配后仍走现有结构、范围、来源与局部保留校验，不能靠删除错误引用或补造理由让旧校验通过。

## 5. Deep：围绕一个问题决定查、答或交接

保留现有 `action=query/answer/handoff` 语义：`query` 选择一个可用 binding 并说明所缺证据；`answer` 给具体答案、支持/反证与限制；`handoff` 明确不能确认的内容及需要的材料。程序已知的 `question_id` 可由外层请求绑定，候选输出如省略它，应在适配时恢复，并继续检查跨问题污染。

输入包含该问题、原 C3 对此问题的判断及补查理由、相关原件/反证、已执行查询的真实状态和新增返回，以及剩余可用工具。相关材料按已冻结计划范围、结构关系和引用依赖选择；共用来源、范围不明及影响整体判断的人工反馈不能因简单成员过滤而丢失。每次重新带齐必要依据，不能假定上一轮对话仍在模型中。

当前六类问题的 scope 来自冻结 Case；旧实测 `impact` 涉及全部三成员，因此现阶段不能声称“已经只发某一告警”。输入选材与工具执行边界分开：候选聚焦一个问题不自动扩大或修改冻结 binding，也不把按主机/时间查询的每一行都归为该成员告警。

当前 C4 能力是进程活动、网络连接、认证活动和产品主机详情。没有实际可用的审批/云/邮件取证工具时，模型不能凭领域名称选择一个并不存在的能力；需要这些材料则说明缺口。当前产品主机详情是当前快照，不是历史授权或历史进程树。能力说明沿配置和运行可用性生成，不写死“永远只有四个工具”。

依据：[Deep 输入](../../../services/api/app/socai2/baseline_deep.py)、[工具说明](../../../services/api/app/socai2/baseline_tool_catalog.py)、[计划调度](../../../services/api/app/socai2/baseline_dispatch.py)。

## 6. C6：最终判断必须重新作出，减少重复表达分两步验证

必须保留的业务输出是：最终案件结论及其范围/依据、最终有效发现和问题、确认的影响与不能外推的部分、与指定历史结果的变化、必要建议和未决限制。实际查询、执行失败、交付状态及报告布局由程序负责。C3 失败时仍按现有规则进入 C6 尝试收尾；没有有效模型判断时明确系统交接，不伪造成功。

输入应包含必要原始依据、有效 C3 判断、原补查计划及逐项真实回执、Deep 答案、实际新增证据、明确人工结果、可用比较基线和图的限制。先校验已执行计划与原 `initial_analysis_artifact_id + followup_index` 对应，不能把 C6 新建议冒充已执行的旧计划。C6 引用重新映射到本次来源，旧正文编号不自动有效。

第一步保持完整 C6 业务输出合同，验证新材料交接和最终复核效果；不把 C3 无条件复制到 C6。第二步再比较“完整重述”与“显式复核后组装”：模型明确哪些旧条目保留、修订、撤回及新增，程序只依据这些明确指令装配最终快照。后者目前只是待验证方向，尚未选定 Schema 或实施。

显式复核方案若推进，必须满足：基线固定且校验有效；每个需要复核的旧条目都有明确处置；保留条目的当前引用仍可解析且范围正确；新增矛盾不能被默认继承掩盖；C3 无有效基线时允许独立形成完整最终结果。不采用任意 JSON Patch，也不能因本轮没有新增材料就自动判旧结论成立。

报告仍由同一份最终结果渲染，不新增“报告撰写模型”。历史 79.11% 仅证明值得检查重复量，尚不能承诺压缩比例、时延或质量收益。

## 7. 原字段与读取兼容

| 既有保存/读取内容 | 候选适配责任 |
| --- | --- |
| `alerts.description`、`alert_materials.raw_text/raw_json` | 保留原件；模型视图的省略不改变原读取和查询 |
| `results.conclusion/conclusion_state` | 来自有效最终判断；不由 C3 摘要或程序猜测替代 |

| 图、证据索引、`report_json` 和报告文本 | 沿现有同轮引用与保存链，不用展示摘要替代原证据 |
| `runs`、`run_steps`、输入新鲜度和采用指针 | 由程序事实确定，失败/unknown/局部拒收及历史状态不被新适配回填 |

## 8. 各层输入结构的取舍

用户指出不只是旧候选第 165 行 `program_facts`，每一层都有无用信息。本轮在独立离线候选中按结构处理，沿既有 task 3.30；不改生产执行器、数据库或模型原答。

| 层次 | 模型需要 | 程序保留或合并呈现 |
| --- | --- | --- |
| 任务、范围、对象、问题目录 | 本轮要回答的问题、有效成员/对象和时间边界 | 空范围字段；同一对象重复的成员包装改为一条对象及成员列表 |
| 原材料的字段和嵌套容器 | 行为、对象、结果、业务属性及非空原文 | 已知元数据、空 enrichment 包装和计数；未知业务分支保留，不能按字段名带 ID 就删 |
| 告警背景、分诊、事件分析 | 上游等级及时间、原判定/理由/建议、每条发现自身范围 | 后台状态、嵌套空可选字段；原分析正文和旧错误不改写 |
| 发现及待核问题内部 | 主张、观察/推断状态、依据、反证、范围与实际缺口 | 无值窗口、空外部成员和空引用包装；引用缺失仍明确，不能补造来源 |
| 查询回执及返回行 | 工具、真实状态/行数、对象/时间/来源限制、错误和截断 | 固定限制按适用记录共用一次；同值字段可合并标签，不能合并独立查询/返回记录身份 |
| 程序事实 | 尚未呈现的业务事实、不同时间/等级、实际材料缺口 | 已在确切同来源显示的值用映射去重；版本、来源对象、执行时间和正常状态统计留账本 |
| 工具目录 | 用途、能返回/解决的问题、不能回答什么、可用 binding 及边界 | 相同返回字段和限制共用一次；不得因省字删掉工具选择所需能力说明 |

规则放候选配置，按类型和精确结构路径递归应用，不匹配厂商、主机或样例值。只在声明可选的路径省略空值，`0`、`false`、业务空列表及未知结构不做通用清空。重复事实必须值和含义一致；活动时间与告警时间不可互相替换，不同来源仍有独立编号。共享内容的适用范围显式列明，账本保存原值、映射与省略原因。

以同一组原材料、I 发现、A 回执和旧输出做离线前后检查，分别统计主正文、工具目录及完整请求字节；保留每条原观察、分析正文、范围、来源和真实查询状态。候选减小不等于模型判断更好或更快，真实 tokens/质量另测。

继续收敛时，已知字段按原结构路径及现有词典转成业务名称，未知编号、不同数据类型或未知分支保留原值。显示层可以合并同材料、同角色、同语义且值相同的多种表示，所有原引用仍分别可用；按成员/角色集中展示，不混合观察与标签。发现/问题的原成员范围进入标题，窗口、对象和非共有限制仍留正文；跨案件成员不能因标题只显示本案成员而消失。所有这些映射另留呈现账本，原值和原范围不改。

C3 只负责提出补查问题和选择已有 binding。工具用途、返回内容的业务说明、能/不能回答的问题及边界继续提供；只有能力说明完整且返回字段属于已审核字典时，逐字段技术清单才留程序侧。新增未知字段、空能力说明均回退保留技术清单，不因工具名或数量写死规则。完整请求固定后，使用现有后端 `/tokenize` 与 chat template 核算输入、Schema/外层字段、余量和输出预留；该检查不启动生成，不记作模型质量测试，也不写业务库。

## 11. Deep/C6 交接细化（2026-11-09，设计及离线核对）

本轮只读已保存的同一 Case、C3/Deep/C6 请求和原答，核对来源、范围、问题和原计划的交接；不调用模型、不创建 Run、不连接数据库、不改生产流程。离线工具和核对结果另存独立批次，不覆盖旧模型批次。

### 11.1 Deep 的目标是解决一个证据缺口

输入按以下顺序组织：本次问题和补查目的 → 已有判断及其依据 → 原始材料/反证 → 已做查询及结果 → 尚可使用的工具。模型应区分“能描述已知行为”和“已回答本次问题”。C3 的补查目标是待评估需求，不强制执行某工具；已有证据足够时可以直接回答，证据不足时必须明确剩余缺口。

问题范围、请求关联和实际执行绑定由程序持有。模型输出候选为 `action、binding_id、reason、answer` 四项，去掉程序已知的 `question_id`；适配器从本次冻结请求恢复它，仍以现有 Deep 合同校验。`answer` 保留 `state、text、support_ids、counter_ids、alternatives、limitations`。`answer/unresolved` 是对现有证据的未决回答；`handoff/unresolved` 表示需要目录外资料或人工处理；二者均不表示问题得到确定解答。

选择材料时以冻结问题范围为上限，结合所分配补查的结构化成员/对象和引用依赖排序。不能把计划里单个成员直接改成问题的唯一范围，也不能丢掉共同上下文、人工陈述、反证或范围不明材料。工具 binding 不随输入压缩改变。后续模型请求必须带齐必要依据，不能只给上次模型总结。

### 11.2 C6 先完成判断交接，再减少输出

C6 的输入须交接实际接受或独立保留的 C3 内容，原答中拒收的部分不能混入有效判断。逐项标明它是历史判断，并将结构化支持/反证引用按原来源映射到本轮可见证据；旧正文不改写。引用缺失要明确标记，不能靠保留旧编号声称证据仍可见。Deep 答案也要交接其支持、反证和限制，不能只复制结论文字。

原补查计划继续由 `initial_analysis_artifact_id + followup_index` 绑定真实执行回执。模型输入用计划短号呈现目的、范围、实际查询、返回、问题答案和剩余缺口；工件 UUID、执行排序等程序字段留在映射账本。查询完成、产生答案、答案确定三个事实分开。C6 不得把所有已执行计划都写成“已解决”。

第一阶段保留当前六块输出：`analysis、conclusion、closing_note、comparison、impact、recommendations`，只改必要输入与可恢复的身份短号。它们最终仍装配为现有结果/报告字段；报告从同一最终结果生成，无新增报告模型。没有有效 C3 时沿独立最终分析及系统收尾，不能伪造“保留旧判断”。

第二阶段才试验显式逐项复核：保留、修订、撤销或新增。每个旧项目都必须得到明确决定；保留时必须能看到原项目及完整引用依赖；新增反证必须进入本轮。范围、角色、引用重新校验，不能默认继承未回答的旧项。该方案可能增加输入，不能只凭旧输出的 `analysis` 占比宣布节约 tokens。

### 11.3 直接验收与推进顺序

1. 离线核对旧 Deep/C6 实际输入、C3 有效内容、原计划及输出；统计显式来源可达性，区分原始来源与其投影，不能把相同字段的重复呈现算独立证据。
2. 接入时复用配置化完整业务材料源，不再经过旧标量视图取回一份更少的材料。分别验证冻结同 A 回执、I 发现/问题、云/邮件及未知业务分支在 Deep/C6 的可达性。
3. 对结构化来源映射做断言：本轮编号有效、历史文本不重写、原跨成员范围保留、缺支持或反证不得静默继承；C3 局部拒收及完全失败均有明确路径。
4. 验证 Deep 四项候选恢复成旧合同、C6 现有六块与原查询/报告字段兼容；新旧 Run 均可读，来源/采用/执行状态不混用。
5. 材料补齐、呈现改变、输出精简分开比较。未完成完整请求容量核对前不发送候选；真实模型测试另起获准的新批次，已结束 C3 批次不再派发。

本节离线核对已完成：48 份保存工件、C3/Deep 到 C6 的结构化引用同源关系及两种输出适配往返均有回执。具体实例、重复呈现与判断交接缺口见[交接分析](case-followup-handoff-20261109.md)。任务 3.30 保持未完成，本节不构成 Deep/C6 已接入、线上发布或质量通过的声明。
