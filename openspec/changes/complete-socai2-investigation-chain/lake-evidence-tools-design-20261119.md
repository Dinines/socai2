#### 单条解析与多条理解分开

1. **确定单条事实。** 按类别及来源结构合同配置路径、类型、角色和枚举；字段有值不等于可解释。动作、活动结果、控制处置、上游告警标记分别处理。完整原文已保存但尚未进入工具业务视图的字段，记为投影缺口，不记为原数据丢失；源日志本身缺的字段不能靠映射补造。
2. **按问题选必要派生结果。** 频次/分布、对象变化、事件顺序、配置内容、扫描覆盖、来源证据关系分别适用于不同问题，不给11类统一套计数模板。程序执行去重、计数和时间排序，模型判断它们与当前调查的关系；模型不负责从整包原JSON手工找字段或统计。
3. **统计范围有依据。** 先按现有事件身份去除同文重投，不把真实多次行为去重掉；不同UID内容相似仍可能是多次观察。只能统计已确认覆盖的记录，分页上限前的片段不能称全时间窗总量。缺发生时间的行保留，不用入湖时间认定凌晨行为；业务时区、时间桶和工作时间规则走配置。
4. **网络审计按端口角色理解。** 先按源IP＋目标IP＋目标端口＋协议聚合访问目标，再分别看控制结果/策略、发生时间、重复次数、目标/端口去重数量。源端口保留用于会话/重复辅助，不把源端口差异直接判为多端口探测；是否为固定源端口及谁是发起方须看明确字段/协议，不能从数值或策略标题猜。
5. **客观模式不等于异常结论。** “凌晨多次访问同一端口”可由程序报告次数和时序；是否异常还需资产用途、授权任务或有覆盖依据的历史行为。没有历史对照不声称偏离基线，也不把工具派生模式自动升级成新告警。本批单例未证明实际存在这种模式。
6. **输出与追溯。** 工具给出必要业务事实、适用汇总及少量有代表性的明细；摘要与明细共同保留后台record_ref和原路径。只把业务结果供分析，执行参数/上限/失败等留后台回执，按根AGENTS区分查空、失败与未知；同源检测及活动记录的关联不冒充独立证据。

#### 描述是事实表达，不是新的判断

输出保留结构化事实与自然语言两种视图；后台另存配置/模板版本、原路径、冲突/遗漏、事件引用和完整原件。一个字段的合法0/false/有效空列表不得因模板真假判断丢失；未知枚举保留原编号，未解析不改成“成功”“拒绝”或“没有”。描述不写入原日志、不覆盖来源说明或修改告警字段合同。

例如网络审计配置把`action_id`与`disposition_id`分别映射为控制动作和处置；只有确实存在且适用时，描述才包含“该访问记录被策略拒绝，记录的处置为阻断”。策略缺失时省略策略名，控制结果未知时使用已知端点/时间描述，不套固定拒绝句。认证模板表达认证服务、对象和结果；合规模板表达检查对象、检查项与结果；管理操作模板表达操作者、资源和提交配置。原文说明如需提供，按来源正文引用而非由程序语义改写。无须为每条日志额外调用模型生成描述。

工具可以有多个业务名称，但共享查询/解析/描述执行器，通常增加能力只需新增类别映射和模板。配置能解析某类，不等于该类已具备可用查询对象或正式工具入口：2004数组端点仍需接入既有冻结对象/固定数组查询，未完成时保留未接线状态；不能只挂一个模板就对模型宣称已可取证。新工具目录由验证通过的能力配置提供，保留现有tool_name和已冻结调用兼容。

### 自动映射与重复处理规则

1. **先定语义和角色，再比值。** 根设备、连接源、连接目标、采集器、外设、登录账号和操作人分别保存。`metadata.loggers[].device.uid`不能补根`device.uid`，厂商`asset_id`也不能按名字认成终端资产ID。相同IP/文字不自动成为同一角色。
2. **同角色别名按明确路径和类型合并。** 标准根字段优先，已定义扩展只在根缺失时作为候选；null/空/类型错误不静默回填。IP/MAC仅做明确比较规范化，原值与全部出处留后台。不同值保留冲突，不任意挑一个。厂商字段通过选定来源结构合同配置，不在业务代码按厂商/主机/样本值分支。
3. **重复正文只选一份，不改写内容。** `finding_info.desc/message/legacy.event.description`及已核别名逐字一致时一次展示并保留多出处；内容不同可分别是事件说明与规则背景，不能强行当一个字段冲突或让程序概括。不同UID记录不因标题/说明相同而合并；同UID同文重试沿4c规则，异文保持待核。
4. **按字段解释类型。** 明确布尔字段允许受控的布尔/0或1/对应字符串转换；`false`、计数0和枚举Unknown保留。资产ID、端口、状态、时间分别校验，不能全局把数字字符串或`result`统一转换。秒/毫秒/纳秒依字段合同，不按位数猜；来源时间回退警告也需保留。
5. **数组保留同元素关系。** evidences/resources/网卡/配置子项保留原索引及整体范围；不能将第0项源地址与第1项目标地址拼成一条连接。重复根设备和证据内设备可以共享对象引用，但保留证据组与来源角色，不增加独立证据数。
6. **明确路径才解码嵌套JSON。** 本例管理配置按`param::<json>.conf::<json>`两层解码并保留原字符串；不递归猜解所有字符串，不执行脚本/命令或打开正文中的下载地址。未知扩展及二进制样式正文保持可读回引用，列入待映射清单。
7. **三份用途分开。** 湖保存完整JSON；后台保存别名、转换、冲突、数组及原文关联；工具按调查问题输出业务字段。设备历史快照按需要取，采集流水和重复库存背景不随每条网络日志进入分析模型。已落湖不等于工具已使用。

### 4001业务定位纠正（2026-11-20）

负责人指出本批发送的是网络审计、禁用端口及拒绝等记录，正常连接可能没有发送。复核已获准的同一条4001样本，其来源、策略和安全控制字段支持“访问被拒绝/阻断”的判断；本轮未读取第二条或扫描全批，不能将单例推成全批均拒绝。当前接入设计按网络审计/访问控制使用，正常连接覆盖没有得到证明，工具查空也不能证明没有连接或通信。

业务结果保留设备字段、观察时间及来源证据角色；record_ref、规则版本、查询预算和冲突诊断留后台。完整原文仍经现有材料读取；新工具不要求新建ClickHouse表或给每个设备属性加列，也不更改对外告警DTO。目录/policy必须同时增加该工具的用途、可回答问题、不可回答问题及返回字段，不能只把5001塞进旧三类枚举。

## 现有代码能力和具体缺口

1. `baseline_evidence_tools.TOOLS`仅有process_activity(1007)、network_connections(4001)、authentication_activity(3002)。`lake_evidence_v2.request`仍从该映射生成根class_uid过滤；公共HTTP能按其他class查询，不表示C4已提供对应工具。
2. v2绑定来自Case冻结告警的host/IP对象，程序绑定来源、映射、对象角色、窗口、profile摘要和行数上限。没有可用冻结对象就没有当前v2候选；不能把3f允许的无selector浏览直接放进模型工具，变成全来源扩查。
3. `baseline_tool_catalog.capabilities`检查运行策略工具名集合严格匹配；新增工具要同时更新工具注册和配置说明，不能只加SQL。返回字段描述也须按新工具调整，不继续把统一旧三类字段表冒称完整业务能力。
4. `baseline_semantics`只识别三类event_kind，选择字段集中于进程、端点、用户、文件路径及流量等。新类的查询成功仍可能没有可分析字段；必须为选定工具定义实际业务投影。完整ocsf_json留后台，不作为模型整包输入。
5. 3f已提供来源/窗口浏览、对象角色过滤、先去重后分页、完整材料及C4 v2共享查询。复用这些能力；旧v1和已冻结v2合同继续识别，不能把旧Run静默改成新查询。
6. `lake_ingress._fingerprints`只读取`file.fingerprints`；OCSF 1.9的File对象定义的是`file.hashes`。`baseline_semantics`虽兼容两个容器，但仅凭算法名称认SHA256，尚未处理只有合法`algorithm_id`的情况。属于源码/公开Schema差异，不据此声称本批存在该问题。首工具若用文件哈希，应同元素核算法/值及冲突；本步只登记，不展开修复其他链路。

待审清单只含class_uid、白名单标准字段路径、JSON类型和非空/可用性，以及同一记录是否同时具有对象与可靠事件时间。未知自定义键不展开，不含数量、比例、正文、ID、具体对象、时间、产品名、来源值或摘要。完整盘点计数仅留21私有报告。字段分别标根路径及`unmapped.spirithub.partial_fields`，不把两者自动合并。

首工具依据三个条件：实际存在；同一记录具备查询条件与回答问题的最小语义字段；现有工具确实缺少该能力。记录多不等于优先。缺对象/可靠时间时先判断是否需要冻结原文定点读取，不能拼接不同记录的字段或虚构host/IP。

以下为公开Schema支持的条件选项，**不是本批实际类别清单或已选工具**：

| 条件候选 | 能回答的问题 | 最少业务字段；缺项时的边界 |
| --- | --- | --- |
| 已有进程/网络/认证工具 | 冻结对象周边发生过什么对应活动 | 按当前三类逐项核查询角色、可靠时间和相关进程/连接/用户字段；能复用则先复用 |
| File System Activity / 1001 | 对什么文件做了什么动作、由什么进程/账号执行 | file、activity、actor字段；路径不证明内容，成功不证明获批 |
| HTTP Activity / 4002 | 冻结端点发起了什么HTTP请求、返回了什么结果 | http_request、http_response及端点；不自动发送请求正文、cookie或完整headers到模型 |
| DNS Activity / 4003 | 查询了什么域名、返回了哪些解析记录 | query、answers及端点；域名解析不等于随后建立了连接 |
| Detection/Compliance Finding / 2004、2003 | 同对象或冻结原文中，上游检测/合规系统报告了什么 | finding_info、evidences或compliance；标明来源判断，不当独立活动证据或自动再次创建告警 |
| 根class0/partial | 原记录声明了什么类别，哪些字段仍可追溯 | 必须同时保留根类、声明、原路径、冲突和缺项；不重写原件、不把所有class0当同类；无可靠分类则只允许材料读回 |

Schema依据：[File System Activity](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/events/system/file_activity.json)、[HTTP Activity](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/events/network/http_activity.json)、[DNS Activity](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/events/network/dns_activity.json)、[Detection Finding](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/events/findings/detection_finding.json)、[Compliance Finding](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/events/findings/compliance_finding.json)。这说明公开字段语义，不证明当前生产者或本批具备相应字段；本接入全局metadata.uid/无更新合同保持。

## 接线方案

调用链为：冻结Case材料及对象→程序生成可用binding→C3选择已有binding_id→C4固定查询→保存原始回执/业务投影/精确湖引用→C6按本次问题使用业务结果→既有HTTP读取工件和原文。对外路由仍经investigation_http用例端口，核心不反向依赖HTTP。

| 接线位置 | 预计修改方式 |
| --- | --- |
| 工具及配置 | 在现有工具注册和policy中只加入首个选定工具，写清purpose/inputs/can_answer/cannot_answer；若返回结构与旧版不兼容，使用新内部合同版本并保留旧版派发，避免改写冻结Run |
| 候选绑定 | 复用v2的租户、来源、映射、对象角色、窗口、profile摘要和上限。按可用字段提供相关角色；没有对象的材料只可另设计冻结lake_ref定点读取，不开放任意来源/任意对象扩查。metadata.uid、来源控制字段和查询执行参数留后台 |
| 固定查询 | 复用LakeQueries的固定SQL、范围检查、去重、排序与预算。新根类无需新增ClickHouse列，类内业务字段从完整JSON按白名单投影。需要partial时，先定义严格类/字段恢复条件，并在过滤和分页前应用；不能取一页class0后才过滤、漏掉后面的匹配项 |
| 业务投影 | 只为当前问题选择字段，保留原值、字段路径及角色；数组按元素保留关联，不把不同element字段拼成一条事实。合法0/false和有意义空数组不能按空值丢弃；缺失/null/冲突分开。上游发现、活动记录和人工判断不相互冒充证据 |
| 保存与读取 | 复用C4的tool_request/tool_response、证据工件及完整湖引用；返回可用业务字段与原文关联。外部告警字段名、类型、空值和路径保持，不新增告警DTO；确需改公开合同再列具体影响确认 |

没有新类别就不新增工具。若只有Finding而无独立活动，优先讨论“上游发现材料读取/周边发现”能力，输出明确来源报告角色；不得称已查到进程、网络或认证证据。若三类已有数据只是字段未投影，则该修正作为首个明确步骤。

## 5a字段处理与查询接线的具体约定

以下是可直接用于5b实施的规则和映射，尚非运行中的新能力。首工具必须由获准使用的实际覆盖结果确定，不按下载目标名单、日志条数或现有工具名字推断。

### partial、缺失与数组

| 输入情形 | 预计处理 | 查询/结果含义 |
| --- | --- | --- |
| 根路径确实不存在，且上游明确标记partial | 读取同一路径的`unmapped.spirithub.partial_fields`，记录原路径及partial来源 | 通过类型、语义及相关对象检查才可作字段投影；不覆写完整JSON |
| 根字段为null、空字符串、空数组或祖先类型错误 | 保留该状态，不自动回填；空对象中的缺失子路径可独立判断，但不做对象整包深度合并 | 未报告、明确空及类型错误分开；不能用空字符串/0统一表示 |
| 根与partial同一路径值不同，或JSON类型不同 | 根原值和partial原值留后台，记录冲突；该字段不用于确定性匹配或组合证据 | 不以root优先为由宣布数据一致；无冲突的其他字段仍可用 |
| `0`、`false`、合法空数组 | 原样保留；是否足以回答问题另判 | `false`不是缺失，空answers不等于DNS查询失败，未知activity不推断动作 |
| 根class为0且有partial分类声明 | 根类保持0；检查声明class/category/activity/type及版本、目标类活动枚举后生成内部effective类别 | 算式成立只是一项检查，不是完整OCSF符合性；不把所有class0归到同一工具 |
| 身份或根事件时间缺失 | `metadata.uid`只认根路径；时间沿现有`time`和`event_time_source` | 不以finding_info.uid替代全局ID，不拿入湖时间当发生时间；冻结原文仍可定点读取 |
| 数组含对象、null或混合类型 | 选择完整根数组或完整partial数组，保留顺序/元素位置；逐元素投影，坏元素保留在原文及诊断 | 不按下标跨来源补齐，不展开多个数组形成笛卡尔积，不拼接不同元素的字段 |

后台投影保存`record_ref`、语义规则版本、原字段路径、来源角色、数组元素位置及缺失/冲突诊断。业务视图只带当前问题所需字段及证据角色，后台诊断/执行参数不整包进入分析模型。数组元素的位置用于回指该原文版本，不当成跨版本稳定ID。

### 公共字段映射

| 原始路径 | 查询/后台用途 | 业务投影规则 |
| --- | --- | --- |
| 根`metadata.uid` | 已确认的全局事件身份；关联现有source_event_id及record_ref | 留后台，不自动变为证据独立性的证明 |
| 根`class_uid`及partial分类声明 | 保留root_class；另算effective_class/分类依据 | 上游声明和程序校验状态分开，不改原文 |
| 根`time` | 现有event_time及`event_time_source=ocsf_time_ms`，窗口前闭后开 | 明确为该记录事件时间，不能直接给数组内每项活动补一个发生时间 |
| `device.hostname` / `device.ip` | device_hostname / device_ip，绑定角色device | 表示设备；不复制成src_hostname而改变源端点含义 |
| `src_endpoint.hostname/ip/port` | src_hostname / source_ip / src_port，角色source | 保留源端点；是否发起方另依语义，不能只靠src推断 |
| `dst_endpoint.hostname/ip/port` | dst_hostname / dest_ip / dst_port，角色destination | 保留目标端点，与device/source分开 |
| `activity_id`、`status_id`、`severity_id`、`is_alert` | 类型校验及来源声明；is_alert不作取证上下文的统一筛选开关 | 区分上游动作/状态/等级与本地调查结论 |
| 完整`ocsf_json`和现有`record_ref` | 固定版本原文保存及读取；校验source_version | 按下表选择业务字段，不整包透传模型 |

### 类内字段映射与候选工具

这里只为工具选择给出合同选项；5b只实施最终选定的一项。缺少查询前提时保留为材料读取，不能用不同记录补齐。

| 候选工具 | 业务字段路径 | 最低能力与边界 |
| --- | --- | --- |
| 复用process_activity / 1007 | `process.name/pid/uid/cmd_line/file.path`；`actor.process`、`actor.user`各自保留角色 | 目标进程与发起者分开；父进程不凭名称构造完整进程树 |
| 复用network_connections / 4001，网络审计/访问控制查询 | `src_endpoint`、`dst_endpoint`、`connection_info.protocol_name/direction_id`、可用`traffic`、`action_id/disposition_id/policy` | 同条审计记录的端点、控制动作与结果；拒绝不等于连接建立，未提供initiator语义时不宣称源端必为发起者 |
| 复用authentication_activity / 3002 | `user.name/uid`、`actor.user`、动作/结果、设备及两端点 | 登录目标与执行主体分开，不能把缺失结果写成成功 |
| file_activity / 1001 | `file.name/path/type_id/size/hashes[]`、`actor.process`、`actor.user` | 文件操作；`hashes[].algorithm_id/algorithm/value`必须来自同元素，校算法和值；不查询文件内容 |
| dns_activity / 4003 | `query.hostname/type`、`rcode_id`、`answers[].hostname/type/rdata/ttl` | 查询、返回码及逐条答案；解析不是后续连接证据 |
| http_activity / 4002 | `http_request.http_method/url.hostname/url.path/url_string`、`http_response.code` | 有请求可答请求，有响应可答返回；缺另一侧则明确缺失；不默认向模型带cookie/headers/body |
| detection_findings / 2004 | `finding_info.uid/title/desc/types[]/analytic`、`evidences[]`、`resources[]` | 上游报告了什么；evidences中process/file/endpoints按同元素投影，标为来源所附材料，不转换成独立1007/4001记录 |
| compliance_findings / 2003 | `finding_info`、`compliance.status_id/status/control/checks[]`、`resources[]` | 上游合规检查与对象；失败不直接等于入侵，缺结果不当通过 |

OCSF依据：[File对象](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/objects/file.json)、[Evidence Artifacts](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/objects/evidences.json)、[Finding Information](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/objects/finding_info.json)、[DNS Resource Record](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.9.0/objects/dns_resource_record.json)。这些是标准语义及设计字段，不表示本批实际具备全部字段。第一版审阅报告只扫描profile列明的字段；其他嵌套字段只在私有库存登记，具体工具选定后再补其必要路径的结构核对，不声称白名单已覆盖所有标准字段。

### 固定查询的实现落点

1. **目录和冻结绑定**：复用`baseline_tool_catalog`、`lake_evidence_v2`及policy。只注册选定能力；冻结来源/映射、对象角色、窗口、上限、查询和投影规则版本。扩展类别/partial语义使用新的内部合同，旧v1/v2按原派发，不能让旧Run复跑时换含义。
2. **范围和去重**：复用`LakeQueries`配置和参数绑定。先限定tenant/source/mapping，沿现有逻辑版本去重，再筛时间/对象/类别。不同source_version不因同一个metadata.uid被任意覆盖；后续告警交付仍按4c的同ID异文阻断。行数、字节和时间预算继续来自配置。
3. **有效类别及字段选择**：新规则先检查根字段存在性及类型、partial标记及声明一致性。只需要返回的类内业务字段在Python投影；参与过滤的有效类别及对象条件必须在分页/limit前实现。不能先取一页class0，再在Python过滤成目标类并误报后面没有记录。
4. **复用列与JSON**：已经正确投影的device/source/destination及时间走现有列；类内字段从完整String JSON读取，不为本轮候选字段一次性加列。涉及partial恢复或冲突的查询条件不能只信空值化后的列，须与原JSON选择规则一致。数组条件在同一元素内完成，例如一个`arrayExists`条件同时检查该元素两字段；禁止两个独立any命中后合成同一证据。
5. **缺失语义**：ClickHouse的JSON提取函数在缺失/错误类型时可能返回默认0、空字符串或空数组。因此使用`JSONHas`及祖先/值`JSONType`判断后再取值，不能把默认值当真实内容；`JSONExtractArrayRaw`也需先分清缺失、null、错误类型和合法空数组。[官方JSON函数合同](https://clickhouse.com/docs/sql-reference/functions/json-functions)注明这些函数行为。当前23.8目标仅使用该版本已具备的函数，5b需要原生验证；本步没有执行SQL。
6. **两种能力分开**：周边活动/发现查询必须有冻结对象、可靠时间和限定来源；冻结原文定点读取只接受Case材料已有的完整record_ref，不要求伪造主机或时间，也不借缺对象开放任意检索。此分支只有覆盖结果证明确有需要时才选作首工具。
7. **结果保存与HTTP**：C4保存请求、原始响应、逐记录业务投影和精确record_ref；原件经现有材料读取端口返回。查空、未覆盖、缺绑定、冲突阻断、失败/unknown分别保留；仅筛出了合格记录不等于来源覆盖完整。公开告警DTO及A/I首次接收合同不改。

5b的直接验收限定为：选定工具的一组必要合成边界；同批湖中一段明确范围实际查询；程序核返回版本集合/角色/窗口及完整原文摘要；保存后读回。ES导出是字段设计输入，不能直接替代ClickHouse命中证据。5c才进入一次实际C4保存和HTTP工件读回；不在本轮顺带运行Case或新增全类型工具。

## 查询验证方案

1. **输入冻结**：固定来源profile、规则版本、预算和同批湖范围。具体查询对象、时间和原文版本只在受控环境生成/保存，不手工改样本补字段。
2. **正确命中**：程序从该类中选择同条具备查询条件的记录，使用实际网关查询；对命中版本集合、类/角色/窗口和稳定排序作程序核对，再按record_ref取完整原文。使用集合和摘要，不要求人工逐条阅读正文。
3. **必要边界**：一组对应合成材料验证角色不串、来源不串、窗口前闭后开、重复去重、partial缺失/null/冲突以及返回原值；只补首工具受影响边界。复用3f已有分页、完整正文和owned连接证据，不铺压力/故障矩阵。
4. **状态真实**：实际无该类为not_covered；有类但缺字段为not_queryable；完成且零条才是empty。超限、失败、unknown保留原结果。不能把无记录/缺绑定改成工具成功或调查安全。
5. **保存读回**：5b核查询及原文；5c再核真实C4请求、原始响应、投影及引用保存后经HTTP可读。若执行了调查Run，按规则更新4177；只读盘点和设计没有Run，不伪造运行记录。

实际验证通过需同时证明查询命中、结果字段可用、原文关联可读；如果只通过结构/合成，明确保留实际未覆盖。整个change的结束审计、发布和产品联验继续沿原任务。
