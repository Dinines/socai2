### 事件失败回执的页面读取

真实失败回执的事件详情仍提供主体、成员数量和记录链接。单轮诊断通过事件作用域下的 GET 读取，数据库按事件和 Run 联合校验，响应中的 Run 合同提供 `id` 和 `kind`。4173 现有读取额外校验了该合同未定义的 `run.incident_id`，导致正确的失败或成功回执被拒绝。

本步按现行合同对齐 4173 所选轮次读取。只核实际返回的 Run 身份、类型及结果来源，等级意见沿原有独立范围校验。定向复验覆盖成功记录、旧轮次与当前判定的区别、错误的 Run/结果身份，以及失败回执可读、诊断空值及任务失败原因可见。直接验证用真实回执的结构和合成值，模型、数据库及 HTTP 合同保持现行版本。

已核对两批原 HTTP 回执及数据库。告警分诊、事件资料和失败原因均可读，事件诊断和判定按实际返回空值。4173 已修正由额外身份字段导致的拒收，并按实际状态显示失败原因；31 项服务模式页面测试和 37 项后端定向检查通过。事件模型连续空白仍阻断完整联验。

这个步骤覆盖分诊保存、运行目录、数据库增量和交接。复用当前五字段分诊输出。自动分诊以新鲜且已采用的完整结果为前提，在判定为正常行为或误报、置信度达到配置门槛且核实建议确认为空时，程序作出 `not_escalated` 决定。初始置信门槛沿用原型背后自动分诊的 0.85，由告警运行 profile 提供。该决定只描述本轮分诊结果，告警业务关闭、事件和 Case 调度沿各自流程处理。失败、待复核、部分交付、暂缺 Case 和无决定的历史运行均没有这个标记。
