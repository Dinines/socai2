# 一个事件、多个告警：I 模型输入审计

2026-11-27。按负责人最新指令，本步只审 I 的输入用途和表示，不实施代码、不投递、不建案、不请求模型。两轮主机包 M0 保持冻结，见[完整回执](../../../docs/operations/evidence/host-context-two-round-20261127-01/README.md)。根进展、两轮方案和任务由统筹维护。

## 先明确 I 要做什么

I 解释**既定事件整体发生了什么、每个成员对整体判断的意义、证据支持或反对哪些解释、还缺什么关键材料**，形成事件判断和独立等级意见。消费方是事件诊断读取/页面及后续 Case 的前序分析。当前成员、原始等级、材料版本、执行状态和覆盖数量由程序确定；I 不重新归并、不评分归并算法，不代替完整 Case 调查或执行处置。

输入选择的标准是“帮助上述判断”，而不是“上游保存过”“模型之前引用过”或“token 还放得下”。原始事实、检测标签、A 的判断、人工陈述及工具执行状态分别标明角色；共同主机、标签和前序判断都不能替代行为证据。

依据为[既有字段审查第1–5、11节](model-input-field-review-20261112.md)、[I 当前职责](../../../docs/investigation/model-input-output-current-20261109.md#2-i既定事件的整体诊断)、[事件自动诊断设计](../schedule-streaming-investigation-updates/stage4-incident-diagnosis-design-20261115.md)及 AGENTS 模型原则。仓库未检索到名为 `incident-judgment-design` 的独立文件；本步使用上述现有事件判断设计入口，没有另造目标。

## 已实现的去重，与本次最小差距

| 当前机制 | 已实现的边界 | 本次判断 |
| --- | --- | --- |
| 同材料事实别名合并 | I 的分组键包含成员、来源身份、角色、语义字段及完整值；如原 OCSF 与 RawAlert 包装的同一字段 | 继续复用；同值不同事实不得靠去掉来源身份强行并组 |
| 对象目录重复消除 | 只有对象条目不含额外业务内容、与该成员已可见观察完全相同时省略 | 继续复用；独有资产属性或规范化差异不能丢 |
| 历史同身份同版本共享 | 同一个历史业务记录共享正文，每个来源原成员范围分别保留；同一 A 判断身份/完整版本可指向已显示的 A | 本冻结组已证实；不同版本/判断/角色保持分开，历史不提升成当前事实 |
| 结构化原文去重 | `raw_text/raw_data` 中已表达的结构化字段不重复，独有字段仍留本成员 | 继续复用，不改成自然语言摘要 |
| 查询结果表示 | 只呈现结果状态和业务记录，执行过程留后台 | 已满足，不为“压缩”新增另一段共享执行限制 |
| 跨成员公共主机信息 | 当前分组受成员/材料身份约束，不会共享不同告警的同一主机观察 | 有可审查的简单改善空间；本组已核稳定共同主机锚点。只扩展明确主机信息，不能整体合并告警或动作 |
| 归并说明 | membership 未传；业务联系来自真实对象/行为字段 | 不列为默认缺口，不补传算法或评分。关系确有独立业务用途而现有材料未表达时才另定具体字段 |

推荐的合并规则仅一条：**对象身份稳定、来源/角色一致、业务字段语义相同、类型和值完全相同，才共享该信息的呈现；所有原来源和适用成员仍各自保存。**

- 可优先限定 `device.hostname/name/ip` 的已识别主机字段。`name` 与 `hostname` 不因为碰巧同字就视为同一语义；分组键使用后台对象键及来源域，提示只显示业务短号。
- 同文字但不同来源/对象、未知对象绑定、冲突属性分别保留；共同项不能把某成员独有事实扩大到整个事件。
- 时间、动作、动作结果、命令、端点连接、进程实例等逐次行为不参与这条跨成员合并。多次相同行为仍是多次；同一原事实的多个包装副本沿既有规则处理。
- 同一资产摘要以后只有在实际稳定资产身份、来源及属性语义明确时复用；本组无有值资产，不能先写成已经验证。
- 共享块须列每条适用告警与其来源短号，不能只给一个合并后的“总来源”。原 source_map 的成员/角色/路径保持，正文不语义改写。

## 推荐的最终输入结构

1. **任务指令一次**：I 的判断目标、角色边界与输出约束。
2. **本轮范围一次**：选入成员短号、材料/A/回执缺失状态；程序已知的整体与选入范围区别。后台身份不出现。
3. **共同业务对象（确有重复时）**：共同主机/有用资产属性，每项列适用成员及逐成员来源。没有共同信息就省略这一块。
4. **逐告警必要材料**：该成员的实际时间、行为、对应结果、源/目的/父子角色及独有事实；引用公共对象，不复制主机资料。检测标签另标，随后放有效 A/相关人工原文及必要支持/反证。
5. **相关查询和历史**：每成员简短真实结果状态；有用业务记录。相同历史原件按现有机制共享，标清原主体、来源和适用成员；不附执行参数或目录命中清单。

业务联系通常由第3–4块自然表达。只有现有材料未表达且确有独立业务意义时才提供简短的关系事实；不固定增加“归并依据”块。

## C3 移交边界与本步结论

C3 已有相同 `object_key/detail` 合并及适用告警、`shared_fields` 和同源同值表示，可作 I 小步实现的参考。本步没有修改 C3，也不把其现有能力写成 I 已实现。

本次审计确认：I 的目标、成员事实、有效前序、必要历史与真实查询状态已有可复用实现；明确需优先收掉已识别入站 source/tenant 元数据，再对**有用途的公共主机信息**做有界共享。关联台账继续后台；认证语义、Finding 角色、模型正文质量及更广 Case 改造不在本步。无生产代码修改、模型/tokenizer、数据库写入、发布、重启或 Git 操作。

## 复杂度合评与本轮实施范围

负责人随后要求与调查核心共同评估合理性与复杂度，避免假定数据格式稳定而增加大量判别；确定值得做的内容先本地验证既有流程保持，再核整体输入效果。此决定收敛上节候选：**本轮只实施I专用的一项已识别入站元数据过滤，暂不新增跨成员主机共享。**

| 事项 | 合理性与复杂度 | 本轮决定 |
| --- | --- | --- |
| 自有RawAlert的`field_metadata.lake_ingress` | 写入端已明确该块用于入站来源、租户、湖定位和版本台账；I已有外壳结构确认和路径前缀过滤。增加一个配置项即可，不枚举所有叶子字段，不分析业务含义 | 实施；只修改`render.incident_only.raw_alert_backend_fields`，未知外壳保持原输入，不全局匹配同名键 |
| 不同告警的共同主机信息 | 当前只确认一组跨成员重复。沿用I现有分组不能直接共享，搬入C3对象机制需要新增稳定身份、来源、字段语义和成员别名处理，格式变化时也需维护 | 暂不实施；保留现有同材料去重、对象目录省略及历史共享，重复主机信息仍逐成员保留 |
| 通用字段相关性判别或兼容规则表 | 无需为本次明确后台块增加语义分类、业务字段白名单、样本/厂商分支或模型摘要 | 不做；未知业务字段和独有事实继续按既有合同处理 |

阶段目标：I最终提示不再包含这块无判断用途的后台信息；其他业务事实、成员、角色、来源、输出恢复和原件保持。无HTTP/数据库/自动调度合同变化。当前本机工作区保留全部既有未提交修改，不操作21及运行服务，不进行新Kafka或真实模型调用。

依赖与影响：A用独立profile；Case不执行`incident_only`逻辑，故有效业务表示应保持。但是Case把同一JSON加载为business_profile，完整文件指纹及`business_sha256`会变化。此变化必须在本地回执中明确记录，旧冻结profile一致性检查不绕过，不为消除指纹差异新增兼容机制；本轮不发布，不能把本地表示保持写成21或旧在途Run已验。

步骤与必要验证：

1. **固定本地基线。** 冻结变更前的相关配置/源码指纹；复用现有三告警事件冻结输入、M0两成员假设外壳及I定向测试。原业务值和完整messages留私密目录，公开只记工程计数/哈希。基线异常按原状记录，不改历史输入消除异常。
2. **实施一项配置和直接回归。** 在I专用列表增加已识别后台子树，沿现有逻辑工作。一个直接检查覆盖确认外壳时排除、未知外壳和同名业务字段/有效空值保持；其他行为复用现有I检查，不新建矩阵或框架。实施前strict通过。
3. **本地效果与流程保持。** 对相同冻结输入重建最终messages，核减少的路径仅属于指定后台块；必要业务内容、A原文、查询状态/结果、引用和适用成员保持，原件不变；复用既有输出身份/字段恢复检查。对A及Case有效业务配置/表示作限定对照，记录Case完整文件指纹变化。字符/块减量只作为输入工程效果，不作模型准确率或线上效果。
4. **统筹独立验收。** 审单项差异、影响边界和直接回执，记录通过、失败及未验范围后再进入两轮数据链路的后续小步。未通过只修本步阻断，不触发部署/Git或拓展其他输入规则。
