## 整条链的通过条件

从既有输入与存储证据开始，逐段核对：接收及任务登记 → 实际处理/保存 → 现行 HTTP → 平台转发 → 列表 → 同一告警详情 → 操作或引用 → 保存后的独立 GET / 刷新。身份、材料版本、Run、人工版本和来源在各段不能串换。只读功能不增加业务写入或模型调用；写功能须有实际保存与读回，不能以成功提示替代。

连续接收中的 `guard_analysis_task` / `public.users` 阻断保留为上游未通过；每两条重连后的分页数据不证明连续处理正常。该缺口与现有记录的页面读取分别判定：页面步骤可以先验，告警整链不能因此整体通过。

每项使用以下明确状态：**待核验、实现阻断、候选验证通过、正式读取通过、整链通过、缺少实际证据、按已确认范围暂缓**。历史证据只覆盖原版本、原数据与已测动作；执行方自测是交付材料，独立审计核其适用范围。类型检查、HTTP 200、空页、离线替身和现成工件分别记录，不互相替代。没有当前正式正例时保留缺证，不为了填满表而新造业务记录或重跑模型。

## 逐步执行与交付

相似历史候选已取得限定通过结论，正式正例补证保留。按负责人最新依赖拆分，当前不再将它设为后续所有告警工作的前置；每次仍只实施并验收以下一个明确步骤。

| 顺序 | 执行内容及责任 | 本步直接出口 |
| --- | --- | --- |
| 1 | **告警自身 A 分诊过程读取**。SpiritHub 接必要的现行 GET、生成类型及固定 Run 详情；服务端提供已有合同。 | 从现有告警进同一 A Run→步骤→原件→返回告警；直接深链及刷新不切轮次。复用现有保存结果，不执行新分析。 |
| 2 | **列表查询和显示收口**。SpiritHub 先将原分页、勾选/无勾选导出、预览和资产/人员证据对应到当前版本，逐项补实际缺口。 | 同一筛选/排序下列表、统计、分页、导出范围一致；当前选中与刷新正确。只验证本步直接受影响的行为。 |
| 3 | **告警详情和已有材料读取**。SpiritHub 核告警字段、AI/人工、解释引用；当前/指定版本、无富化及历史正文失败分别处理。 | 同一告警、同次分诊、同版原件可核，缺失与读取失败各自表达；本步不冒称历史目录已补齐。 |

| 5 | **独立评论**。服务端完成存储/接口及直接写读，SpiritHub 再接页面。 | 单独评论成功保存、同告警刷新可见，与管理附言有清晰来源；服务端依赖先通过。 |

| 7 | **告警剩余正例与上游连续接收**。正例在有明确验证材料时补，接收阻断由服务端单独安排。 | 非空/续页/同对象和原件证据按原功能补齐；连续接收有真实证据。缺证不核销，已有页面不反复重测。 |
| 后续阶段 | **事件、Case 和调查执行联动**。按上表后续边界另行派工。 | 目标模块真实写入、任务、Run、结果及跨主体读回完成后再核总链路。 |

第 1 步固定 A Run、第 2 步列表主体和第 3 步详情/已有材料已完成下述限定范围的本机候选验收，账号相关正例按用户最新指令暂缓。资产按用户最新决定转为待清洗模块明确 OCSF 资产关联 ID；第4步正常管理/反馈已按下文简化规则完成独审，当前交负责人查看8181；不同历史版本、无富化和同版来源原件的正式正例仍缺证，历史目录/UID沿后续单步补齐。

**本机候选运行是第 1 步的必要接线。** SpiritHub 的现有代理记录仍指向 21 平台服务，该版本缺少步骤/工件目录转发。执行方须先明确能实际加载新转发代码的本机候选后端入口、配置 profile、8181 代理目标与平台会话，再验证实际请求确实经过该候选。前端文件和类型已改不代表现场服务已加载。沿服务返回的 `content_url` 替换旧原件引用依赖，核来源所属 Run/材料；本机候选与 21 正式结果分开记录，不因本步骤安排新增一轮正式发布。

两执行方已完成前两步交付：SpiritHub 负责页面/转发/本机候选运行，服务端负责既有 Run、负责人读取及合同支撑。负责人明确“继续推进到告警的验收完成，有问题和我沟通”，随后明确“就账号的这个不用管”。组织者停止账号工作，按已验范围派发第 3 步，不重复申请日常派工授权。

组织者第 1 步期间发现的 F01-02“分配给我”禁用已由第 2 步修复。现有 Q04 与正式 `owner_id` 的同 UUID 关系保持，页面按实际登录身份核对应，不按姓名猜测，也不以空对应退回全部告警。候选当前登录者无对应的真实分支已验；账号相关恢复和实际本人登录正例不再推进。

第 1 步的旧 IO 定位在本轮正式步骤目录、同告警详情及主体 Run 均返回 404，不能作为当前正式验证起点；这不单独证明步骤接口损坏。服务端保留旧失败，再从既有正式告警验收记录另建可追溯的只读定位，不换成 latest 追认原定位恢复。组织者首轮源码审计退回的状态表达缺口已修复：告警 Run 分别展示 `is_current_pointer`、`valid_for_current_input` 和 `freshness`，与执行状态、交付完整性和业务判定分开；最终候选及回执已完成下节独立复核。

**第 2 步具体工作单。** SpiritHub 主责 F01-01–06、F01-09 的列表读取闭环，先对应原 8/15/25 分页、跨页选择、两种导出、预览和资产/人员有效证据，再补缺口。首先沿登录主体及 Q04 的实际 ID 对应接通“分配给我”，已映射者提交正确 `owner_id`，未映射、目录读取失败和本人名下为空分别表达。沿用既有核准测试人员，不为验证此按钮新建身份或映射；若现有登录条件不足，交组织者判断。

随后按同一组筛选/排序核名称、严重程度、处理状态、带时区时间、全量游标、列选择、清除条件和刷新；指标保持既有全租户口径，筛选总数与已加载范围分开。服务器已按 `critical/high` 统计高严重程度、按告警去重统计调查中，实际调查状态变化留跨模块阶段。无勾选导出保留全部筛选范围，跨页勾选导出使用真实所选 ID；先复用原回执，不重复造记录或全仓回归。原九个必备字段与后续独立判定展示一起按正确来源核对。

本步不改管理/反馈、详情材料、评论、事件或 Case。服务端只支撑本人的既有映射和读合同；发生实际本步接口阻断时另行明确最小修复。执行方先在原收口记录补本步依赖/步骤/直接检查并严格校验，再改必要页面接线。出口是有对应和无对应分支明确、实际请求与相同筛选结果/统计/导出一致、列表→预览→同 ID 详情及刷新一致，业务写请求和新模型调用为零。交最终源码、候选运行身份、直接测试/浏览器结构回执及剩余边界后，由组织者独立验收再进入第 3 步。

**第 3 步具体工作单。** SpiritHub 主责告警详情、已保存解释/建议及当前或明确指定版本材料的只读闭环，服务端只提供同一既有告警、A Run、材料/原件与可用空态定位。先核 F01-07、F02-01、F03-01–02 的属性、检测来源及量纲、已发布 AI 分诊与独立人工判定、同一 `source_run_id` 的解释和引用，复用已通过的事实/人员/资产证据；失败、未知、未保存、过时与实际业务判定保持区别。

已有材料按最新确认设计读取所选版本的 `content_json.ocsf_json`，只有有效补充数据才给富化入口；核无富化、缺正文、有效零值/布尔/空列表，以及明确指定历史材料 ID 的身份、元数据、正文与引用，不退回当前版本。旧零值测试先按当前 OCSF 规则判断适用性，保留旧失败原因，不恢复已替换的旧正文入口或仅删除断言。历史目录和同版本来源的新接口仍为第 6 步；本步不能因缺目录停止已有按 ID 读取，也不能用当前来源冒充历史来源。

同一详情的已存事件/Case 关系及告警自身建议/回执按实际 ID、来源、状态和空态核对；告警自身 Run 入口复用第 1 步，跨主体完整目标页和真实执行仍后置。本步不改人工管理/反馈、不增加评论、UID/湖查询或材料目录接口，不创建数据、不跑模型、不发布或推送。后端优先复用已核正式选择器，在既有授权批次内有界定位无富化和已保存历史材料；缺正例时清楚交代，不扫全库或制造新结果。执行方先补本步设计和必要测试、严格校验，再逐项修实际阻断；完成后交最终源码/定向检查/实际读取回执供组织者验收。

阶段收口按告警独立项、告警缺证项、跨模块联动项分别出结论。发布、正式读回和主 change 结束审计沿原整体交付规则执行；分步验收不触发逐步发布或推送。

**第 4 步工作单。** 本步只收口 F23-01、F03-04 及相应活动读回，SpiritHub 负责实际入口/表单/请求/回执，服务端负责原保存规则及必要的真实保存验证。先对应已有正式分配、改派、处理状态、人工判定、列表/详情/活动和冻结快照证据；仍有效的动作不重复写。账号恢复、角色或人员映射保持停止，不以本人实际登录作为管理功能前置。

核单条及明确勾选的实际 ID；既有 `expected_row_version`、`operation_key` 请求字段保持兼容，告警按最新确认采用最后成功写入为准，不再因旧版本拒绝，不新增重试流程。只分配不改状态，直接关闭必填理由并保留原判定；误报/正常关闭，已关闭改真实威胁/需跟进恢复处理中，其余状态保持。原 AI 结果、输入材料和冻结内容不被改写；新鲜度按既有合同变化。管理/反馈保存成功后，对同 ID 的详情、筛选列表及活动独立 GET/刷新核结果；批量保留既有事务和回执兼容，页面只提示成功或失败；独立验收核明确选中主体的实际保存，不能把成功提示当读回。

原 F23-01 含告警标签，而当前 `alertPage` 分支隐藏标签控件。执行前核最新三字段管理弹窗的设计边界：保留已确认的状态、分配给、评论顺序，以单独的告警标签编辑入口承接原有标签能力；若存在明确移除标签的后续决定，先交组织者判定。单条标签修改/清空、其他字段修改时标签不变沿现有管理合同；用户已取消批量标签，页面及告警批量接口不再提供该能力。单独评论保存仍属第5步，本步不以随管理附言核销它。

只补直接受影响的保存/读取缺口；需要新验证数据时先由服务端写明隔离环境、独立批次与最小步骤，使用现有真实 PostgreSQL/HTTP 验证入口，不改正式既有告警或扩大真实数据范围，不调用模型。前端候选与该明确测试入口接通后核提交及刷新；正式既有证据与隔离候选结论分开。完成实现、必要接线、直接检查及保存读回后交组织者独立复核，再进入下一步，不顺带评论、材料新接口、事件或Case。
