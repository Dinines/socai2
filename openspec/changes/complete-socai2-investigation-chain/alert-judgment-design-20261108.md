## 1. 现版实际做了什么

本批 `production-multialert-20261108-01` 的三个告警均经过：冻结告警 → 资产、历史、威胁情报三个既有查询 → 装配 JSON 输入 → 一次模型分诊 → 引用/格式校验 → 保存分诊、解释与当前指针。模型不负责本阶段的工具选择；本设计继续沿用这个查询顺序和既有查询范围。

原答和实际发送正文取自[冻结数据库快照](../../../docs/operations/evidence/production-multialert-20261108-01/exports/20261108T013952440775Z/database.json)，不是从页面摘要重建。现版入口为 [alert_basic_executor.py](../../../services/api/app/socai2/alert_basic_executor.py)，输入/输出合同为 [alert_basic_contract.py](../../../services/api/app/socai2/alert_basic_contract.py)。

现版模型输出有 8 个字段：`verdict`、`confidence`、`rationale`、`explanation`、`evidence_ids`、`recommendations`、`limitations`、`decision_basis`。其中理由、解释与判断依据容易重复生成相同事实；程序之后仍需另补运行身份、正式来源引用、版本和保存状态。

这不是把完整数据库行全交给模型，但实际发送的正文仍含内部 UUID、租户标识、Schema 版本、空值、重复日志字段和重复历史分析。PowerShell 告警中，7 个独立原始观察字段出现了两遍，同一份登录分诊因主机/用户两次匹配再次重复。

## 2. 新版职责划分

| 环节 | 现版 | 本版设计 |
| --- | --- | --- |
| 上游准备 | 多组结构化材料、字段路径和部分元数据一起发送 | 按字段职责精简结构，已知结构化值按模板拼接；描述、历史分析等自由文本原样附入并标明来源 |
| 身份与版本 | 一部分内部 ID/版本进入模型正文 | 程序管理租户、告警/Run/工件 ID、执行时间、版本、hash、幂等和关联，不要求模型复述 |
| 证据 | 单字段大量编号，重复字段也占编号 | 同一原始记录按事实单元编号；后台保留每个编号到原件、字段、角色、成员及版本的映射 |
| 模型任务 | 同时重写行为、依据、解释、限制、建议 | 每次明确要判断的业务字段；理由只生成一次，不撰写整份存储对象或执行报告 |
| 下游保存 | 校验模型大对象后再补程序字段 | 校验小结果，解析证据号，程序装配现有存储/读取对象；不让模型决定发布状态 |
| 局部纠正 | 当前 C3/C6 空引用纠正要求完整 JSON；A 没有同类纠正调用 | A 的候选纠正只返回受影响的判断单元；程序合并后复验依赖，不要求重写无关建议/解释 |

常规告警仍只需一次模型请求。精简输出不等于每个字段拆一次调用，也不新增模型摘要器。

## 3. 根据实际输入结构转换

先读取冻结材料和真实查询回执，分成可确定解释的结构化值和原文块，再组织输入。结构化值按固定规则渲染；原文块只加来源标题、证据号和引用边界，内容交由分诊模型理解。

| 输入内容 | 程序可做的操作 | 保持的边界 |
| --- | --- | --- |
| 空字段、冗余嵌套、内部路由/版本字段 | 按字段合同省略空项、展开结构、转为清晰名称，程序身份留后台 | 不按文本中的词语或 `id` 子串删除内容；业务 ID、0、false 另按字段语义处理 |
| 已知动作、结果、时间、账号、端点、查询数量/状态 | 用配置好的映射和模板拼接，保留原值和来源对应 | 不增加原字段未表达的含义 |
| 描述、历史 rationale/explanation、建议理由、人工正文 | 作为完整原文值放入对应来源块 | 不缩写、不提炼、不纠错、不因判断为“重复意思”删句；文本内部的旧编号/名称保持，来源标题区分旧引用上下文 |
| 同一记录因多种匹配关系重复出现 | 记录身份、版本/来源和内容一致时只显示一份；合并确定的匹配关系 | 不同记录即使文字相同也不合并；同一记录不同版本或值冲突均保留区别 |

例如历史原文为“登录成功，但缺乏授权依据”，输入仍是 `历史分析原文：登录成功，但缺乏授权依据`，仅附上本次来源编号和明确的历史身份，不将其拆成程序断言的两个事实。正文有错误时原样留存，程序不把它改成正确结论。文本完整性可用字段原值与传入原文逐字核对；无需另建文本语义理解/摘要环节。

| 当前来源/字段 | 处理规则 | 模型看到什么 |
| --- | --- | --- |
| `ocsf_json.time / actor.user.name / device.name / activity.*` | 作为当前活动事实；时间含明确时区，原值及转换保留在后台；活动时间与告警时间有业务上的差异时分别标明 | 谁、何时、在哪台主机、做了什么、记录结果 |
| `process.name / cmd_line` | 原值保留，命令行不截成“侦察命令”等人工结论 | 进程启动句中的名称和完整命令行 |
| `src_endpoint / dst_endpoint / connection_info.protocol_name` | 保留有值的方向、地址、端口、协议；不从 443 推导 HTTPS | 网络连接句 |
| `raw_json.raw_event.ocsf_event.*` 与上述字段重复 | 同一原始记录且语义/值一致才合并；不同或冲突的值都保留并区分来源 | 同一事实只出现一次 |
| `source_groups` 的历史行 | 按原记录 ID 去重；合并主机/用户等匹配依据 | “一条历史告警，经同主机和同用户两种关系匹配” |
| 历史 `triage` | 精简身份/版本等外围字段，同一历史结果按身份、版本和内容去重；既有理由及建议正文原样保留 | 结构化判定等可按模板拼接，正文明确标为“历史分析原文”；不据其他字段看似表达了相同意思就删正文，结构化引用在后台映射 |
| `human_statement / feedback` | 有值时保留人工确认的内容、适用对象/时间和撤回等状态；不与历史模型解释一并删除，不扩展授权范围 | 带独立证据号的人工陈述；本批三样例没有该类输入，含人工反馈的转换仍待验证 |
| 本次 `program_facts.query_statuses` | 以实际回执表达成功、有结果、查空、未查、失败；保留查询范围 | “租户内部情报未查询：无可查询对象”等 |
| 上游检测信息 | 有值的规则、标签、级别和评分可按任务提供；来源角色明确。评分公式、权重、缺字段的默认特征不进入本版正文 | 短句背景，不把 `no TI match` 评分标签冒充本次查询结果 |
| 内部 UUID、租户路由、Schema/执行版本、工件路径、hash、存储元数据 | 后台保存，不进入判断正文；业务主体名称/有实际分析意义的账号标识仍保留 | 不出现程序关联信息 |
| 普通可选字段的 `null`、空字符串、空数组、空对象 | 该条记录中未提供的普通信息从正文省略；不能因本批为空就永久删除该字段规则 | 没有空字段铺陈；若空值本身表示业务状态或变化，须按该块合同表达其含义 |

`0` 和 `false` 不作为空值删除；“成功查询返回 0 行”是有效执行事实。统一指令只说明一次：未提供的信息视为未知，不能推定不存在。若缺少足以生成告警行为句的必需事实，程序记录输入不完整，不能编造一句完整事件。

同一日志的多条字段引用可以归入 E1，后台展开为现有合法引用数组；不同日志不能因描述相似而合并。人工陈述、原始观察、历史判断、标签和查询回执分别标明，不能仅因都叫“证据”就具有同样证明力。模板未覆盖的有意义原文/字段，应作为带来源的补充文本保留，不能静默丢弃。本轮只有三种已知告警的设计预览，尚不是覆盖所有来源的通用渲染器。

### 字段业务语义与输入前处理

2026-11-08 用户进一步明确：先理解业务告警输入，逐字段确定意义，再设计模型前后的解析和关联。不能仅以字节减少作为改造依据，也不能把模型结果随意拼回名称相似的字段。以下依据当前 [Fusion 投影](../../../services/fusion/app/services/socai2_projection.py)、[冻结输入](../../../services/api/app/socai2/stage_inputs.py)、[数据模型](../../../services/api/app/models/socai2.py)和 [程序事实](../../../services/api/app/socai2/program_facts.py)核对；范围是当前 A 链与三种样例，不宣称已定义所有厂商的所有日志字段。

| 业务内容与实际字段 | 字段到底表示什么 | 模型输入及处理要求 |
| --- | --- | --- |
| `alert_materials.ocsf_json.activity.action` | 这条日志记录的活动类型，例如登录、进程启动、网络连接 | 决定模板中的动词；不把进程启动命名为命令执行完成或恶意侦察 |
| 同记录的 `activity.outcome` | 对该活动的记录结果 | 必须与同条记录的 action 成对描述；success 不能泛化为整个任务成功 |
| `actor.user.name`、有业务意义的账号标识 | 活动涉及的账号；不能仅凭名字证明操作者身份或授权 | 保留账号语义和必要命名空间；不能按字段名含 `id` 就删除日志中的 SID/业务账号 ID |
| `device.name`；`alert_objects.object_key/namespace` | 活动主机及程序用于对象匹配的键/来源范围 | 主机名进入文本；后台保留对象键。来源范围不同的同名对象不能合并，必要时在文本中区分来源 |
| `process.name/cmd_line` | 记录的进程及完整命令行 | 有值原样保留；命令中的参数、路径、哈希不能因为形式像元数据而删除 |
| `src_endpoint.* / dst_endpoint.* / connection_info.protocol_name` | 带方向的端点和原字段明确给出的协议 | 有值时保留；不交换源/目的，不从端口推测协议，不把建立连接解释为数据外传 |
| `ocsf_json.time` 等活动时刻 | 原始活动时间，带单位和时区 | 进入行为句；与告警时间不一致时分别表达，不能用入库/执行时间补齐缺失的活动时间 |
| `alerts.event_time/event_time_source` | 告警来源给出的或明确派生的告警时间及其来源状态 | 与活动时间含义相同时可省略重复文本，否则单独标注；unknown 不改写成当前时间 |
| `ingested_at / received_at / runs.started_at` | 系统入库、材料接收、分析开始时间 | 默认仅后台运行记录保留，不混入事件发生顺序；只有任务明确分析延迟时才选入 |
| `alerts.title/description` | 上游对告警的概括，不等同原始观察 | 非空值原样保留，注明上游描述；只按同源同版本同字段同值去重，不按语义相似删减或重写 |
| `alerts.severity`、日志 severity | 告警严重度与原始日志等级，各有所属对象 | 分别标明来源；不得与模型 verdict 或 confidence 互相替代 |
| `alert_materials.detection.confidence_value/label/state` | Fusion 的告警置信度，投影值为 0–100；标签/状态来自 Fusion | 作为上游评分背景。不能写入模型自评 confidence，也不能当作已证恶意/良性；公式、权重默认留后台 |
| `detection.rule_id/rule_name/tactics/techniques` | 上游检测标识及分类标签 | 有值且相关时给出准确释义；标签不能自动成为已发生攻击或授权证明。`no TI match` 评分文案不代替查询回执 |
| 历史查询 `rows[].record_id/object_key/record` | 已有告警及本次命中的对象关系 | 按记录身份去重、保留多种匹配依据；两条匹配关系不能算两次独立活动 |
| 历史 `record.triage` | 另一条告警在某次分析时已有的模型判断 | 单独标为历史判断，不代替原始日志，不继承其查询状态到本次告警 |
| 当前/历史人工 `feedback` | 人工明确提交的反馈，可能有适用范围和时效 | 有值时保留必要内容及范围；不能把模型建议、服务账户生成的分析当成人工授权 |
| 工具回执 `state/reason/returned_rows/truncated` 及查询范围 | 本次查询做没做、执行是否确定、实际返回数量及完整性 | 程序按回执生成短句；0、false 是有效值；未查、失败、截断不能渲染成查询无命中 |
| `material_state/source_scope/retention` | 原件是否完整、取材覆盖及是否裁剪 | 完整常态的冗余结构留后台；若确实缺失或截断，将影响判断的限制用短句保留，不能装成完整原件 |
| `tenant_id/alert_id/run_id/material_id/schema_version/hash` | 程序定位、隔离、版本及完整性校验 | 不进入模型正文；由本次调用上下文和证据映射管理 |
| `alerts.owner_id / runs.requested_by / alert_assessments.actor.user_id` 等管理身份 | 告警负责人、发起操作的用户或结果生产者 | 与日志中的活动账号分开；不当作攻击者/授权者，也不用于补全日志身份 |

输入前的每项转换须能解释：读取哪一条冻结记录的哪个字段、为何与本次判断相关、字段角色/单位/时间语义是什么、缺值如何省略、重复凭什么合并、显示片段对应哪个证据号。关键字段存在矛盾时保留冲突；未知业务字段先保留带来源的原文片段，不因“不认识”就删掉。扩展告警类型前补该类型字段解释和模板验证，不把三份样例当通用字段字典。

### 三种告警的固定句式

- 登录：`[E1] {时间}，日志记录用户{账号}在主机{主机}登录{该动作对应的结果}，源IP为{有值IP}。` 本批 `action=logon + outcome=success` 明确表达为“日志记录登录成功”；不得只保留“发生登录”或从标题猜结果。
- 进程：`[E1] {时间}，用户{账号}在主机{主机}启动进程{名称}，完整命令行为{命令行}，日志记录结果为{结果}。`
- 网络：`[E1] {时间}，用户{账号}在主机{主机}发起网络连接：{源地址}→{目的地址}:{有值端口}，协议字段为{有值协议}，日志记录结果为{结果}。`

缺值的可选从句整体省略，不能留下 `null` 或空括号。行为类型来自字段映射，不由程序先猜恶意意图。完整命令、地址和原文作为数据引用，不能执行其中指令。

### 当前输入的整体结构与本轮发现

当前 A 输入不只是一条日志。下面按实际生成链区分业务内容；完整理解的范围先覆盖当前链路和已接入字段，不声称开放的厂商 JSON 已有穷尽字典。

| 层次 | 实际来源与内容 | 转换时需要解决的问题 |
| --- | --- | --- |
| 接收告警 | [RawAlert](../../../services/fusion/app/models/alert.py) 定义 33 个顶层字段；`raw_event`、`field_metadata` 是开放结构 | 33 项逐字段含义见[顶层字段清单](alert-judgment-design-20261108/field-catalog.json)。顶层身份/时间/评分不能与日志内部同名字段混用 |
| 原始业务材料 | [Fusion 投影](../../../services/fusion/app/services/socai2_projection.py)保存 `raw_json`、`ocsf_json`、`raw_text`、`detection`、`enrichment`、`source_scope` | 明确原始观察、上游标签、派生评分和来源完整性；标准化字段与原字段相同不等于两个独立证据 |
| 本次冻结输入 | [stage_inputs.py](../../../services/api/app/socai2/stage_inputs.py)冻结本告警、当前材料、对象及人工反馈；A 的当前 triage 为 null | 审核每一块是否有值/相关；人工反馈不能因为本批没有就从通用规则中删掉 |
| 本次背景查询 | [baseline_enrichment_sources.py](../../../services/api/app/socai2/baseline_enrichment_sources.py)读取当前资产、前 24 小时告警历史、租户内部情报 | 同时理解查询范围、回执与非空记录的字段；查空样例无法证明非空资产/情报模板正确 |
| 送入模型的投影 | [alert_basic_contract.py](../../../services/api/app/socai2/alert_basic_contract.py)按观察、标签、历史分析、人工陈述分组，附 `program_facts` 和状态 | 当前路径角色和省略清单不是业务字典；已有代码能接收未知字段，不代表已理解它们的含义 |
| 旧模型分析 | 历史 `record.triage.rationale/recommendations` | 是既有分析，不是原始事实；可能含事实复述、判断依据、待核实事项及错误，不能整体视为无效元数据 |

本轮逐项核对结果：

| 内容 | 当前实际来源 | 初稿处理与问题 | 修正要求 |
| --- | --- | --- | --- |
| A1 自身登录成功 | `ocsf_json.activity.action=logon` 与同记录 `outcome=success` | A1 初稿 E1 保留了“发生登录／结果 success”，没有丢该值，但表达不够直接 | 固定映射为“日志记录登录成功”，保留字段回指；不扩大为已授权 |
| A2/A3 的历史登录成功 | history 返回的旧分诊 `record.triage.rationale`；历史概要只有标题、时间等，没有动作和结果 | 删掉整段理由后，只剩 `Account logon observed`、needs_review 和分数，确实丢失历史分析信息 | 先保留唯一一份历史理由并注明来源。若要作为原始事实呈现，须按返回的确切 material_id 读取、冻结相应历史原件，不能凭旧模型正文补事实 |
| 缺乏授权依据 | 旧分诊 rationale 和建议 | 初稿整体删除；仅留 needs_review 无法说明为何待核实 | 作为旧判断的理由保留；不能改成“确认未授权”，不能从缺少标签自动产生该结论 |
| 威胁情报未查／无命中 | 本次 tool_response 的 state、reason、returned_rows、truncated 与 actual_args | 初稿 A1/A3 写查空、A2 写未查，这部分方向正确；“有 TI 信息”不等于执行了查询 | 保留本次回执和对象范围。Fusion `confidence_rationale` 的 `no TI match` 只是评分解释，不能替代本次查询事实 |
| 历史进程的具体行为 | A3 中 A2 的旧分诊理由；history 概要没有完整命令行 | A3 初稿只有 `Process start observed`，不能还原曾讨论的进程行为 | 与历史登录采用同一规则；缺少原始历史材料时不自行拼出命令或运行效果 |

history SQL 当前返回 `id/title/event_time/material_id/severity/original_vendor/triage/feedback`，不返回 `ocsf_json`、`activity.action/outcome` 或命令行。这是实际读取范围限制；本批全库快照虽然另有历史原件，也不能因此声称 A2 当时已经收到它。本轮保留已有历史分析原文即可，不补读历史日志、不从原文提炼事实。以后如讨论历史原件补读，需另列读取适配、冻结版本和容量，不混入本次“同输入只换排版”的对照。

### 按业务块定义固定文案，而非按三种样例删字段

每块合同必须包含来源路径、数据类型、业务角色、单位/枚举释义、适用条件、缺值规则、固定文案和证据回指。文案与可变映射由配置文件管理。下表是设计要求，尚非生产渲染器；同一告警可同时有多个块，不按事件类别只选一块。

| 业务块 | 必须理解的字段与联系 | 固定文案原则 |
| --- | --- | --- |
| 时间、动作和结果 | 活动时间与告警时间；action、outcome 必须来自同条活动；开始/结束时间与单位 | “日志记录在{时间}发生{动作}，结果{该动作结果}”；登录成功、启动成功、连接成功分别表达 |
| 主体与对象 | actor.user、user、device、源/目的端点、对象命名空间；操作者与目标账号不能互换 | 明确谁对谁/在哪台设备发生行为；用户名、账号 UID/SID 有业务意义，不按 `id` 字样过滤 |
| 进程 | process 与 actor.process、父进程、PID/UID、路径、完整命令、会话 | “进程{名称}，命令{原文}，父进程{有值内容}”；不由命令名称推断已完成的效果 |
| 网络 | 源/目的 IP、端口、协议、端点主机、traffic 字节/包计数及方向 | 保留方向与单位；0 字节与未提供不同，连接成功不等于发生外传 |
| 文件与 IOC | 文件路径、哈希及算法、domain、URL；明示来源和对象角色 | 按原值表达；不猜哈希算法，不将任意域名当作已连接或恶意目的地 |
| 认证与会话 | 登录动作/结果、日志提供的认证方式、会话/账号标识及相关上下文 | 本批仅验证登录动作/结果；其他认证字段须先核来源合同，不能靠本批空值推断永不需要 |
| 检测与评分 | 标题/说明、规则、战术/技术、风险分、Fusion 分、标签来源 | “上游报告{原文}”；分值保留刻度/状态。描述正文保持，计算公式/权重按明确字段合同留后台，不在自由文本中删词句 |
| 资产背景 | 查询记录的 name/fqdn、类型、IP、重要性、标签、负责人、OS、更新时间及匹配依据 | “当前资产库存匹配到{对象及有用属性}”；不能冒充事件发生时状态，负责人不是日志操作者 |
| 历史关联与判断 | record_id/material_id、匹配对象、告警时间、标题/严重度、triage/feedback 的身份和内容 | 同一记录同一版本只出现一次，合并匹配依据；旧模型理由及人工正文原样保留，结构化字段另行拼接 |
| 威胁情报 | IOC 类型/值、来源/来源引用、记录分/等级/标签、有效期与本次查询范围 | “本次内部情报查询{状态}，记录{实际返回内容}”；未查与失败不得说无命中，记录分不当本次判定置信度 |
| 人工反馈 | 本次/历史反馈的实际正文、判定、对象、时间和可用状态 | 标明人工意见的对象与范围；没有明确授权内容就不生成“人工已授权” |
| 材料完整性与未识别业务字段 | material_state、source_scope、真实裁剪/冲突；未覆盖的有值字段和原文 | 有影响的缺失/冲突明确表达；未知字段按原路径、原值保留为来源补充，不猜含义或静默删除 |

[现有语义投影](../../../services/api/app/socai2/baseline_semantics.py)只给进程、网络、认证三类设置了事件类别映射，并选择若干字段；这不是完整 OCSF/厂商字段字典。规则导入里已有文件、DNS、HTTP 等分类也不等于 A 已有对应语义模板。样例没出现的字段，须根据实际来源和契约补规则；无法确认释义时保持原文和“未映射”，不编造中文释义。

保留顺序由业务用途决定：本次行为与结果、关键身份/对象、有效人工信息、有用关联事实与判断依据优先；实际查询状态及影响判断的限制也必须准确。派生分数/标签是否保留再按本次任务确定，不能先保留评分却删掉唯一的行为或理由。`0`、`false` 和“明确清空权限列表”之类业务状态按含义处理；没有提供字段不等于字段取空，也不等于否定事实。

每个非空业务字段需登记为：结构化拼接于哪段文案／作为哪段原文保留／与哪项同源同版本同值记录合并／为何仅在程序侧保留／因何无法呈现。自由文本以原值完整传递为验收条件，不逐句判读或删减。原文过长按配置报告容量不足或采用另行明确的容量策略，不能静默摘要或截断后声称完整。覆盖检查同时核当前告警、关联历史、判断依据、人工信息、查询结果与范围，不能只数 `role=observation` 的字段。关键内容未覆盖则本版转换不通过，不用一个高压缩比例抵消。

## 4. 输出只包含本次需要模型判断的内容

核心判断单元只有 `verdict + rationale + evidence_ids`。为了保留已经对接的告警置信度及核实建议，本版“完整告警分诊”候选请求再明确要求 `confidence` 和 `recommendations`，合计 5 个字段；不是让任意局部任务都输出这五项。核心三项和完整五项的选择由程序的任务合同确定，不交给模型自行增删。

| 当前模型字段 | 新版分工 |
| --- | --- |
| `verdict` | 模型判断，保留原四态含义 |
| `rationale` | 模型给一份判断依据，避免再复制行为和查询结果 |
| `evidence_ids` | 模型选择支持该判断的本次编号；程序解析来源 |
| `confidence` | 完整 A 任务为兼容当前功能保留；仍是模型自评，不能估计可为 null，不当风险等级或准确率 |
| `recommendations` | 完整 A 任务保留必要核实建议及引用，可为空；不表示已经执行；单纯改判定的任务不重复生成 |
| `explanation` | 不要求模型再写第二份解释；程序用确定性行为句与已保存的原样判断依据组成展示内容 |
| `limitations` | 程序依据输入完整性、实际查询/执行结果生成；需要模型表达的判断缺口写入唯一依据或核实建议 |
| `decision_basis` | 不再让模型重复选择依据类别和重写主张；类别由 verdict 对应，主张/引用沿唯一 rationale/evidence_ids。确定性定性仍必须通过直接证据角色及语义支持检查，不能把类别映射当作证明 |

候选格式见[输出 Schema](alert-judgment-design-20261108/proposed-output.schema.json)，[任务指令](alert-judgment-design-20261108/proposed-system.txt)同时说明判断含义及所需输出。Schema 是设计文件，尚未通过实际后端兼容测试；来源编号枚举、长度/条数和输出上限由实施时的文件配置/合同确定并计入实际完整请求。

局部修改示例：只修一项核实建议时，程序保留原答和原结果版本，明确本次允许修改的建议，由模型返回该建议的理由及引用。若修 verdict/rationale/evidence_ids 中的一项会影响其他项，则把这三个联动字段作为一个判断单元重新校验；依赖该判断的置信度或建议需复核，不能把互相矛盾的新旧字段拼成结果。目标 ID、版本和合并路径由程序掌握，模型不提交任意数据库对象或修改路径。

## 5. 下游完整落库与展示

1. 校验响应形状、只包含任务允许字段、枚举、来源号和来源角色；核心判断的依据必须真实支持主张。格式/编号正确不自动证明正文正确。
2. 对可核实的空引用或结构矛盾，候选支持一次明确反馈纠正；只在已取得确定答复且原 Run 额度/时间允许时执行。A 当前每 Run 调用上限及纠正预留须同步文件配置，未调整/无余量时明确不纠正；超时/unknown 不重派。
3. 核心判断有效才采用。建议局部无效时保留有效判断和其他建议，并记录部分交付原因；核心无效不通过程序改写出一个 needs_review 结果。
4. 程序补运行/告警身份、时间、版本、正式引用和建议 ID，沿现有事务与新鲜度检查保存。`alert_assessments.verdict/rationale/confidence/recommendations` 保持字段职责；`confidence=null` 对应 `score_state=not_computed`。不新增表或改 V1 设计。
5. `alert_explanation` 采用模板组合的行为事实与原样模型依据，明确模板生成及模型文字来源，避免冒充一份额外模型原答；`program_facts` 与真实查询回执保留。实施必须核现有 API/页面解释字段的兼容性，不能为了缩小输出把既有业务数据悄悄变成缺值。
6. 交付完整性按本次 A 任务要求计算：完整待复核判断也可完整交付；存在真实缺项/局部拒收才 partial，执行失败/unknown 分开。I 阶段的同类状态问题已登记，本版不同时改造 I 输入/输出。

原始输入、实际发送文本、模型原答、纠正答和来源映射都保留在程序侧。程序模板只组织真实字段，不修改模型自由正文，也不编造授权、执行效果或安全结论。

### 输出后解析、字段归属与固定关联

模型输出结构与数据库完整对象是两份不同合同。下面是候选输出与现有字段的对应，实施前必须核告警 API、页面和后续读取，不能仅把字段名相同当作语义相同。

| 来源 | 去向/处理 | 业务含义及不得混写的内容 |
| --- | --- | --- |
| 模型 `verdict` | 新增 `alert_assessments(kind=triage).verdict` | 本轮模型分诊；不自动写 `alerts.disposition`、关闭告警或改变处置流程 |
| 模型 `rationale` | 同一分诊的 `rationale`；解释中原样引用 | 唯一一份模型判断依据；程序不把错误正文改成自己的分析再冒充模型输出 |
| 模型 `confidence` | `alert_assessments.confidence`，数值有效时 `score_state=available`；null 时 `not_computed` | 模型对本次判定的 0–1 自评；页面已有 `confidence_percent=confidence×100`。不得与 Fusion 的 0–100 分数换用或用默认数补齐 |
| 模型 `evidence_ids` | 按本次证据映射解析成正式引用，保留在 `alert_explanation.content_json.source_refs` 及相关工件；模型原答仍保留短编号 | `alert_assessments` 没有 `evidence_ids` 列；不能凭编号重新搜索全库。模板事实和模型依据分别保持来源，不因引用同一材料就自动证明整段话 |
| 模型 `recommendations` | 程序按现有合同补建议 ID、verify 类型和未执行标记，保存至分诊/解释建议 | 核实建议，不是已创建任务、已审批、已处置的回执；建议中的主体不得超出允许范围 |
| 冻结活动事实＋原样模型依据 | 模板生成 `alert_explanation.content_json.body`，明确 `generation_method=template`，保留原答和各部分来源 | 用于页面解释；模板中的动作来自原字段，不把模型推测写回原始日志 |
| 实际来源/查询/执行状态 | `program_facts`、`limitations`、Run/Step 状态和交付状态 | 程序事实，模型没有修改权限；needs_review 不决定是否完整交付 |
| 发请求前冻结的调用上下文 | `alert_id/tenant_id/input_material_id/source_run_id/producer/assessed_at/operation_key` 等 | 程序关联到准确告警、材料版本和本轮执行；不让模型填这些值，不按模型返回的用户名/主机名猜关联 |
| 经新鲜度和采用条件检查的已保存结果 | `alerts.latest_triage_id/latest_explanation_id` | 只在输入仍对应当前材料、且没有应优先保留的新结果时更新。旧答保存不等于覆盖当前指针 |

调用前，程序内部保存同一组绑定：租户、告警、Run、冻结输入/材料版本、实际请求、输出合同、允许更新字段及 E1…En 映射。不同请求可以各自有 E1，但必须使用各自的映射，不能跨调用混用。模型原答只能回到发出该请求的绑定；返回多余的主体 ID、版本或任意修改路径不作为关联依据。

返回后依次核：响应属于哪次调用 → 形状与允许字段 → 引用是否在该输入中/角色和范围是否符合 → 判断与关联字段是否一致 → 来源是否仍新鲜 → 保存原答和可用结果 → 按采用规则更新指针。编号能解析不等于正文已证真，语义质量单独验收；无效核心不覆盖已有判断，unknown 不通过猜测补成成功。

例如本条 PowerShell 告警，即使模型只返回 `needs_review`、一段理由和 E1，程序仍能凭请求绑定写入正确的 `alert_assessments`，并把 E1 回指到本轮进程日志字段。它不会据此改写原始 `activity.outcome=success`、上游 `severity=medium`、Fusion 的 20.8 分或告警处置状态。这正是缩小模型输出后仍能保持业务字段完整关联的依据。

| A3 网络 | 20,674 B | 1,793 B | 91.3% | 18 → 9 | 8,004 / 718 |

这里的“独立原始观察字段保留”只核本条告警中标为 observation 的字段，未覆盖历史分析中的内容，不能等同业务信息完整。上述减少还包括删除历史自由正文、评分公式及内部元数据；A2/A3 的历史理由缺失已确认，原有 90% 左右字节减少暂不作为可接受方案指标。历史匹配关系仍保留：A2 两条关系对应一条历史告警，A3 四条关系对应两条历史告警。

机器对照：[comparison.json](alert-judgment-design-20261108/comparison.json)。另两条输入：[A1 当前](alert-judgment-design-20261108/A1-current-input.txt) / [A1 拟议](alert-judgment-design-20261108/A1-proposed-input.txt)，[A3 当前](alert-judgment-design-20261108/A3-current-input.txt) / [A3 拟议](alert-judgment-design-20261108/A3-proposed-input.txt)。三个 `*-current-output.json` 都是旧原答的解析副本；没有生成或填写“新版模型结果”。

## 7. 下一步如何验证效果

先完成已接入来源的字段含义与业务块清单，逐项标记已理解/未覆盖，再定义保留条件和模板。用同三条冻结告警核当前事实、历史理由、查询范围等内容的逐项去向；另覆盖本批未出现的非空资产/情报、人工反馈、混合业务块、不同告警类型、0/false、字段冲突及未知字段，不能仅用当前三例证明通用能力。本轮只转换已有输入，不补读历史原件。自由文本逐字段核原值完整传递；结构化字段核映射、缺值和同源去重，不要求程序判读自由文本语义。关键业务内容完整、来源角色正确后，才比较字节和实际 tokens。之后验证输出合同、局部合并、A 的完整/部分/失败状态，以及现有告警读取字段。

完成实现与实际后端计量/Schema 兼容验证后，才另建独立 A 评估批次，同后端、同冻结事实对比当前与候选版本；不重派旧 Run，不写回旧案例。本版先看告警效果，不启动 I/Case。实际对比项包括：

- 输入/输出真实 tokens、耗时、失败/拒收与可用输出；必要事实和来源号是否保留。
- 主机/时间等事实是否抄错，未查是否仍说成查空，启动是否扩大为完成，历史判断是否被说成人工确认。
- 判定、理由、引用和建议是否一致，程序是否正确装配现有页面数据，待复核是否与交付完整性分开。
- 对缺原文、没有授权、字段冲突、重复历史和局部修改分别检查；无独立良恶真值不报准确率，新的模型答复不得用人工示例代替。

输入更短是本次离线可证明的结果；模型判断是否更准确、速度是否更快、整条告警流程是否更可靠，均待实际验证。

初稿检查：三个旧输入/原答与冻结记录一致，83 条来源引用能回到原件，当时 113 个相对文件链接有效；这只证明原件/映射可定位，不证明所有业务内容已呈现。见保留的[初稿检查](alert-judgment-design-20261108/design-checks.json)及本轮[语义复核](alert-judgment-design-20261108/semantic-review.json)。候选输出仅完成 JSON 及字段结构检查，实际后端 Schema 兼容未测。

## 8. 两个适配模块与三组对照

用户先选择“先完成设计和测试方案”，随后要求“先跑出数据”，并明确要分析输入精简及输出明确后是否出现误判。按最新请求准备独立候选实测；生产接入仍待评估结果，不在当前运行版本中直接换逻辑。

### 任务目标及最小接入

A 的目标固定为：依据这条告警的行为、相关背景和既有分析，判断恶意/良性/误报/待复核并说明依据。模型置信度和核实建议保留是为了现有告警读取功能，不能让模型重写程序身份、查询状态、完整存储对象或调查执行报告。精简先检查字段与该目标的关系，原文作为完整数据块传递；不由程序先做安全定性。

```text
现有冻结输入及三类查询回执
  → 输入适配：结构精简、同源去重、固定字段文案、原文保留
  → 同一模型及对应输出Schema
  → 输出适配：严格解析、引用检查、装配现有AlertOutput
  → 现有保存/读取（本次隔离对照不执行这一写入）
```

- 输入模块接在 `alert_basic_contract.build()` 与实际请求准备之间；复用已冻结的材料、角色和来源映射。首版沿用 `N…_S…` 原子编号及一号一条正式引用，结构去重只改变呈现；不引入 E1 一对多的新存储格式。原先 E1 预览仅保留为设计探索。
- 输出模块接在 `parse()` / `review_alert()` 边界，五字段答复适配为现有 `AlertOutput`。原始模型答复与程序装配对象分别保存，explanation 标记 template；输出不存在的事实、授权、执行状态不补造。
- 若以后接入生产，现有代码还需同步选择输入/输出合同、绑定 Schema、分支校验和配置加载。数据库表、主体绑定、新鲜度和发布事务复用；不能声称只插两行即可，也不需要重写调查引擎。
- 当前候选位于 [input_adapter.py](../../../tools/testdata/alert_io_eval/input_adapter.py)、[output_adapter.py](../../../tools/testdata/alert_io_eval/output_adapter.py)，配置及试验参数在 [config.json](../../../tools/testdata/alert_io_eval/config.json)。现有生产源码未替换。

五字段候选的 `evidence_ids` 是唯一主要判断依据的引用：确定性定性要求这些引用全部为观察或人工来源；needs_review 可以引用其他角色说明不足。适配器用原样 rationale/引用生成现有校验用 basis，kind 由判定对应，绝不生成新的主张或选一条“看起来有效”的引用。这个限制比现版“总引用可混合、basis另选直接来源”更严格，可能增加待复核或拒收，必须单列比较；五字段不预先判为优于八字段。

### 对照、样本及统计

| 组别 | 模型输入 | 模型输出 | 回答的问题 |
| --- | --- | --- | --- |
| current | 现版实际请求结构 | 原八字段 | 同时段基准表现 |
| input_only | 结构精简、原文保留 | 原八字段及同样业务校验 | 仅输入整理带来什么变化 |
| input_output | 与 input_only 相同 | 五字段及适配 | 输出合同进一步改变哪些结果 |

三个已有实测样例分别做两轮，另用六个不同业务场景的合成模板生成新身份/时间实例，各做一轮：共9样例、36格调用。同一样例三组使用完全相同冻结事实，温度0、输出上限3000、超时300秒和模型路由一致；按样例/轮次轮换组别顺序，避免总是让某一组先请求。每格一次，不挑选最好答复；unknown 保留且不重试。两轮只是观察波动，不能当作稳定性能分布或给出可靠P95。

六个新增场景覆盖云权限、MFA、PowerShell、外传上传、邮件与数据库查询，分别包含已有合成语料的良/恶标签。标签、作者判据、样例类别后缀只在独立答案文件，不进入请求。来源是已有人工编写模板，新身份/时间不等于全新语义，也不声称模型训练或其他历史测试从未见过模板。新增模板只构成模型边界测试，工具回执标明未执行；非空资产/情报、人工正文、字段冲突、0/false与未知业务字段另用无模型检查覆盖，不冒充真实查询。

| 指标 | 记录与判据 |
| --- | --- |
| 输入与输出 | 请求完整字节、后端报告的输入/输出/总tokens、缓存/推理tokens（未报告则未知）；不拿字符估算替代usage |
| 时间 | 本机输入整理、模型HTTP往返、输出解析各自记录；SSH总耗时单列。没有流式测量时不报首token时间 |
| 格式和数据 | 原文逐字保留、字段和匹配关系完整、来源可解析、结果能适配既有输出合同；拒收和局部有效结果分别列 |
| 判断 | 每样例每组的判定/置信度/理由/引用/建议；定性改变逐条解释是更有依据、更加保守，还是新增错误 |
| 误判 | 有独立合成标签时统计良→恶、恶→良；needs_review单列，非确定判对；格式失败不当待复核。实测三例没有独立真值，不计算准确率 |
| 语义 | 人工核动作与结果、时间/主机、历史与本次来源、查询状态、授权和因果等；格式通过不代表正文正确 |

旧批参考：A1/A2/A3 输入tokens为3590/5793/8004，输出447/520/718，记录的模型步骤耗时10.558/10.951/15.069秒。旧步骤时间包括步骤内处理，并非纯HTTP延迟；它们只作历史参考，性能结论以本轮同环境配对结果为准。

先通过必要信息完整和引用约束，再评估性能。若新组出现由遗漏导致的事实错误/方向性误判，即使更快也不通过；若单次差异在各组本身波动范围内，结论保持不确定。先比较 current→input_only，再比较 input_only→input_output，避免把两项收益或损害混在一起。本次没有全链落库、API或4177新Run，不以隔离对照替代后续生产接入验证。

### 本批实际结果

36次调用已结束、107,544已报告tokens、0重试。三组平均输入tokens为4299/1774/1600、平均HTTP耗时10.77/8.59/6.49秒；12/12/12份Schema有效、9/9/12份核心解析有效。性能改善有据，正文仍有TI未查写查空、历史180次扩大成全成功等错误，尚不接受生产替换。名义六个合成标签无良恶方向反转，但S3误报/良性定义、S6生成时间/原计划未对齐须先审定；待复核与原答拒收分别统计。五字段还减少建议并改变指令/直接引用枚举，不能仅归因于字段数量。详细输入保留、判定变化、样例问题及用户问到的history四行来源见[实测分析](alert-io-evaluation-20261108.md)。任务3.23仍待生产适配与业务验收。
