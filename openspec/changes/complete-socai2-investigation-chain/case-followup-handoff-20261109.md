## 1. 结论与推进顺序

接下来先补齐 Deep/C6 与新版 C3 的材料和判断交接。Deep 聚焦一个补查目标；C6 形成最终案件判断，报告由程序生成。第一阶段保留 C6 当前业务输出；等输入和依据交接稳定后，再验证显式逐项复核是否优于完整重写。

旧例子的主要问题不能概括为“后续没有证据”。C3 已保留内容的 33 个结构化来源、Deep 答案的 17 个结构化来源，在 C6 中均能找到同源材料。但 C6 只看到 C3 的摘要与两项补查计划，没有完整看到 C3 已保留的发现、问题答案及领域判断，仍需要重新生成这些内容。这里同时有**判断交接不足**和**同源材料重复呈现**。

这些是程序输入组织的事实；它们是否导致某次模型正文错误，只能作为待验证原因，不能由一次历史输出直接归因。

## 2. Deep：发生了什么、为什么仍未解决

实际问题是：“哪些影响已经观察到，哪些只是待核的可能影响？”冻结范围为三条告警。C3 分配的补查则聚焦 A3 的目的 IP `198.51.100.88`，希望核实连接细节及流量特征。两者的范围层次不同，计划里 A3 不会自动把冻结问题缩成只允许讨论 A3。

这次 Deep 可选进程活动、网络连接两个 binding；已有认证查询完成但返回 0 行。模型选择 `action=answer`、`answer.state=unresolved`，没有追加网络查询。回答主要复述登录、进程启动及网络连接，再列出外传、授权等不能确认的内容。

这并不违反当前 `answer/unresolved` 合同，也不意味着必须强制查网络：未必有工具能回答所有缺口。但是“产生了回答”不能记成“本次补查目标得到解决”。应在输入中把问题、补查目的、已有判断、尚缺证据和工具能力按顺序分开；输出明确已知答案及剩余缺口。

本例 C3 的 `required_evidence` 还把 `file_path/hash_sha256` 写进网络补查需求。这是前序模型提出的取证期望，不等于网络工具保证能返回这些字段。下一阶段仍以实际工具目录为准；不可用的材料留作限制或人工交接，不因模型要求就扩展工具能力。

旧正文质量问题另外保留：它说输入提供了 `program_facts`，实际 Deep 用户输入没有该键；它又把 `network_connect + success` 解释为“TCP 握手完成”。现有输入没有独立握手证据，后者是效果扩大。这些都没有在本轮被程序改写或追认正确。

### Deep 输入与输出设计

| 输入块 | 必要内容 | 程序保留的关联 |
| --- | --- | --- |
| 本次任务 | 指定问题、C3 补查目的、成员/对象/时间边界 | Case/Run/问题身份与原计划索引 |
| 已有判断 | 此问题的有效 C3 答案、依据、限制 | 原判断版本和引用解析映射 |
| 证据 | 相关原始观察、反证、人工陈述、共同/不明范围背景 | 原值、来源角色与范围，不按单成员强行裁剪 |
| 已做查询 | 实际查了什么、失败/未查/空/有行、可见字段及限制 | 真实回执、返回行及工件身份 |
| 可选工具 | 用途、可返回内容、适用问题、能力边界及 binding | 具体参数、去重、资源与执行 |

候选输出为 `action、binding_id、reason、answer` 四项。`answer` 仍包含状态、答案正文、支持、反证、替代解释和限制；这些是单问题决策所需内容，不能机械照搬告警五字段。程序从实际请求恢复 `question_id`，然后走现有校验和保存合同。

## 3. C6：需要交接的是判断及其依据

实际保存的 C3 局部分析有 3 个成员、3 个发现、6 个问题、4 个领域、1 个冲突和 2 项补查。C6 中来自该 C3 工件的三条输入分别是：

| C6 来源 | 实际显示内容 |
| --- | --- |
| `N4_S1` | 原补查计划 0 |
| `N4_S2` | 原补查计划 1 |
| `N4_S5` | `previous_summary`，此例为局部保留后的概括说明 |

因此不能要求它“沿用已完成的详细分析”却只提供一句摘要。也不能直接把原始模型答复整体补回，因为其中有被拒收的内容；应使用实际保留的结果并标明限制。

Deep 答案在 C6 中标为 `prior_analysis`，角色正确；但只传状态、正文、替代解释和限制，没有传结构化支持/反证对应关系。原文里的 `N3_E*` 属于历史编号，不能直接当成 C6 的 `N4_S*` 引用。虽然本例 17 个引用都可找到同源材料，程序仍需明确重建依赖；后续缺材料、引用不再可见时，必须显示缺口，不能无条件继承。

原补查计划与回执的绑定已经存在，应保留。本例第一项查询 `completed / answer_available=false`；第二项 Deep 为 `completed / answer_available=true`，但答案仍 `unresolved`。真实执行完成、有回答、确定解决三个概念不可合并。

第一阶段 C6 仍输出：

- `analysis`：最终成员认识、有效发现、六问、领域、冲突和后续需求。
- `conclusion`：本轮最终结论、适用成员、支持与限制。
- `closing_note`：本轮收尾说明，不宣称已执行响应措施。
- `comparison`：与程序明确选定的历史结果相比发生了什么变化。
- `impact`：已经有据支持的影响与不可外推的部分。
- `recommendations`：需要的后续动作及依据；建议不等于执行。

程序继续保存和渲染原结果/报告字段，不让模型生成后台身份、执行状态或单独重写第二份报告。第二阶段的“保留/修订/撤销/新增”必须逐项显式复核、重新校验引用和范围；本轮没有实施此模式。

## 4. 材料覆盖与重复的精确口径

旧 Deep 有 64 个来源，C6 有 78 个；两者各有 47 个 `observation`，按原材料与字段路径归一后各对应 25 个原始位置。也就是说其中 22 个来源是同一原始字段的另一种投影表示，不是 22 份独立佐证。值和转换语义不同的表示不能只因同源就直接删除。

新版 C3 离线账本有 120 个来源，旧 Deep/C6 各能直接匹配其中 28 个同源位置。剩余项包括不同原件表示、离散 I 发现/问题和离线补充的 A 回执。**这不是“丢了 92 个业务事实”的计数**：

- I 的摘要、结论、限制在旧输入的父对象中仍然可见，虽然与新版子路径不相同。
- 8 个 I 发现、2 个问题未在旧父对象中呈现。
- 同 A 的 21 个来源条目包含 9 份回执及其行，不是 21 次查询；这些 A 回执没有进入历史 C1，本次不能追认旧模型看过它们。
- 原件同时有 OCSF/原始载荷等多种表示，不同路径可能表示同一事实；路径缺少不能直接换算成判断信息损失。

当前业务代码中 Deep/C6 仍调用旧 JSON 基础视图，新 C3 的完整结构材料接入尚未延伸到它们。后续应复用同一冻结业务来源，再按阶段选择，避免 C3 能看到云/邮件等字段而后续退回旧标量投影。材料必须按原范围和引用依赖保留，不能为了压缩把判断所需信息省掉。

## 5. 本轮验证与限制

校核同一历史 Run 的 48 份工件 hash 和大小，历史文件前后 hash 保持。来源清单和所有同源映射保存在回执中；引用同源可达不等于可见内容相同，更不等于模型正文正确。

输出只做旧答机械转换和还原：

| 检查 | 结果 |
| --- | --- |
| Deep 删除已知 `question_id`，从请求恢复 | 与旧原答逐值一致，候选四项 Schema 通过 |
| C6 结构化成员/对象换短号再恢复 | 与旧原答逐值一致，旧/候选 wire Schema 均通过 |
| Deep 紧凑输出 UTF-8 字节 | 1,649 → 1,626，仅少 23 字节 |
| C6 紧凑输出 UTF-8 字节 | 9,813 → 8,412，减少 14.28%；正文、引用不变 |
| C6 原 `analysis` 占紧凑输出 | 79.11%；仍不能推断删掉这些职责就能节约同样 tokens |

这些是字段适配和字节检查，未计量新 tokens、耗时或模型质量，未验证完整业务接入。原语义错误不因 Schema 通过而消失；旧引用没有换到新版 120 来源上强求通过。

初次核对脚本把所有工件都按 JSON 计算 hash，遇到正文存储的 Markdown 报告而停止。已按实际 JSON/文本存储分别验证，48 份原件通过；输出目录只在所有断言完成后创建，初次没有生成结果或修改原件。不计“首轮全过”。Ruff 和 OpenSpec 严格检查通过。
