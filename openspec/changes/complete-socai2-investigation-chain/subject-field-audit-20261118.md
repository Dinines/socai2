## 2. 等级意见及优先级计算

### 2.1 严重程度的含义与输入

等级从低到高为 `info < low < medium < high < critical`。判断针对本事件/Case 的安全影响，不是恶意概率、置信度、人工是否复核或 Run 成败。

| 等级 | 本阶段使用的判断口径 | 优先级系统建议 |
| --- | --- | ---: |
| info | 有依据说明正常、已授权或误报，且未发现仍需处置的安全影响 | 10 |
| low | 当前可识别的安全影响有限、局部，未见较高影响依据 | 30 |
| medium | 存在需调查处置的安全风险，现有材料未达到 high/critical 的影响依据 | 50 |
| high | 有依据指向重要资产、特权身份、敏感数据或较大业务范围的高影响风险；未确认影响必须明确为潜在风险 | 75 |
| critical | 有明确依据支持关键系统被控制、核心业务严重受损或正在持续的重大破坏/泄露等紧急重大影响 | 95 |

没有查到数据、查询失败、材料不足均不证明安全，不能据此判 info/low。等级可与 `uncertain/待复核` 同时存在；模型要说明支持该等级的实际事实、潜在与已确认影响，以及限制，不按关键词命中机械打分。

- **建立时**：事件/Case 按实际纳入的告警成员中已知等级取最高值，注明 `member_max`、所用成员/材料版本和时间。全部未知时，配置初始值为 `medium`，注明 `initial_policy/待分析/来源等级缺失`；这是保守规则初值，不是模型意见。明确创建时人工指定等级视为人工设置，同时留存计算的系统初值。
- **分析时**：I 判断本次选入事件成员的风险；C6 判断本轮调查范围的风险。只在已有 I/C6 调用加入独立 `severity_opinion` 单元：`level`、`reason`、`impact_basis`（已确认/潜在影响及证据限制）、`source_refs`、`limitations`。业务范围由程序绑定本轮冻结成员；引用沿现有局部别名还原，程序补真实主体、Run、结果/工件、时间、版本。模型不生成数据库身份、租户、测试来源、任务状态或优先级数字。
- **必要输入**：本阶段已选业务事实、来源等级的角色、所需前序判断/证据、相关资产或身份影响（实际查到才有）。保留反证和限制。人工调整等级的后台操作不自动当作业务证据；需要人工事实时沿既有 H 材料。计算配置、人工覆盖台账、测试标识不新增到提示词。C3/Deep 中间意见不直接改当前等级；定向分析保存局部建议，不直接修改全案等级，待后续综合。
- **成员变化**：标记原意见的范围/新鲜度，沿既有流程触发后轮；不反复用同一批来源最高值撤销人工降低。来源汇总始终另存，不冒充新模型判断。

### 2.2 优先级

`system_priority = configured_mapping[current_effective_severity]`，仅使用上表映射；保存所用生效等级、映射版本、计算时间。现有量纲保持 0–100。首版不加入资产/身份乘数，不采用置信度，不新增第二套千分制。

无人工优先级覆盖时，当前优先级等于系统建议；人工可以设置 0–100 内的值（含 0），必须记录理由、操作者、时间。人工覆盖存在时，等级上升只更新系统建议，当前人工优先级保持；页面并列说明两者。显式撤销优先级覆盖恢复**当前**等级映射值，不恢复创建时旧值。配置变更不在 GET 中追改历史数据；后续真实写入按所选 profile 和新版本计算，旧轮次保留原版本。

参考的是只读 `../SOCAI/opensource/AiSOC` revision `34ca18c57dd4175539e5c6dd3d04a72dc057306b` 的 `services/api/app/api/v1/endpoints/alerts.py` 中五档映射。该工程另一个 `alert_priority.py` 的千分制及上下文乘数不引入；也不把参考工程的人工建案默认值当成本项目已实现分析链。

## 3. 自动与人工更新规则

每轮保留自己的意见，当前等级是独立持久状态。自动处理在同一事务中锁定/校验当前版本，按等级顺序比较，不取字符串排序。

| 输入或操作 | 当前等级处理 | 必须保留/展示 |
| --- | --- | --- |
| 新、有效且适用的模型意见高于当前等级 | 上调，含当前值曾由人工设置的情形 | 原值→新值、本轮依据、来源 Run、自动上调记录 |
| 意见等于当前等级 | 等级不变，保存本轮意见及其新鲜度 | 不重复生成“等级变化”提醒 |
| 意见低于当前等级 | 当前等级不变 | 本轮降低建议及未自动采用原因；允许人工查看后主动降级 |
| 人工明确升/降级 | 接受合法等级，写入当前值，不保留永久锁定 | 必填理由、操作者、时间、前后值；新的有效后轮仍可自动上调 |
| 人工改后重放已处理的模型结果 | 幂等，不再次写当前值 | 同一意见的原处理记录；不能撤销后来的人工调整 |
| 模型运行期间有人改过等级 | 保存本轮意见，因人工版本变化不自动生效，提示需复核 | 冻结的人工版本、当前版本和未采用原因；之后启动的新轮可自动上调 |
| 过期轮次、范围已变或非全案定向意见 | 保存本轮意见，不自动改当前全案等级 | 真实覆盖、过期/局部原因；不回落到更早成功轮冒充最新 |
| 整轮执行结果 unknown 或尚不能确认本地交付终态 | 等级仅作为候选保存，当前值不变 | 沿既有 unknown 候选不可采用边界；不因一个完整单元宣称本轮可生效，不重派未知调用 |
| 截断、缺字段、非法枚举或不能可靠恢复等级单元 | 保留原答/已完整单元；缺等级则保留当前值，继续合法下游 | 本轮等级未更新和原因；不能把初值/旧值标为本轮模型意见 |

有效等级单元须结构完整、依据非空、绑定真实来源和冻结范围，并有已知的交付处理结果。`finish_reason=length`、已知部分交付、纯引用质量问题不自动否决可独立使用的完整单元；**整轮 unknown 不属于可自动应用的部分交付**，候选仅保存。不得从残句、自由正文关键词或补默认值拼造意见。无法绑定范围的单元仅留原件/问题，其他有效分析继续。已有有界补答和交付恢复机制复用，本阶段不新增重试框架或为等级单独追加模型请求。

**更新顺序**：独立等级单元先保存为本 Run 工件→校验适用性/人工修订号/已处理身份→比较当前值→事务保存当前值、系统优先级和活动记录→HTTP 读回。等级状态与结论采用状态分别展示；仅有等级单元不能伪造完整 C6 Result、正常完成或已人工采用。较早轮次晚到不得压过已经处理的较新轮次。人工操作及自动操作都携带幂等身份，版本冲突返回明确冲突并读回最新值，不以客户端最后写入覆盖。

## 4. 持久化及 HTTP 兼容方案

以下为本阶段目标结构/合同；S1 的创建状态、增量132及读取、S2 的独立意见/应用/活动工件及S3人工修改/撤销/回执已在候选实现，S4页面候选及直接验收/限定独审已完成；后续步骤仍待，新增合同尚未正式发布。使用增量迁移，保留 V1 原件、旧记录及原模型输出。复用现有主体表、Run 工件与活动历史，不新增另一套评级服务或双主状态表。

| 数据位置 | 目标保存内容与唯一来源 |
| --- | --- |
| Case 主体 | 现有 `severity/severity_source` 为当前生效值；现有 `priority_*` 为当前生效优先级，不在前端重算 |
| Incident 主体 | 增量增加 `severity/severity_source` 存当前生效值；现有 `severity_override*` 保留人工设置记录，不能作为永远覆盖自动上调的第二份当前值；现有 `priority_*` 存生效优先级 |
| 两主体的增量 `risk_metadata` | 版本化结构：当前等级依据/时间、已应用意见引用、最近意见引用及应用/未应用原因、最新已处理轮次、人工等级修订号、系统优先级及映射版本、人工优先级覆盖记录。类型/必需条件在内部 DTO 固定；不接受任意客户端整包写入 |
| Run 等级意见工件 | 原模型意见与程序还原后的单元、冻结成员/材料版本、意见 schema/policy 版本；用真实 Run+阶段+单元身份唯一定位，不要求缺 Result 的部分交付伪造 Result ID |
| 活动历史 | 等级变化/降低建议、优先级人工修改/撤销、来源/未采用原因；与生效修改同事务，按操作键或意见身份去重 |

人工等级修订号只在人工操作后推进，运行开始冻结到后台，不送模型；`row_version` 仍负责通用并发管理。自动过程同一事务比较最新当前值，因此两个上调结果不能反向覆盖。引用工件保存成功而状态事务失败时，当前值及活动均不伪称更新；记录异常，后续对同一工件幂等处理，不重新调用模型。

HTTP 由 `services/api/investigation_http/` 用例端口承接，核心不反向依赖对外包。改动清单：

| 对象/入口 | 增量和兼容处理 | 受影响读取 |
| --- | --- | --- |
| Case 查询 | 原 `severity/priority_*` 名称、类型和含义保持；新增 `risk` 明细暴露本轮意见、当前依据、系统建议/人工设置、版本和未应用原因 | 列表、详情、管理、过滤/排序/统计、导出、4173/4177 必须同源；旧轮次读冻结工件 |

| 人工管理 | 沿现有 Case/Incident 单条管理与 Incident 批量入口增加 `severity_reason`（Case）、`priority_value/priority_reason` 和显式 `clear_priority_override`；省略保持，设置/撤销互斥，保留 `operation_key/expected_row_version`。Incident 沿用 `severity_override_reason`，明确调整为设置和撤销均必填非空理由 | 管理回执返回当前值及版本，详情可独立再次 GET 核对；批量成功时逐项回执，任一冲突整批回滚，保持现有原子合同 |
| 原严重程度清除入口 | Case `severity=null` 原来清空，目标不再允许清空业务必需等级，返回明确 422 并提示选择等级；Incident `severity_override=null` 保留“撤销人工设置、恢复成员规则”的显式人工操作含义，**目标允许且要求同时带 severity_override_reason**，使用当前成员最高/未知初始政策，保留清除历史；后轮自动仍只升不降 | 前端移除 Case 清空选项，Incident 明示恢复后的等级并填写理由；现行合同禁止 null 带理由，本次明确变更。旧客户端无理由的撤销返回422、原值不变。该增量须随同 OpenAPI/交接发布，不能静默改 null 语义 |

## 6. 任务时间字段及耗时口径

任务是分析任务 `task`，不是人工核查任务；task→attempt→Run→step 沿真实关联。复用现有任务和步骤表，不新造“正在执行”业务集合，也不改变队列容量、串行或重试规则。

| 字段/层级 | 语义、写入时点与读取 |
| --- | --- |
| task `submitted_at`（已有） | 原始受理/创建时间，终身不随重新入队或重试重写；页面称“受理时间”，不再增同义 created_at |
| task `first_enqueued_at`（新增）、`last_enqueued_at`（已有，补 HTTP） | 首次确认写入 Redis 队列及最近确认入队时间。补充入队不覆盖 first；先 Redis 成功再确认 PG 保存，写入结果不明保持未知并记日志，不拿 submitted_at 猜入队时间 |
| attempt `enqueued_at`（新增，可空） | 本次实际尝试对应的首次确认入队；同次补充推入不重置。重试产生新尝试的入队时点，不能把上次尝试等待/执行混入本次排队时间 |
| task/attempt `started_at`（已有） | task 首次实际开始、attempt 本次开始。开始涵盖取数/输入准备，可能尚无 Run；在槽位取得后记录真实起点，不把模型开始时间当任务开始。尚未开始为 null |
| task `ended_at`、attempt `local_ended_at`（已有） | 本地实际收尾。unknown 也可有本地结束时间，Run 的结果与结束时间另读，不能伪造成远端执行已确定结束 |
| Run/step `started_at/ended_at`（已有） | 真实执行步骤起止；新增任务读取投影 `active_step` 带实际 step ID/名称/开始时间，仅本地仍在执行且有已记录活动步骤时提供；准备中无 Run/step 就明确“准备阶段，尚无步骤记录” |
| 原有状态与原因 | 保留 retry_count、next_retry_at、reason_code、失败/中断时间及 error_stage/error_code；尚未真正启动不能显示运行中，重试预约不保证该时刻执行 |

同一尝试的排队耗时 = `started_at - enqueued_at`；执行耗时 = `local_ended_at - started_at`；总历时 = `task.ended_at - submitted_at`。仍在排队/执行时，用查询服务的 `observed_at` 算“已等待/已执行”，随同响应返回，页面刷新不能改起点。重试等待单列；当前步骤耗时从该步真实起点计。所需起点未知则耗时为 null/未记录，不是 0。负时差记录时钟/数据异常，不能悄悄截成 0。

实现时把“下一次尝试的首次确认入队时间”暂存任务、开始时冻结进 attempt，避免靠最近 LPUSH 推测本次队列起点。时间统一带时区保存，UTC 计算、本地显示。旧任务不回填；队列/PG确认之间失败可能缺时间，要诚实展示并从日志查因。4177 只是读取上述字段、状态、耗时和实际步骤，不承担异常日志存储，不做心跳/卡死判定平台；“等待很久”不直接判断死锁。

## 7. 异常日志文件

复用现有 Python 日志设施，给本流程的 fusion 消费/入库/任务登记、analysis dispatcher 的 Redis/PG/输入准备/执行/结果落库、内部 HTTP/组件调用，以及对外查询/管理错误接入统一字段和**文件 handler**。当前若只有 `logger.warning/exception` 或容器控制台不算验收完成。

日志每行结构化记录：带时区时间、level、service/module、instance/process、operation、stage、dependency、error_code、exception_type、程序定义的事件 message 和 traceback；有上下文时增加 correlation_id、task_id、attempt_no、Run/step/subject 引用、首次观察/本次发生时间、实际重试次数及已有下一重试时间。调用前尚无 task/Run 的 Redis 断连等服务异常允许这些键缺失，不伪造关联。可重试/未知结果与实际是否已安排重试分开记录；恢复仅在真实操作恢复成功时另记一次，不猜测恢复。

traceback 保留文件、行号、函数及异常链类型，**不包含 locals、完整请求/告警、提示词、模型原答、密码/token/连接串凭据或隐藏推理**。按11-20负责人最新澄清，本轮不新增业务数据脱敏或通用脱敏专项；不改写业务原件，既有凭据保护保持。文件仅选程序事件码及关联字段，第三方异常正文不复制，直接记录异常类型与调用栈结构；不另建文本清洗规则。模型/工具原件仍在既有受控工件。4177 HTTP 只给受控错误摘要/关联键，不返回堆栈。正常排队、模型待复核、等级降低建议不是 ERROR；查询失败、保存失败、真实超时按实际严重性和错误码记录。

配置文件显式指定目录、级别、JSON 格式、轮转大小和份数；首版模板 `INFO / 20 MiB / 10 份备份`，部署 profile 可调整。容器目录挂载持久卷，控制台同步保留；多进程按 service/instance/pid 分文件，避免多个进程争写同一轮转文件。日志写入不依赖 Redis/PG。文件写失败向 stderr 给出一次受控降级记录，不能递归写同一失败 handler 或掩盖原业务异常；不得悄悄声称已写文件。不增加集中日志平台、告警升级、自动重启或通用故障注入框架。
