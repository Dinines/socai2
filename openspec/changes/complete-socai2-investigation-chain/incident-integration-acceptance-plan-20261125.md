## 2. 对应测试方法与接口

本计划采用“功能 → 场景/前置条件 → 用户操作 → 接口与保存 → 预期结果 → 证据/缺陷”的对应表。ISTQB将验收标准作为测试依据，强调需求、用例、结果、缺陷的可追溯性；先定义预期，再比较实际，不以接口成功码代替业务通过。[ISTQB CTFL v4.0.1，§1.4.1、§1.4.4、§4.5.2–4.5.3](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

页面验收以用户可见行为为中心，检查文字、状态、跳转、表单和刷新结果；必要自动检查优先复用现有测试。[Playwright官方测试实践](https://playwright.dev/docs/best-practices) 本项目据当前目标裁剪为正常业务流程、直接数据核对和少量必要空态/失败态；不开展压力、极端并发、故障恢复矩阵或全仓回归。页面等待显示就绪不等于自动重发业务写请求。

以下路径省略公共前缀 `/api/v1/socai2`；`{id}`、`{run_id}`等是结构占位符。前端仍经SpiritHub后端访问调查HTTP，不改成浏览器直连调查核心。列出接口代表目标调用关系，**不代表21平台已完成转发或真实测试已通过**。

### 2.1 测试条件与数据

- 业务验收复用之前确认、已经由Kafka发布者发送的10条OCSF告警及其自然形成的事件；先只读确认当前事件数量、成员和已有任务。不得假定本组一定有多事件、多成员或多轮诊断正例。

- 优先选一个代表事件进行读取和单条管理；有足够记录时选两个做批量、另留一个不操作对照。若数量不足，相关正例标“缺数据”，复用已有测试证明实现的部分另列，不能把替身结果记作真实批量通过。

- 4173是产品页面主基准，8181是对齐后实际验收入口，4177是指定事件Run的执行材料辅助查阅；本轮不依赖5601，不新建测试框架。
- 数据值、真实身份、正文和原始请求/读回保存在受控环境。仓库回执只写接口、字段、检查项目和不含业务数据的结论；Codex侧沿现有数据边界处理，不读取私密快照正文。

### 事件管理先沿现有合同，不混用告警规则

| 事项 | 当前事件合同/本计划依据 |
| --- | --- |

| 人工判定 | 不新增事件版告警反馈；事件业务判定按既有诊断结果来源显示 |

诊断测试按实际前置条件选模式：确有未分析变化时用一次`check`验证新任务执行；若无变化且需证明新的执行链，计划用一次明确`rerun`。不为了同时覆盖两种模式连续调用模型，无变化跳过语义复用既有直接测试；实际意外跳过则先记录原因，不盲目追加重跑。模型正文质量沿既有记录单独评价，已有明确后置问题不反复采样；程序不能保存、错绑对象或不能读回仍是阻断。

在授权的21环境推进与一个change的交付安排并行：各步先完成实现及直接验证，不随每个小修反复发布/推送。确需21运行候选才可验证的部分由统筹合并对应依赖、记录实际版本并按既有阶段授权执行；本规划不触发任何更新。事件计划完成也不等于主change可以归档。

## 6. 验收、缺陷和回执

每个功能都要有明确结论。实现者先提供直接证据，统筹对关键读取及每类正常写入独立核验，最后由负责人进行业务可用性查看。技术验收与人工验收分开记录。

| 检查层 | 验什么 | 不能当成通过的替代物 |
| --- | --- | --- |
| 数据/业务 | 已提交的事件、成员、修改、活动、任务和结果，以及字段来源和固定版本 | 只有准备中的请求、合成样本或旧批证据 |
| HTTP/平台 | 请求目标、筛选范围、响应身份/字段/错误与保存相符 | 仅200/202、Schema存在或接口能连通 |
| 8181页面 | 用户可见数据、操作、刷新、分页和跳转与前两层一致 | 只有截图好看、组件替身通过或开发者自述 |
| 人工查看 | 事件信息是否能理解、常用操作是否顺畅，产品文案和布局是否合适 | 统筹代替负责人声明已人工验收 |

回执字段保持简洁：功能编号、用例编号、环境/版本、来源批次引用、步骤、预期、实际、状态、证据路径、问题及责任会话。操作和真实记录ID留受控回执，公开文档只放安全引用。查询只核本组和必要字段，不做全表全接口逐字段对账。

- **阻断本功能**：读不到事件、筛选失效、数据串对象/轮次、保存后丢失、批量影响未选中对象、任务/结果无法追踪。先修当前步骤并复验。
- **可记录后置**：已确认的模型正文质量问题、负责人名称可读性、资产上游关联ID等；必须保留具体影响和未通过范围，不能写成已修复。
- **缺数据/未验**：本组没有多事件、多成员、旧轮次或匹配资产正例，单独标记；不得用空结果核销非空功能。
- **范围后置**：Case创建/关联/执行及跨模块联合验收。现有关系只读通过不能核销这些项。

计划的最终交付为一份可逐项核对的事件验收表，而不是测试次数或“接口全部200”。阶段完成至少要求纳入范围的正常读写闭环有证据、阻断问题关闭、所有缺口有明确处置；仍有范围内缺口则只报限定通过。
