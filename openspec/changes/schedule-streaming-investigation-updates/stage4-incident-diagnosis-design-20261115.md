# 第4步：事件自动诊断实施设计与直接验收

本步承接第1–3步，不改队列算法。范围为任务2.2/2.3的I分支、2.5的I容量和2.7的事件HTTP。先完成此设计，再strict、实施、直接验证及HTTP交接；本轮不部署、提交或启动生产消费者。Case及知识后台队列留后续步骤。

## 输入、执行与保存

1. native入站首次保存事件及首个成员的同一PG事务登记I initial task；同一事件后续入站不重复登记initial，告警A首轮仍各自登记。受理只保存任务，不创建Run，不直接调用模型。调度使用已有A高于I的优先级和共享N；不等待全部A的屏障。
2. I handler执行前重新取最新成员：按linked_at倒序、alert_id升序选最近最多100条，独立配置incident.max_alerts_per_diagnosis。总成员数、选入ID及时间在同一SQL快照捕获；只装配选入材料，原事件和历史Run不删成员。初轮、check、rerun使用同一选择规则。排队期间可纳新材料，开始后固定输入原件。
3. 本步继续使用现有I模型业务视图、输出Schema、引用修正和局部保留能力。原始材料、配对A及工具回执留在输入工件；只有既有I业务视图进入模型。Run、input/policy工件和attempt绑定同事务保存，然后才调用模型。
4. 更新摘要只包含选入告警ID集合、可用A的业务判断及建议正文、当前有效人工反馈正文。A记录ID、Run ID、actor、时间戳、负责人、事件自身诊断指针及未选成员的A不构成变化。事件总数保存于选入回执，不用总数单独触发同输入模型。没有同告警原材料更新/重新分诊入口。
5. I中A可用性核配对身份、正常完成Run和相同原材料；当前负责人/标签或晚到人工反馈不抹掉原有A历史判断。A作为prior_analysis，反馈作为human_statement分别输入；此规则仅作用于新I输入，不改变告警公开freshness/DTO。冻结摘要与当前摘要用于新I新鲜度；读取按该Run冻结的选择规则检查现有材料，执行器配置改变则在下一次检查/执行时按新规则重新选择。历史输入沿原规则，不改写原件。
6. 完整请求容量在发送前检查，超限保存准备后的请求、测量/原因及输入，Run失败，task以capacity_exceeded结束，不自动重试/删成员/分段。同输入同容量配置停止重复尝试，容量配置改变允许新预检。其他明确临时连接故障仍沿60秒/一次重试；回复未知沿已有本地收尾，释放N。

## 定期检查与生命周期

在唯一dispatcher循环调用I检查器，不新增进程。一次读取配置数量的到期事件，扫描不调用模型；只有登记过且开放、在7天活动窗口内的对象才产生新自动请求。先比较当前业务摘要与最近成功/已停止摘要，有变化才登记check；真正执行仍再比较一次。扫描更新next_check_at，默认4小时，不因无变化、入队或通知延长活动窗口。

首轮未开始时不做周期检查；首轮结束（含失败/unknown）安排下一检查。失败停止摘要不永久禁止新材料检查；相同材料按既有停止规则跳过。正常完成以完成时间续7天，失败不续期。关闭停止新自动请求，排队尚未开始的请求跳过；正在运行者完成但不重试/重开事件。窗口内已受理的首次执行跨期仍可执行、不重试；已等重试的跨期终止。手动check/rerun开放事件不受7天限制；重开本身不执行、不续期。

## HTTP与读取

统一门控还覆盖受影响的运维入口：移除旧production_processing/processing_job直接执行incident的CLI动作，保留内部I执行类供唯一调度器和测试调用；Case既有CLI随其后续步骤处理。避免HTTP已异步但仍保留可绕开共享N的正式I启动命令。

HTTP侧仅提交task：E37 operation_key + mode(check/rerun)，202返回task_id及status_url。pending和Redis不对外暴露，Case提交路由不在本步启用。

核心新增IncidentStageEntry/IncidentStagePage，保持共享告警StageEntry/StagePage不变。事件E23/E25增加合同8.5的input_selection和analysis_coverage，来自该Run冻结输入及实际保存的delivery_assessment。analyzed/unresolved/not_analyzed三数在选入集合中互斥；analyzed与unresolved共同构成covered IDs。未选成员仅计omitted；相对捕获的整个事件给complete/partial/none，无法确定则unknown/null。历史未保存选择回执则两个对象null。不将选入成员完整交付冒充全事件覆盖。E29沿同源latest_diagnosis_id与analysis_url读取。

## 实施顺序和验证安排

1. 输入选择/更新摘要/新鲜度及事件专用读取类型：离线检查排序、可用A及反馈、互斥计数与告警Schema不变；真实PG核最近100/全事件成员保留和历史读取。
2. 入站I登记、真实I适配器、周期扫描及显式A/I配置：真实隔离PG+Redis，以受控模型回复走输入→Run/attempt→模型调用→诊断保存→读取。核正常A→I、晚到A/新增成员/反馈、无变化跳过、执行前重取及运行中固定范围；复用第1/2步生命周期证据，只定向核I接线。
3. 容量和失败：受控直接检查一次超限不发送、原请求/测量可读及旧结果保留；相同材料配置不重复、变更配置可预检；失败/unknown不堵下一事件。不开压力/恢复矩阵。
4. 新独立真实模型批次，最小A→I必要调用，保存实际提示、Schema、配置、可见原答、验证、装配、保存/读回；已知模型正文质量问题保留NOT_PASSED，不反复采样。
5. 向HTTP交付实际handler/config及成功、部分覆盖、无变化、失败样本后切E37；同隔离PG/Redis联验202→消费→task/Run/结果GET，读取不产生模型调用或写入。同步Swagger、运行/配置/部署清单及本机静态4177导入；实际21服务不动。

证据使用新批次analysis-incident-auto-20261115-01；测试替身与真实模型分目录，不覆盖前轮证据。只在本步全部直接验证和HTTP读回后更新完成状态，整个change的独审/发布仍在第11步。
