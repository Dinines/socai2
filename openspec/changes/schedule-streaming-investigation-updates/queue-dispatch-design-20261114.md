# task / pending 调度设计

2026-11-14定稿；2026-11-15通用调度第2步已完成[本地验收](../../../docs/operations/evidence/analysis-dispatch-20261114-01/README.md)，实际自动业务待第3–7步接通。业务规则见[主设计](design.md)，字段见[存储设计](storage-and-runtime-design-20261114.md)。采用单一领取者，不因Python GIL假设任意多线程读改写都安全；多生产者只追加，执行器异步运行，完成通知由同一调度循环处理。

2026-11-15最新简化：不同请求不做跨task归并，各自入队并在执行前检查材料；同key重放保留。以下目标算法更新，F4直接验收前当前代码仍含归并路径，不能据旧第2步回执认定新规则完成。

## 1. 职责与Redis结构

| 角色/结构 | 职责或内容 |
| --- | --- |
| HTTP、入站、周期检查生产者 | 先持久保存task；可追加UUID，未追加者由调度补投；不领取、不改运行集合 |
| 唯一调度器 | 每60秒（独立配置）收尾、领取、核N与主体占用和安排重试 |
| 异步执行器 | 获取最新材料，先保存范围/Run再执行；只回报完成，不自行领取下一项 |
| task普通队列 | 逻辑上一个普通队列；按case/alert/incident/knowledge四个优先类别使用Redis FIFO List |
| pending队列 | 一个FIFO List，存因主体忙或可重试故障而等待的task_id |
| running索引 | 按租户/类型分组的Hash，原主体UUID→task_id；全局Set保存占槽task_id以核N |

本期入口显式选择一个租户和唯一领取实例，N覆盖本实例所有种类；不得另开独立profile绕过额度。所有key加配置的部署命名空间，值不含完整告警或模型正文。tenant/type是分组条件，主体ID本身不变，不造长业务ID。数据库记录是查询依据，Redis TTL不是自动期限或释放名额的依据。这里只使用RPUSH、LPOP、LLEN和Hash/Set基础操作，不操作链表中间节点。

同级FIFO；普通优先级Case > A > I > 知识维护，顺序来自profile。pending先于普通，但本轮扫描有限。严格优先级首版不提供公平性/最大排队时间保证，不能宣称持续高负载下低优先级一定不饿死；当前不加权重和抢占。N限制本地活动任务总数，Case内部沿既有顺序调用，不新增并行子模型请求绕过限制。

## 2. 每轮算法

调度轮询dispatch.poll_interval_seconds默认60；与事件4小时、Case6小时检查及故障60秒等待是三个不同设置。一次tick可启动多个不同主体直到N满，不能在调度循环里await整轮调查完成。

```text
每次tick（到期业务材料检查在第4/7步接入，本步实现补投已受理task）:
  收尾已结束future，保存结果/实际结束并释放running
  处理到期的I/Case材料检查和未入Redis的已受理task
  若running_count >= N: 本轮结束

  P = LLEN(pending)
  最多循环P次，且每次先确认还有名额:
    id = LPOP(pending); 空则结束本队列
    处理候选(id, 来源=pending)

  按case、alert、incident、knowledge顺序:
    Q = LLEN(该task队列)
    最多循环Q次，且每次先确认还有名额:
      id = LPOP(该task队列); 空则结束本队列
      处理候选(id, 来源=task)
```

处理一个候选：

1. 从PG读task。不存在、已终态或同一task已经实际运行的重复队列项记/略过，不再次执行。
2. 校验当前主体状态和本次领取类型。关闭→skipped/closed_before_start；期限内已经受理、尚未实际尝试的自动任务，即使排队跨期仍放行这一轮，并记录跨期后不自动重试。等故障重试期间关闭/超期则最终failed并记录retry_stopped原因，保留此前attempt，不能改成从未执行。超期只阻止新受理自动任务，不撤销此前受理的首次尝试；同主体、N及最新输入/无变化检查保持。
3. 不同请求不相互归并；同operation_key的受理重放仍指向原task。保留各请求source/intent，手动与自动执行前分别核适用范围。
4. 主体已有其他本地活动任务→放pending尾；故障重试未到next_retry_at→放pending尾。等待不占N，不sleep到这条任务到期，不刷新时间或加次数。
5. 获得槽并登记活动句柄，执行器取最新材料再比较；普通check无变化或同材料已停止自动尝试就只更新task并释放槽。普通任务有变化，或显式rerun/定向/综合请求校验通过后，才建attempt和Run，保存输入后开始分析；定向/综合不能因为普通材料摘要未变被误跳过。
6. 实际开始自动重试才retry_count加1。普通任务首次执行不是重试。running期间后来的通知只能成为等待任务，不能改本轮输入。

P/Q为各队列本轮开始扫描时的长度，不是N或剩余名额。新追加和本轮转入pending的请求下次tick处理。队列只逐条弹出、按需要放回，不把整个队列取出重写。多个生产者的RPUSH不会插到正在扫描的前面；单一领取者足以实现该策略，不为跨命令流程增加Lua/分布式锁。各Redis命令本身仍由Redis执行。

## 3. 两个额度的例子

N=2，Case A已经占1个槽。pending有10条A；普通队列有Case B：

- 读P=10，最多逐条检查10次；A仍忙就放回尾部，不在本轮第11次继续取A。
- 还有1个空位，开始检查普通队列；B空闲，启动B，N满。
- 若A先完成，下一tick先收尾释放，再检查pending；其中一个A可执行，其余A等待或在完成后因无变化跳过。

若pending前两条均A、第三条是空闲C，不按“只检查2个额度”截断；会继续到C并使用空位。若pending全忙，也会进入普通队列。避免的是队首忙导致的空位闲置，不保证所有待办立刻执行。

## 4. 独立请求与可接受重复

T1和T2各自保留task。T1运行时T2进入pending；T1结束后T2读取最新材料，已经覆盖则跳过，有变化则新建Run。T1启动的同时收到T2也不需要原子归并；唯一调度器负责同主体串行。不同请求的执行范围不互相替换，手动check不能被自动check的较窄范围吞掉。

普通新请求不得绕过同主体正在等待的故障重试或已停止的同材料摘要；原task重试时间和次数保持。等待不占N，其他主体继续。显式rerun保留重做意图；同operation_key重放只查原task，不创造新请求。本规则待F4实现，旧归并回执仅是历史证据。

## 5. 失败分类与有限重试

采用程序异常类型、调用阶段及实际回执分类，不能只看failed或HTTP状态码。以下是实施映射的确定规则：

| 故障 | 自动进入pending重试？ |
| --- | --- |
| ConnectTimeout、临时连接拒绝/DNS或网络不可达，确认请求尚未发出 | 是；明确地址/证书/配置错误除外 |
| PoolTimeout，尚未发出请求 | 是 |
| 明确429限流/服务忙拒绝且本次未被执行 | 是；next_retry_at取失败+60秒与有效Retry-After更晚者 |
| 502/503/504 | 只有确知未执行/已失败且无未知在途调用才是；仅有状态码不足以重试 |
| 读取必要材料的暂时依赖故障，阻断本次且没有未知调用 | 是；可选查询失败但整轮完成则不重跑整案 |
| ReadTimeout、写出后响应中断、提交成功与否未知 | 否；本次调用失败收尾，原结果未知如实保存 |
| JSON/Schema/引用/正文质量、结论待核 | 否；走阶段一局部保留/有界补答，不把每个补答变成新调度attempt |
| 401/403、错误参数/模型配置/证书、程序缺陷、用户取消 | 否；保留错误，修正后可明确rerun |
| 实际输入/上下文或预算超限，即使成员未到条数上限 | 否；保留测量、准备范围和已完成结果后收尾，释放槽；不自动裁剪/分批综合或重试同输入 |
| 知识维护外部写入未知 | 否；保留原卡/索引回执，不盲重放 |

默认retry.max_retries=1，retry.delay_seconds=60；0次表示不自动重试。每个root在受理时保存策略。失败后确定可重试且当前开放/仍在自动窗口，task转waiting、next_retry_at=failed_at+delay并入pending；可重试故障的原attempt已结束，所以不占槽。最早时间不保证准时开始，还需等下一tick、主体空闲和N。

窗口内受理但跨期后才执行的那一轮不自动重试，即使错误本来属于临时故障。本轮正常完成仍按真实完成时间刷新活动窗口；失败、排队和开始本身不续期，不新增人工判断或单独队列。

第二次实际尝试仍失败则最终failed/retry_exhausted，记录全部失败。未知、不可重试或耗尽次数将该实际材料摘要登记为停止自动尝试；周期重复通知只跳过，不以新task偷开新额度。新的实际业务输入或明确rerun仍可执行，无人工解除门。

容量停止还复用原失败策略/测量核相关容量配置：同输入和配置不重复自动尝试；配置或输入变化后可以重新预检，仍超限则不发模型。此规则只针对可判定容量，不给其他故障重置已用自动重试次数。

已排重试期间变成关闭/超期：原失败和次数保留、取消后续重试，不制造新Run。等待主体忙与等待故障是不同原因，前者不要求额外60秒。

## 6. 本地结束与结果未知

本地调用返回/异常/超时按现有deadline完成取消和收尾后，释放running索引及全局槽；不是收到“超时提示”但仍有本地任务就提前当作已结束。结果未知用Run unknown及调用回执表示；attempt保存真实local_ended_at，外部task最终failed。原unknown ended_at不补假值，不要求人工核实远端或解锁。

N=1时A未知收尾后B照常领取；历史unknown不再阻塞claim/结案。远端服务可能继续生成，系统记录此事实，N只表达本地活动执行。异常与退出统一finally路径，不能仅释放Redis而漏改本地状态。

数据库任务/Redis追加不作分布式事务。追加失败用持久task下次补投；Redis不可用时停止新领取，不能绕过容量直接执行；已有运行允许正常收尾。最小重启处理、数据库约束调整和本地收尾写回记录见存储设计，不新增通用恢复框架。

## 7. 直接验收

用可控执行器+隔离PG核N=1/2、同主体串行、10个忙A不挡B、同tick可填多个槽、无变化无Run、T1失败60秒后最多一次重试、等待不计次、T2独立等待且不绕过已有重试时间/次数、unknown收尾继续B。真实模型只用于一批必要业务闭环，不用真实服务故障反复采样。

官方依据：[LPOP](https://redis.io/docs/latest/commands/lpop/)、[RPUSH](https://redis.io/docs/latest/commands/rpush/)、[Hashes](https://redis.io/docs/latest/develop/data-types/hashes/)。异常分类沿[HTTPX异常](https://www.python-httpx.org/exceptions/)；429的Retry-After见[RFC6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)。这些资料支持基础操作和分类，不证明本项目调度已实现。


## 8. 第2步实施落点与直接验收

本步承接已验三表和核心任务读写，只实现内部调度。生产者仍仅持久受理/追加；A/I/Case的自动入站、周期材料构造和真实模型适配分别在第3–7步接入，知识执行在第10步。调度接收按kind注册的材料读取/执行适配器，缺适配器时保留已受理请求，不伪造成功或启用旧同步入口。

1. 新增显式调度profile、Redis FIFO/索引适配及单实例运行入口。默认总N=1、轮询60秒，优先级Case/A/I/知识；连接、命名空间、运行租户、执行时限和本地收尾回执目录均配置化。单一服务实例领取，HTTP worker不启动循环。
2. 在现有Store补可见待办归并、完成/停止摘要检查及中断收尾。先读取最新材料，再判断无变化；决定尝试后保存attempt，由业务适配器创建/绑定真实Run并冻结输入。输入比较失败也保留真实准备失败，不生成模型Run；已受理跨期首试保持。
3. 每tick先收尾/补投，再按开始长度扫描pending及四级普通队列。执行协程只返回完成信息，不读写Redis；本地活动字典控制N和主体串行，单次tick不等待模型完成。关闭/重试到期、归并不重置额度、重复通知和停止摘要均按前文实现。
4. 本地执行真正结束后先保留小型脱敏收尾回执，再释放活动占用并写PG。PG补写失败保留回执供下tick再写，不重派执行；日志/调度状态明确保存未确认，PG/API不能据此宣称成功。启动只在唯一旧进程已经退出的单实例入口下执行：先补已有回执，剩余遗留attempt记interrupted/发现时间，无准确结束时间；清本命名空间运行索引并补投待办。该短回执不存完整模型内容，不建设恢复平台。
5. 直接验证使用现有隔离PG、新的隔离Redis命名空间和可控执行器，冻结新UUID输入并产生可读的合成Run。核N=1/2、10忙A不挡B、同tick填额度、重试60秒/最多一次、归并策略不变、无变化无Run、unknown释放后B继续、跨期/关闭、Redis不可用不新领及一条收尾补写/中断续行。时间由测试时钟推进；不做压力测试、故障矩阵或真实模型采样。通过后记录保存/读取和未验边界，再报告本步结果；不继续铺开自动业务。
