## 2. 验收口径与范围边界

| 维度 | 本次判据 |
| --- | --- |
| 环境准备 | 明确环境、数据与服务归属；结构/依赖满足当步要求；上下文可查；原有资料得到保留 |
| 正常流程 | 按真实入口受理并执行；身份、冻结范围、前序、保存和HTTP读取一致；依目标取得可读取业务交付 |
| 边界流程 | 无变化、失败、unknown、局部结果、关闭等按合同如实结束和读取，副作用与实际动作一致 |
| 真实模型 | 有实际发送请求/回执/原答及来源关联；空usage保持未知；替身、历史答复导入不能标成本批真实生成 |
| 模型质量 | 独立记录not_evaluated/issues_recorded及原NOT_PASSED；不报准确率，不通过程序accepted推断正文正确 |
| HTTP | 使用实际独立服务TCP完成提交和查询，核真实持久数据；已有ASGI检查可复用，但不能替代本批TCP结果 |
| 查阅 | 4177默认HTTP读取本批真实业务与测试记录，沿同task/Run/步骤打开输入、输出、质量问题和失败；归档模式注明快照时间，不借另一Run补空态 |

模型输入和提示会影响分支、格式、容量及交付，不能假设“质量后置所以模型不影响流程”。只要程序按现行合同处理了模型失败，可以通过相应失败路径；正常成功路径仍记未覆盖/受模型输出阻断，不伪造Result或降低接收规则。已知正文问题记录后继续独立用例，不为它反复采样。发现程序问题只修当前一步并定向复验。

本期不增加检测/采集平台、普通AI聊天、模型读取附件正文、自选全案时间窗、同ID新材料提交/重新分诊、真实响应执行或旧对象迁入。对应现有功能边界及外部依赖保留在接口清单中；测试建议/回执关联不等于执行真实响应。用户页面开发不是后端测试前置。

### 2.1 先单点再集成的执行层次

采用分层测试、按依赖逐步集成。底层用小而确定的数据定位规则，上层核真实接线；每层复用既有有效用例，只补直接受影响行为，不按固定比例追覆盖率。纯函数/离线检查可在开发工作区执行；**真实服务、数据库和模型测试选21明确资源**。下列层次属于同一T步骤，不另起任务树。

| 层次 | 边界与方法 | 进入下一层的必要证据 |
| --- | --- | --- |
| L0 就绪预检 | 版本、配置、迁移、来源和接口；T1只读 | 目标版本/依赖相符；不符记blocked/awaiting_release，等待发布 |
| L1 单元/规则 | 输入筛选/装配、Schema、身份/范围、状态、容量/幂等；外部依赖可用明确替身 | 固定输入→明确输出或错误；正常及必要边界通过，替身不能标真实模型/来源 |
| L2 单模块/组件 | 每次一个模块及直接真实依赖：输入→处理→PG保存→读回；上下文单源真实查询；模型模块真实请求 | 同一主体/Run的回执、原答、工件及持久结果一致，单点失败闭环。成功与失败路径分别判定 |
| L3 HTTP合同单点 | 该模块真实数据的method/path、DTO、状态码、幂等、分页/错误、task/Run/原件链接；最终独立TCP | HTTP与核心合同一致，写后原GET可读，GET无业务副作用；ASGI可前置，不能替代TCP |
| L4 局部集成 | 每次相邻一段：Kafka→Fusion→Socai2AlertSink材料/任务保存；任务→调度→A；A→I；建案→Case；H/材料变化→后轮 | 两端单点及相关合同通过，身份/范围/状态/来源跨边界一致；一段通过后再接下一段 |
| L5 端到端/验收 | 少量代表场景串起告警+上下文→调查→人工核实→结果/采用→4177 | 参与局部链通过，业务效果可见；同源读回、未覆盖/后置及质量问题清楚 |

准入按本段依赖判断，无需等全部未来模块完成；正常链必需的单点失败则阻断该链，独立模块可继续。先正常业务和数据关系，再空态、非法输入、重复/版本冲突及实际失败/unknown等必要边界；不建设压力、复杂故障/恢复矩阵或新通用框架。

真实模型用于对应L2首次实际验证及L4/L5主流程，记录实际发送、回执、原答和来源；读取/展示复用同批结果不再生成。L1替身只检程序规则；正文质量NOT_PASSED独立记录。格式/交付失败可以验证失败路径，但正常成功路径仍未通过；不能以质量后置豁免请求构造、身份、状态和存取错误。

## 6. 真实模型、覆盖与证据

### 6.1 调用计划

### 6.3 分开记录状态

- 用例结果：`not_run / blocked_dependency / passed / failed / not_covered`；blocked写责任模块与缺项，not_covered写未走到的分支。混合用例按子断言记录，不用一个passed盖住未走通步骤。

- 页面及报告分别展示受理、实际执行、交付完整性、业务判定、待核、采用/新鲜度及质量。失败和unknown可读是边界能力，不替代成功链验收。

本次文档验证只说明规划自洽与入口可达。后续直接验收、交接及未参与实现者结束审计完成后，才能按原change规则收口、发布和归档。

```text
dataset/
  scenario.json
  part1/
    alerts/001.json、002.json
    context/001.json、002.json
  part2/
    alerts/001.json
    context/001.json
```

一个dataset是一个验收场景，part1/part2是它分次投放的材料段；不把part解释成模型批处理。一轮实际验收自动生成独立执行记录，同一记录里手动追加后续段，原始材料和旧回执保留。

交互顺序：

1. **启动并选目录。** 选择挂载给Docker的材料目录及明确环境profile。脚本列出发现的part、各段告警/上下文数量和数字发送顺序，校验格式、关联和重复身份。
2. **检查当前环境。** 核本次部署版本/配置、必要PG/湖表、Kafka、Redis、HTTP及模型配置就绪；仅核准备条件，不自动清库或用模型发试探调用。缺失项写清停在哪一步，版本不符等发布。
3. **选择并执行首段。** 有part1默认选part1，显示计划后由用户开始；没有part1则提示选择已发现的段，不静默发送别的目录。每段先上下文ACK及入湖读回，再按001、002等数字顺序和配置间隔发少量告警。
4. **自动等待并核结果。** 用只读连接核相关告警/事件、分诊/诊断和适用Case任务/结果的真实落库，再经HTTP读回身份与状态；有ACK不算完成。不要求固定时间内恰好返回，按配置的运行时限等待，错误/unknown如实记录。
5. **显示本段结果并等待选择。** 告知投放及落库数量、分析是否收尾、Case/事件/告警入口和实际问题；模型质量单列，不额外调用模型做测试判分。只有前段所需任务终态且结果或问题保存/读回后，才可选择后续part追加。
6. **追加并检查变化。** 发所选part，核新告警/上下文保存、实际事件关联、新分诊/诊断，以及场景要求的原Case成员/新轮次/前轮关系；不硬保证所有新材料都会触发新Case轮次，确无有效变化时核未新增Run。重复选择已执行part不重投，未知结果先核原回执。
7. **查看或结束。** 可查看当前结果、追加下一段或结束本轮。脚本自动保存简短汇总和原件索引，包括通过、失败、未覆盖及质量问题；用户不需要手写账本或让Codex临时编写每批核对代码。结束后旧记录不可覆盖。

工作台保持简单：左侧Case（默认）/事件/告警→业务列表→对象ID→轮次与流程→节点输入输出及结果；直接HTTP取数，不以账本为前置。测试只用紫色来源标识，红色仍为错误，同一Case不因补证重复显示。Case和事件均按各自多轮执行展示，Case每轮展示当轮冻结材料及沿用/新增来源；告警保持简单分诊，事件和告警没有Case也可独立查看。

首版验收：同一脚本分别读取两份不同的小数据包，无需改源码；一个场景能先part1、人工确认追加part2并自动核本段与更新，所有使用到的模型请求真实。脚本负责程序可判定的流程、关联、保存和读取，用户通过工作台核业务结果，模型正文质量保留单独记录。默认不一次发55模板，不做压力、超时/恢复专项矩阵。任务1/2及3a–3d的已验边界见§9.6–9.13；4a新小场景准备已通过；本轮按§9.14最新授权先21发布/清理，收到就绪及核零回执后再按检查点执行。
