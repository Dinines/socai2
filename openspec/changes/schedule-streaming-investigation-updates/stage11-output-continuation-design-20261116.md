## 2. 输入与质量的边界

### 2.1 输入过滤

负责人再次澄清：这里只改变发给模型的业务视图，**原始记录中的tenant_uid、数据库租户归属、告警/来源关联及查询隔离全部保留**。不得删除存储字段、清理原件中的租户值或解绑告警；D1直接检查须同时断言“实际模型请求不含该后台标识”和“后台原租户值及关联完全不变”。

真实业务来源/对象ID、未知但有意义字段、0、false和有意义空列表必须保留。A/I的嵌套原材料、Case的原告警投影及C3/Deep/C6逐步选择都要从实际构造器验证，不能仅检查模板或顶层dict。

### 2.2 不再因质量问题整份拒收

引用编号进入正文、重复引用、引用覆盖不足、引用角色不适当、证据不足、不适用/待核领域缺少限制说明等，保存原结论、原判定和原声明范围，记录质量诊断并继续。`unapplied_domain_needs_limitations`归此类；类似业务解释不足不能作为整份结构失败。不得仅据这些问题改判良恶、删除结论、降为unavailable或拒绝全部分析。

引用不存在/不属于冻结来源时不建立有效证据绑定；原引用字符串和对应质量问题保留。合法引用可去重建立链接，不能去改模型正文。声明范围与证据实际关联分别展示，跨成员发现不缩成单成员发现。结论仍以`prior_analysis`角色传给下游，质量标记不能包装成独立观察事实。

仍须拒绝具体不可解释单元的情况：JSON值未闭合、字段类型不能解释、必需身份缺失或与冻结身份冲突、对象/成员别名不存在、相同键冲突导致解释歧义。只隔离受影响单元及其必要依赖，其余独立内容保留。完整结论文字缺少结构化范围时可以保留为待核文本，不能猜范围、作为已覆盖结论或派发依据。

## 3. 唯一的阶段处理路径与程序回执

所有新执行都走“保存实际收到的原件→解析/恢复→单元校验→保存阶段回执→选择下游输入”，完整正常输出也走同一路径；不按旧/新版本或异常种类另启业务执行链。历史原件只读，旧拒收不经新读取器重新解释为accepted。

复用`source_snapshot`保存内部工件，`schema_version=socai2.stage-delivery.v1`、`type=stage_delivery`。它是完整的程序状态记录，不是补写后的模型答案；通过现有Run/步骤工件目录与content_url读取，不改变告警业务DTO字段/枚举。本文件定义以下内部字段，实施时须给对应严格结构校验和直接存取测试：

| 字段 | 含义与约束 |
| --- | --- |
| `run_id`, `step_id`, `stage`, `input_artifact_id` | 当前实际身份、阶段及冻结输入；无Run的准备失败沿task/attempt读，不虚构ID |
| `originals` | 实际请求、模型正文/响应或已收到片段的工件ID、sha256；补答各自列出。无响应时为空并说明，不能填一份空成功答复 |
| `execution` | `call_state`沿completed/failed/unknown/skipped，`local_state`与实际本地结束时间、提供方finish_reason、错误码/阶段、重试是否允许及原因；未知usage保持未知，预算预留不是实际消耗 |
| `parse` | `state=complete_json/closed_units/unusable/no_response`，`truncated`及实际检测原因；解析完整与finish_reason分别记录 |
| `delivery` | `state=complete/partial/none`、原因；只按该阶段实际必需业务单元判断，不按HTTP200/工件存在/质量问题数推导 |
| `retained_units` | 每项包含稳定路径/原数组序号、类型、原内容、冻结主体/声明范围、原答工件和字符区间、单元sha256、结构校验结果、合法来源绑定及独立质量诊断。保留声明与验证后链接的区别 |
| `missing_units`, `invalid_units` | 路径、原因；缺失与显式空数组不同，未读取的成员不能填成已分析。绑定失败与正文不可用也分开 |
| `quality` | 复用现有citation_review及本轮新增解释缺失诊断，保留issues_recorded/checked/not_checked等真实信息；不由结构通过产生正文质量PASSED |
| `use` | 明确可作后续材料的单元、可派发的完整请求、有效结论是否存在、采用/比较资格及阻止原因；不存在适用资格时为false/原因，不能把完整回执当有效Result |

回执引用原工件，后台保留完整IO；下游模型只接收按本阶段目标选择的业务内容、原角色和必要缺口，不透传这张执行台账。工具未查按既有规则仅给“工具名称：未查询”；查询参数/次数/堆栈仍留后台。没有收到服务端正文时只能保存真实错误；页面显示“无响应正文”，不能提供虚假原答。

供实现/测试绑定的内部子字段固定如下，均不是新增公共告警字段：

- `originals[]`：`artifact_id`、`kind=request/response/received_fragment`、`sha256`；不存在原件时不填假ID。
- `execution`：`kind=model/tool/program`、`call_state`、`local_state=ended`、`local_ended_at`、`request_dispatched=true/false/null`、`finish_reason`、`error`、`retry_allowed`、`retry_reason`。error为null或既有结构的code/message/retryable/occurred_at；unknown表示远端未知，不是本地仍运行。
- `parse`：`state`、`truncated`、`reasons[]`；`delivery`：`state`、`reasons[]`。只有收到提供方length或实际记录的内容传输中断/EOF不完整才标截断；普通结构类型错误不能一律声称截断。
- `retained_units[]`：`path`、`kind`、`value`、`original_artifact_id`、`original_content_path`、`value_span=[start,end]`、`value_sha256`、`declared_scope`、`resolved_refs[]`、`structure_state=valid`、`quality_issues[]`。未声明范围为null，冻结请求身份另由input_artifact_id关联，不以请求范围补成声明范围；只作为待核文本时kind须体现文本而非有效结论。value为原解析值，引用去重/失效放resolved_refs，不改value；缺失/无效项为`{path, reason_code}`。
- `use`：`material_paths[]`、`dispatch_paths[]`、`conclusion_available`、`adoption_eligible`、`comparison_eligible`、`reasons[]`。材料/动作路径只能引用retained_units；阶段不适用的资格为false并记录not_applicable，采用资格不等于已采用。最终采用仍走现有新鲜度/预览保护，不能仅信回执布尔值。

结构校验、恢复/回执版本和输入profile版本随现有执行快照保留。回执只在该步骤本地处理完成后封存，不用一条可变工件反复覆盖原答；后续阶段另存自己的使用决定/回执。original_content_path定位原工件中的实际正文字符串，value_span相对于该字符串，value_sha256对该区间的原UTF-8字节计算。单元path使用如`$.findings[0]`的结构路径，不用临时模型ID代替。字符来源必须在保存的原答中重算验证，不能只验证一份模型重排后的JSON。

### 3.1 截断恢复

1. `finish_reason=length`先记录，再尝试严格JSON解析。若完整，逐项正常校验和传递；仍保留截断标记，不仅凭length拒收。
2. 若不完整，沿原JSON结构从头读取已闭合的值/对象/数组项。复用C3读取器的词法与原答定位，扩展为阶段指定路径的单元提取；不搜索任意花括号、不eval、不让模型编补、不补括号把半成品充当完整答案。
3. 字符串必须闭合且转义完整；数字/布尔/null必须有可确认终止边界。数组最后半项、半个转义、半个数字都舍弃为缺失；已闭合F1可保留，半个F2不可保留。完整数组项不要求外层数组已闭合，但必须知道它的父路径及冻结身份。
4. 解析中途发现不合法语法，停止从该位置提取；之前独立完整单元可保留。发现重复键时排除该冲突分支及依赖它的内容，不任取第一次/最后一次。未恢复的身份/范围不能靠相邻正文猜测。
5. 单元经本阶段结构和冻结身份检查后，引用质量单独记录；引用不足不导致该结论被丢弃。只有结构完整、目标/权限/工具绑定完整的操作单元才能派发。
6. 对`stop`但JSON不完整/结构局部错误使用同一保留规则；空答、纯空白、无独立单元、不可解释的错误协议记none。未知字段保留原答，但不能猜成新的执行指令。
7. 原始完整字符串/收到的片段不改；派生回执可形成合法JSON，但不能把它标成模型原答。字符区间明确为Unicode字符下标、左闭右开；sha256对UTF-8原字节计算。

| 环节 | 可以独立保留的内容 | 缺失或异常后怎样继续 |
| --- | --- | --- |

## 4. 超时、连接中断、重试和本地收尾

每次真实调用都受所选profile的请求超时、阶段/Run deadline、调用次数、token/工具预算限制。新增或调整可变值必须进配置示例和快照，本轮不改变现运行值。连接异常在实际调用边界捕获，记录错误发生阶段和是否确定发出；不能把所有网络异常都归为可重试连接失败。

| 情形 | 本步记录 | 后续及重试 |
| --- | --- | --- |
| 确认请求未发出的临时连接故障 | failed，未收到正文，实际尝试记录保留 | A/I在尚无可交付内容且整任务失败时沿原策略60秒后最多1次；Case中间可选步骤留缺口后继续，不因该子步骤将已执行全案投入重试 |
| 请求已发出后超时/连接断开，无法确认远端状态 | 调用unknown，真实本地结束、已有片段和错误保存；原Run在最终收尾保留unknown | 不自动重发，不等待人工解除；本地结束后其它独立步骤/主体继续。不得把timeout统一改为确定远端失败 |
| 收到明确响应但length/空白/格式错误 | 提供方状态和解析/交付状态分别记录 | 本地提取可用内容；不进队列重试。C3仍允许原配置上限1次缺失部分补答，0可关闭；A/I/Deep/C6不新增自动续写 |
| 明确工具/组件失败或未接通 | 原失败/未查询及可用部分分别记录 | 使用其余事实继续；只跳过确实依赖该工具的步骤，不把失败写成查空/安全 |
| 冻结身份、配置或持久化依赖不可用 | 明确失败/不可用范围；尽可能保留已有工件/本地结束记录 | 不进行不能可靠留存/定位的分析。沿现有结束保存机制处理；DB不可用时不得声称工件已入库，恢复可读前页面保留读取失败，不引入无限重试 |

C3补答是同一Run内子调用，不新增任务attempt。补答只请求缺失部分，带原冻结上下文和已保留内容，受现有预算/C6预留；补答失败、再次截断或预算不足后，保留初答及补答的独立有效单元，不覆盖初答、不进行第二次补答，不取消C6。原`c3_completion.max_attempts`配置校验需支持0/1，默认1。

质量问题本身不触发纠正模型调用；沿现有有界结构纠正能力的场景仍须保留初答/纠正答和明确预算，不叠加队列重试。本文新增的保留处理不增加A/I/Deep/C6调用次数。未知消耗不得填0：已派发请求按冻结最大预留继续占本轮预算，实际usage仍unknown；不足以容纳后续调用时只跳过受影响模型步骤，继续程序收尾。

Case流程局部调用异常要返回阶段回执，而不是直接抛出终止所有步骤。活动判断区分“本地仍运行”与“调用unknown但本地已经收尾”；后者不阻止其他独立步骤。最终有unknown调用时沿原Run unknown、task failed/attempt本地已结束的合同，保留收尾工件，不伪造terminal Result；现有数据库unknown/ended_at规则不在本轮改造。可用分析仍可读，但不自动采用。迟到返回不改已封存回执或冒充新Run结果。

无unknown且有合格最终结论时，Run可以completed，遗漏内容令delivery partial；只有片段而没有合格最终结论时保留partial分析、结论unavailable及失败/收尾原因，不伪造正常完整交付。质量诊断本身不改变Run completed或结论业务状态。完整程序收尾的阶段completed仅说明回执已保存，页面同时展示真实模型子步骤状态。

## 5. I结束之后继续Case，避免失败重复触发

这是对旧F4“仅可用I触发”的明确增量：否则I因截断没有完整结论时，已有活跃Case会一直等不到新材料。目标改为**当前输入对应I任务已在本地终结，并已保存完整的阶段回执**，才能作为下一次Case检查的材料信号；完整/部分/不可用回执均可承载这个信号，不把失败回执称为有效诊断。

- A晚到仍先更新I；单告警关联不直接触发Case，下次调查读取。新告警写库不等待A/I。
- I仍在运行、等待合法重试或只有旧stale诊断时，不以此触发Case。最后一次尝试本地终结后，即使无可用结论，Case也可使用自己的原告警和其他有效材料执行；记录I缺口。无需用户补点一次调查。
- 自动检查仍只针对明确关联、仍为活跃接收者且符合关闭/七天窗口规则的Case；当前4/6小时扫描及手动check规则不变，不增加立即循环任务。
- 比较“本轮I冻结业务输入摘要＋可用单元/业务内容摘要＋可用性”，不比较Run ID、错误时间、重试次数、原始error message或工件ID。新输入下不可用与旧输入不可用不同；同输入同内容的重复终结不会重复触发。既有完成输入与自动停止摘要继续使用，不把失败输入记成成功分析覆盖。
- 当前输入上已有可用I时，后续同输入失败尝试仅保存错误，不用空失败替换原可用内容并制造新材料变化。后来首次产生可用内容或实际业务内容变化可触发一次。
- Case固定实际选用的I回执、原输入、实际覆盖和摘要；执行中到达的新内容留待下一轮。I选入范围不替代完整事件分配范围。回执仅向下游传递，不能反向触发A/I或Case自身循环。

程序接线须同步`analysis_incident_executor`、Case更新输入/扫描、事件来源恢复与读侧；仅放开I解析器而不改此门控，不能算“下游继续”完成。

### 13.1 D5a接收与使用合同

Deep只回答冻结的一个问题或请求一个已提供binding。程序仍恢复question_id，模型输出四字段及生成Schema不变。接收器复用closed_json_units，按action、binding_id、reason、answer四个闭合字段留原路径/span/SHA；answer作为完整结构独立验证其state/text/引用/限制，引用和说明质量沿D2记录。半answer只留原件与缺口，不补字段。控制字段缺失不删除完整answer，C6按prior_analysis使用它，不把Deep答案变为全案结论。

只有四字段可解释、动作组合合法、冻结binding存在且query的answer明确为null时，才形成可执行Decision。缺字段、重复键、未知binding或冲突组合均不触发查询；不能用另一字段猜出action或补null。完整answer/handoff按原行为结束；独立answer保留但控制不完整时记录partial并结束本次Deep，其他Deep及C6继续。没有完整answer时保存缺口，不编造模型结论；不自动续写或重试。

每次Deep模型子调用保存一份同Run/model-step的stage_delivery，引用实际请求和先保存的model_original_response，严格核原件hash和值区间；多次合法查询迭代各自保留，deep_summary记录这些回执链接及真实最终answer。模型子步的结构失败、阶段程序收尾、delivery和正文质量分开。C6继续读取deep_summary.answer及其source_map；只传业务答案和必要缺口，不透传span/哈希/请求台账。所有正常Deep答复同样经过此接收和保存路径，不另留旧版执行入口。

本步已收到正文的空白/非法协议保存none或unusable。未发出、超时/断连及usage未知的统一收尾留D5c，本步不据解析成功宣称这些异常通过。C6自身截断、最终采用/比较留D5b。

**接收器。** 在`case_c6_delivery.py`提供`receive(content, prepared, context, comparison, original_id, ...)`，返回保留原单元、恢复身份后的业务单元、缺项/无效项、质量诊断及资格决定。使用已有`closed_json_units.read_units`，不补括号、不续写、不调用模型修复。所有响应先保存原件；C6与C3/Deep一样允许stop/length进入接收器，其他提供方结束原因先保留真实原因。`FinalReview.partial`不再充当截断兜底，避免再次要求整份JSON可解码。

| 单元路径 | 恢复及依赖 |
| --- | --- |
| `$.analysis.summary` | 只留完整字符串 |
| `$.analysis.members[*]` | 每个完整成员独立校验、按冻结别名恢复ID；重复定义或未知成员隔离 |
| `$.analysis.findings/questions/domains/conflicts/followups[*]` | 逐完整项接收，复用C3的类型、身份及质量校验；finding关系仅绑定实际保留项，缺依赖的原说明可留待核，但不造关联。C6输出中的followups仅作建议，不派发 |
| `$.conclusion` | text/state/alert_ids/support_ids/limitations整个对象完整才是核心结论；正文保持，成员别名按冻结表还原，引用问题单列 |
| `$.comparison` | 模型比较对象完整才接收；本来由程序固定的initial/not_comparable继续按冻结比较决定还原，不能由当前判断替代 |
| `$.impact`、`$.closing_note`、`$.recommendations[*]` | 完整对象/字符串/建议项独立保留；建议ID按原数组位置生成，不能因删掉无效前项重排身份；缺失不产生模型影响、收尾正文或建议 |

先定位原单元，再做身份恢复和类型校验；`retained_units.value/span/hash`始终指实际收到的原值。映射后的UUID和合法引用进入独立derived视图，不能改写原unit来让来源校验通过。质量诊断沿D2独立保存。数组显式空与没有读到分别记录。

**派生视图。** 用有版本的内部`retained_output`保存实际存在的analysis、conclusion等字段；缺失字段不在这里补空对象。可采用`RetainedFinal`类型封装可选字段，数组迭代可以返回空集合，但持久化保留“缺失/显式空”的区别。复用C3类型和校验函数时增加嵌套路径参数，不先拼一份假完整Analysis/Delivery再验。完整正常输出也走该接收器，仍复用现行完整语义校验；模型要求的生成Schema及枚举不改。

**Publication装配。** `baseline_delivery_projection.make_publication`从保留视图装配，而非以`value is not None`直接决定accepted。`results.members`仍完整列出冻结成员；没有C6成员分析的行由程序明确填assessment=null、assessment_state=not_analyzed、conclusion_covered=false，read_state来自实际读取。这些是程序交付说明，不能写回retained_output冒充模型成员分析，也不能从C3借结论填满C6。

可选影响缺失时，case_impact.summary为null、实际changes为空，程序说明“本轮未交付影响分析”；比较正文缺失时用现有not_comparable及“本轮比较未交付”的程序原因，不能造unchanged；建议/问题未交付的事实另列missing_units。系统closing_note只解释交付缺口，原模型closing_note如已收到则逐字保留。最终Markdown和领域工件都从同一个派生视图生成，支持局部数组，不再强制`Analysis.model_validate`整份成功。

**建议的保存决定如下。** 完整正常输出的现有程序规则保持；本次新增截断恢复分支按以下条件决定，不把引用/说明质量问题当结构缺失。

| 新恢复结果 | 正式保存与执行状态 | 采用/比较 |
| --- | --- | --- |
| 完整核心结论覆盖冻结全案，且全体成员有有效analyzed/unresolved判断；只缺可选章节 | accepted模型Result，delivery=partial，Run completed | 允许进入既有新鲜度、覆盖和采用保护；有资格不等于已采用，可作后轮比较 |
| 核心结论存在但只覆盖部分成员，或所需成员分析缺失 | 原核心文字/判定仍保存，Result validation=rejected、delivery=partial、Run failed，并注明是全案交付资格不足 | 只作受限背景，不更新有效判断，不作全案比较 |
| 没有完整核心结论，但有完整分析单元 | Result conclusion=null/unavailable，validation=rejected、delivery=partial、Run failed；保留成员/发现及回执 | 不采用，不作比较；后轮可取有效单元 |
| 没有任何可用模型单元 | conclusion=null/unavailable，validation=system_only、delivery=none、Run failed；系统收尾单独保存 | 不冒充模型判断；已有模型/人工判断保留 |
| 任一调用unknown且本地已结束 | 不走terminal Result发布；原C6结论/局部内容仍保存为报告、stage_delivery和原答工件，Run unknown | 不采用、不比较；D5c接通此收尾分支 |

正常本地结束但无合格结论建议用failed，避免现行`finish_attempt(outcome=completed)`把该轮写为last_normal_completed_at并刷新活动窗口。这是要讨论确定的执行语义，不能用“有报告”报正常完成。已结束旧Run不改。系统空案提示沿现有`record_case_closing`只填无有效判断的Case，标system_only；不覆盖模型/人工判断，也不计为模型采用。§14中的“不更新当前判断”具体指不推进有效模型/人工判断，空案系统提示与之分开。

**持久化。** 每个C6模型子步新增严格stage_delivery工件；delivery_report引用它和retained_output。原`delivery`字段仅在整份模型Delivery成立时保存完整对象，局部内容放retained_output，避免原消费者误认完整答复。report_json保留原Result合同，新增内部内容带自己的版本；`citation_roles`同步识别可引用的retained_output实际路径。Result、result_members、报告、C6结束记录和采用决定沿`BaselineStore.publish`同事务提交；原答先单独持久化。unknown分支只提交工件/收尾，不调用publish。

### 15.4 D5b：采用、比较与上一轮局部材料

`case_adoption.preview/adopt`沿现行来源Run completed、模型结论、全员覆盖、输入新鲜度、review_token及较新人工判断保护，不另造采用入口。**当前自动采用SQL只要求至少有一名成员conclusion_covered并有全体交付记录，人工采用要求全员覆盖，两者并不完全相同。** 建议本次对“截断恢复分支”在发布前用§15.3全案门槛控制accepted，避免宽自动规则采用残缺全案；不顺带改正常完整输出的自动采用SQL。若要统一全项目自动/人工覆盖规则，应明确列为另一项业务取舍，不能悄悄随恢复实现改变。

`case_comparison.select_previous`仍先固定同Case最近实际开始且本地结束的whole_case Run，再检查这一轮的Result；补明确Run completed、conclusion_origin=model及新恢复结果资格核对。没有合格Result仍保存previous_run_id、comparison_result_id=null及原原因，不查询更早成功轮。比较只要求与当前范围有可说明的交集，旧全案不必等于新扩展Case；原范围、共有/新增/移出成员分别保留。

另外增加上一轮材料装配函数，供`CaseTaskExecutor.prepare`/C1冻结时调用：

1. 只从已选previous_run_id读已保存C6 stage_delivery及有效C3/Deep摘要；按当前问题/成员选必要内容，先核同租户/Case/原件hash、单元身份和来源。新恢复规则不重解析旧拒收原答。无合法回执的历史原件只供查阅，不借新解析追认为可用。
2. 将单元快照及原出处保存到本Run的source_snapshot，类型`previous_analysis_material`；来源描述包含原Run/工件/路径/hash、原声明范围、当前适用交集、业务内容和缺口。跨成员结论保留原范围，不缩窄成某一成员证据；正文不重写。
3. 在现有Context.update_context下冻结有版本的previous_analysis_material描述和本Run工件引用，并补citation_roles/selected_refs。业务模型构造器显式选其业务字段，绝不整包序列化update_context；产物校验只授权这些已冻结路径，不开放任意跨Run引用。使用本Run副本引用，后台保持原来源链。
4. `case_input_text/case_c3_input_selection`与`case_followup_input`将这类单元作为prior_analysis，按C3/C6任务分别选；不套用当前“无conclusion就丢整个prior_result”的过滤。单元来源、必要待核和原范围可见；执行参数/错误堆栈不入模型。不得影响case_update_inputs.business_view，避免“上一轮刚结束”自己触发下一轮。

因此“可参考上一轮发现”与“可比较上一轮最终结论”走两条明确的数据选择规则，但仍进入同一个C1–C6执行流程。验收用R1有可用结论→R2无核心但保留F1→R3：R2冻结比较R1；R3只把R2作为上一轮，比较为空，仍能实际读到R2的F1，绝不回退R1。

### 15.5 D5c：局部调用状态、本地结束与预算

**调用边界。** 扩展现有`model_errors`/`baseline_failure`内部结果，记录call_state、request_dispatched、local_ended_at、实际响应或已收片段、usage与错误类型。`ModelSteps.call`对已分类模型/网络异常保存回执并返回；C2/查询同理。不能用catch所有Exception后继续，冻结身份/配置、工件来源不可信、DB提交未确认和程序错误仍走硬失败/收尾。外层Run取消或总deadline到达只收尾，不在捕获CancelledError后继续发模型。

- 已确认未发出的临时失败：failed、request_dispatched=false，不造原答；只有整任务符合原重试条件才由调度器最多重试一次。可选Case子步失败留缺口，不重做已执行全案。
- 明确响应拒绝：保留实际错误响应及known failed，不把任意5xx当成确定未执行。
- 发出后超时/断连：call_state=unknown，不重发；保存真实已收正文或no_response。只有网关确实提供完整内容/记录片段才走同一单元接收器。当前普通HTTP模型请求不是流式API，没有返回正文缓冲时明确无正文，不为这次实现另建流式模型协议。
- 关闭/取消本地请求并确认句柄结束后才封存local_ended_at；原unknown不改failed。晚到返回不覆盖封存回执。

**本地活动判断。** 在`baseline_failure.py`提供限定调查用的“步骤本地是否结束”读取函数：running/planned仍占用；unknown只有匹配本Run/本step、来源校验通过的stage_delivery.execution.local_state=ended才不再视为活动；旧unknown没有回执不凭空解除。`ModelSteps.idle`、C2/C3/C4/C5阶段前置检查复用这一判断。模型/工具unknown保留原state和远端结束未知，local_ended_at放回执，不为放行伪填Run.ended_at。

父Run在本地仍执行独立后续时保持running，unknown体现在子步骤/回执；所有可执行下游完成或跳过后，再将整Run收为unknown。`BaselineDelivery.finish`发现任一unknown调用时走工件收尾，`BaselineStore.publish`保持禁止unknown步骤形成正式Result的保护。`BaselineClosing.interrupted`改为可接收已保存分析/最终候选及冻结比较决定，保留它们而不另造一份空白报告；终态为unknown、ended_at=null、Result为空。已有原件/报告不覆盖，收尾工件按原operation key幂等。

**预算核算。** `budget_reason`读取每个实际调用的请求工件：已reported的计实际total_tokens；已派发但用量未知的计该请求冻结的reserved_token_upper_bound；确定未派发才释放未用预留。没有可核对预留时保持预算未知，跳过后续模型，不临时估计。调用次数、输入上限和deadline仍按原profile；保留的最大预算只用于准入，不能写成实际usage或费用。这样Deep超时后C6能在确实有余量时继续，余量不足则留下真实skip。

同时调整`ModelSteps.call`中“usage未reported就先拒绝正文”的顺序：原答、协议/内容解析与计量分别处理，计量缺失不抹掉已收到的完整单元。收到明确完整答复但缺usage只表示用量未知，不自动变成远端执行unknown；超出实际预算或计量矛盾记录独立错误并阻止新增超预算调用，原内容照存。传输本身未知才沿unknown收尾规则。

### 15.7 D6：HTTP、4177和最终交付

HTTP沿现有Run/task/steps/artifacts/content_url/Result/采用预览读取；没有Result时仍能从Run目录读到原答、C6报告和stage_delivery。原答/回执只读，不在GET时重新运行恢复器。只为新内部工件补来源角色/序列化接线，外部API包仍通过用例端口，调查核心不调用外部HTTP路由。

4177具体改`viewer.js`的fetchSelection/allPages、`execution_flow.mjs`的节点/组件读取和现有状态辅助函数：

1. 先核所选主体/Run身份；这个硬依赖失败就显示目标读取错，不能切latest。steps、artifacts、Result、task及上游来源分别加载，用局部结果封套保存`data/availability/error`，不再由任一Promise拒绝丢掉全部详情。
2. 分页逐页保留已读条目。中途失败显示“目录未读全”和重试入口，禁止把已读条数当总数；身份检查仍逐页执行。只有同Run同generation能复用成功缓存，切轮取消旧请求并隔离缓存。
3. stage_delivery渲染“实际保留内容/未收到或不可用项/原答/来源/用途”；分别展示模型调用状态、本地是否结束、交付、质量、采用和比较。unknown但本地ended显示“本地执行已结束，远端结果未知”，不显示一直运行。
4. C6有Result显示实际Result；无Result则读同Run的C6报告和阶段回执，明确“保留了分析，但未形成可采用结果”。程序收尾completed不显示模型调用成功；没有收到原答与原答读取失败分别显示。
5. 同节点多原件读取逐项捕获错误、即时保留成功项；一个content_url失败只影响该卡。单卡重试仅GET，错误响应不缓存为成功空数据。沿已有精确Run链接、紫色来源及宽窄屏布局，不另建异常面板。

D6复用D5已保存样本，实际TCP→浏览器验证partial、无核心、unknown/no_response及一处局部读取失败；新增模型0、重投业务0。实现与直接验收后，对齐PROGRESS/交接/问题清单/原任务，保留旧原答和NOT_PASSED。未参与实现者核同包源码、配置、身份、原文、采用/比较、后续执行及页面证据；最终发布和change归档条件仍按§14.6。

### 15.8 讨论时需要确定的具体取舍
