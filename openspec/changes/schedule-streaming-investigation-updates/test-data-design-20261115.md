## 2. 数据包合同（测试内部，不改变业务DTO）

### 2.1 身份、时间与版本

- 以`dataset_version + batch_id + tenant_id + scenario_id + logical_id`产生稳定测试来源UUID。相同参数和种子离线生成相同字节；新执行批次换batch，不重用历史未知发送身份。Case/task/Run/Result由真实服务产生，记录响应映射，不能预造最终结果ID。
- 区分逻辑ID、source_alert_id、canonical alert_id、event_id、incident_id、case_id、analysis_task_id、attempt及run_id。使用真实fused/HTTP回执确认canonical和归并关系；共享主机不是已归同一事件的证据。
- `base_time`显式带时区，原始事件用相对偏移形成一致时间。告警、raw_event、日志、授权窗口、H适用窗同步物化；不能只改顶层event_time。发生时间、投递时间、入库时间和执行时间分别记录，后者以真实回执为准。
- 生成参数包含tenant、实体集合、来源namespace、source-v1身份、相对时间、数量、目标profile引用及场景版本。环境地址、端口、开关、模型、额度、时限来自配置；凭据不进入数据包。
- 数据标为合成/演练，但不在模型可见原文写预期良恶答案；历史模板自带结论必须注明其局限。原始事实、检测标签、历史判断、人工陈述、工具回执保持各自角色。

### 2.2 文件与记录职责

| 逻辑产物 | 内容及用途 |
| --- | --- |
| `manifest.json` | dataset/batch/scenario、生成器/源模板/hash、输入文件摘要、逻辑身份、配置引用、依赖及使用限制 |
| `alerts.jsonl` | 一行一条已有告警；按当前RawAlert合同生成source-v1及来源事件引用，运行时拆成单消息 |
| `context-events.jsonl` | 规范化日志事件信封，认证/进程/网络源记录；提供实际工具查询上下文 |
| `background.json` | 资产、账号、维护/授权说明、情报/行为背景的场景声明与目标来源适配；缺省/未提供明确标记 |
| `knowledge.json` | 技术解释、取证指导、历史参考的原文、来源/时间/范围、可用索引身份；不预造检索回执 |
| `actions.json` | 顺序/依赖事件、人工任务与修订、建案/管理/check/rerun/定向/综合意图；使用逻辑ID待运行时解析 |
| `expected.json` | 程序事实及允许状态、查询命中/排除条件、分配/关联、无副作用断言；仅核对器读取 |
| `identity-map.json` | 执行后保存真实投递、canonical、事件/Case/task/Run/result映射及来源，不能从expected反向写结果 |

以上为拟定生成器输出，不表示文件/命令已实现。expected与输入分开，投递器、上下文导入器和模型执行路径不得读取期望答案；生成阶段校验模型可见字段中无答案、用例判定和测试报告内容。

### 2.3 告警字段与上下文最低内容

| 类型 | 必备材料与检查 |
| --- | --- |
| 告警 | schema/identity_version、tenant、source/source_alert_id、title/description、severity、可靠event_time、独立created_at、明确source_event_ids、实际存在的主机/账号/IP、原始正文；标准DTO不增减 |
| 认证 | 同一账号/主机、来源地址、登录方式/结果、可靠时间、会话/事件身份；登录success只证明该动作，不证明进程获授权 |
| 进程 | 主机/用户、进程名/PID、父进程PID/可用身份、命令行、时间与启动观察；不能仅同PID就声称跨时间同一进程 |
| 网络 | 源/目的地址及端口、协议、时间、主机、字节/包计数与明确动作结果；0与unknown分开，连接观察不等于外传成功 |
| 资产/账号 | 目标来源认可的身份、主机对应、用途/标签及负责人；维护记录只限定明确对象/动作/时间，缺映射不造库存资产ID |
| 知识/历史 | 原文、用途、来源、时间、适用范围及真实检索身份；历史案例不冒充当前行为证明，模板预期不作为知识条目注入 |
| H | 任务身份/版本、原文、result_scope、source_refs及限制；演练核实明确为演练，引用实际已保存材料 |
| 对照 | 其他主机、账号、时窗、来源/租户的材料及有限结果；按真实工具过滤条件分别定义预期 |

字段按当前入站和查询适配器映射后才能投放。`source_event_ids`只引用实际原始来源事件；周边日志是查询上下文，不能全部挂成告警直接来源。未知但有业务意义字段、0、false、有效空列表不因旧样例未出现而丢失。

## 3. S01：认证—进程—网络完整链

目标：用3条告警、一组实际日志和必要背景验证F01–05、F13及正常Case首轮。事实足以提出核实问题，不预设恶意/安全结论。测试实体示意为`host-app-a`、`svc-report-a`、`192.0.2.10`与目的`198.51.100.20`，物化时按batch一致替换，地址只使用受控测试/文档范围。

| 逻辑ID | 相对T时间 | 记录内容/直接来源 |
| --- | --- | --- |
| E01 | -2分钟 | 该账号认证失败，来源地址明确 |
| E02 / A01 | T | 该账号认证成功；A01来源仅E02，描述保留先失败后成功为待核背景 |
| E03 | +5分钟 | 父进程启动，实际父身份和账号 |
| E04 / A02 | +6分钟 | 子进程启动及命令行；A02来源E04，父记录为周边上下文 |
| E05 / A03 | +10分钟 | 到目标地址的连接观察、非零收发计数；A03来源E05 |
| E06 | +11分钟 | 同主机到另一个目的地址的DNS/网络观察 |
| E07 | +12分钟 | 同目标另一连接，bytes/packets=0，保持0值 |
| E08 | +13分钟 | 同主机后续进程结束/动作结果，按来源可表达能力记录，不推断网络成功 |
| E09 | +10分钟 | 另一主机相似连接，核主机过滤 |
| E10 | T-1小时-1毫秒 | 原窗口前对照，避免湖时间精度舍入回窗口 |
| E11 | T+70分钟 | 原3告警默认查询窗口的结束边界对照 |
| E12 | +1分钟 | 同主机另一账号认证，核是否存在账号过滤 |

基础3告警发生窗T到T+10分钟，默认前后各1小时的Case查询候选窗为T-60至T+70分钟；实际每步按其相关告警范围生成，不能强求所有工具共用全案窗。上下文先入湖并按当前工具验证：

- 主机窗口网络查询应包含符合窗口的E05/E06/E07；E06仅在明确目的地址过滤时才是排除项。
- 认证工具只按主机/时间过滤时E12也是业务上下文；只有实际支持并使用账号过滤时才应排除。
- E10必须在原窗口之外；E11边界是否排除由实际查询的区间合同确认并冻结在expected，不沿列表接口的前闭后开规则猜测工具合同。
- E09只有在本次目标主机集合不含其主机时排除。新增后轮告警可扩大查询窗，原“窗口外”记录可能变成合法输入，expected按每次实际查询重算，不静态贴标签。

配套背景：一条目标资产记录、对应账号用途、一份技术解释、一份取证指导和一条独立历史参考。来源无法提供时不直接写调查结果表替代，应在IF02标缺口。投递前冻结实际Fusion归并规则/窗口、来源字段与版本，按这些规则在expected中写明A01–A03应归属的逻辑事件组、成员关系、事件路由及各事件上下文命中/排除集合。允许多事件须有事前规则依据；运行后保留实际映射并逐项比较，错归并/错路由判失败，不能根据实际结果反改expected或以“保留了多个事件”当关联正确。共享主机不自行等同归并规则，无法给出预期时先列规则供给阻断。

最终整链执行：准备并查回上下文来源→**真实Kafka投递A01–A03**→消费/解析→告警落库→实际归并/事件关联与事件路由→A/I及上下文查询路由→HTTP建Case自动首轮→读取C1至C6/Deep实际走到的阶段→核HTTP task/Run/result/artifact。记录每条消息分区/offset、消费/解析回执、source/canonical/事件映射、上下文source_event_ids/查询来源及适用范围。上下文在确认的真实来源准备，禁止用预造查询回执代替；业务关系及结果不能事后直写补齐。无需模型同意某个良恶标签，成功/失败及未选分支分别报告。独立模块可以用直接夹具，但其证据不冒充Kafka整链。

## 4. S02：授权背景、人工核实与反证范围

目标：正常/授权与误报材料传递、H版本、采用保护；不评测分类准确率。使用S01结构的新身份变体，不改S01原件。三条观察均保留，补一份只覆盖A02进程动作及特定窗口的维护记录，不能声称网络和登录自动获授权。

1. 无H时完成一次真实调查，记录实际Result（可能部分/失败）。
2. HTTP创建“核实进程是否为维护操作”的人工任务，未完成时不提供核实结论；PUT完整修订为completed，正文说明核实材料、范围A02和限制，source_refs指向真实保存依据。
3. 后轮冻结该H实际修订；修订为扩大/收窄窗口或撤回时新建修订，不覆盖旧版本。负责人/截止时间等管理字段单独变更不应触发分析。
4. 采用符合当前规则的真实结果，检查旧判断/历史与后轮新鲜度；若没有可采用结果，采用成功路径记前置不足，复用已有采用直接检查不能伪称本批真实成功。

可增加一条“来源字段与检测描述不一致”的误报核查材料，但expected只要求原文及矛盾保留，不强制模型输出false_positive。H演练陈述不是对现实环境的授权。

## 5. S03：材料稀疏、查询空态和矛盾

基础包1条网络告警，1条直接来源事件和若干不满足实际查询条件的对照。没有登录、进程链或有效授权材料；保留0计数、false业务字段、有效空数组及缺失字段。选择三个明确不同的变体：

| 变体 | 场景材料/来源状态 | 验收 |
| --- | --- | --- |
| S03-empty | 数据源实际可查询；指定工具/范围真实0条，直接来源仍可读取 | 查空及未查分开；0条不当安全结论，其他阶段继续 |
| S03-missing | 对该工具缺可靠时间/主机或未配置来源，按合同不执行 | 明确not_queried/unavailable及缺口；不伪造一次空查询 |
| S03-conflict | 原始观察和范围明确的人工陈述矛盾 | 两份原文/角色/范围进入需要的阶段，原答及程序交付如实保存 |

选择真实能产生查空的范围或工具：不能把工具本来能查到的直接来源删除来强造查空。工具失败/unknown另归S06受控检查，不能用“源不存在”假装真实查询成功。

## 6. S04：持续更新、定向与手动综合

复用同一批S01的真实主体，**经Kafka再次投递**有独立来源的A04及对应已准备上下文，阶段间保留原Run；不修改同ID告警原始材料。投递前按冻结归并规则选择关联键和时间，明确A04应进入哪个已有逻辑事件及其当前接收Case，并冻结更新后的上下文路由预期；不能实际错归后手动改关联来通过。该组覆盖未来能力，未交付依赖标blocked_dependency；源头持续整链与直接模块夹具分开标记。

| 时间线动作 | 输入与预期 |
| --- | --- |
| Q0 首轮与模型前可读 | 记录A/I/Case对象、关系、task的先保存/读取，再记执行前冻结范围、结果与完成基线；三个直接变体在模型请求已进入但未返回时查主体/task/Run及合法空结果，失败不删主体/关系/旧结果。观察点使用明确可控依赖，真实模型主链另记 |
| Q1 新成员与两种关联 | 新A04及日志先准备；同源设置整事件活跃接收Case与单告警固定范围Case。告警范围/有效材料变化先进入I诊断业务更新，再由活跃接收者沿自动材料链检查；不能越过I让已有Case先用旧I调查。单告警Case不跟随所属事件扩员；旧Run不回写，投递/事件/执行时间分别记录 |
| Q2 晚到A/I及不触发对照 | 整事件关联的晚到A/有效反馈须经过I可用业务变化再触发Case；I未完成/失败、只改Run ID/时间或同值内容不算新诊断业务更新。单告警关联首次A晚到不直接自动调查，下次首轮/手动或其他合法调查读取最新可用材料。保留其固定成员，不新增上游等待屏障；可复用直接夹具，不改真实模型原答 |
| Q3 排队/执行中变化 | 开始前到达可纳入；冻结后新到达留下一轮。通过现有检查/步骤观察同步，不靠固定sleep猜测冻结点 |
| Q4 H核实 | 按S02创建/完成/修订/撤回，下一完整C1–C6使用实际有效修订；上一实际完整Run无结论时保持不可比较 |
| Q5 check/rerun与独立排队 | 不同operation_key的initial/check独立task，忙时pending，执行前读最新材料；已覆盖则no_changes、0Run/模型，有新材料则必要新轮。同key同内容重放保持原任务，显式rerun新任务/新轮，旧失败保持；手动/自动各自保留检查范围 |
| Q6 定向 | “核对A01认证记录与本案账号是否对应，并列出缺口”；选择A01及authentication_activity，仅允许当前工具目录能力 |
| Q7 停在定向结果 | 读取独立结果；不提交综合则无额外综合任务/Run，不改变全案采用/完成基线 |

3a转换保留原身份与事件时间，`conversion.json`保存来源/目标hash与仅为source-v1补充的身份封装字段；计划标`requires_new_execution_identity`，所有段均为`not_executed`，还不是可投递的新执行批次。3b发送前才实例化独立投放身份并统一映射跨part关联，实际主体ID从真实回执读取，不能把预测canonical ID当保存结果。转换不改写正文、不删除有意义的未知字段、0、false或有效空列表。3b已冻结为`time_policy=preserve`，不实施时间平移；需要当前活动时间的合成场景在制作新材料时明确给定时间，prepare保持原值。真实历史记录不静默改成现在，也不声称过期数据验证了当前活动窗口。

### 17.4 每段执行及最终验证判据

脚本先校验材料/当前版本及必要依赖，再按“context逐条ACK→必要湖读回→alerts有序发送→相关任务处理→必要PG与HTTP读回”执行。一段结束后可查看、手动追加或结束；模型质量诊断不拦截合法后续。只读数据库核验限本场景相关记录，页面仍通过HTTP读取；不做全库全表对账或自动清理历史。

最终报告由程序按本轮实际材料和回执生成，至少回答：

1. **投了什么、是否保存。** 每个已选part的计划/发送/ACK/实际落库数量及身份是否对应，告警与独立context原文/规范化事实及关联是否保持；未选part明确未发送，不能只有Kafka ACK就判通过。
2. **业务是否处理到位。** 所需告警分诊、事件诊断、适用Case任务是否到达真实终态，应该保存的阶段、原答、结果或问题回执是否可读；程序失败/unknown不能因有工件就记通过。合同允许的partial/none按保留内容和合法下游效果判断，不强求模型确定判定。
3. **关系与更新是否正确。** 按场景声明检查事件成员、Case范围及本轮冻结来源，新增/沿用/更新不能只比较数量；追加后比较实际前轮与新轮，旧轮原件不变。若未触发变化如实记录，不能强造新Run；场景明确要求更新但没有发生就报未达到预期。
4. **读到的是否同一次执行。** PG保存身份/必要值与HTTP任务、Run、结果、分页目录及原件一致；Case与事件各轮不串轮，告警分诊对应其材料，普通无测试账本主体照样可查。
5. **模型与质量是否分开。** 保存实际提示/输入、原答和结束状态，统计只取真实usage，未知费用不记零；正文/引用问题单列，不新增模型替程序汇总或判通过，也不质量重采样。
6. **结论与缺项是否清楚。** 按步骤列通过、失败、未执行/未覆盖及原因，给Case/事件/告警入口和证据索引；准备文件未导入、未查询分支及未接来源不能算已验。数据更换后同一源码仍可自动完成这些核对，不再临时手写本批报告逻辑。

当前02的4告警/13上下文及实际HTTP/浏览器证据可作输入和已有结果参考，但不替代新脚本复用验收。3a已用两包验同一convert/inspect入口：包A拆出part1的3告警/12context与part2的1告警/1context，保留整案和固定告警两案计划；包B选两个中性模板，2告警/0独立context，5条内嵌telemetry留在告警内。[独立回执](../../../docs/operations/evidence/test-acceptance-materials-20261117-01/independent-review-01.json)核16份冻结文件、19条原值/hash、来源/两案计划及保存读回一致，6次离线CLI入口调用通过；缺part1时明确待选择，显式选段仍未执行。16项现有检查复跑通过，输入/历史证据保持，0业务/模型调用。后续3b–3d再验证真实执行、一次手动追加和Docker入口；不默认发送55模板整包，不安排压力、超时/故障/恢复专项矩阵。

### 17.5 当前3b材料与投递范围
