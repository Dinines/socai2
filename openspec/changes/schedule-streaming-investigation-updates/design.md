## 2. 三层身份与状态

| 身份 | 含义 | 创建时点 |
| --- | --- | --- |
| case_id / incident_id / alert_id | 被分析的对象 | 业务保存时 |
| task_id | 已受理的分析任务，前后端查询身份 | 自动首轮、周期发现变化或手动提交时 |
| run_id | 一次实际分析，保存当时输入、步骤和结果 | 获得名额、读取最新材料并决定执行后 |

新增 analysis_tasks、analysis_attempts、analysis_subject_state，与现有人工核实 tasks 分开。自动重试沿用 task_id，创建新 attempt 和 Run；C3补答/工具子步骤不增加队列尝试次数。排队或无变化跳过没有Run；准备失败的实际尝试允许run_id为空。完整Case Run kind为baseline，包括普通后续轮次和手动综合；人工定向Run/Result使用targeted。task.intent的targeted/synthesis区分业务意图，同Case继续共享case_investigation及串行限制。

公共任务状态仅 accepted/running/completed/failed/skipped。accepted包含等待重试；running仅表示本地实际还在执行；completed不代表结论确定、质量通过或已采用；skipped必须区分无变化、已关闭等原因；七天内已受理的首次尝试不因排队跨期跳过。原Run结果可以是unknown，但本地已经结束的任务不再显示running，也不占名额。对外不增加request_id，不暴露Redis队列/位置或归并ID。

Q2已确认前后各1小时、条数可配置、缺时间只记录补查缺口并保留其他分析；本轮将单次日志默认值设计为50。窗口按相关成员的最早/最晚真实发生时间生成，不改Case成员或历史知识回看策略。日志超出上限保留有界结果及不完整限制，不自动翻页；已取得原件/额外探测记录保留后台，未知总量不填假数。50条不是整轮累计数或Token保证。受影响请求构造和工具校验的原50硬上限一起配置化；不另设最大查询跨度或自动拆窗，沿配置的查询超时收尾并保留补查缺口；实际模型输入超限按Q4保留已有分析并失败收尾，不自动重试。

自动期限从最近一次正常完成的实际分析时间起算，尚未正常完成时使用对象创建时间。质量诊断/待复核不直接否定正常完成；失败、unknown、扫描、排队、通知、无变化和点击不续期。检查后按周期推进next_check_at，不被新通知无限推迟。超期停止自动检查，开放对象期限内外都可手动check/rerun；只有实际正常完成才重开完整自动窗口。

Q6已确认：期限内已受理的首次尝试可在排队跨期后执行，仍按执行前最新已有材料检查，记录跨期事实；该轮失败不自动重试，已等故障重试的超期也终止。期限只阻止新受理自动任务，不取消此前受理的一轮；本条不放行过期后的新自动扩案/续建。运行中到期不取消，只有正常完成按真实时间更新活动窗口，失败不续期。关闭规则保持。重开本身不调查、不续期；仍在窗口内恢复周期检查，超期需手动触发。Case仍有实际运行任务时沿现有规则阻止结案；事件运行时被关闭则允许当前执行收尾，但不重开、不继续自动重试。

## 4. 变化判断与范围

主要比较告警ID集合和本环节实际使用的上游分析结果：I先按当前策略选择最近归并最多100条，再比较这些成员及其A/反馈；Case读取适用I和当前输入对应的本地终结回执。告警材料引起的自动更新只经明确关联且本Case仍为活跃接收者的I终结材料变化触发，不因A晚到、告警范围变化或I暂时过期直接启动Case。I的partial/none回执可通知Case用自身原件继续，不能冒充有效诊断；仍运行/等待重试不触发。按I冻结业务输入、可用内容和可用性比较，同输入已有可用I不被后续失败替换，错误时间/RunID变化不制造新材料，详见新增设计§5。历史关联事件不广播各案，单告警晚到A仅在下次调查读取，有效H保持原规则。摘要和真实来源分别保存，不新增同告警原材料更新或重新分诊。

| 变化 | 下一次检查的处理 |
| --- | --- |
| 新成员、明确增删成员、事件归并 | 识别范围变化；新A只分诊自己，不重跑所有A |
| 同一告警重复投递 | 沿现有重放规则，不新增材料版本提交/判断入口，不因此重新分诊；原件与已有历史保留 |
| 晚到可用A或实际选入的A结论/依据变化 | 先供I检查，I本地终结并保存当前输入回执后再驱动活跃Case；单告警关联不直接触发Case，仅Run ID/时间变化不触发 |
| I诊断内容或当前输入的终结可用性变化 | partial/none也可让唯一活跃Case带缺口继续自身调查；手动/自动同规则，不广播历史Case、不反向触发I/A，同输入同内容不重跑 |
| E48/E49有效告警判定、理由、适用性变化 | 更新相关I，再由其当前输入终结回执驱动活跃Case，不重跑A覆盖人工判定 |
| 已完成有效H的正文/范围/引用变化或撤回 | 更新Case，下一轮完整C1–C6使用适用版本 |
| 人工指定工具/方向的定向分析 | 已确认独立交付建议/结论，后续综合由用户手动提交新任务；输入/结果分类见存储设计第11节和HTTP目标合同，不设永久方向、不因保存结果自动全案重跑，也不把description/评论改义 |
| 标题、负责人、标签、同值保存、普通评论、附件元数据 | 不单独触发模型 |
| 仅采用结果、Case自身结果、知识索引完成 | 不自循环或反向触发；现有新鲜度/采用校验保持 |

I/Case按可取得的材料执行，明确未完成/不可用A/I，不无限等待上游；晚到A在I下次检查补入；单告警关联不因A晚到直触Case，下次调查再读取。当前I终结材料变化仅驱动事件活跃Case的下次合资格检查，手动调查仍可在原范围使用适用I。I支持手动check/rerun及告警驱动，输出/回执只向Case传递。I原结论作为prior_analysis保留范围/依据和质量诊断，不能当独立证据；无结论回执只能说明缺口。H保留human_statement角色、原文及范围，不构成独立真值或处置授权。已支持的成员移出/H撤回必须识别，未提供的证据正文撤回入口不宣称已实现。

事件可以关联多个彼此独立的Case，case_incidents保存全部关系；每个事件只保存一个可空active_case_id，表示唯一后续接收者。明确整事件新建/关联时切到本次实际接收Case，普通检查/执行/单告警关联及幂等重放不切换。告警可加入多个独立Case，不维护活跃目标。事件自动新增先找其active_case_id；手工指定Case新增沿该案容量接收指针，均复用同一分配用例。当前接收Case未满100条时加入它，满后创建后续Case；只将活跃目标仍指向旧接收者的事件转交新Case，旧Case保留全部历史关联和成员，不抢回已转到其他独立Case的事件。新增不能再写回已满旧Case，批量溢出依次分配且不丢弃，同串已分配告警不重复加入。新Case有独立首轮task/Run，原Case任务仍只分析原Case。人工移出保存排除，同串后续跟随不能加回；明确重新添加才取消排除并路由到当前接收Case。事件移出成员不反向删除Case材料。

续接关系仅用已有Case ID：保存最初Case、前一Case，最初Case维护当前接收Case；不新建分组表。原Case成员/历史不重新分配，后续Case不自动继承原案采用判断或全部分析，新Case首轮不冒充与前案Run比较。分配与必要Case/task创建在同一短PG事务核容量，事务后投队列；回执必须返回实际接收Case和新增首轮task。详细字段/路由见存储设计第13节。旧Case满额仍可更新原范围结果，不能据此声称该串整体都已调查。

事件活跃目标为空、关闭或自动期限已过时不自动扩范围，不回退其他历史Case；开放目标可手动检查，普通检查不取得其他Case持有的事件接收权。Q5按负责人最新要求不建设上线前旧对象识别、回填或启用分支；从上线后新对象正常登记，active_case_id在没有明确关联时为空。明确整事件关联才指定目标，普通check/rerun不切换事件接收权。共享告警和共享事件不建立Case前后关系。关联Case读取区分满额续建与共享事件，展示时前者优先、后者其次并去重；当前原型相似Cases仅占位，正式入口与接口侧对齐。

告警、事件、Case在短事务中先保存对象/关联及异步task，模型未返回时已可读取。接收端不等待模型；执行时再保存范围/Run并调用模型，完成后独立保存结果及关联，失败保留对象、旧结果和失败记录。

## 5. 执行前保存范围，完成只更新结果

第7步接线、逐步验证及Case比较读取增量见[持续更新与上一轮比较](stage7-case-updates-design-20261115.md)；依序完成7A输入/比较、7B周期跟随、7C HTTP联验。第7步后按测试模块方案完成本期1–7整体交付，结束审计后按负责人11-15授权统一发布并读回；8–10仍后置。

1. 获得空位且主体空闲，登记本地占用，读取当前状态、最新完整有效材料。
2. check比较最近正常完成分析的实际输入。无变化只记skipped/no_changes；同材料已终止自动尝试则skipped/automatic_attempts_stopped，不伪造覆盖。明确rerun可绕过这两种跳过。
3. 确实执行才先保存attempt、Run、材料清单、原件引用、模块输入及配置，再调用模型。Case内部pending_update→running可在同一短事务完成；A/I沿各自begin一次创建，不预建Run让begin误认已执行。
4. 固定Case比较对象为同Case**上一轮实际执行且本地已结束的完整调查**，按实际开始顺序取最近一次。它没有可用结论就明确不可比较，不回退到更早采用结果。首次无比较对象。
5. 运行期间新增材料不修改起始输入；查询业务结果、实际模块输入输出、原答、校验及诊断按步骤追加保存。
6. 完成只更新本次结果、状态和结束记录，覆盖范围永远是第3步保存的内容，不用结束时最新成员重写；下一次检查会发现运行中新输入。

变化比较的“最近正常完成输入”与结论比较的“上一轮实际调查”分别记录；失败不能当完成覆盖。采用仍沿新鲜度及人工采用保护，不自动覆盖运行期间更晚的人工选择。因I参考变化导致结果不可采用时保留原因，不只为该参考变化再跑一轮。

## 6. 队列与失败

多入口只追加，唯一调度器领取和维护运行集合。每轮先收尾，再最多检查pending开始时P条；忙或未到重试时间放回尾部。还有空位则按Case > A > I > 知识维护检查普通task，每类最多其开始长度，N满即停。N限制同时运行，不限制扫描条数；不批量取出整队、不操作中间链表节点、不新增Lua/分布式锁。

不同operation_key的请求各保留task，分别排队，不做跨task归并；同operation_key重放仍返回原请求。主体忙则进pending，空闲时执行前读取最新材料，普通check无变化记录跳过且不建Run/不调模型。不修改在途输入，不承诺零重复；已有重试等待/次数和同材料停止摘要不能被新check绕过，显式rerun保持独立意图。此最新规则由审计F4实现和直接验证，原归并实现的历史回执不算该规则通过。

已确定未发出或未被服务接受的暂时连接/服务不可用故障可自动重试；响应超时/结果未知、结构/引用/正文质量、预算、参数和配置问题不靠队列重试。具体分类和收尾见队列设计。保留阶段一独立有效分析及原始诊断，不把所有局部错误变成整轮业务失败。

本地返回、抛错或配置超时完成取消/收尾后释放名额，继续队列，不增加人工解锁。原Run可保留unknown和空ended_at，attempt另记实际local_ended_at；不虚构模型服务已失败/已停止。N表示本地活动执行数，不保证远端超时请求即时停止。

## 8. 知识维护

完整Case沿现有C2三目的检索和C3/Deep/C6筛选，先保必要事实、人工输入、前序依据；不增加H-only知识复用。知识仅参考，A/I不新增知识检索。

新采用且材料对应的A在业务事务中登记knowledge_sync任务，提交后A即可结束。知识维护由同一调度器最低优先执行并计入N，不生成分析Run，attempt关联源A，回执仍由原trace/工件读，不进入公共analysis-tasks列表。旧提交后等待索引路径被替换，显式知识维护也经过执行保护，不同时双派发。

执行时重新核源资格，保存卡片/索引真实结果；仅排队不代表可检索。普通告警反馈/Case H不自动建知识卡，未知外部写不自动重试，维护失败不回滚A；不回填全历史。

## 8.1 事件限量与实际容量收尾

事件完整保存成员，I单次按归并时间倒序和告警ID稳定顺序选择最多incident.max_alerts_per_diagnosis条，默认100，独立于Case关联上限。执行前保存选择/实际原件引用、事件当时总数和未选范围；结果只对真实覆盖负责，执行/交付与全事件覆盖分开展示。初轮/定时/手动一致，旧诊断保留，不自动补跑未选批次或把历史判断拼成全量结论。Case关联仍从完整事件成员分配，不依赖I全量诊断。

I和Case每步复用完整请求、输出预留和安全余量测量。超限则保留已完成分析和全部原始输入输出，task如实失败并释放名额，不自动再删成员/分批综合/进入pending重试；同输入及容量配置不重复尝试，变化后可重新预检，显式rerun也不绕过容量。详见存储第14节和Q4；本轮未改配置或调用模型。
