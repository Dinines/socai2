# 流式更新的简单处理规则

## Context

2026-11-12 确认：事件/Case 持续变化，冻结的是每次 Run；允许粗粒度全案重跑和数分钟更新延迟，先解决重复并发、更新遗漏及反馈如何使用。本文件是目标设计。实际运行见 [PROGRESS](../../../PROGRESS.md)，历史队列讨论见 [inv-review](../../../docs/handoff/history/2026-11-11-local-cleanup/root/inv-review.md)。

**实施顺序以负责人后续指令为准：先固定调查，再更新/流式。** 本项等待主 change 的[固定流程收口](../complete-socai2-investigation-chain/fixed-flow-plan.md)，当前不实施下列队列/API/迁移，也不把反馈复核插入固定首轮。知识的母版装配原则可用于固定流程，后台异步维护仍留本项后续实施。

当前 `case_relations.incident_selection` 只获取关联当时成员；`baseline_store` 已有单活跃及 pending 合并，`case_service.start_case` 仍同步等待执行且不自动接续；`stage_results.begin` 只有同 operation 幂等，不能视为同事件单活跃保护。H 已保存版本，Q 尚未实现；C2 三目的知识已有筛选/去重，A 保存后的知识同步当前在提交后等待执行。

## Goals / Non-Goals

用现有 A/I/C 执行器和一份数据库待办完成持续更新。完整 Case 更新仍跑现有 C1–C6，不做复杂阶段复用；仅反馈变化复用证据跑 C6。只新增这条链必需的持久化、配置和读取。

不增加调度平台、多级消息系统、按知识库分 Agent、自动全库回填、自由指定方向执行或通用恢复框架。人工提出新调查方向先列待核问题，不能显示为已补查。A/I 独立知识检索、告警级人工反馈写入口继续后置，Case H 不替代告警人判。

## Decisions

### 1. 什么变化触发什么工作

| 已保存变化 | A 分诊 | I 事件诊断 | 活动 Case |
| --- | --- | --- | --- |
| 新告警/同告警新实质材料 | 只处理该告警当前版本 | 合并为待更新 | 对已包含该告警或跟随该事件的 Case 合并完整调查待办 |
| 新 A 结果被采用 | 不再次分诊 | 合并待更新 | 包含该告警的 Case 合并完整调查待办；领取前与材料变更合并 |
| 人工归并/调整事件成员 | 不重跑材料未变的 A | 受影响事件分别待更新 | 跟随新增；原 Case 已纳入材料保留，移出 Case 必须是明确范围操作 |
| 创建 Case/将整个事件关联进来 | 不重跑 A | 不因建案重跑 I | 纳入当前成员并开启后续新增跟随；首轮/明确更新请求优先 |
| 人工直接加/移 Case 告警 | 不重跑 A | 不改事件成员关系 | 更新本 Case 范围，合并完整调查待办 |
| 完成、实质修订或撤回适用的 Case H 反馈 | 不改 A | 不把 Case H 扩为事件事实 | 仅反馈变化走综合复核；已有完整调查待办时合并进去 |
| 相同投递、读取、任务负责人/标题等非判断材料变化 | 不触发 | 不触发 | 不触发 |
| I 生成新诊断或知识索引完成 | 不触发 | 不自触发 | 不仅因产生新总结/知识版本再次调查 |

新告警原件先保存，再调度模型，不能让入站等待整个调查。I/Case 领取时使用已获得的有效 A 及原始材料；未完成、失败或不可用 A 明确标记，不无限等待流结束。I 诊断是 Case 的参考，不是 Case 领取的硬前置。只认被跟踪的成员/材料/分诊/H 版本，不用总告警数量或普通更新时间判断是否变化。

### 2. Case 如何跟随事件

新建/明确关联**整个事件**的活动 Case 跟随该事件后续新增成员；只选**单条告警**不隐式订阅其事件。人工事件合并按实际新增成员传播；移出事件不自动删除已纳入 Case 的调查材料。人工从 Case 移出的告警登记该 Case 的排除身份，后续跟随不能加回；明确重新加入才取消排除。

已结束 Case 保存关联新数据提示，但不自动加入成员、重开或调查；显式重新打开并更新后再纳入。当前没有正常重开入口的路径保持提示，不在本项扩建结案/重开工作流。切换前的旧 Case 关联默认保持快照方式，不扫描补入历史；用户通过已有明确事件关联动作选入当前成员并启用跟随。多个活动 Case 明确关联同一事件时各自跟随，串行约束按 Case 身份判断，不按相似告警集合跨案去重。

### 3. 一份待办、一个执行槽

同租户的 `alert + id`、`incident + id`、`case + id` 分别是业务排队身份，不能用本次 Run ID/告警数量作为去重键。知识维护是独立工作类型，按告警身份合并。每个身份最多一份运行快照和一份可更新待办；Case 完整调查与反馈复核共用同一槽。

1. 保存业务变化时，同事务登记/更新对应持久化待办。跨事件→Case 的传播在执行器领取前完成，传播失败保留源待办，不视作已处理。
2. 尚未领取：合并最新目标版本和原因，保留首次待办时间；不为每条变化排一个 Run。
3. 领取：短事务内锁定对象、核单活跃、冻结最新输入并记录实际 Run，再提交并执行。外部模型/工具不占数据库事务锁。
4. 正在运行：原输入不改、不取消重启；后续变化只更新下一份待办。完整调查原因优先于仅反馈复核原因。
5. 已明确结束：保留其结果，下一份待办在到期且槽空闲时领取。失败不因待办扫描反复重试；unknown 继续占槽，复用现有核实/显式处理规则，不盲目重派。

持久化采用一张内部 `investigation_work_items`，记录主体、待处理原因/版本、首次待办/到期时间及活跃 Run 关联；沿用现有 runs/run_steps/artifacts 表保存执行事实，不另建执行账本。Case 已有 pending Run 由同一领取入口使用，不能与队列各创建一轮。跟随开关置于现有事件关联；Case 的人工排除名单作内部持久化标记，不新增权限或规则引擎。增量迁移使用实施时下一可用编号，保留 V1 和既有 127 迁移。

### 4. 简单频率和优先级

| 工作 | 初始配置建议 | 排队规则 |
| --- | --- | --- |
| 新 A | 立即可领取 | 自动任务按到期时间排序 |
| I 更新 | 首次待更新起 60 秒 | 后续变化不推迟已确定到期时间 |
| Case 自动完整更新 | 首次待更新起 300 秒 | 同上；上轮运行超过窗口则待槽释放后领取 |
| 人工建案/明确更新/有效反馈复核 | 立即可领取、优先 | 不抢占同一对象正在执行的 Run |
| 历史知识维护 | 低优先级 | 允许晚于业务判断完成 |

建议初始全局执行并发为 1，随后按实际资源配置；同对象始终单活跃。这是可接受的首版吞吐取舍，不增加复杂权重/配额算法。自动任务同级按 `ready_at`、首次登记顺序执行，新 A 不能因持续到达让已经到期的 I/Case 永久排在后面；不要求某类队列清空。人工请求持续占满资源时允许自动任务变慢，先不做抢占。

周期、并发、worker 轮询和启用开关全部来自显式 profile，缺配置不静默选环境。主调度关闭时保留原手动方式；开启时手动/自动入口共用领取保护，禁止旧消费者旁路执行同一任务。

### 5. 人工反馈只重算什么

完成/实质修订适用反馈进入立即可领取的 Case 待办；草稿、空正文、范围不适用和纯管理编辑不触发。撤回原已使用反馈也要复核。复用 `tasks/task_revisions` 原文、作者、时间和范围，人工陈述不自动成为事实真值或处置授权。

只有反馈变化：新建一轮带 `final_review` 内部模式的 Case Run，冻结所选原调查的必要材料、查询/Deep 原件、原结论及新 H；重新装配可追溯来源映射后只执行 C6/保存读取，不运行 C2/C3/C4/Deep，不把旧步骤记成本轮执行。旧结论缺失/拒收时如实提供状态，只能复用独立有效材料，不能追认旧结论。没有可复核调查材料时保留反馈并提示需首轮调查，不暗中升级为 Deep。

复核输出说明维持/改变的判断、所依赖反馈范围及仍待核问题；人工说“正常维护”只影响其明确对象/时段。提出“再查终端”但没有终端证据，只能形成待补查事项。若同时已有新增/移出成员、材料或有效 A 变化，则待办提升为 `full`，下一轮 C1–C6 一并使用反馈；不能再额外并行跑反馈 C6。领取时核实变化类型，防止已排复核任务遗漏后来材料。

### 6. 知识如何进入固定母版

共享现有 PG/Qdrant 存储，按技术解释、取证指导、历史参考三种目的选择，不拆物理库。固定模板负责本步骤目标、来源角色和输出要求；程序填入当前范围/观察、必要前序结果、人工反馈、相关知识及实际查询状态。知识块带原文、来源/版本、用途和适用限制；相似度、索引成功和历史判断都不能当本案事实。

| 模型位置 | 本项知识输入 | 发挥的作用 |
| --- | --- | --- |
| A/I | 保持已有材料/前序输入，本项不新增知识检索 | 不把下层历史参考重新包装为当前观察 |
| 完整 Case 的 C3 | 本轮 C2 三目的筛选结果 | 技术含义、可验证的问题、取证方法与历史差异 |
| Deep | 已冻结且与当前问题相关的条目/必要引用 | 指导当前问题取证，不扩大工具或问题范围 |
| 完整 Case 的 C6 | 必要前序引用及与未决问题相关条目 | 综合解释和比较，结论仍取决于本案证据 |
| 反馈复核 C6 | 原调查实际使用且仍关联本次复核的冻结条目 | 支持理解原判断；注明原版本，不再检索整库 |

先保必要证据、反馈和前序引用，再在现有配置预算内按身份/版本去重选择完整可选条目。保留原检索工件和未送入原因，不改写/裁断正文、不丢相反证据或必要引用以凑容量；必要材料装不下时明确输入受限。无需新增模型总结检索结果。旧知识只作为可追溯历史参考复用，不冒充最新文档；新完整调查按当时有效索引重新检索。

历史告警何时入库：仅新采用且材料对应的 A 判断触发本告警知识维护，原始告警到来不入库、Case H 不直接入库。采用事务内持久化维护意图，提交后 worker 保存卡片/嵌入/索引；A 完成不等待索引。同告警待办合并到最新有效源，较早意图记录被替代，不能报告其已索引。保留原卡、原回执、当前版本资格和显式维护接口；知识任务失败/unknown 不改业务判断，不自动重试未知外部写。

### 7. 保存、读取和兼容

结果始终说明冻结成员和版本。当前范围 5 条而 R1 只覆盖 2 条时，R1 可以作为历史结果读回，但不能显示成已调查全部 5 条；显示已有结论、运行中轮次和合并待更新范围。现有采用/新鲜度保护保持，不因源持续变化将旧结果标为 current。

现有新鲜度还跟踪 I 诊断指针。只因 I 参考更新导致本轮未采用时，保留结果及具体原因，不绕过校验，也不仅为该指针变化自动再跑全案；后续实质输入变化或明确更新时再纳入。接受首版“可读完成结果但尚非当前采用判断”的情况。

原 GET、告警 DTO、A/I 结果字段和身份关系保持。调度进度用独立只读 `/{alerts|incidents|cases}/{id}/update-state` 返回运行身份、待更新原因/到期时间和已冻结覆盖，沿原 Run/Result 链接读取正文；读取不触发执行。Case 用户建案/关联沿原服务，新增有效 H 保存后按开关登记待办；现有显式 start 仍保持原响应语义，已被 worker 领取则按现有幂等/冲突返回，不把 HTTP 成功解释为模型完成。需要立即排队更新的动作使用独立 POST `/{incidents|cases}/{id}/updates`，operation key 重放返回同一受理回执，不改旧 start 的返回含义。

## Risks / Trade-offs

接受合并窗口内旧结论继续可见、Case 全案更新的重复计算及单 worker 初期吞吐；不丢原始变化，只合并执行请求。长时间连续数据会使结果始终落后最新范围，必须展示覆盖/待更新，不能承诺瞬时全量最新。未改变的模型质量问题及 NOT_PASSED 保留。

## Implementation and validation

固定流程先在主 change 按原范围完成并留下收口证据；之后才按本项 tasks.md 实施持久化待办/领取、入站与事件跟随、A/I/Case、反馈 C6 和知识维护/读取。同一 change 本地收口后统一交付。最少验证见 [validation.md](validation.md)，本轮不执行模型或运行链。

回退采用 profile 关闭新任务领取和自动触发，保留已保存待办/原件；有运行中/unknown 时继续沿现有槽保护，不切换到另一套执行器重派。仅做必要配置回退，不建设恢复平台。

参考 [AWS 队列积压实践](https://builder.aws.com/content/3EuRcgkTP1MI0c7zM8W6HL3WIqA/avoiding-insurmountable-queue-backlogs)的工作量隔离、[事务 outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)的业务与待办原子登记思想，以及 [Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)的相关内容选择原则；本项目据此简化为现有数据库待办与固定模板，不引入其外部平台。
