# 第6步：Case首轮执行与材料准备

2026-11-15，沿现有tasks第6步及HTTP合同§8.19实施，暂不部署。第5步已交付建案、成员分配及initial任务受理；本步使该任务实际进入既有C1–C6，保存并读回完整链路。第7步再接Case周期/手动check和rerun、跟随及上一轮比较。第8–10步按负责人最新确认后置，保留设计与未完成状态。第11步结合测试对话既有完整方案验证第1–7步，不另建测试任务树。

## 执行与保存

1. 新的A/I/Case联合执行器工厂复用唯一调度器、总N、同主体串行和任务/尝试表；Case仅受理initial执行。本步不增加Case扫描器或外部启动旁路。队列只传task身份，任务受理时无Run。
2. 领取后读取当前Case材料做准备检查；实际执行事务锁Case，按当时最新关联成员及上游版本生成C1。事务内插入内部pending Run、领取为running、保存C1/完整输入清单/运行配置并绑定attempt；事务提交后才调用模型或工具。内部pending不等于Redis pending，不对前端暴露。实际冻结摘要以该事务的C1为准；准备读与执行读之间的新成员也纳入，运行中新增材料不再回写本轮范围。
3. 首轮没有上一轮比较对象，不借用续建前Case的结果。复用现有按职责筛选的C3/Deep/C6输入、原答及引用质量处理，不透传整包原始数据、不更改告警公开字段。执行后按实际Run终态结束attempt并释放N；失败、unknown及原件继续可查，无人工解除步骤。
4. 无新表或迁移；沿128/129的task/attempt、Run成员、工件和结果。冻结的运行配置新增内部Case查询准备信息，不修改历史工件。对应input/策略工件ID记录到attempt。内部旧prepare/start供既有核心调用保留，外部退役由HTTP本步验收后完成。

## 查询材料与容量

联合工厂显式JSON配置增加`case.query_window.before_seconds/after_seconds`（默认各3600）、`case.log_query.max_rows_per_query`（默认50）；值须非负/正整数，且窗口总扩展大于0。Run预算继续来自明确选定的investigation-policy，实际日志上限为配置与本轮`limits.max_rows_per_query`的较小值；政策原文、额外查询配置及实际额度均在执行前保存。配置提高到50以上时，请求和工具校验同步使用该实际上限，无隐藏50门槛。

- 只用来源可靠的告警发生时间（source/derived_source且带时区）；不以入库时间或当前时间补齐。全案窗口取有可靠时间的成员最早/最晚时间扩展；每个主机的日志绑定按其关联告警生成窗口。没有可靠时间的成员记录补查缺口；对应主机无可靠时间则不发日志查询，其他分析及不依赖时间的产品查询继续。
- 不限制最大跨度、不裁剪或拆窗；沿既有配置时限。条数有界且保留多取一条的截断探测及原件；未知总量不填假数，不自动翻页。C2/知识候选数保持原独立限制。
- 每次模型请求沿现有实际token计量及预留策略。容量预检拒绝时保存准备好的请求/Schema/来源映射、计量和拒绝原因，明确未发送；不删成员适配容量、不伪造模型回复。已完成分析/查询及局部结果保留，后续模型不继续消耗，C6做程序收尾，Run和task以capacity_exceeded失败结束，不入重试pending。配置或材料变化后的重新检查留第7步接入。
