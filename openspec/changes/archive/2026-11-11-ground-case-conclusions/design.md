## Context

审计已完成且独立复核 ACCEPT；该结论接受报告，不代表 A01/A02 已修复。程序已有范围、来源角色、有限纠正、预算和真实落库，当前重点是正文有据及补查上限一致。目标是一次可交付的功能修正，主调查仍为 31/41。

## Decisions

### 1. 直接使用已有证据定位，不再次开展全面审计

输入依据为 `investigation-audit-20261111-01/historical-model-review.json`、`followup-limit.json` 以及其引用的原始请求/原答。仅按修改定位读取原件，不重算全仓清单、不重跑原 56 项审查，也不重新创建数据环境。实施前确认实际分支、涉及文件和所选本地 profile；新的实测使用独立 Run，已结束批次与 unknown 不重派。

### 2. Deep/C6 按问题表达主张和不足

首先修改 `services/api/app/socai2/case-input-v1.json` 中相应阶段的任务指令，必要时调整 `case_followup_input.py` 的材料分区/用途说明：

- Deep 回答本问题的支持、反证和未知；未提供资料只构成缺口，不构成相反事实。标题、标签、验收描述均保留归属，只有实际原事件来源才能支持环境/授权判断。
- C6 区分已经观察到的行为、需要验证的解释、已证影响和可能风险。条件性影响可以保留，但不得填成 `supported_changes` 或确定性结论；并非一律删除“若”的正常风险说明。
- 现有来源、描述和人工正文不由程序语义改写。沿用 `answer`、`conclusion`、`impact`、`limitations` 等原输出字段与保存映射；不增加页面必须理解的新内部结构。
- `case_followup_input.py` 已能提供实际查询状态。只修确有遗漏或含混的输入/报告呈现，明确 completed/empty、skipped/not_queried、failed、unknown 及实际数量；模型不重新计算系统状态。原答与实际工具回执分别保留。

正文质量通过对实际输入和交付文本的直接核对判断；不承诺正则或 Schema 可以判定任意自然语言真伪，不新增评判模型、额外纠正轮或通用事实审核服务。

首个本地真实批次实际暴露前序无据说法在 Deep/C6 中被继承、资产查空写成未查及伪冲突，未通过本 change 验收。定向续修仍在上述范围：前序块明确标为待复核原文，Deep 的 reason 也需原始依据；C6 重判问题状态，缺资料不能变 not_applicable，行为与标签并存不构成矛盾。程序将冻结 C2 回执的工具、状态、结果、行数、截断标记直接投影为尾部简表，引用原 source_id，不从模型正文抽取或推算；原完整范围与原文仍保留。新增 `followup_boundary.background_status` 仅为本轮内部模型输入账本，业务 DTO/数据库不变。使用新批次定向复验，不重派首轮、不随机重复采样。

第二批已纠正授权交接和主要查询覆盖表述，但 C6 仍继承前序“标签/行为与未知项矛盾”。独立复核建议补最小来源门禁：当前 Case C3/C6 的每个冲突涉及的 finding 必须有相应成员的直接 observation 支持，冲突引用须逐 finding 覆盖这些支持，至少两个不同原始来源。回执、标签、前序判断及仅查询绑定不能充当冲突事实。保留有观察依据的 inferred 表达，不一律强制 observed；未知及解释差异分别表达为 limitations/questions 或 alternatives。该检查进入当前适配器、生成来源枚举、原有一次反馈和逐单元 partial 校验，失败原答保留，C6 拒收总结不重新采用；共享历史合同默认保持。它只保证来源和依赖合法，不判断任意正文是否互斥，不引入评判模型或通用语义框架。

### 2.1 程序装配固定事实，保留模型业务判断

第三批已不再生成伪冲突，但已采用 C6 仍把有回执说成无回执，将前序错误网络方向从 inferred 升成 observed。两项均被独审确认为本 change 阻断，不能登记后就发布。进一步调整当前模型边界，沿用既有六问和保存字段：

- 新边界随 Case profile 冻结程序职责标记。C6 模型只生成五个业务问题；程序装配 `coverage`，汇总实际成员读取、模型分析/问题状态、遗漏、查询回执、冲突与后续需求/执行。它是覆盖记录，不表示调查已结束或正文已经核实；没有回执明确未记录，不填成功/零行。
- 当前 C3/C6 的 `observed` finding 不再由模型生成 `statement`。程序按原来源身份、成员、路径与原值呈现所选 observation，不跨原记录拼接方向、因果、内外网或主机归属。`inferred/unresolved` 的判断文字继续由模型生成，不能通过更换状态规避直接语义验收。
- 新模型若擅自提供程序所有字段，明确拒收；不将它的错误语句覆写为合法事实。历史冻结边界没有职责标记时按原结构恢复；原模型答复、冻结输入和装配结果分别保留，数据库及告警交接合同不变。
- 文本须满足既有长度合同，超长按明确错误进入现有一次反馈/逐单元 partial，不静默剪断原观察。合法独立单元可保留，被拒收的 C6 总结仍不采用。partial 的覆盖记录根据实际保留单元重新装配，不能统计已经被排除的分析。

新增检查只核程序装配、越权字段拒收、长度边界和历史兼容；之后仅针对该职责改动做一次新的本地代表性链路。既有三批失败保持，不重跑审计、压力或恢复矩阵。能否交付仍取决于实际语义与保存读回，不能仅据程序化字段收口。

第四批覆盖状态正确，但部分保留的影响回答仍从命令文本推成已取得用户信息，Deep 仍把本地 Case 说明当原事件非生产环境。最终结论因来源覆盖不足被拒收，没有采用；保留回答的语义错误仍是阻断。下一修正只针对这两项：配置化排除 `$.case` 中无业务用途的 title/description，原件和独立人工陈述保留，按字段记录遗漏；依赖恢复复用相同投影，不能从旧引用带回被排除内容。实际命令行/action/outcome 字段旁增加配置化含义说明，明确同一原记录、同一 action 与结果的边界；impact 问题旁明确观察动作、有据结果、未知影响三者。不得按本批命令、主机或描述值特判，也不得修改已有原答。此次改动后仅走一条新的本地链路，不扩展模型比较。

独审同时发现 C4 的 `$.state` 路径未获保存层认可，改为既有整份工件的 `execution_receipt`（source_path=null），统一投影与依赖恢复，保留原状态/问题/数量/截断/原因的值和存在性，不改全局角色表。coverage 从实际 material.members 记录读取状态/限制/遗漏，缺记录用 unrecorded；available 只代表选择字段可读取，视图包含成员不能代替读取回执。以上只补直接保存门禁与投影验证，不另跑数据库矩阵。

### 3. C3 两项补查成为程序约束

本次取当前提示预期的 2 作为新 C3 响应上限，写入现有 Case 输入/执行 profile 并随 Run 冻结。生成和接收从同一配置值取数，不在业务代码散落常量，也不提高总预算。

`case_output_adapter.py` / 必要的配置读取处限制新生成的 `followups.maxItems`，在恢复/接收和 `CaseReview.partial` 路径共同保证超限补查不进入派发。超过两项时记录明确校验错误，禁止按列表顺序截断为两项。若使用已有一次纠正，仍要重新通过数量/来源/范围校验和原预算；不为了此项增加纠正机制。

不要全局收紧 `baseline_analysis_contract.ExecutionAnalysis` 的历史读取上限；旧工件仍按原冻结合同读取。C6 的后续建议不是 C4 执行计划，不在此次顺带限数。原冻结的六个问题不增删；“两个补查”不是“两个动态新问题”。

## Validation and Delivery

### 最小验收

1. **直接检查改动边界。** 复用现有用例：输入里缺口/运行说明/查询状态仍有正确来源；C3 两项合法补查通过、三项拒收且零派发（包括 partial 入口）；历史合法工件仍可读取。只补现有用例无法捕获的行为，不设测试数量或覆盖率目标。
2. **一条代表性完整路径。** 在现有本地配置下，以一份有明确判据的材料实际经过本次修改的 Deep/C6，保存并读回 Run/Result/报告；同一批次合并真实数据库、模型和读取验收，不再先做一套重复的替身 PG 完整矩阵。沿当前每 Run 6 模型/4 工具/131,072 token 及实际时限；没有独立真值不报准确率。
3. **验收只看本次目标。** 缺资料没有变反证；验收说明没有变原事件事实；查询状态逐项对应；影响的已证/可能/未知清楚；输出保存和读取相符。仅查该路径所用字段和关联，不复查全表/全部接口。未实际经过的修改环节标为未覆盖，不能用另一个节点成功代替；需要补充时针对缺失前置或具体故障，不随机重复采样。
4. **达到目标即停止验证。** 具体失败先定位、修正，再定向复验，采用新 Run 保留原失败；不因还有任意质量瑕疵就扩展多模型/多轮比较。影响本 change 目标的问题不得只登记就冒称完成；无关问题回到原清单，不阻止其他独立功能规划。

本 change 不做压力/故障/恢复矩阵、可用性专项、全仓回归、全量字段对账、重复跨后端比较或新的测试框架。已有预算、去重、unknown 保护继续使用；被本次改动实际影响时才补一条对应边界检查。

### 一次交付

本地实现和上述验收 → 更新受影响交接及既有 4177 记录 → 一次独立结束审计（只看本次差异和证据，不重复全项目审计） → 统一发布到获准的 21 服务并读回该功能的配置/结果 → 补发布回执与 PROGRESS → 归档/校验 → 子仓库和父项目引用各一次最终推送并核对远端。

归档和推送的实际结果写 `audit.md`/交付回执，不提前勾选未来动作。小修与测试均在本地，不每次更新 21。发布后默认不再重复同一模型案例；只有目标环境特有差异使原验证失效时才做对应验证。

## Risks / Trade-offs

提示改善不保证任意样本语义正确，一条直接案例只覆盖其明示范围。上限由 12 收到 2 只作用于本次新 C3 执行路径，历史读取及 partial 路径是必要兼容检查点。回退使用前一发布及配置，不回写既有 Run 或改变失败语义；不借回退放开告警交接合同。
