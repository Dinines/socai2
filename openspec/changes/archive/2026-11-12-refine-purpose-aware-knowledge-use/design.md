# 知识如何检索、交给模型及更新

## Context

基线为 `dee94ea66f280129074c4e77544a4028abf9fa0b`，父项目远端 `444bfbaf55e2d7b99f14d5d4e933f23bfe2cde9a` 已读回且 `server` 指向该基线。上一项[验收](../2026-11-12-use-historical-alert-knowledge/validation.md)及[独审](../2026-11-12-use-historical-alert-knowledge/release-audit.md)完成；本设计已按 2026-11-12 的继续指令进入实施，当前证据见 tasks 与 validation。

现状有三处直接缺口：`knowledge_config.selectors` 对各目的复用同一组材料词；目的标签和相似度不足以排除不适用资料；`knowledge_source.query` 保留逐查询命中行，模型视图仍可能重复正文。Deep 主要按成员范围筛选，范围为空的历史参考会继续进入不同问题。现有 `history` SQL 是同对象／本案时间窗查询，继续保留，与相似历史案例检索分工不同。

## 1. 不同目的用不同知识范围

采用**逻辑分库**：同一套 PG 文档表、向量集合和嵌入服务，分别配置目的、资料范围、适用条件和返回数量。现有 `doc_kind` 表示资料类型，`purpose` 表示这次拿它做什么，二者不能互相替代。同一技术文档可支持两个目的，但模型内只保留一份原文及两个使用目的。

| 目的 | 优先资料 | 模型拿来回答什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 技术解释 `technical_explanation` | 技术参考、命令／协议／检测规则释义 | 行为有什么功能、成立需要哪些条件、还有什么解释 | 本案已经成功、恶意或获得授权 |
| 取证指导 `investigation_guidance` | 调查 SOP、runbook、日志／字段说明 | 为区分解释应查什么、如何解读实际结果 | 建议已经执行、当前具备所列全部工具 |
| 历史案例 `historical_case_reference` | 有源版本的历史告警卡片 | 哪些观察相似、哪些条件不同、当时如何判断 | 旧 verdict 就是本案 verdict、旧人工陈述是本案授权 |

组织业务基线／授权规则和处置手册以后有实际维护来源再接入；现在不新建空库。资产、威胁情报命中、原始日志仍由原查询工具提供，不复制成知识正文来代替实时事实。

## 2. 先核用途和条件，再交给模型

1. **查询依据**：从本轮冻结材料中提取已有技术主题和少量结构条件，例如事件类别、动作、平台、产品或进程名；路径和标准化规则写入显式 profile。检测标题／规则标签仍标为检索线索，不推导成已发生事实。技术解释问功能与前提，取证指导问证据与方法，历史参考问可比较条件；无合适主题则不查。
2. **检索范围**：沿用同租户、目的标签、资料类型和原历史时间窗／当前成员排除。技术／方法文档使用已有 `tags` 中受控的适用条件标签；历史卡片条件从保存的原字段提取，不能根据旧 verdict 反推。没有标注的旧文档仍可读，但不能默认为适用或自动改标。
3. **适用筛选**：仅比较 profile 声明的同语义、同命名空间条件。至少一个主题条件明确匹配且没有已知冲突，才可作为本次知识输入；相似度只负责候选排序。明确冲突的条目排除，缺必要条件的条目标记未知并不选入。明确标注通用范围的技术／方法资料可在其主题范围内使用，并注明通用性；历史卡片不走通用兜底。仅有标题、没有可比较条件时默认不查历史。
4. **数量控制**：候选上限与最终条数分别配置，回读候选一次完成筛选；不循环补搜凑满、不增加生成模型做重排。先按“目的＋主题＋实际过滤范围”合并相同查询，保存所有原材料路径与查询成员映射，再在既有总额度内执行。不同时间／范围不得合并。
5. **状态保存**：原候选与排除原因留在既有 `source_metadata`；查询失败、真实无命中、候选全被筛掉、未查询分别表达。来源身份或 hash 失效仍按现有失败语义处理，不能伪装成不相关或成功查空。

这些规则能核实显式条件，不能判断所有正文语义。未知不能改成匹配；没有适用知识时继续使用本案证据，不强塞通用攻击说明。阈值和条数不在本轮规划中凭空调优，沿用现有值，实施时只为新增候选／输入上限给出配置。

## 3. 同一知识只提供一次，按阶段选择

模型可见单元保留：目的、标题／来源、原文或历史原字段、版本状态、可核对的适用条件、未知／限制、可引用来源。相似分、hash、索引调用统计只留回执／4177；程序不生成知识摘要，不改写分诊理由或人工正文。

普通块按 `document_id + content_sha256` 合并；历史按同一告警的同一材料／判断快照合并，不合并不同版本、不同角色或不同告警。检索行及查询归属全部保留，模型映射选择一个真实冻结路径作为引用，并记录其他命中的对应关系。卡片、分诊、人工字段分别保留原角色；多次命中不增加独立证据数量。

| 使用阶段 | 实际选择 | 输出要求沿用现有字段 |
| --- | --- | --- |
| C3 主分析 | 与当前主题相符的技术／方法片段及少量历史卡 | 用本案观察形成解释；历史只能提出可比较的条件或待核项，补查上限仍为两项 |
| Deep 单问题 | 当前问题的前序引用依赖，加与该问题主题相符的方法／历史参考 | 根据当前工具结果判断条件是否成立；不能因为知识提到某命令就直接执行或扩大范围 |
| C6 最终交付 | 前序实际引用的完整依据，以及与未决问题／建议直接相关的本轮知识 | 本案结论引用本案证据；知识用于解释、比较和建议，不继承旧 verdict 或执行状态 |

Deep 的相关性用已接受问题的引用／绑定和原查询主题映射筛选，不能只用历史卡 `alert_ids=[]` 就当成全案通用。没有明确问题关联的可选片段不加入；已经成为前序结论依据的片段优先恢复，不被裁掉。恢复仍从本 Run 冻结原件读取，不能查询最新正文来替换。

知识属于可选背景：先保留本案必要观察、人工材料、真实查询状态和所需前序依据，再按本步骤知识容量选择完整条目。容量不足时省略整条可选知识并记原因，不切断适用条件、分诊理由或人工正文。复用现有容量检查及引用恢复，不另建输入框架或输出 Schema；不把“引用了”改称“正确采用”。

## 4. 历史告警何时、如何进入知识库

当前**显式入库**继续作为本 change 的执行方式：指定告警列表调用 `POST /kb/alert-experiences`，保存后对返回 ID 调用 `/kb/index`，索引成功才可检索。原材料仍在业务库，卡片只是带源版本的历史参考。

| 时机 | 当前设计动作 |
| --- | --- |
| 新告警刚接入，尚无判断 | 正常保存业务库，不把原始告警自动灌进 KB |
| 有可读材料、事件时间，且有效分诊或人工反馈已提交 | 可显式选入历史参考。只有模型判断也可以作为 `prior_analysis`，必须标明未独立核实；失败／被拒收的模型原答不冒充有效判断 |
| 判断与所选材料不一致，或只有不对应当前材料的判断 | 不作为当前可用案例发布，返回具体原因；原记录保留。独立有效的人工或分诊部分可用时保留该部分及原对应状态，不掩盖冲突 |
| 人工反馈修订或材料／有效判断版本改变 | 再显式导入该告警，生成新快照并索引；相同源内容不重复生成卡。旧卡和旧 Run 不改写 |
| 人工确认误报、Case 关闭或有处置建议 | 可以增加历史参考，不能仅凭该动作升格为通用误报规则／成功处置经验。规则需维护者通过原文档入口提供原始依据、适用／排除条件和范围；缺实际执行／验证回执就不写处置有效 |

检索默认只选择与当前源指针及内容对应的最新可用快照；旧版本、来源缺失或不再满足选入条件的卡只供原件追溯，不自动回退使用。来源更新但新卡尚未索引时显示无当前可用历史；不会在调查请求里顺便导入或建索引。

首次历史整理采用明确告警列表的小批导入，复用现有批次上限，不扫描／重嵌入全库。日后自动化的正确触发点是**有效分诊／人工反馈提交成功后**，仅传入发生变化的告警身份，沿同一导入规则和显式索引处理；不在事务提交前触发，不把 Case 关闭当质量确认。自动调度和开关启用留到自动处理范围，本 change 不加任务队列、定时器、回放框架或自动经验提炼。

## 5. 改动位置与最小验证

改动集中在 `knowledge_config.py`、`knowledge_source.py`／`knowledge_vectors.py`、`knowledge_history.py`、`case_model_boundary.py`／`case_followup_input.py` 和既有 4177 inspector。适用条件从原 tags／卡片字段派生，候选回读后比较；索引只沿用现有目的／类型／历史范围过滤，不额外复制条件到向量 payload。保持已有入库、GET、告警合同和输出 Schema；需要补的处理元数据放现有知识回执／模型输入记录，不给 tool_response 新增顶层字段。

规划阶段只检查规格与文档一致性。实施阶段只做以下直接验收：

- 复用现有用例，小量补核：用途／条件冲突排除、同卡多命中只送一次、Deep 所需前序依据仍可见、修订后只选当前卡。缺知识／失效／失败语义复用旧检查，仅对改变路径补断言。
- 一条新批次的正常路径：选入／更新指定历史卡→索引→C2→C3及自然经过的后续→保存／GET／4177。结合一份适用方法资料核实际使用；已结束批次的来源和卡片不改写；新批次使用明确标注的演练来源和独立向量集合。没有触发 Deep 则用本条保存输入核选择规则，不为覆盖分支再跑模型。
- 功能可见、引用和正文质量分别记录；已知质量问题保留原答，禁止重复采样追求通过。独立结束审计后一次统一交付。无全仓回归、全接口对账、多模型比较、压力／故障恢复矩阵。

回退使用原发布版本／profile，保留知识文档和既有 Run，不删库或改写历史。实现／功能验收／实际发布分别记账，不由规划产物齐全推断完成。

## 6. 本次配置与落地细节

- `knowledge-profile.json` 增加 `candidate_limit=8`；原最终条数、相似阈值与总额度保持。`applicability.facets` 使用带语义命名空间的字段键（如 `ocsf.process.name`），只按配置的字段路径做精确、大小写或路径 basename 规范化。文档标签形式为 `applies:ocsf.process.name=powershell.exe`；同一字段多个值表示可选范围，跨字段同时约束。未提供字段为未知，不猜测操作系统或产品。
- `applicability:generic` 仅供明确维护的技术／方法文档；仍需一个主题条件匹配、不能有已知冲突，可保留缺少的条件作为未知。历史卡始终要求其已声明观察条件可比较。
- 模型可选知识字符上限放在原 `case-input-v1.json`：C3 12,000，Deep/C6 各 8,000；已被引用的前序依赖优先且不可裁掉。C3 正文准备及 Deep／C6 组装阶段若超过既有字节上限，先移除整条可选知识；必要内容仍超限则显式失败。C3 后续附加工具目录和实际 token 测量沿用原检查，超限时显式失败，不声称这两处另有自动知识裁减。这里不承诺容量或压缩率代表质量。
- Deep 可选目的由 `stage_purposes` 配置为取证指导／历史参考（任一原用途符合即可）；纯技术块只有成为前序依赖才恢复。C3／C6 仍允许三目的。Deep 用当前问题的成员范围与原检索主题成员映射选可选知识，coverage 不主动附加知识；C6 只给未决问题保留可选知识，之前已引用的知识独立恢复。程序不对问题正文或知识正文做语义重写／推断。
- 历史资格要求判断正文和 verdict 存在、对应当前材料；带 `source_run_id` 的分诊还须对应告警 Run completed。独立合格反馈允许保留另一份不合格原判断及真实 `assessment_usability`／`material_alignment`，不能将它写成当前可用依据。
