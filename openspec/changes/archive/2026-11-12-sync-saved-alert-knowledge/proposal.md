# 分诊保存后同步历史告警知识

## Why

上一项用途筛选、模型去重和当前历史版本选择已归档，服务端 `f993e630`、父项目 `048668b4` 的 `server` 引用已推送读回；最近核验的 21 发布为 `v1.2-20261112-r3`。本轮按“规划，继续推进”建立本项变更并完成本地接线；当前交付状态以 validation.md 为准。

基线历史卡片必须分别显式调用入库和索引。新分诊保存后不会同步知识；来源修订时旧卡会被检索排除，新卡仍须人工指定。缺口是判断保存与知识维护之间的接线，不是新的知识库或模型环节。

## What Changes

- 在告警分诊事务成功提交、结果被采用为当前判断后，按显式配置对本次告警尝试一次历史卡片同步：资格核验、保存当前快照、索引及记录结果。
- 复用现有卡片身份、资料表、嵌入／向量服务和租户过滤；知识同步独立于已保存分诊的状态与结论，失败不回滚判断或触发重新分诊。
- 用现有工件保存同步意图与结果，通过原 Run trace／工件读取和 4177 原件查看；保持告警交接 DTO 和既有入库／索引 HTTP 合同。
- 默认关闭，实施时由所选 profile 显式启用。只接本次新保存且被采用的 A 分诊，不扫描历史全库、启用消费者或建立调度队列。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `historical-alert-knowledge`: 增加配置控制的分诊提交后同步、原判断与同步状态分离，以及可追踪的同步回执；保留显式维护入口及当前快照规则。

## Impact

归属主调查 3.14 的知识维护子范围；不核销 F02 合理使用、M01/M02 质量或 3.21 自动处理主链。改动 `stage_results.py` 的提交后接线、一个小型知识同步函数、知识 profile 与原工件保存路径；无调查 DDL、告警字段／模型输入输出 Schema 变化。

本仓库目前未发现正式告警级 `human_feedback` 保存入口；Case H 写入的是 `task_revisions`，不能当成 `alert_assessments`。因此本项只自动接分诊保存；人工反馈或外部材料修订继续按指定告警显式入库／索引，不在本项新造人工反馈接口。

本项不调整提示词或模型判断规则。验证复用已有有效判断和测试，仅补触发／结果分离的直接断言及一条真实存储→索引→检索→读取路径；不为该接线重跑 Case 模型或追加质量采样。
