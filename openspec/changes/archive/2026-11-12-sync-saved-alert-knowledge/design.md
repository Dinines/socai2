# 分诊完成后的历史知识维护

## Context

基线 `f993e630`。本设计已完成本地实施、直接流程和独审，已统一交付 `v1.2-20261112-r5`；实际加载与读回边界见 validation.md。

| 已核对代码 | 当前行为及可复用点 |
| --- | --- |
| `stage_results.py:StageResultService.finish` | 在同一事务保存判断、采用指针、publication 回执及 Run completed；退出事务后返回 `result_id/adopted/reason`。可在提交后接入维护，不能在事务中调用外部索引。 |

## 1. 触发点与资格

在 `finish` 已提交且本次 `kind=alert_basic`、`adopted=true` 后调用同步函数。保留原 publication outcome，知识维护不产生新分析 Run，也不回写 verdict／rationale／采用状态。

- 只有配置启用的新保存分诊进入维护。关闭时不增加知识写入、嵌入或工件；同 operation key 重读旧结果不再次触发，不给历史已完成 Run 补派。
- 同步前重新读取当前来源，确认该告警最新分诊仍为本次 `result_id`、材料对应且原资格检查通过。已被新判断替代或来源已变更则记录跳过；不把另一次更新冒称本次同步结果。
- 原始告警刚接入、分诊失败／unknown、结果未采用、I／Case／H 保存均不触发。可用但待复核的分诊仍只是未独立核实的历史判断，不因同步提升可信等级。
- 新分诊产生新快照；旧卡、旧输入和旧结果保留。相同当前源内容沿稳定 ID 复用，当前来源与索引不一致时仍按原检索规则排除。

## 2. 最小执行路径

`分诊事务提交 → 读取开关及本次身份 → 保存同步意图 → 独立会话入库 → 新会话设置租户并索引 → 保存结果回执`。

每个新分诊至多一次尝试、一张卡；复用现有 `import_cards`／`index`，不通过本机 HTTP 绕回服务。知识入库函数会提交事务，索引时须重新建立会话／租户上下文，不假定事务级 RLS 设置跨提交保留。调用不占用原判断事务或行锁，不放到无回执的后台任务。

知识 profile 增加 `history.sync_after_adopted_triage`（缺省关闭）及启用时必填的 `history.sync_timeout_seconds`。总时限、原嵌入／向量时限、模型与地址均读配置；不增加分析模型调用或改变原 Run 分诊预算。默认不做自动重试、回填、定时扫描、消息订阅或新队列。

写向量前沿现有来源核验，完成后再核本次源版本；若期间更新，则回执注明来源已变化，不能报告“当前可用”。已写旧点不删除，后续检索仍重新核当前来源。程序只保存真实状态，不能通过丢弃版本检查维持命中。

## 3. 回执与失败边界

沿 `artifacts.kind=source_snapshot`、新内容版本 `socai2.history-sync.v1` 保存本次 Run 的意图与结束回执。两份工件各自不可变，以固定尝试身份关联，保存原 publication 工件引用；不修改已有 publication／input／模型原答，也不追加模型或工具执行步骤来伪装为分诊内容。

回执只需：触发 Run／判断与源版本、profile hash、实际文档 ID／内容 hash、入库状态、索引状态、时间、原因及已有嵌入／向量调用回执。`stored`、`indexed`、当前来源是否仍匹配分别表达；通过原 trace 和工件 GET 读取，4177 复用已有原件入口，不开发新的状态页面。

- 资格不足或本次判断已非当前：记录 `skipped` 和原因，不调用嵌入。
- 卡片保存后索引失败：保留卡片，记录索引失败；原分诊仍按原状态读取，不变成分诊失败，也不重调模型。
- 写请求结果不明或只有意图没有结束回执：保持 `unknown`／未确认，不当成成功或可自动重试。结果记录失败时保留已有意图，日志只记必要身份／错误，不能补造成功。
- 成功以实际索引完成及来源核对为据；Run completed 不表示知识同步完成。没有持久队列不承诺进程退出后自动补齐；需要维护时沿原显式入库／索引接口先核现状再处理。

## 4. 实施与直接验收

1. 复用已有分诊保存、历史卡片和索引用例，只补：配置关闭；提交并采用后触发；未采用／失败不触发；同请求不重复；索引失败不改变已保存判断及回执区分。用有限替身检查异常语义，不做故障／恢复矩阵。
2. 一个新演练批次，通过真实 `finish` 事务保存一份明确标记的合规判断，再走同步入库、真实现有嵌入／独立向量集合、历史目的只读查询、Run trace／工件和卡片 GET。判断可复用已有有效结构作为测试输入，记录为测试材料，不声称新增真实模型质量证据；无需重新执行 Case 或 A 模型。
3. 只核本次源身份／当前版本、卡片／索引对应、原判断保持及读取状态；保存必要回执，复用上批的去重、适用筛选和旧卡保留证据。若未触发正常接线则补该处，不能以直接调用同步函数替代 `finish` 提交后触发验收。
4. 本地功能、交接和独立结束审计完成后一次统一交付，读回实际 profile、源版本和本功能回执；不默认追加同义模型测试，最后归档及统一 Git／父项目引用。

## 5. 配置、回退与未纳入范围

API／处理入口使用同一选定知识 profile，示例及部署清单同步；沿功能使用现有租户／处理身份，不另建权限方案。启用只影响通过当前服务新完成的 A 分诊，Agents／Kafka 消费者仍关闭。

处理身份保存卡片需要既有知识表的 SELECT／INSERT。新装配置已同步 INSERT；现有安装使用 `deploy/database/knowledge_history_write_access.sql` 按明确数据库／处理角色增量授权，不重跑会撤销已有 API 读权限的全量初始化脚本。不增加 UPDATE／DELETE、角色或表结构。

关闭 `sync_after_adopted_triage` 即停止后续维护尝试；已经保存的判断、卡片、索引和回执均保留，原显式维护和检索继续可用。不清库、不回算旧 Run、不把旧失败或 unknown 核销。

人工反馈自动触发、历史全库回填、A/I 新知识检索、Deep 动态检索及自动处理主链另按实际功能范围推进；本 change 不预建这些框架。F02 知识合理使用及 M01/M02 正文质量继续开放。
