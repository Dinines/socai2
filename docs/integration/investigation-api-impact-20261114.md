# 调查变更对独立 HTTP 接口的影响评估

2026-11-14。范围为当前调查阶段一改动及后续调度规划；本轮只评估、记录，不修改业务代码、部署或提交 Git。

**结论：有影响。现有 71 个业务操作的固定请求/响应 Schema 未因阶段一改动而变化，但结果含义、动态正文和读取兼容性已变化。新调查核心发布时必须同步独立 API 使用的读取代码；仅更新 Swagger 不够。后续调度还会改变调用顺序，目前仍未实施。**

## 负责人后续决定：统一版本，未定稿接口暂缓

评估后负责人明确：先完成设计，不影响已定稿接口的开发；不开展新旧版本兼容工程，按一个统一目标版本推进。调查核心、独立API、相关表结构/配置和Swagger按同一份最终合同开发、验证及发布，对外HTTP与内部调查仍分开。

接口本身或依赖的数据库表结构暂时无法定稿时，先暂缓该接口，不猜字段、不建临时表、不做占位接口或兼容层。两边设计交接须分列“已定稿、可开发”及“未定稿、暂缓”，暂缓项注明功能/接口、未定规则或表结构、缺少的设计决定。已定稿且不受影响的部分继续推进，不等待整个调查阶段结束；不因此删除现有已交付接口或数据。

此决定已转达两个相关聊天，取代此前要求补旧客户端兼容方案的安排。下文旧版本差异保留为事实证据，解决方式是统一版本同步，不新增兼容任务。

后续协作已将启动、分析任务查询、状态和持久化职责讨论成[统一目标合同](../../openspec/changes/schedule-streaming-investigation-updates/http-workflow-contract-20261114.md)：告警自动，Case建案首轮/再次调查与事件诊断异步，以task_id跟踪各次run_id；不再以旧prepare/start或同步返回作为目标约束。最新定向分析/手动综合、补查默认范围、Case100条续建/实际分配、唯一事件接收者、两级关联列表及事件最近归并100条诊断覆盖已同步目标合同第8节；不是已发布能力。Q5不新增旧对象迁入/激活、Q6期限内已受理首试跨期仍执行但不重试、查询不另设最大跨度/裁剪/拆窗已同步；同告警新材料及据此重新分诊提案已撤回；自选完整调查时间窗属本期外扩展，模型读取附件正文未纳入原125项文件功能，均不阻塞现有文件上传下载。下文发布基线与只读证据不变。

负责人进一步要求由产品需求反向提出供给，已形成[125项功能的数据与接口要求](product-api-data-requirements-20261114.md)。实现缺失与业务规则未定分开，跨主体完整目录/统计仍待提供；完整步骤/原件目录已完成[本地实现与验收](run-records-http.md)、待统一发布，不能靠现有接口的局限缩减产品功能。本文为影响证据，不替代该产品范围。

## 3. 已确认的混合版本问题

### 新事件结果被旧读取器误判过期

在同一个只读PostgreSQL事务中，对既有事件Run `c2e40c20-837e-5d1e-8fbc-322fb72ba021` 分别运行正式版本和当前源码的实际 `freshness_sql`：

| 同一已保存结果 | 判断 |
| --- | --- |
| 正式旧读取逻辑 | `stale`（过期） |
| 当前新读取逻辑 | `current`（当前有效） |

原因是新I冻结输入带有上游引用质量版本及对应信息，旧SQL没有按该版本构造比较输入。直接影响E23/E25的有效性展示；这不是事件事实列表字段改名，也没有证据表明E27/E29本身直接执行了这段事件新鲜度比较。

[只读对比证据](../operations/evidence/http-impact-review-20261114-01/freshness-compatibility.json)没有新增模型调用或修改数据。这是**真实数据库上的读取逻辑验证**，不是正式HTTP业务调用通过：本轮正式业务GET用既有凭据返回401，未为评估更改接入配置。

### 大原件的读取不兼容

正式版本 `case_reader.py/stage_reader.py/page_reader.py` 仍含旧大小拒读条件，正式策略上限为1,048,576字节；新步骤6已实际保存并读回7份约1.57 MB原件。因此新核心写入大原件后，旧API可能将正文标为不可用。

这是**正式源码检查 + 既有大原件保存读取证据**，未冒充本轮已通过正式TCP复现。依据见[步骤6回执](../operations/evidence/stage1-original-retention-20261114-01/README.md)。发布前应让实际独立API读取同一份新大原件并核对size/hash。

## 4. 调度规划将改变哪些调用行为

以下全部尚未实施，不作为当前可调用能力：

| 接口/功能 | 已发布行为 | 新规划及待定边界 |
| --- | --- | --- |
| E01创建Case | 返回 `pending_run_id`，后续显式启动 | 目标已定：保存Case及首轮分析任务，返回case_id/task_id；实际执行时才建立Run，不再对外预建pending Run |
| E11准备、E13启动、E36告警分诊、E37事件诊断 | 显式调用，执行接口同步等结果 | 目标已定：Case主体级investigations与E37异步受理；E11/E13/E36退出目标外部API，内部执行保留，不做旧版本兼容 |
| E07–E09成员、E38/E40人工任务、E48/E49人工反馈 | 保存变更，不自动重算 | 有效变化进入后续定时/手动检查；保存接口仍不等待新调查。完整调查是当前规划，早前H-only/C6-only不再作实施依据 |
| E44管理条件、E46关闭；E47重开及事件管理 | 当前代码仍以running/unknown阻止Case关闭；重开不启动 | 已结束的unknown不再代表占用执行名额，关闭条件要区分真正仍运行与结果未知；关闭停止后续自动处理，重开不直接派发或续期 |
| 任务状态与重试读取 | 主要按Run读取 | 目标已定：analysis-tasks按原task_id查询，自动重试另有run_id；任务/尝试/主体时间分别归analysis_tasks、analysis_attempts、analysis_subject_state，不暴露内部队列 |
| 多轮结果与采用 | 保存和采用分开 | 新结论与上一轮实际调查比较，不能把上一轮偷换成当前采用结果；既有显式采用及新鲜度保护继续保留 |

早前复用pending Run及保留旧同步调用的讨论已被本轮[目标合同](../../openspec/changes/schedule-streaming-investigation-updates/http-workflow-contract-20261114.md)取代。规划侧继续统一主设计、规格及任务；后续实施完成再更新可用OpenAPI及示例，不能把设计确认写成已实现。

## 5. 接口侧后续处理顺序

1. 先按两边定稿清单划分范围：接口合同及所依赖表结构明确的继续开发；未定项暂缓该接口，并记录缺少的设计决定，不做临时实现。
2. 在同一个目标版本同步调查核心、独立API读取代码、策略及必要表结构设计；保持对外路由、用例端口与内部调查职责分开。不做旧版本适配或双轨逻辑，不把调度器放进每个API进程。
3. 补齐同版本Swagger的动态正文示例、引用诊断、初答/补答/合并来源及大原件说明。固定Schema相同不等于返回内容和业务含义完全相同。
4. 在同版本候选服务做必要的定向读取：A/I及Case结果、同一新I的current判断、大原件完整正文、采用保护；与保存快照核对。不新增新旧版本测试矩阵，不重新采样模型或重跑全仓。
5. 调度按对应OpenSpec先定自动首轮、最终执行入口、任务/Run读取及关闭规则，再恢复对应接口实施。未定稿部分不加入可用操作清单；定稿前不成为其他接口开发的前置。

本轮未改业务代码、未发布本地/21、未调用模型、未写入业务数据、未提交推送。此次是定向影响评估，不是全量兼容认证或模型质量验收。
