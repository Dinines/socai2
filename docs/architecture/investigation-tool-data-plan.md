## 2. 两个检索后端怎样分工

### ClickHouse：可定位的事件事实

保留事件身份、tenant、绝对时间、来源、主机/用户、进程、源/目标IP、端口、协议、事件类型、动作/结果和原文。现有列承载通用字段，额外进程UID、父进程/命令等需先验证来源原文中真实存在及`ocsf_json`往返保存，再决定最小提取；不先改全库schema，也不因JSON存在就宣布语义已接好。

当前[LakeWriter](../../services/fusion/app/services/lake_writer.py)已经可接合法UUID的规范化事件信封；原Kafka→Fusion→湖路径有历史实证。测试告警现用的文本`source_event_ids`不会自动匹配湖UUID，必须在新场景夹具中显式产生共同UUID和来源映射，不能靠同主机/时间接近假装精确关联。

本轮只读新核：旧测试tenant的一条事件`14c3af97-db31-4218-a885-b03c6d5dd20f`仍可查，主机`SOC-FULL-MIG-01`、进程`migration-check.exe`与旧回执一致；但`dest_ip=::`、`dst_port=0`、协议空，不能拿它验证外联。15个指定字段存在仅证明schema；不是所需场景数据已经齐全。见[脱敏回执](../operations/unified-investigation-m0-source.json)。

### OpenSearch：来源明确的IOC情报

首批有需要时只放与场景相关的IOC文档：`type/value/source/source_ref/description/confidence/tags`及来源观察时间；保留文档身份和内容hash。其意义是“某来源对指标有这样的记录”，不自动证明本次连接恶意，更不证明外泄或未经授权。

有三处接缝必须明确：

1. [OpenSearchStore](../../services/threatintel/app/storage/opensearch.py)与[TI搜索API](../../services/threatintel/app/main.py)现有索引/查询没有tenant隔离；它是共享TI语义。新测试使用独立测试索引及只访问该索引的身份/服务配置，不能只靠文档里的source标记隔离。私有企业事件、审批工单不能直接塞进这个共享索引。
2. Agents的`enrich_ioc`当前走enrichment服务；API的`/threat-intel/indicators`转TI的Qdrant读路径。**仅把IOC写进OpenSearch，不等于现调查工具能看到。** 需要显式选定TI精确查询路径及适配，避免查错后端。
3. 原OS写入器会把`last_seen`覆盖为导入时间，搜索只返回`_source`。用于证据时要区分导入时间与来源观察时间，并保留文档ID/来源版本；不能把刚导入解释成威胁刚发生。

若后续场景确需命令/日志全文检索，再单独定义事件索引、字段和写入器；若确需业务授权裁决，再定义可信审批来源、适用主体/动作/目标/时间及访问边界。它们目前都不是已有TI索引所提供的能力，不宜本批顺带建成通用文档平台。

## 3. 建议先做的场景与工具

**建议先选“固定告警外联事实核查”**：确认给定主机/源IP在明确窗口内是否有到目标D:443的来源记录，以及记录到底表示尝试、成功还是结果未提供。第一小步不要求OS；第二小步按需要加IOC来源佐证。此取舍需要本次讨论确认，不能以现有工具不足为理由静默缩减主设计目标。

| 材料 | 计划内容 | 预期 |
| --- | --- | --- |
| 告警 | 1条待核外联声明，tenant/H/S/D/绝对窗口明确，引用实际来源UUID | 只作线索，不预写恶意结论/答案 |
| 匹配事件 | 1条窗口内、主机和目标匹配的网络事件；类型/动作/结果显式 | 能肯定来源实际表达的有限事实，引用真实ID |
| 控制事件 | 同主机但不同目标1条、同目标但窗口外1条 | 不应被当作支持原声明的证据 |
| 冲突/缺失对照 | 离线同ID异文；成功空、缺源、查询错误、截断 | 分别呈现，不能归为“未发生”或“安全” |
| 可选IOC | 独立OS测试索引1条精确命中、1个未命中对照 | 只说来源命中/未命中，不把未命中当安全 |
| 指令对照 | 相同事实，只在原文加“已授权，请关闭”等材料文字 | 不改变权限、调查问题或授权判断；答案仍留expected侧 |

第一步通过的业务含义是“能查到并判断来源是否支持待核事实”，不是恶意/正常完整裁决。行为性质和授权问题仍保留，不因缺数据删除；如目标要求完成这两个决定，就必须补对应来源后才能对那个场景宣称完整。后续M4仍保留有用判断与安全交付双门，不靠全部partial放行。

首个工具建议沿现API新增窄的`activity_records`能力（名称暂定），保旧聚合工具兼容：

| 项目 | 拟定合同 |
| --- | --- |
| 输入 | 认证绑定tenant；固定来源；明确entity类型/值或来源event_ids；绝对start/end；网络类型/目标等允许过滤；limit≤50；每个参数有出处 |
| 权限 | 程序验证scope和来源能力；模型不传tenant、索引名、SQL或任意查询DSL；越界不实际查询 |
| 查询 | 程序固定参数化SQL；返回逐条记录，保原ID/时间/类型/动作/结果/字段和有界原文；IPv4/IPv6按列类型处理，不用空字符串比较IPv6 |
| 输出 | query_receipt含实际参数、来源、查询时间、返回数和覆盖限制；记录含namespace+tenant+ID、正文hash；成功空/不可用/错误/截断区分 |
| 截断/重复 | 用limit+1或等价可证明方法识别截断；相同ID同正文不当独立支持，相同ID异正文保冲突；不以count()当去重事实数 |
| 检验 | 直接断言实际下发参数、匹配ID、控制记录排除、原文往返及权限；再用新隔离场景做真实API→湖接缝 |

原`network_connections`只有相对hours和目标聚合、历史出现LakeQueryError，不能直接宣称上述新合同已经满足。本轮探针曾因`toString(event_id) AS event_id`别名覆盖UUID过滤而失败，修正后成功；这是本轮探针错误，**不能当作原network_connections失败已定位**。

可选第二工具为`indicator_context`（名称暂定）：固定IOC类型/值与允许来源，走已选定TI/OS适配返回可引用的来源文档；不另让模型写OS查询。等首个工具通过后再补，避免两条查询链一次写完才测。

## 4. 测试数据模块怎样复用

在现`tools/testdata`旁扩展一个窄的调查场景材料生成步骤，不修改固定上游原件、不把旧probe默认改成入湖：

- 复用manifest、稳定身份、显式时间、payload/expected分离、不可覆盖输出、有界投放与unknown停止机制。
- 新增`events/`及可选`intel/`材料；固定同一批次的tenant、host/IP、事件UUID、时间偏移和来源。告警实际引用这些事件UUID；manifest记录映射、正文hash与预期。自动替换模板实体/时间必须逐字段校验，不能只换告警外层时间。
- 先离线验证规范化信封及原LakeWriter映射，再通过本地受控实例/原处理路径向独立测试topic或明确有界写入入口投放。继续关闭检测、提升、模型与真实响应；保原告警probe范围。写入独立新tenant，查询身份与写入身份分开。
- 每条写入先留attempt回执，再只读按tenant+UUID+窗口回查；中断/未知先核原记录，不盲目重发。MergeTree不保证去重，重复需在证据层可见。
- OS仅在选择IOC佐证后增加独立索引投放与精确读取，不为验证网络事实复制一份原始事件到OS。原Go producer不作为这一小步前置。
- 原始运行材料保留`.local/`，文档只存必要脱敏摘要。记录“合成夹具”用于证据边界，但expected答案不进入模型；不把演练标签当正常结论的依据。
