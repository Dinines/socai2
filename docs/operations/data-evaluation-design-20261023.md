## 1. 评估结论与复用

当前工具能生成/投放告警、观察实际调用和持久结果，尚不能证明“成功检索指定事实→模型采用→正确结论”。下一步不增加场景数量优先，而是把已有数据、评分及真实查询证据连起来。

| 现有材料/代码 | 实际能力 | 本轮取舍 |
| --- | --- | --- |
| 55模板、200条 `synthetic_incidents.json`、361条合成telemetry | MITRE/报告/响应的离线规则与模板回归；不是四分类真值集 | 保留，不改成研判准确率数据；不用换主机名扩数量来虚增独立场景 |
| `verdict_corpus_v1.json` | 72条、36对，TP36/benign18/BTP10/FP8；标题/规则/严重度相同而证据不同 | 复用原件，先完成答案隔离的数据导出及原评分器接入 |
| 原 `run_verdict_eval.py` / ReplayRunner | 给定证据→原分诊，shadow拦截写入；opaque ID/答案泄漏检查 | 参考并复用接口；不直接执行原脚本将全部模型角色pin为同一模型的行为 |
| API已有 `aisoc_benchmark.replay.score_replay` | 混淆矩阵、分类P/R/F1、balanced accuracy、MCC、恶意召回、弃答、关闭精度、置信校准 | 直接调用现有评分实现，不复制第二套公式；阈值由测试声明，不能隐用上游0.9替代当前0.85策略 |
| Agent Quality | 期望工具/证据集合与观察集合的覆盖计算 | 可复用计算；现在只有评分器与替身测试，缺真实trace接入，不宣称已验工具选择 |
| 本批真实8工具记录 | 真实调用，6不可用/2错误、0有效补证 | 保留为失败/缺源交接证据，不当成功查询或质量通过 |

原wet eval给模型的raw_alert含 `evidence_keywords`，并以命中至少一个期望技术计MITRE命中；不能把该口径当严格盲测。72条全部是手工合成，不是客户历史录制。真实历史Replay另需结案标签、时间切分和冻结上下文，保持后置。

## 2. 三条独立评估线

1. **给定证据的研判**：只看原分诊对四类标签的区分、弃答与依据，不要求工具。答案、解释、配对关系不得进入输入；使用opaque UUID并打散原B/M顺序。
2. **工具正确性**：数据准备→原工具/API/真实查询→结果逐行核对。固定调用只证明工具，不算模型主动选择。
3. **调查采用**：真实模型的tool_calls→实际执行→同call_id的ToolMessage→下一次实际模型请求→模型候选结论→程序采用→最终报告。仅将结果追加到内存对话，未发生下一次请求，不能标为已被模型看到。

三条分列状态、分母、来源，不合成一个总分；区分离线规则、替身、给定证据模型、真实查询、完整调查。任何失败保留原记录，不重投同输入刷结果。partial与Run执行结束分开。

## 3. 最小数据与结果合同

继续使用本地文件及现有工具目录，不建常驻评测服务或业务库表。

- **输入**：题目ID、标题、严重度、来源、规则及可见证据；不要把答案、预期工具、`decisive_evidence`、配对或B/M后缀暴露给模型。
- **答案**：四分类真值、配对、允许结论/未知、工具与证据预期，仅评分阶段读取。原72条真值不自行修改。
- **来源**：固定语料hash、输入hash、答案hash、执行版本、模型角色配置摘要、运行类型和实际样本数。输入只生成不代表模型执行。
- **观察**：opaque ID、原输出/采用分类、置信度、错误、真实请求/回复/工具及usage引用。缺失、运行中、失败、弃答各自计数；不存在记录时不填“0次模型调用”或“100%弃答”。
- **评分**：按ID关联，拒绝重复、额外ID或观察结果夹带替换答案；调用原Replay评分器。错误/未知/未测按原分母规则分别说明；阈值显式给定。导入观察只是离线重算，不凭一份JSON自证模型真实调用。

输出均在 `.local/`，0600权限、拒覆盖；源码、固定语料及测试可提交。原 `.gitignore` 足够，不忽略整个testdata或所有JSON。

## 4. 主机登录案例：先明确查询对象

拟议问题：“在绝对UTC窗口W内，账号U是否成功登录主机H？属于何种授权/异常活动？”题目与取证条件分别保存，不能只靠标题定答案。

当前 `authentication_events(user_name,hours)` 只按租户/账号/非空源IP/相对时间查 `aisoc.raw_events`，没有主机条件或登录事件类型、成功/失败字段筛选。因此它最多作为账号相关事件检索；不能标成精准的主机成功认证查询。首次真实联测应先用已有 `process_activity(hostname,hours)` 验证成功查询链，登录专项等待字段/合同选定。不得为测试通过偷偷改业务SQL、改模型schema或把非登录事件伪装成登录结果。

登录专项需要讨论：现有 raw_payload 中来源事件ID、event type/action/outcome、账号、源/目标主机、会话ID及时间是否足够；选择上游提供规范字段、按已确定来源解析，或使用既有第三方HTTP工具。无论选择哪条，都需独立业务设计和直接测试；当前工具和新统一调查设计均保持未实施状态。

已核原湖schema实际有 `class_uid/activity_id/action/outcome/event_id/src_hostname/dst_hostname`，原LakeWriter有相关投影；主要差距在工具参数、筛选、返回与字段业务含义，不应先建新库。现查询只有时间下界，没有上界；模型hours说明默认24小时，而认证函数默认168小时。后续必须记录实际采用的参数与执行时间，不将提示说明当已生效合同。

## 5. 工具案例的最小集合

| 场景 | 数据准备和调用 | 必须验证 |
| --- | --- | --- |
| 成功命中 | 测试租户/主机/账号/窗口内写2条目标记录；混入其他实体及窗外记录 | 原工具真正查询；只返回目标记录，记录身份/字段一致；不靠mock结果 |
| 成功零行 | 同源可用，另一个明确无匹配实体/窗口 | available=true且0行；只说本次查询无匹配，不外推整机安全 |
| 同账号其他主机 | H1/H2共享U，区分会话/目标 | 查询合同若不能区分就明确不支持，不能以标题代替条件 |
| 有调用但不可用 | 来源失败或已声明缺字段 | available=false/error，不计成功补证或零行；只复用已有失败，非重做故障注入专项 |
| 已执行但模型未再读取 | 最后一轮工具后预算停止 | 留存成功与实际模型消费分开，保持待采用/partial |

所有夹具只写隔离测试数据，经明确的原入口/表合同；告警内telemetry不会自动进入ClickHouse。先读取实际可查询数据和字段，确定插入方式再写；外层event_time与内层日志时间一致。绝对窗口从固定anchor派生；现有相对hours工具按执行时钟记录有效范围，不能宣称已支持绝对窗口参数。

## 6. 分步推进与当前边界

| 顺序 | 本模块交付 | 验证后继续 |
| --- | --- | --- |
| E0 数据与离线评分 | 72条可见输入/答案隔离；原评分器离线导入；语料/ID/hash/未知与部分覆盖校验 | 原语料全量导出、不调用模型；受控错判/弃答/失败/缺失检查；不报实测模型准确率 |
| E1 给定证据实测 | 原Replay shadow分诊接上当前角色配置与请求记录 | 先少量完整对照对；有界新调用，不改提示/模型合同。72全量另据小样本情况决定，禁止默认全跑 |
| E2 查询成功联测 | 先原主机进程查询，夹具在实际数据源；固定调用 | 身份/窗口/目标行/干扰行核对通过后再交模型；登录合同未明确则该专项停留设计 |
| E3 模型选择与采用 | 一对可由工具区分的案例；初始告警不直接给后续答案 | 调用参数、返回、下一模型输入、实际采用及最终结论逐步核验 |
| E4 可重复回归 | 固定案例/标签/来源版本，保存同数据前后报告 | 仅比较同语料/执行模式/角色配置/可观测程度，不以零调用替身结果排名模型 |

本次先落实E0，并完成E1—E4设计；不运行新模型、不连接生产、不写湖仓、不改调查提示、编排、工具API/SQL及配置，不部署/提交/push。这些后续阶段不是本批已通过，原restore仍5/15。需要调查业务改变时按用户要求先讨论；不因此阻塞独立的E0工具工作。

E0同时增加已有probe轨迹的离线核对：关联真实模型tool_calls、程序执行及结果、同Run后续请求中的ToolMessage；程序未记录call_id时只作保守顺序关联，歧义标未核，不伪造原生关联。返回进入模型输入不等于模型语义采用、SQL正确或成功补证。复用上批记录，0新增模型/查询。

E1执行前还须解决原脚本的实际边界：`--deterministic`只是标记而非断网；总llm_calls>0不保证每案例有真实回复；空FrozenContext仍可能访问知识/身份来源；不能直接导入staging脚本而误跑旧业务代码。保持当前角色配置、逐例请求/回复/失败及fallback归因，明确只测给定材料。原评分的关闭精度是四分类精确命中率，不是实际关闭安全率。

## 8. 用户继续后的E1执行范围

用户在指标说明后要求继续，本批推进E1。先选原VRD-AWS-01和VRD-AWS-03两对共4条，覆盖BTP/TP/FP；选择在模型运行前固定，不因结果换题或重调。先数据/输入检查和替身HTTP直连原Replay合同测试，再第一对真实调用并核回执，再第二对；最多4次HTTP模型请求，每条最多1次、SDK retry0/45秒、单例60秒。保triage原temperature0、512输出上限、JSON合同及角色pin；实际请求累计已知tokens达到20000或出现无回复/usage未知/解析失败则停止后续，不把此轮后停止说成硬token限。网关内部重试另核，不以客户端4次代表provider物理尝试。

使用原ReplayRunner/replay_window、原信封组装/worker/ShadowTriageWriter；只在工具进程注入明确不查询的上下文reader。清空业务DB/Kafka/Redis/资料凭据，不启动lifespan，沿原无DB分支不读租户策略/不写QA或ledger；结果限定为给定证据、默认环境策略，不代表生产上下文/自动关闭。只放行本地SSH隧道内原21模型网关，禁其他连接；关闭测试进程响应缓存，每例记实际请求/回复/程序采用及fallback，保原业务实现。

运行器只读opaque输入及manifest，不加载答案；评分再关联E0原答案。检查原请求中无源ID/配对/答案字段，完整保存正文供独审；小样本不发布总体准确率，按案例/类别/缺失/错误分别说明。请求失败unknown不自动重试。E2/E3及登录合同仍不实施；无部署/提交/push，原5/15不变。

## 9. E1预检发现与待讨论的小改动

已用原Replay/worker/模型SDK组装4份实际请求正文，通过HTTP替身预检，0真实模型。`raw_event`当前经`format_extra_fields_for_llm`按键排序，最多10行；AWS-01两例分别缺3/2个叶字段：良性例缺sourceIPAddress/sourceIpOwner/ticketState，恶意例缺前两项。审批窗口属于原预期分类的重要依据，不能把完整答案直接套在缺材料的模型输入上。AWS-03两例9/8个叶字段全部可见。

工具侧已加发送前叶字段可见性检查，真实模式不完整则存blocked-request并拒发送；预检可收集所有缺失项但固定标offline_http_stub，预检观察不输出成普通observations.json。未知原分类即使业务默认TP，也另记原输出无效和程序采用TP，不能算模型答对；不修改业务parser。连接先超时，用户恢复后SSH只读确认成功，当前待讨论项是输入合同而非网络。

**建议的最小修改（未授权实施）：** 只给分诊的raw_event证据块独立上限，候选为40行且4000字符；其他扩展字段继续原限制，保原模型角色、temperature、512输出、JSON合同。超出时显式标注省略字段并保留不可完整评测状态；不宣称所有嵌套材料都能完整进入。先以原两对验证关键字段/实际请求/上限，再重做同题首次真实调用；原预检不算已调用或旧样本重调。

需要用户决定是否进入这个分诊输入小改动。也可保持业务现状，只实测输入完整的AWS-03一对，把AWS-01标为输入不完整、未评测；不能更换答案或补写模型未见的证据。按此前“涉及后续调查设计先讨论”的要求，本批不擅自改共享序列化函数或提示，不启动完整统一调查设计。
