# 标书需求符合性与模块迁移评估及后续推进建议

评估日期：2026-10-22。需求依据为 [AI SOC2.docx](../requirements/AI%20SOC2.docx) V1.1。本文评估 socai2 / stingAISOC 的当前实现，不继承旧 SOCAI 的完成状态。

**当前实现可以作为标书中告警处理、辅助调查和报告交付的服务端基础，但尚不能判定满足整份标书，核心调查与攻击链要求也只能认定部分满足。** 已有真实证据证明告警持久化、关联、受控自动分诊与关闭、无需再次点击的自动调查、人工调查以及 Markdown 持久读取能够运行；这些成果值得保留。主要差距集中在真实业务数据接入、调查范围约束、结论与证据的逐项对应、时间和因果校验、行为攻击路径、完整知识检索及人员工作流。

**迁移是否正确与需求是否满足应分别判断。** 固定来源、必要接口适配和多条代表链路已有较强证据；部分上游原有缺陷也被完整保留下来。原版正确迁入不意味着原版设计已经满足标书，模型能返回报告也不意味着报告事实正确。最新 19 文件候选已通过隔离组合检查，并已完成本地镜像构建和镜像内离线核验，尚未发布到 21；不能把本地成果当作线上已交付能力。

建议先沿现有 B5→B6 收口迁移版本，再围绕标书的 2—3 个试点场景补齐“真实资料可查、关键结论可核、缺证明确、报告可交接”。暂不推翻 Fusion、合并全部编排或重做基础设施。完整逐条对照见 [164 条功能需求矩阵](../requirements/socai2-requirements-matrix-20261022.md)；本文件给出判断理由、技术差距和推进顺序。

### 1.2 责任范围不等于删减标书

按 [当前服务端职责](alert-processing-scope.md)，本仓库从已有告警进入 Fusion，负责后续处理、调查、API、消息与持久结果；当前报告交付要求是 Markdown。采集、原始事件生产/规范化/检测、前端和独立展示推送由其他模块承担；Playbook、反馈及真实响应专项暂缓。

因此必须同时保留两个结论：本仓库可以在限定服务端范围内完成迁移；整个平台仍须交付标书中的采集、扫描、探针、工作台、审批、实际联动和运营效果。标成其他模块负责，不表示这些要求已满足，也不推定其他团队已完成。此次评估没有扩大实施授权。

## 3 当前几个模块的设计与迁移评价

### 3.1 Fusion 与告警数据模型

**适合继续保留。** 不同来源告警各存一行、保留原正文，再通过 Incident 关联，符合 P176—P180 的归并不丢证据方向。B1 修复了 HTTP/Kafka 身份、首次材料和处理合同，已有真实 PG/API 与消息证据；无需重新迁入或重新验证整条旧链。[B1 回执](integrity-b1.md)、[Fusion 说明](../architecture/fusion.md)

但当前关联是固定规则。Incident 主实体优先取 src_ip，再取 hostname、username、domain，并加首战术；Fusion 候选链按 host→user→src_ip 首个活跃命中。它们既不是语义相似聚类，也不保证同一攻击活动归入同一组。窗口可配置，匹配字段与归并规则的任意配置尚未实现，因此 **P179 部分满足**；不能把声明中的相似阈值当作已执行算法。

还有一处直接影响标书查询功能的静态差距：当前 `GET /alerts` 支持等级、状态、类别、分配及可信度过滤，声明的 `search` 未参与查询，接口也未提供来源、资产和时间区间筛选。它影响 P169/P293；这是固定上游已有接缝，本次未发 HTTP 复现。下一次处理告警查询需求时做定向补齐，不把它扩成当前迁移全仓回归。[查询源码](../../services/api/app/api/v1/endpoints/alerts.py)

Fusion 候选链已有内部续组、交付和留存，但当前没有下游业务消费。暂不强接或删除：标书需要的是有依据的关联结果，未要求一定消费这一个 Chain ID。

### 3.2 UEBA

**作为行为风险辅助信号，设计基本可用；作为完整行为分析引擎，能力不足。** 原服务基线、异常、API 读取及 Kafka→Fusion 的三档异常和关闭对照已有真实基础设施证据；常驻 Fusion 联动开关仍为 false。调查读取接线已经随 full 发布，不能继续列为整体缺失。[UEBA 说明与实证](../architecture/ueba.md)、[full 回执](full-support-migration.md)

原实现采用累计统计，`window_days` 不会持续淘汰旧样本；normalized 消息只按 user→device→ip 选择一个实体。Fusion 缓存保留等级/分数，未保完整异常来源 ID。调查读取还存在“先取最近 50 条同类型基线，再客户端找实体”的限制，不能保证长期数据量下目标实体被命中。这些限制使它不能单独满足 P173 的复合攻击或 P223 的权限/横向活动分析。

标书没有要求必须重写 UEBA、必须新增实体名单或必须采用滚动窗口。建议仍让上游决定投喂对象；在真实试点确需历史基线、精确异常引用或定向实体读取时再补最小合同，不先开展算法和长稳专项。

### 3.3 威胁情报 IOC 与增强

**接口迁入和基本读写方向正确，数据覆盖与 IOC 验证不可混同。** PG 历史 IOC、OpenSearch 项目 IOC 写入/搜索/精确匹配、TI/API 代理和 enrichment 返回均有证据。单 IOC 的 `type`→`ioc_type` 修正在本地真实接缝成立，已纳入候选但未发布。[依赖用法](dependency-usage.md)、[本地工具修正](investigation-functional-20261021.md#6-两处最小本地修正)

无 provider 时 `sources=null`、零分不表示安全；合成 IOC 命中也不表示真实威胁覆盖。原提取器曾把 `.exe` 文件名识别为域名，影响 P183/P221。TI 的 OpenSearch 搜索按共享情报设计，不能把 tenant 头当作私有 IOC 隔离；租户私有 IOC 继续使用既有 PG 路径。

后续先为选定试点提供少量可核来源的 IOC，明确历史命中、当前命中、未命中和查询失败；不以全量 Feed 或新厂商客户端作为当前迁移收尾条件。

### 3.4 知识库与 RAG

**PG 全文检索是可用的 RAG 基础，当前还没有覆盖标书的完整知识服务。** B3/R01 已证明同一知识块进入同一 Run 的四份实际模型输入，来源工件和 candidate04 引用解析已有接线。不能因为没有向量消费就说“完全没有 RAG”。[知识实际消费](integrity-b2b3.md)、[引用修正](integrity-citations-tools.md)、[人工 R01](integrity-investigation-r01.md)

不过默认调查复用的 for-triage 检索限定 runbook/playbook/sop，当前 PG 查询使用 `english` 全文配置和词法排序。向量集合存在、embedding 可用、单独 IOC 精确匹配，都不等于 P377—P379 所列知识类别、向量召回、条件过滤与重排序已在调查中组合生效；对企业中文材料的召回效果也未验收。[KB API](../../services/api/app/api/v1/endpoints/knowledge_base.py)、[调查知识预取](../../services/agents/app/investigator/knowledge_prompt.py)

更关键的是 P379 明确禁止用知识替代当前事件事实，而已有报告出现这种错误。因此“片段已送达”和“引用格式可解析”只证明迁移接线，不能证明知识采用正确。后续先选真实 SOP/案例与明确版本，补所需检索路径和结论引用，再考虑资料规模；不必让每次查询机械地跑遍所有检索方式。

### 3.5 分诊 自动关闭与自动调查触发

**能够满足无需再次点击的自动处理机制，尚不满足稳定可信的自治结果。** C1 真实 BTP/0.95 经原 0.85 阈值实际关闭；C2 未关闭并自动进入 graph/deep，报告及工件可查，证明不是只创建 Run。原分类、时间/授权理由及报告质量失败仍保留，常驻 worker 仍 OFF。[自动主链回执](integrity-autonomy-r01.md)、[分诊设计](../architecture/triage.md)

P202 要求支持高风险自动触发，但并未规定只能调查高风险；原 worker 对符合条件的未关闭告警升级，并非本身不符合该要求。若业务希望仅调查指定风险或事件类型，应另定策略，不能从标书直接推导一个未经确认的新阈值。

当前规则的 `route_to/tags/category` 没有完整进入下游 state，worker 不按 `route_to` 切 Router；有规则配置不等于调查路由已生效。groundedness 主要查指标是否出现在材料中，不能证明时间换算、授权关系或全部理由正确。后续应优先让依据与有效业务决定一致，而不是只调高分数阈值。

### 3.6 三种调查编排

| 路径 | 当前适合的需求 | 迁移证据 | 对标书的不足与建议 |
| --- | --- | --- | --- |
| 默认 Case 四节点 | 整理已有材料、时间线/根因假设、响应计划及可读报告 | 已部署人工 R01；本地链图成功 Case 四次实际模型消费与报告可读 | Forensic 无主动现场查询循环；四 Agent 不是四次独立复核。保留产物价值，不把它当完整证据验证 |
| graph/deep | 按工具结果继续查证，适合 P206/P207 的动态调查 | 自动 C2 及本地 Deep 有真实工具→ToolMessage→下一轮输入 | 原工具后端不全、预算软边界、停止时无完整结论；作为后续主动调查的主要补齐位置 |
| Router 领域分支 | 有结构化领域材料时快速专项判断 | 本地 Identity/Cloud 与模板 Markdown 可运行；新链图材料交接有直接测试 | 分支无取证循环，领域 verdict 不支持 NR；Case 告警嵌套字段不自动 flatten。不能默认替代前两种 |

上游资料与源码支持演进并存，没有明确证据要求把三套串跑或立即新旧替换。**建议保留原入口和编排，在共同的材料、工具返回、证据引用与结果语义处补缺口。** 这比先重构成一套总框架更直接对应标书。[设计评价](../architecture/investigation-design-review.md)

两个必须面对的设计问题：一是当前 typed 查询多以 `now()-hours` 回看，不等于 P204/P210 所要求的人员限定范围和告警发生前后窗口；二是默认人工 stream 在报告生成后才执行 groundedness，修改 Forensic 分数/摘要却不重建已有 Markdown。提示词提醒不足以证明最终报告与校验结果一致。[查询实现](../../services/api/app/services/investigation_tools.py)、[人工编排](../../services/agents/app/investigator/orchestrator.py)

### 3.7 调查链 图与攻击路径

**当前已形成有价值的关系上下文，但尚未满足行为攻击链重建。** 本地新 Case 的 11 节点/15 边、四份模型输入及三类 Run 工件有证据；Kafka 分诊前 prepare 的真实联合也已证明直接邻域 5 节点/4 边。两者来自不同观察，不能合并成一次最新全链验收。[链图回执](attack-chain-path-local-20261021.md)、[Kafka 联合](kafka-graph-joint-20261022.md)

当前图主要表达 Case 包含 Alert、Alert 涉及 Host/User/IOC、映射 Technique。PG Chain 搜索同租户相关告警，Case Path 展开已有关系；它们没有凭空补出进程父子、登录会话、横移或外传的行为边。共享 Technique 可使 blast radius 扩到同租户历史对象，14 个可达候选不是 14 个确认受影响对象；MERGE 也未解决解绑后的旧关系撤销。

因此 P229—P239 的实际关联、时序逻辑、关键行为、传播路径、人工确认，不能只凭有图数据库、有边、有 ATT&CK 标签判通过。后续先从选定行为的原日志/工具结果建立可核证据，再增加必要关系；避免把同主机、同技术标签或路径可达当作攻击因果。[对象与范围说明](../architecture/attack-chain-path.md)

自动调查不自动建 Case，本身不是“必须每告警建 Case”的违规，因为标书没有这样规定。但 P191/P299 要求事件组织、负责人、状态和处理期限；当前 Fusion Incident、自动 Run 和人工 Case 的关系还不能直接交付完整事件工作流。是否新建或复用 Case，应按业务事件生命周期明确，不能用 Incident ID 或 Run 表中的 `case_id` 列名代替。

### 3.8 报告 持久化与审计

**Markdown 生成、保存、按 Case/Run 读取已具备代表交付证据。** 这是当前迁移可认定成立的重要成果，不需要为文档评估重跑报告模型或恢复 PDF 专项。[阶段交接](investigation-stage-handoff-20261022.md)

不过标书 P242—P250 要求报告中的确认异常、时间线、入口/传播、影响范围及证据均有实际含义；报告中有对应章节不表示内容已成立。P385—P391 的五类证据状态目前也没有在各条路径中一致、可靠地实现。Run completed、工具成功、模型高分和事实确认必须分开。

建议在原 state、工件和报告出口补最少必要的结构化结果：结论、证据引用、事件时间、判断状态、缺口/冲突、使用范围；优先处理已复现错误。复用现有账本，不另建审计服务。人员确认及修改须记录操作者和版本，后续由 API 与工作台共同交付；本轮不新增其业务实现。

## 4 标书中不能遗漏的技术与成效差距

## 7 建议用三个试点场景证明核心需求

场景是对 P404 的推进建议，尚未新增测试或确定厂商。后续优先使用真实脱敏资料；合成数据只能证明其受控合同，不能替代业务准确率。

| 场景 | 需要的资料 | 要证明的业务结果 | 对应需求 |
| --- | --- | --- | --- |
| 已授权运维与相似异常区分 | 告警原文、批准对象/命令/UTC 时间窗、资产与账号 | 有依据的 benign/BTP 与未知授权分开；关闭条件、分类理由、实际状态一致 | P182—P191、P230—P232 |
| 终端执行到网络/横移的多告警调查 | 进程父子/命令、网络连接、身份会话、来源记录与事件时间，必要时跨 Incident | 实际查到行为后才关联；只共享主机或 Technique 的历史资料留作候选，输出可验证时间线/范围 | P210—P239、P242—P250 |
| 身份异常且后续数据缺失 | 登录记录、账号/MFA 状态，以及确有接口的授权/邮箱日志；无接口明确 unavailable | 数据存在时按查询分析；无 OAuth/邮箱来源时输出待核，不将未查询或零行写成“没有攻击” | P203/P204、P223、P229—P232、P385—P391 |

每个场景保存“输入→实际工具请求和结果→模型可见材料→结论/引用/缺口→Markdown→人工复核”。固定调用验证合同；只有需要证明模型选择/采用时才增加有界新模型样例。复用已验权限、持久和归属证据，按新增差异补最少验证，不重调旧失败输入，也不安排全部入口模型矩阵。

成效评估应把 P412 的指标拆开：识别准确率需约定标签、正负样本及混淆结果，不能把模型 confidence 当准确率；效率和负荷需人工同类任务基线；攻击链时长须以证据充分且人工认可的结果为终点；处置覆盖率需固定常见威胁集合；MTTR 涉及完整响应团队和实际执行，单靠本调查服务不能证明。
