两份完整请求只有`max_tokens`不同；4096原答是8192原答的逐字前缀，且与旧C02截断原答相同。本次多生成299tokens、增加约5.914秒后结束，没有用满8192。共2次新生成、22,535tokens；不代表失败率或稳定性统计，也没有测试拆分方案。原提示仍写目标1800tokens，本轮为了控制变量未修改。

实际生成Schema验证通过，但严格接收失败：

- A1的逐成员依据混入8个只归属A3的来源，触发`source_member_mismatch`。
- F1声明覆盖A1/A2/A3，依据却未覆盖A3；两条依赖F1的冲突也缺少所需原始支持。
- F1及两条冲突的引用列表共6个多余重复项。已确认的“同列表完全相同ID保序去重”离线预览能移除这些重复，但重验仍拒收；未改原答、未实现生产去重。

人工阅读另发现：两条conflicts把“部分动作有授权、其他动作尚未获确认”或“可能有不同解释”写成冲突；cloud仅因主机/出站连接判适用；followups选择Deep取得业务授权文档/人工确认，而当前无查询候选，不能据此证明它能取得新证据。它们仍分别属于原正文质量和RV04目标/能力问题，不因额度试验变成已解决。

**实施建议：C3先保留单次七部分，以8192作为后续配置候选；优先修引用、范围和可执行补查约束。当前证据不足以把这些错误归因于七部分合并，也不足以证明拆分会改善。** 只有后续直接验证仍显示任务之间干扰或遗漏时，再讨论按职责拆分。正式配置和保存读取闭环尚未实施，不核销RV01/RV02/RV04或主调查任务。
