# 3A-01：规则抑制的持久回执

状态：3A-01已按下述范围完成限定验收，实际行为/失败/限制见[实施回执](3a-policy-suppression.md)；本文保留实施前规划，下一项3A-02尚未实施。前序见[2C-03回执](2c-event-ueba-sources.md)；整个2C仍有真实事件/UEBA源和模型材料消费缺口。

## 本批范围

生产`services/agents/app/workers/fused_alert_consumer.py`的`triage()`在business-context规则命中抑制时，直接返回含规则指纹的摘要，先于state、writer及ledger建立。原Kafka主循环的提交承诺依赖持久完成；这个分支当前不能满足。先形成可查询、幂等、带tenant/告警身份/实际规则指纹的持久处理决策，再核offset提交，不把有规则授权的抑制写成模型判定benign。

优先复用现有ledger/outcome存储与writer接口；先核schema、事务、查询接口和shadow分支，只有现有语义无法表达时才提出最小新增存储。原始告警和既有Run不改写，未知结果不自动重发动作。持久化失败应传播到重试/DLQ路径，不吞错后提交。

本批不启用常驻Kafka worker、不默认消费现有积压，不开放自动graph升级或真实响应。先通过生产方法加真实PG验证，再用独立测试topic/group、唯一标签做有界broker验证；若需要额外部署差异，保留源码/镜像/配置及恢复回执。

## 验收

| 输入 | 实际中间产品/调用 | 最终要求 |
| --- | --- | --- |
| A tenant命中抑制，实际规则revision已知 | 生产规则applier → 持久决策/ledger | 可经认证接口回查抑制理由、实际revision、tenant和输入身份；无模型/厂商调用，不产生虚假的模型verdict |
| 同一告警重复投递、进程重启后再投递 | 相同输入身份 → 相同持久决策键 | 决策幂等，旧原文和账本保留，只有持久完成才能前进offset |
| B tenant同实体/不同规则；A取消抑制 | 实际规则来源/缓存revision → 正常分诊分支 | 租户隔离，规则变更与重复输入的决策冻结语义明确；不借旧抑制使无关告警跳过 |
| 独立探针持久写失败 | 真实PG失败或受控写入口失败 → 原生产重试/提交判断 | 不返回持久成功、不丢消息；恢复后可完成，保留失败记录；不停止共享PG |
| shadow或材料缺失 | 实际writer/上下文选择 | 遵守原shadow只读语义；未知/缺源保持明确，不能转成已核实安全 |

相关原测试加本批关键边界通过后才进入3A-02：明显恶意、有授权背景、材料不足三样例和模型失败，真实模型输入/输出、usage、verdict、依据、升级及Run各自取证。下一批实施前仍核实际源码和环境，不能把本计划当作完成证明。
