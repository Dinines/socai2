# C01：Fusion持久交付与source-v1恢复

状态：**限定验收及独立结束审计通过**，实际结果见[回执](c01-fusion-delivery.md)。承接[迁移审核R1/R3](migration-review-20261020.md)及用户持续完成迁移、逐change审计的授权。对应原路线2A/2C及整链交付，不扩大到采集、检测、前端或模型质量。上游非阻塞问题按统一清单暂缓；本批只修会丢持久结果、越过失败输入及本地缺行修复丢关联的阻塞。

## 限定变化

- live Fusion成功处理当前消息后，仅显式提交该topic/partition的offset+1。处理/发布/提交异常终止本次消费，清除attached，不继续越过失败项；不新增并发水位算法。
- PG真实行确认在先，fused消息broker确认在后；二者未确认不得提交raw。DLQ只在真实持久写入/发布确认后可提交，不把日志或吞掉的异常当成功。
- 新source-v1保存完整首次FusedAlert（原告警、关联、增强、分数、narrative/session），首次PG插入与快照同条语句写现有JSON元数据，无DDL。重投先核PG快照，再核有界TTL/大小的首次Redis快照；恢复不重跑关联、增强或评分。
- 暖dedup/旧PG记录缺确切首次快照时保持hold/unknown，不从当前材料拼造历史，不回填旧首次结果。legacy原指纹、UUID及合并规则不改；live持久确认不能把其不查PG的duplicate回执当行存在证明。

预计差异为Fusion consumer、alert_sink、新delivery_recovery模块及dlq/dlq_sink的确认边界；必要直接测试、新镜像层及运行Compose追加层。若实施发现必须改变身份、关联算法或数据库schema，先收敛并记录本批范围再做。旧回执、旧14表行和三unknown、A积压不改写/退款/重调。

## 验收

1. 缓存镜像、网络禁用的直接测试：PG不可用/SQL失败、发送/交付Future失败、commit失败和前项失败均不越过offset；显式提交不带其他分区位置；坏schema无DLQ确认不提交，确认后提交。
2. 完整PG首次快照在Redis失效后复用；暖dedup且PG缺行从确切首次缓存恢复。输入事后修改不能覆盖首次正文/时间/关联/增强；错tenant/ID/hash/超大小和无完整快照不能生成伪恢复。
3. 真实21 PG/SSL Kafka/Redis，以新的合成来源/UUID/topic/group定向验证正常、故障及恢复，不停止共享服务。故障限独立worker接缝；替身与真实持久/消息结果分别记录。每个开始/发送检查点独占创建，未知先回查，不盲目重发。
4. 只构建/替换Fusion同依赖父镜像，部署前保存容器/配置/源码hash；成功后核健康、真实HTTP正常主链、旧材料/reader/预算/其他35容器及18卷保持。0模型，无新外部厂商动作。
5. 未参与实现者审计最终差异、测试、真实坐标、旧数据保护和限制。审计通过才记本change限定完成并推进C02；不由本批宣称高可用、完整缓存丢失可恢复或整个迁移完成。

已有PG行缺首次快照，或尚有暖dedup痕迹而无完整首次结果时只能hold。Redis的dedup和快照痕迹全部过期后，不能区分fresh输入与曾计算但未留完整结果的输入，不承诺永久unknown或完整Redis丢失恢复。Kafka at-least-once允许相同首次信封重交付，下游幂等保护仍须保持，不承诺跨PG/Kafka分布式恰好一次。回退只恢复前一Fusion镜像/定义，保留新行/快照与消息，不反向删除数据或重置消费组。

## 真实探针执行前的计数补充

初始准备冻结的`broker_test_publishes=12`没有区分raw输入与worker的fused输出。真实探针尚未执行时补充统一口径：所有broker发送尝试（包括失败）上限20，其中raw输入不超过10、fused输出不超过10；交付/独立回读合计上限仍为20。计划值为9次raw、7次已确认fused及1次已停止SDK发送尝试，合计17次；worker交付及fused回读合计18次。新PG告警不超过6行、topic不超过12、group不超过6，模型0、共享服务重启0、DDL0均保持。原`limits.json`和`scope-before.md`不覆盖，另存带原hash的补充回执；按实际坐标逐条计数，失败也保留。
