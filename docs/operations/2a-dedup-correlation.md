# 2A 告警重投与关联核对

本页保留首次诊断/成员修复阶段事实；后续2A-01已按[独立身份合同](2a-source-identity.md)通过限定验收，当前推进2B。本页下方“未完成”是首次阶段状态，不代表当前最终结论。

2026-10-20。本批先验证固定原版运行行为，不改指纹/事件身份算法，不重写已有结果。输入是已有告警，不启检测、模型或响应；使用两个新标记tenant。

范围：同一投递重发、相同特征但不同发生、同实体不同告警、不同实体/战术及跨tenant。每次输入记录HTTP受理、raw/fused broker坐标、PG行/来源以及Redis incident摘要；重投检查来源列表不重复增长。另仅删除一个已核归属的测试dedup key，模拟去重缓存丢失，再重投同一输入；不清共享缓存、不改全局TTL、不重启服务。

验收：真重投不增加独立告警或虚增关联；不同发生的材料与身份可解释；关联与持久结果一致，跨tenant不串用。保留原版不符合项作为阻塞缺陷，不用“探针执行成功”代替业务通过。标记API key在验后停用，样本与消息保留。实际结果完成后补充。

## 实际结果

固定1F运行镜像上完成8次真实投递、20项HTTP检查，逐条取得raw/fused坐标、PG行与Redis摘要，见[机器回执](2a-dedup-correlation.json)。同一重投的canonical ID及来源列表稳定，跨tenant访问404、伪造tenant拒绝403；同实体不同告警关联，不同实体及战术样例分组。战术样例同时改变title/technique，因为原指纹不含tactics，不能外推“只改tactic必分开”。

| 输入 | 实际结果 |
| --- | --- |
| A首条已有告警 | new_incident/inserted，创建独立关联摘要 |
| 完全相同投递重发 | duplicate/duplicate，同一PG行，来源列表不重复增长 |
| A第二次发生：新ID/来源ID/厂商ID，时间+1分钟，特征相同 | duplicate/duplicate，仍为首条canonical行；新来源ID保留，PG时间、raw_event及external_id保持首条；后条完整材料只能按保留期内的broker坐标读取 |
| A同实体第二种告警 | correlated/inserted，同一incident，成员数2 |
| 不同实体/战术样例 | 不同incident |
| B同形告警 | 独立canonical/incident，A/B互读404 |
| 删除已核归属的单个A dedup key后重投首条 | 原版correlated/duplicate，PG无新增行，却把incident计成3，列表实际只有2个不同ID |

由此确认2A-01（不同发生未独立持久）及2A-02（缓存丢失重投虚增成员）两个阻塞点。原版首次5条PG行、错误Redis摘要的快照和消息保留；没有为了测试改指纹或覆盖旧记录。

新增3项回归在修复前2失败/1通过，修复后连同直接相关原测试共25项通过。以原1F精确image ID为基底，仅叠加该文件，从源码构建2A镜像并只重建Fusion；其余35个容器及18卷保持，运行env映射与原镜像默认值+未改1F env一致。

独立实体上再投递首条、关联告警、清除一个自有dedup key后原条重投，共3次真实投递/8项HTTP检查：同一incident仍为2个成员、count2，last_seen和PG来源列表保持。最初复验只换标签而未换关联实体，2条新样本合法加入原测试incident，探针停止在缓存操作之前；失败证据保留，之后换独立IP，没有回写原计数。

首次部署校验比较了env列表顺序而误报，服务实际已更新；只读核对原镜像默认值和受控env映射、挂载、源码hash及健康后补齐回执，未再次重建。首次客户端import失败也保留；修正/app搜索路径前没有任何业务投递。

全批共13次受理、34项HTTP检查（含上述失败探针的已完成请求）；9条合成告警和消息保留。原诊断5条PG行材料逐列保持。两枚测试API key已停用，实际401；网关成功调用计数与1G完全一致，没有新增模型或厂商调用，费用不写零。
