## 2. 对我们自己设计的判断

**主设计方向可以保留，当前完整 Case 执行尚未落地。** 需要收敛和接通已有能力，同时补齐结果合同；不能把“文件已存在”或“有一轮模型与工具调用”当成完整基础调查。

值得保留的具体设计：

- 问题、证据、分析判断、执行状态是四块逻辑数据，复用既有 Run／Event／Artifact，不是四个新服务或四张新表。
- 同一 Case Run 只有一个主调度者。材料整理、专业分析、Deep补查、关系分析和响应建议服务于本轮整案问题，共用范围、证据身份、预算和最终结果。
- 来源事实、历史分诊、模型推断、人工反馈分开；同一来源不能因经过多个 Agent 而变成多份独立证据。
- 执行结束、交付完整性、Case业务解决分开；旧报告保持，范围变更后生成下一轮，不修改运行中的快照。
- 结构化结果与可读报告应来自同一份正式结果，报告整理不再产生新的无源事实。

需要按当前需求调整的设计内容：

| 原设计/原实现边界 | 现在的设计要求 | 判断 |
| --- | --- | --- |
| 主要分告警侦察、Case调查两层；事件、问答、人工承接较少 | 明确 A/I/C/Q/H 五条流程及交接；事件诊断有独立产物 | 补业务合同，保留公共能力 |
| 案件可做有限目标或所选成员调查 | 标为“基础调查”的 Run 必须处理本轮完整成员；局部问题归问答/补查 | 不能用有限网络验证或子集结果冒充整案基础交付 |
| Deep、领域、Graph“按需”接入 | 完整基础流程必须具备这些能力和适用性判定，保存实际执行或未适用/不可用原因 | “按需”控制实际调用，不免除能力建设和阶段交付要求 |
| questions/assessment 中列了很多理想字段 | 先实现本案真正需要的目标、发现、支持/反证、未决、变化及影响；有限规则不能冒充语义验真 | 不先造通用推理平台，不照搬所有设计枚举 |
| 长期预留自动建案/启动/持续续接 | 本期手动启动、单活跃、待更新合并、启动即冻结 | 自动策略留后续，本期不增加领取器/自动接续 |
| 跨 Run 的 validity、supersedes、当前采用结果只是长期设计 | 页面已需要“本轮变化/影响”和“案件当前认识” | 本期需要明确结果引用和版本；不能仅取最新 summary 或用自由文本记忆代替 |

这里的 Graph 必须分清两件事：LangGraph 是执行编排技术；关系图/攻击路径是要读取和核验的数据能力。使用 LangGraph 不等于已经做过关系分析。

## 3. 当前调查实际做了什么

### 3.1 当前 Case 主路径

直接源码：[Case执行与输入](../../../case-baseline-history-20261103/services/api/app/investigation_v2/case_analysis.py)、[结果综合](../../../case-baseline-history-20261103/services/api/app/investigation_v2/case_synthesis.py)、[湖工具](../../../case-baseline-history-20261103/services/api/app/investigation_v2/case_analysis_tools.py)、[来源产品工具](../../../case-baseline-history-20261103/services/api/app/investigation_v2/case_product_tools.py)。

| 顺序 | 当前确实执行/保存的工作 | 明确边界 |
| --- | --- | --- |
| 1 待更新与启动 | 本地新增 pending_update 记录；未启动时合并成员变化；启动按 Case→Run 加锁，检查版本/全部成员/活跃记录，提交 running 后调用执行器 | 迁移122未应用，真实PG并发尚未验；不是自动领取模块 |
| 2 固定输入 | 读取 Case标题/说明、成员告警原文/时间/对象/来源/检测、同次分诊判断和评分；固定 all/selected/read 成员、窗口和材料hash | 不读取人工任务结果、事件诊断正文或完整 ContextBundle；read_member_ids 只证明读到，不证明完整分析 |
| 3 选择查询 | API进程直接请求模型，可调用 process_activity、network_connections；满足来源绑定条件时提供 product_host_details | 当前不是旧 Deep/领域/Graph 的整案流程；产品工具是当前主机快照，不是历史取证 |
| 4 执行与留存 | 服务端限制租户、主机、窗口，保存工具请求/返回、模型视图和 E 引用；适用历史查询可以明确复用 | 当前工具字段及能力仍窄；成功空结果不证明告警错误或安全 |
| 5 分析与校验 | 生成 summary/findings/counterevidence/gaps/recommendations、逐成员判断、关系和未决；做结构、引用及有限语义约束；原预算内一次纠错 | 校验不是通用事实证明；没有完整领域阶段产物、Graph证据或逐阶段完成判断 |
| 6 交付 | 程序补成员覆盖、时间线、查询来源；保存 case_analysis_result JSON 与 Markdown、停止原因、用量及步骤 | 无 comparison/change/case_impact；未获得模型结论时仍保存系统收尾summary，不能当有效结论 |
| 7 读取与续问 | 结果、证据、步骤、历史与关联入口可读；previous_run_id 支持明确同范围续问并保留旧结果 | 续问要求同成员/窗口；不是新成员加入后整案更新的比较基线 |

当前循环固定上限为4次模型、4次工具、24,000 tokens、主循环120秒。它已经能做有限范围的分析与补查，但这些限制和现有两轮查询决策**没有证明能承载 C1–C6 完整流程**。不能只增加上限就宣布完整能力成立；本轮未修改额度。

## 5. 旧AiSOC作为能力下限，怎样才算做得更好

参照的是仓库保留的旧实现及 [历史设计评价](../../../../../docs/architecture/investigation-design-review.md) 中固定的上游版本，不是本轮重新核验的最新开源版。旧版存在多条入口，不能声称它的一次手动调查已经同时跑完四阶段、四领域和Deep/Graph。

| 应保留的能力 | 我们应额外做到的事 | 当前判断 |
| --- | --- | --- |
| 上下文富化、历史/基线、TI和图材料 | 覆盖整案，逐来源说明查了什么/没查到什么；不截头3条后称整案完成 | C尚未接通，不达标 |
| 分阶段或专业领域分析 | 必要能力参与同一个Case流程，有阶段产物；避免多条流水线重复下结论 | C尚未接通，不达标 |
| Deep与实际工具查询 | 支持据返回继续查，工具真实能力与数据覆盖公开；已存字段不丢，调用均可回查 | 有局部能力，完整目标未达标 |
| 关联、时间线与影响解释 | 区分事实关系和候选/推断；每条关键关系、影响指向依据，图可达不等于攻击成立 | 现成员关系/时间线部分支持，Graph与影响未达标 |
| 报告与响应建议 | 同版结果/报告、逐成员范围、反证/未知；有引用仍须核实语义，建议与实际执行分开 | 留存/有限校验已有改进；r13质量未通过，不能宣称更准确 |
| 历史可读 | 新成员后整案新一轮、清楚说明变化；运行中冻结，人工及AI保存结果有版本 | 待更新生命周期已有本地实现，其余合同未齐 |

三个“四”不能混用：ContextBundle的图邻域/历史相似案例/UEBA/TI是**四类上下文**；Phishing/Identity/Cloud/Insider是**四领域**；Recon/Forensic/Responder/Report是**四阶段职责**。完整能力也不要求每案盲跑所有领域、所有工具：各职责要有执行结果或真实的不适用/不可用理由。

旧工具中 process_tree、mailbox_activity、oauth_grants、persistence_mechanisms 存在不可用占位，不能把名称当作已具备能力。现有7类查询原语也须逐项核本案输入、来源和返回再接入，不宣称都已线上验证。

## 6. 建议的完整执行形态与实现顺序

```mermaid
flowchart TD
    A[告警基本查询与诊断] --> I[事件汇聚与诊断]
    A --> C[Case成员和待更新记录]
    I --> C
    C --> S[用户启动：原子领取并冻结整案]
    S --> P[C1输入与C2上下文富化]
    H[人工反馈：人、时间、范围和版本] --> P
    P --> M[C3整案问题与领域分析]
    M --> D[C4 Deep与Tool补证]
    M --> G[C5图关系核对]
    D --> M
    G --> M
    M --> R[C6综合、比较、影响与同版交付]
    R --> Q[按问题AI对话；必要时查工具]
    H --> Q
    Q --> V[用户明确保存：冻结答案及依据]
```

图是职责关系，不要求每节点都调用模型，也不表示已经接线。C1–C6由一个执行器负责；事件无需另建Deep循环，人工反馈无需执行器，Q可以复用材料和工具能力但有独立问题/保存合同。

| 次序 | 工作包 | 交付与直接判定 |
| --- | --- | --- |
| 1 先定完整Case执行合同 | 对R02–R08逐阶段固定输入/输出、必需问题、适用性、停止/交付条件；确定一条新版执行入口和可复用能力清单 | 每项都有函数接入点、材料/结果schema、读取位置；不是只改“基础调查”名称。不先建完所有页面表 |
| 2 接通一条完整整案流程 | 保留现待更新/锁/Run身份，接材料富化、分析、必要Deep/图、综合；同步处理已有字段漏读 | 同一Run能回查真实阶段产物，全部成员有覆盖或明确缺口；旧能力适配不偷偷启动另一Run或提前完成全案 |
| 3 补结果和人工数据合同 | R08–R11：结论来源、完整性、比较基线、变化/影响、人工反馈与版本；明确Case当前结果采用方式 | 已有表/Artifact可承载的部分复用；有新增持久事实和索引需求才加列/表；待更新范围不被旧结果覆盖 |
| 4 接同案AI问答与正式保存 | R12：发送时读取案件上下文、按问题工具调用、答案和依据保存 | 保存不再次调用模型，不修改Case成员或旧结果；反馈后编辑也不改变已保存依据 |
| 5 做针对性验收与页面交接 | 固定字段读合同，核真实PG事务与必要端到端语义 | 页面交专门人员；没有产出的字段明确为空或未完成，不由文案补事实 |

下一步最合适的是**工作包1：将C1–C6写成可实现的输入／处理／输出合同和具体接线清单**。已有生命周期修改保留；不从旧M编号重新开整套框架，也不把直接调用完整旧orchestrator作为最终方案。

验收聚焦这几类有区别的案例：首次多告警整案；新增成员后整案更新及比较；启动与第二次成员变化竞争；成功空查询/来源不可用/矛盾材料；人工确认被引用后再编辑；AI发送与明确保存；模型失败或截断仍能读到真实部分产物。更好应体现在这些场景的覆盖、可追溯与结论质量，不以Agent数量或测试总数判断。

尚需产品决定的少量事项：哪类结果可以更新Case当前认识及如何采用；AI实际补查是否与基础Run共用单活跃约束。用户已定的基础Run手动启动和单活跃不重问；上述选择在相应实现工作包前确认，不阻止先定义完整基础流程。
