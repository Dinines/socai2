# 测试数据准备与调查模块独立设计评审

2026-10-24。评审基线：`main a82346ddb4846e1fbb22c4023ef2be0c7f4ec87c`。对象是数据准备与评估设计、调查v4设计及其v2实现边界，供两个开发分支讨论下一步。用户要求重新独立评审、不修改代码。

**结论：两条线的总体方向合理，值得继续；数据评估的标准答案有效性需要优先重新审定，调查则需要补齐材料处理的两个合同接缝，并验证模型对业务判断的实际价值。** 当前证据支持有限场景的工程能力，不能据此认定通用调查质量或标书成效达标。

本轮从原需求、当前主设计和源码重新建立判断，不用此前的ACCEPT或合并结论作为通过依据。数据与调查分别由未参与实现的审阅者独立分析，再由主审核对关键原文和纯内存反例。没有逐题人工重标72条语料，也没有运行新的模型、HTTP、数据库、Kafka或数据湖操作；代码、测试、配置和既有设计正文均未修改。下列建议尚未实施。

## 数据准备与评估的设计意见

### D1 标准答案需要先证明能由公开材料支持

**P1，评测有效性问题。** 数据设计第33行要求保留原72条真值；保留历史原件是正确的，但冻结标签不能代替标签有效性审核。当前只将标题、严重度、来源、规则ID和evidence交给模型，见[输入导出](../../tools/testdata/verdict_eval.py)第24、54—62行。部分答案解释中包含这些输入没有提供的决定性事实。

| 例子 | 公开输入与隐藏解释的差异 | 为什么影响判分 |
| --- | --- | --- |
| AWS-01-B | [语料](../../services/agents/tests/eval_data/verdict/verdict_corpus_v1.json)第35行解释称审批覆盖窗口、允许重启；第36—46行只有工单ID、批准描述、02:00—04:00窗口和实际动作，没有活动绝对时间、审批主体/资产/动作范围 | 同样公开材料可以对应窗内获批活动，也可以对应窗外或超范围活动；无法独立核定隐藏解释中的完整授权主张 |
| AWS-02-B | 同文件第81行固定为benign；第87、93—101行显示“批量修改策略”与实际38次收紧策略。现有[taxonomy](../../services/agents/app/agents/dispositions.py)第17—29行又允许把有效检测到的非恶意行为称为BTP | 缺少足以区分“信息性benign”与“有效检测的BTP”的规则判据；合理标签可能不唯一 |
| AWS-03-B | 语料第146行解释称“规则匹配了sinkhole回答”；第147—155行公开输入没有规则匹配字段或谓词，只有DNS信息及零后续会话/流量 | 阻断成功或没有后续连接，不能单独证明针对DNS查询的检测条件无效；缺少把该例唯一判FP的必要依据 |

这不等于已证明三个原标签都应换成另一个标签，也不代表其余69条已经逐题审定。发现的是：**当前输入与判据不足以支撑唯一答案式的严格质量验收。** 旧[分诊提示词](../../services/agents/app/llm/prompt_registry.py)第197—198行把预期配置变更举为benign例子，因此AWS-02-B可能正沿该提示词标注；该例说明分类边界需在判据中明确，不能直接认定标签错。同一提示词第220—234行要求活动时间与具体动作、账号、目标的授权证据，而[运行器](../../tools/testdata/verdict_live.py)第48—52行的anchor明确是语料编写日，不能补作活动时间。将raw_event上限从10行增大，只能解决传输丢失，不能补出原语料不存在的授权事实。

建议保留原语料和标签作为历史回归，新增独立的判定依据记录：公开事实、检测条件、可支持结论、允许未知、禁止推断及审定依据。材料不足的题目不进入唯一标签质量分母；若确需补事实，形成新版本并保留旧版差异。不要为了匹配某次模型回答修改答案，也不要把隐藏答案解释补进模型输入。

验收应先由未看答案的审阅者，仅凭最终模型可见材料和分类定义，给出允许结论及证据路径。选定授权场景至少能区分窗内/窗外、目标匹配/不匹配、动作获批/未获批；只有这些事实实际出现在输入中，才能评价模型有没有正确采用。

### D2 配对数据应按配对目标评价

**P2，实验设计缺口。** 设计以36个对照对验证“相似告警、不同证据能否改变判断”，但[评分桥接](../../tools/testdata/verdict_eval.py)第164—175行主要转成逐条分类；[原评分器](../../services/api/app/_vendor/aisoc_benchmark/replay.py)第670—677行对逐条结果计算准确率及重采样区间。

一个系统18对两条全对、18对两条全错，另一个系统每对只对一条，逐条准确率都为50%；完整对照对识别率却分别为50%和0%。只看逐条指标不能回答原先的配对实验问题，同一对也不应默认当两次独立抽样。

建议保留分类混淆矩阵，同时记录完整对数量、双成员全对率、单侧失败、未完成对；比较版本时按同一pair关联。需要统计区间时，以pair作为重采样单位，区间仅作为该语料构造和配对抽样假设下的不确定性描述，不能外推生产分布；固定集合的已观察正确率本身无需用抽样区间证明。以后需要测泛化，才增加未参与调试、按pair或规则家族隔离的验收集。

验收使用上述两个50%结果集：逐条成绩相同，配对成绩必须不同；只完成单侧的pair不能计作完整配对通过。无需为了补这个指标先扩大真实模型调用数量。

### D3 非法输出的指标分母不一致

**P2，已独立复现的评分实现问题。** 保留一个原评分公式源的设计合理，但复用不保证边界正确。[桥接](../../tools/testdata/verdict_eval.py)第165—166行保留非法非空预测，避免默认成TP；[MCC计算](../../services/api/app/_vendor/aisoc_benchmark/replay.py)第633—639行却仅将四个合法预测放进矩阵，丢掉其他预测。

本轮用72条原标签构造纯内存结果：每个类别只答对1条，其他68条返回`bogus`。实际输出为：正确4/72、headline accuracy `0.05555555555555555`、balanced accuracy `0.07708333333333334`，但MCC为`1.0`。这是人为反例，不是模型实测成绩。

建议统一非法输出的判分合同：纳入明确错误统计，或在存在非法预测时将MCC标不可用并显示失败率。不要再复制第二套评分器。验收时该反例不得得到完美MCC，合法数据的原语义保持。这个问题影响具体指标可信度，不推翻三条评估线。

### D4 数据库读回与字段语义应分别验收

**评审边界澄清，非当前D2阻断。** [写湖探针](../../tools/testdata/lake_fixture_probe.py)第123行用被测LakeWriter的`event_to_row`生成expected，第218行再逐列比较读回值；这能证明同一映射后的写读一致，不能独立证明47列业务含义都正确。例如映射函数若将某字段统一映错，expected也可能同步映错。

同时，[已有直接测试](../../tools/testdata/tests/test_investigation_fixture.py)第83—99行另有时间、类型、动作/结果、端点、主机及原文等固定值断言。因此当前并非完全自证；准确结论是“47列传输一致，加选定字段的独立语义检查”。

后续每接一个调查问题，只补它需要的字段语义断言：来源字段→规范字段→库列→API字段→允许命题。预期值来自独立场景规格，不从待测映射函数反推。无需先重建全库schema或完成所有字段专项。

## 调查模块的设计意见

### I1 可选正文异常应局部降级

**P2，已复现的设计与实现接缝。** 主设计第349、527行要求保留原返回、披露解析和裁剪缺口；但[EvidenceView](../../services/agents/app/investigation_v2/evidence_view.py)第125—148、249行，对可选`message`超过512字节或类型非字符串直接抛异常，使整个证据视图不能生成。

本轮用已有纯合同夹具，仅改变同一合法记录的message：短文本成功；513个ASCII字符触发`data_only_excerpt_exceeds_byte_limit`；对象型message触发`source_message_must_be_text`。身份、时间、端点、action/outcome及hash仍符合来源合同。失败发生在模型调用前。

建议把“来源记录身份/必要字段不可核”和“可选摘录不可用”分开处理。保留已核结构字段、原文引用及其他记录，摘录记录明确缺口；仅阻断依赖该正文的命题。若正文可能包含关键反证而无法读取，相关结论继续待核，不能静默裁掉后宣称完整。

验收覆盖短正文、超长正文、结构化message及关键正文不可读。前几项应保留可核的有限事实，后一项应限制相应判断；不因一个可选字段使整批有效材料消失。

### I2 输入预算必须以完整模型请求计算

**P2，已复现的跨层合同不一致。** [EvidenceView](../../services/agents/app/investigation_v2/evidence_view.py)第22、351—353行允许模型视图小于12KiB；[模型执行器](../../services/agents/app/investigation_v2/execution_models.py)第31、205—206行又限制完整messages为12KiB，两者没有共同扣除固定提示词和任务封装开销。

本轮构造允许的10条网络记录，每条message仅128字节。builder交付的视图为`7882`字节，加入现有focused提示词及封装后为`14194`字节，超过执行器`12288`字节上限，触发`ExecutionRejected: snapshot exceeds retained byte limit`。这是实际同路径序列化结果，不是token估算或模型服务错误。

建议由任务的完整请求预算反推证据预算，组装器和执行器共用相同计算依据；超过时在输入准备阶段分组，或交付明确的材料缺口。必须保留对当前命题必要的支持与反证组合。只增大全局上限会掩盖接缝，并不能证明小模型可以有效处理更多材料。

验收包括1条、10条和临界大小：上游宣布可消费的视图应能通过对应任务的完整请求限制；装不下时能够说明分组/遗漏及受影响的问题。字节留存上限与模型token预算仍分别记录。

### I3 来源版本差异与命题冲突应区分

**P2，保守策略的粒度改进建议，非安全漏洞。** [来源版本](../../services/agents/app/investigation_v2/evidence_view.py)第118—120行包含完整正文hash；[回答采用](../../services/agents/app/investigation_v2/analysis_adoption.py)第160—165行只要看到任意来源版本冲突，就拒绝Q1的supported回答。

本轮两个完整版本的event ID、时间、端点、action/outcome完全相同，仅message为`collector note A/B`。现实现仍拒绝有限网络观察的Q1回答，原因是`answer_ignores_source_conflict`；Q2/Q5保留，整体候选因缺Q1被拒。

保留版本差异和全部原件是正确的。建议在此基础上区分“完整内容有分歧”“当前命题所依赖字段矛盾”“尚无法检查”：在全部相关版本可读且有限谓词可核时，可表达共同记录的有限事实，同时保留全文分歧。缺失版本、未知正文语义或关键字段冲突时继续待核，不自动选一个赢家。这是提高有用性与表达精度的建议，不要求放松来源真实性或权限校验。

### I4 需要验证模型的增量价值

**实施决策建议。** 主设计第181、482—485行已经允许简单字段命题由程序处理、已知参数查询直接执行，这个选择应落实。当前[采用器](../../services/agents/app/investigation_v2/analysis_adoption.py)第23—24、51—87行只有七类有限谓词，大部分可以由已知结构字段和查询状态直接计算；当前M5首例也只有一个固定工具与固定参数的一次查询。

这些例子适合验证模型引用、采用约束和选择→执行→回流接缝，但不能证明模型比程序核字段更有价值，也不能证明Deep提高了调查结论质量。应保留既有阶段成果，同时明确它们证明的能力。

建议首个告警产品路径允许“程序固定查询→有限事实→同版交付”，不为填满编排增加选工具模型。需要评价Deep时，再选一个结果确实会改变下一步查询的有限分支案例；需要评价主分析时，再选一个来源已具备、不能仅靠字段相等判定的业务问题。比较相同材料和目标下的正确结论、缺口、调用数与成本，分别看模型原文、程序采用和最终交付。无需先接完四领域或另造总规划Agent。

## 应保留的设计选择

| 选择 | 本轮判断与理由 |
| --- | --- |
| 三条评估线分开 | 分类正确、工具正确、模型选择与采用分别回答不同问题；合成一个总分会掩盖失败位置 |
| 可见输入与答案隔离 | opaque ID、字段白名单、hash、实际请求检查与shadow限制有效；输入文件完整不代替最终请求完整 |
| 有界夹具与原writer复用 | 小批量隔离数据足以验证具体问题；当前一次三条、空tenant的探针边界合理，无需先做通用造数服务 |
| 两个profile共用内核 | 告警局部侦察和Case整体调查有不同目标与成本，共用证据、预算和发布合同有助于减少重复 |
| 四块逻辑状态 | 问题、证据、判断、执行职责可区分，不需要因此增加四个服务或四套存储 |
| 程序控制与模型分析分工 | 身份、权限、范围、预算、版本及采用归程序；复杂语义保留模型分析性质，避免用引用存在冒充验真 |
| 性质与授权独立 | 能表达误操作但越权、获批模拟但有影响；比用一个TP标签承载所有业务含义更清楚 |
| Case继承与全成员快照 | 避免重复分诊、最近三条冒充全案、同源多次计证及运行中成员变化污染结论 |
| 创建关联与启动分开 | 建Case不等于启动调查，模型建议不等于动作授权；稳定操作键与新Run准入能控制重复成本 |
| manifest同版交付 | 解决结构判断、Markdown、热读/冷读和通知各取“最新”导致的混版问题 |
| 原文采用交付分别评价 | 程序拦截错误不等于模型答对；partial也可以有用，但不能用全拒答替代能力验收 |

因此，不建议重写两条线、把所有功能塞进一个Agent，或为了简化文档撤掉这些边界。复杂度应集中在程序合同和必要适配，避免把每个逻辑阶段都变成一次模型调用。

## 数据湖与双方协作

**需要受控写湖，但需求来自具体调查场景。** E0/E1给定材料分类不依赖写湖；E2查询与E3补证需要真实可查的来源事件。正常数据生产仍由相应上游负责，调查保持读取；不因评测需要开启告警全量写湖或新增第二套生产入湖链。

当前三条网络事件加一条告警的配方适合验证身份、窗口、不同目标排除和来源关联。它的[告警telemetry](../../tools/testdata/investigation_fixture.py)第87—88行已经包含匹配事件，不能原样用来证明“模型必须补查才知道答案”。E3主设计已要求初始告警不给后续答案，应按这个目标另做最小对照，而不是把现配方当设计失败。

| 工作 | 建议主责 | 共同验收内容 |
| --- | --- | --- |
| 场景定义与判定依据 | 数据线组织，调查线核业务语义 | 该问题需要什么事实、允许哪些未知、哪些推断不成立 |
