# 调查需求到字段、现表和改造工作的对应方案

2026-11-03。承接用户要求：理解产品需求，结合当前代码确认所需字段、现表支持范围、具体存储改法和配套工作。本文给出推荐方案，不是已实施迁移。与前一份 [22 项差距分析](investigation-gap-assessment-20261103.md)相比，本页进一步落实到字段、表、约束、读写位置和旧数据处理。

## 1. 基线与设计结论

- 需求：本设计分支 `c71afb5c6c4f939bf0243b60e02f224d01c6249a` 的 [产品说明](alert-incident-case-product-requirements.md)。后台：主工作区 `E:/aisoc/socai2` 的 `39f4033663bf478c7a8e8af2adb8333b45a6eb41`。
- “当前有列”指已核仓库迁移、ORM 和对应代码；本轮没有连接实际数据库，不能证明某环境已经应用这些迁移。上线前须执行 [只读 schema 核验清单](investigation-schema-preflight-20261103.sql)。
- 继续复用 `aisoc_cases`、`aisoc_case_tasks`、Copilot 对话和 Run／Event／Artifact。推荐核心新增 **3 张表**：正式 AI 保存记录、当前 Case—事件关联、图谱探索。Case 当前判断先用结构化 JSONB 加业务活动保存，不另建记忆／判断服务。
- 告警／事件配套另推荐 **2 张表**：事件业务状态、普通告警评论。它们不是三类调查各建一套库；事件 AI 摘要缓存、Case 评论和反馈理由不能替代这两个业务对象。
- 原始日志湖暂不加列：确认的进程／网络缺口均先补已有列或已存 OCSF 的读取。案件故事、覆盖差集和统计不建冗余计数表。
- 各字段名和新增表名是本方案建议；产品未定策略在第 8 节单列。本轮不改源码、DDL、真实数据，不恢复报告开发或 r13 重试。

## 2. 先纠正“现表支持”的判断方式

| 当前表／结构 | 已支持 | 不能因此视为支持的内容 |
| --- | --- | --- |
| `aisoc_cases`：迁移 012＋083＋086＋090＋106 | 案件资料、六态处理状态、成员 UUID[]、图／证据链 JSONB、摘要、优先级、负责人、SLA、重开和合并事实 | `summary` 不是有确认人与覆盖的当前判断；没有待更新范围；新旧负责人写入不一致。旧 `cases` 已有合并迁移，不能再把它当另一个主表 |
| `investigation_case_links`：121 | 一次关联的选择、来源事件、幂等键、回执 | 是操作历史，不是当前事件关系；移动两案不能直接套其一条记录的 case_id；仅关联事件但无新告警也需独立表达 |
| `investigation_runs`：008＋063 | 实际执行、状态、起止、用量、raw_alert 范围／来源元数据 | `case_id VARCHAR(200)` 是历史外部引用，不能给所有行直接加 Case UUID 外键；同操作幂等不等于同案单活跃 |
| `investigation_events/artifacts`：008 | 步骤、Tool、输入／结果、报告与来源 hash | 工件 run_id 非空，不能为了保存一段答复伪造 Run；JSON 能装内容不等于已有正确的任务／判断引用 |
| `aisoc_case_tasks`：027＋044＋086 | 标题、负责人文本、期限、三态、创建更新、依赖／阻塞 | 没有工作说明、结果、完成时间、取消、结果范围和引用；当前 API SELECT／DTO 也只读基础字段 |
| `aisoc_copilot_conversations`：076 | 租户对话、messages JSONB、消息 UUID 和时间、并发追加 | 没有 Case 绑定；所核 chat 的请求 context 不进模型 messages；没有正式保存出口 |
| `case_timeline_events`、`case_status_transitions`、`aisoc_case_comments` | Case 业务活动、状态变更、评论各有保存位置 | 当前 v1 时间线还从当前任务行按 created_at／assignee 拼接，不能当完成者／完成时间；Case 评论不能当普通 Alert 评论 |
| `fusion_incident_summaries`：120 | AI 摘要、生成时间、输入指纹、尝试／错误／用量 | 是生成材料缓存，不是事件自身 title/status/owner/tags/resolution 的主记录 |
| `agent_approvals`、`aisoc_action_records` | 审批人／意见／时间、动作及执行回执，审批 ID 已复用为动作 ID | 通用文字建议没有稳定 recommendation_id；当前 action.incident_id 的此入口值是 Run／审批 ID，不是 Fusion Incident |
| `audit_log` | 操作人、业务主体、变更、不可变审计链 | `changes` 默认有 16 KiB 裁剪且会脱敏，不能把完整引用快照或无限批量目标仅放进去后声称可完整回查 |

Case 自定义字段、外部工单和 war-room 表已存在，但它们不是人工确认结果、同案 AI 对话或正式调查记录的替代物。

## 3. 67 个字段组逐项对应

标记：**现有**＝存储和已核出口可复用；**映射**＝有列／材料，但需改实际读写、形态或语义；**派生**＝从明确事实计算，不加同义列；**新增**＝需要新字段、对象关系或 JSON 合同。一个字段组列出服务于同一需求的一组字段，不把它称作 67 个数据库列。

### 3.1 Case 资料、范围及当前认识（C01—C14）

| ID／页面需要 | 当前存储／出口 | 结论与具体改法 |
| --- | --- | --- |
| C01 案件身份、租户、编号 | `aisoc_cases.id/tenant_id/case_number`，v1 CaseResponse | 现有；新表引用 UUID，展示编号不作关联键 |
| C02 名称、说明 | `title/description`，v1 create/update/read | 现有；说明是背景，不自动当已证实事实 |
| C03 严重程度 | `severity`，v1 已读写 | 现有；不由分诊置信度替换 |
| C04 业务处理状态 | `status` 六态及 `case_status.py` | 映射；保留原状态，页面可映射为新建／处理中／已解决。旧 `OPEN_STATUSES` 包含 resolved，不能直接拿来算新版未解决案件 |
| C05 负责人 | `assignee TEXT` 与 `assigned_to_id UUID/assigned_at` 并存；v1 写前者，部分编排写后者 | 映射；新写统一已有 UUID 列，兼容文本显示。仅同租户唯一可解析值可补 ID，冲突／无法解析返回 unknown；明确清空才能按未分配统计 |
| C06 优先级及依据 | `priority TEXT` 已有；v1 CaseResponse 未暴露对应列；现无统一数值评分来源合同 | 映射；已有原值可读，来源不明明确标注，不改成数值平均或补造评分；评分合同待产品确定 |
| C07 案件标签 | `tags JSONB`；v1 请求／响应是字典，原型为数组，ORM 默认亦为数组 | 映射；维持当前 KV 存储兼容，新增列表标签建议存保留命名空间 `tags.labels:string[]`，读接口输出 labels；旧字典不直接强转数组丢键值 |
| C08 当前成员告警 | `alert_ids UUID[]`，Case 和链接接口 | 现有；保为当前成员真值，不立刻再建重复的成员主表；所有加入／移动／合并写入需走统一事务 |
| C09 当前关联事件 | Alert enrichment 可派生来源事件；121 仅记录历史关联 | 新增 `case_incident_links`，表达显式当前关系；来源事件集合仍可派生，不能把两者混成一个数 |
| C10 创建／更新／解决／关闭及发生范围 | Case 时钟已有；成员 `Alert.event_time` 已有 | 现有＋派生；发生范围取成员时间，Run 完成不写 Case 已解决；新增业务写入更新 Case 业务时钟 |
| C11 当前成员版本 | 当前无稳定范围版本 | 新增 `scope_revision BIGINT`，实际成员变化递增；重复添加或仅关联事件不冒充成员改变 |
| C12 基础调查待更新 | 当前无服务端持久状态 | 新增 `baseline_state JSONB`，保存待更新版本／新增移出／请求时间、已派发轮及其范围版本；不只存一个布尔值 |
| C13 当前判断、依据、确认者／时间、未决事项 | `summary` 文字；单轮结果有判断 | 新增 `current_judgment JSONB`；采用时写来源引用、确认事实和覆盖快照，不能直接用最新报告覆盖 |
| C14 未分析／未被当前判断覆盖 | 当前成员和每轮 scope 已有，判断覆盖尚缺 C13 | 派生；分别计算当前成员减符合产品条件的已结束调查输入集合、当前成员减判断覆盖集合；参与分析不等于被证实 |

## 4. 推荐的具体表结构调整

### 4.1 修改已有表

**`aisoc_cases`：增加 4 个字段，复用已有基础列。**

| 新字段 | 类型／空值 | 写入规则 |
| --- | --- | --- |
| scope_revision | BIGINT NOT NULL DEFAULT 0 | 当前成员集合实际变化时递增；与成员及活动同事务 |
| row_version | BIGINT NOT NULL DEFAULT 0 | 管理／判断／成员等业务写入递增，用于条件更新；不是调查版本 |
| baseline_state | JSONB NULL | schema_version、pending_scope_revision、added_ids、removed_ids、requested_at、dispatched_run_id／scope_revision、last_finished_run_id／结果状态。旧记录未知为空，不凭空称已完成基础调查 |
| current_judgment | JSONB NULL | schema_version、judgment_id、conclusion、basis_refs＋必要快照、covered_alert_ids／object_refs、formed_at、confirmed_by/at、author、unresolved、scope_revision。形成与确认时间分别保存已知事实；无明确采用事实时为空 |

`baseline_state` 保存当前待处理事实，scope 变化活动记录到 `case_timeline_events.detail`。派发时冻结所接版本；Run 完成只能更新自己的接收版本，不能清掉后来新增的 pending。失败是否重新排队、何时认定更新已交付仍按产品策略决定，字段保留事实，不自动填成功。

待更新不是第二个 queued Run：已有活跃执行时只保存 pending；获得同案执行名额后才创建 queued／running Run。基于已有材料阅读／提问不因保存记录而伪造一次 Run，确需新执行的提问遵守同一约束。

当前判断更新与包含前后判断及引用的 CaseTimeline 活动同事务；新的分析保存再冻结所用判断。这样首版无需另立判断历史表。不要把唯一完整判断快照放入会裁剪的通用 audit_log.changes。

负责人统一写已有 assigned_to_id；旧 assignee 作为兼容文本同步，读取返回 owner_id/display/state，两个值冲突显式呈现。不要只改 ORM 而漏掉 v1 SQL、case_depth 编排和关联创建入口。tags 兼容上述 labels 命名空间，旧数据不丢失。已有 priority/summary 没有必要重复加列。

标签迁移先检查保留键是否被旧数据占用：已有字典键值保持，旧数组可无损包装为 labels；若 labels 已被用于别的类型，不覆盖，先明确兼容映射。来源环境不能取浏览器任意传入字符串作为授权依据：单部署从受信服务配置／来源映射得到命名空间，引用同时绑定 tenant、对象类型及 ID；未知来源不自动匹配到任意环境。

**`aisoc_case_tasks`：扩现表，不重建任务系统。**

新增 `description TEXT NULL`、`assigned_to_id UUID NULL`、`result_text TEXT NULL`、`result_scope JSONB NULL`、`completed_at TIMESTAMPTZ NULL`、`completed_by UUID NULL`、`result_updated_at TIMESTAMPTZ NULL`、`result_updated_by UUID NULL`、`source_refs JSONB NULL`、`row_version BIGINT NOT NULL DEFAULT 0`。用户引用由服务端校验同租户；账号删除后的展示需保留当时作者标签或已冻结来源，不从当前负责人反推。

- 将状态 CHECK 和 API 枚举同时扩为 todo/in_progress/done/cancelled；不要只改页面枚举。
- 新进入 done 的写入校验结果非空并填 completed_at/by；结果变化写 result_updated_at/by；仅改事项／期限不修改完成时间。
- result_scope 明确所确认的成员／对象和范围说明；source_refs 是引出任务的材料，二者不是同一概念。
- 已有 done 但无结果的历史行保留缺失，不用 title 充结果，也不拿 updated_at 回填完成时间。首批不加会拒绝所有历史行的“done 必有结果”全表 CHECK；新写由服务层落实，旧数据质量单列。
- 列表／PATCH／RETURNING／DTO、上下文冻结、故事读取同时更新。支持 PATCH 显式 null 清空可选期限／负责人；当前 `is not None` 写法无法表达清空。

**`aisoc_copilot_conversations`：增加 `case_id UUID NULL`。**

建立同租户 Case 引用和 `UNIQUE(tenant_id, case_id) WHERE case_id IS NOT NULL`，原通用会话为空。Case 入口按 Case 找到唯一共享会话，不能按任意 conversationId 绕过归属。保留现 messages JSONB 和原消息 UUID，不立即加 messages 明细表。

消息增加版本化元数据：request_id、context_kind、scope、source_refs、material_snapshot/ref/hash、可选 run_id、reply_state。**发送／执行时先固定实际输入；明确保存时复制该答复使用的版本**。如果任务在问答和保存之间已改，保存旧答复仍引用旧版本。模型上下文经过既有 guard／预算，再真正进入 messages，不只是答后 grounding。

**`investigation_runs`：增加 `case_ref_id UUID NULL`；started_at 改为可空。**

- 新的 Case 执行强制填 case_ref_id；其他旧执行保持空。原字符串 case_id 继续兼容，不能对全部历史内容强转 UUID。
- 基础初次／更新／AI 问题类型、trigger、scope_revision、comparison 和来源任务引用先扩 raw_alert／结果 JSON 合同，不为每个展示字段增列。类型筛选确有负载后再评估表达式索引。
- Case 活跃执行以 case_ref_id 为范围建部分唯一索引 `(tenant_id, case_ref_id)`，条件覆盖 queued/running/unknown 及仍占用原执行的 awaiting_human。awaiting_human 作为本方案建议执行态，具体续接策略不在本轮实施。
- 入队显式写 started_at=NULL，created_at 是请求时间；真正开始才写 started_at；旧入口默认值可先保留兼容。所有以 started_at 排序／游标／耗时的读取需处理空值，不能只放宽 DB 约束。
- Case 行锁负责成员／待更新和派发衔接；唯一索引负责不同操作键的执行冲突。现 operation_key 幂等继续保留，两者各管一件事。
- 老行仅在 profile 明确属于 Case、字符串 UUID 有效且同租户 Case 存在时补 case_ref_id。多个旧活跃冲突先核事实，不为建索引直接把它们标完成。

`investigation_events/artifacts` 不改 run_id 非空约束，不更改旧原件；新增结果／来源合同标版本。步骤、报告、图和原始 Tool 继续放这里。

### 4.2 三张核心新增表

| 建议表 | 字段与约束 | 为什么现表不能直接承担 |
| --- | --- | --- |
| `case_saved_ai_records` | id UUID PK；tenant_id/case_id/conversation_id、question_message_id、answer_message_id 均 UUID；source_run_id UUID NULL；title/conclusion TEXT；conversation_snapshot/input_snapshot/reference_snapshot JSONB；schema_version SMALLINT；content_hash VARCHAR(64)；saved_by UUID、saved_at TIMESTAMPTZ。唯一 tenant+case+conversation+answer_message_id；索引 tenant+case+saved_at+id | 对话保存的是交流，Run 保存的是实际执行；此表保存用户明确确认的结论。无真实执行时 source_run_id 空，不产生假 Run／费用 |
| `case_incident_links` | tenant_id、case_id、incident_id 均 UUID，组合 PK；linked_at TIMESTAMPTZ、linked_by UUID、source_operation_key UUID、source_namespace TEXT。Case 同租户引用；事件按实际 Fusion 成员／来源校验 | 121 是操作回执，只能证明曾关联。新表表示当前显式关系，支持只加事件关系但没有新增告警，以及多事件分别计数 |
| `case_graph_explorations` | id UUID PK；tenant_id/case_id UUID；base_kind TEXT(run/members)、base_run_id UUID NULL、base_scope_snapshot/graph_state JSONB；schema_version SMALLINT、row_version BIGINT、created_by/updated_by UUID、created_at/updated_at TIMESTAMPTZ。索引 tenant+case+updated_at+id | Case.observable_graph 没有独立探索身份／底图；历史工件不能随探索改写。选择具体 exploration_id 保存，不能自动覆盖历史图 |

正式记录的 JSON 快照须有来源路径、版本／hash、保存范围和缺失说明；现有真实执行材料可通过稳定工件引用复用，必要的人工作用内容要冻结。原问题／答复与编辑后结论分别保留；不可用截断文本冒称完整。超出保存合同的材料应明确拒绝或使用已有可回查 blob，不静默截断后返回“完整保存”。

新记录的主体键、类型、版本、保存时间和必要内容为 NOT NULL；选择性来源如 source_run_id 可空。创建／保存操作者由认证主体填写，历史迁移或用户删除后无法保持外键的情况须保留作者标签并明确空因，不能假填 system。保存后的内容不提供覆盖旧快照的 PATCH；如以后需要修订，另定修订合同。现 events 有数据库不可变触发器，不代表 artifacts／新表已自动具有同一保障，迁移与服务写权限需明确落实。

消息位于 JSONB，没有可直接 FK 的 message 表：保存入口须在同一 Case／会话内验证消息确实存在及对应关系，不能把这项写成数据库已经保证。可选源 Run、工件和任务也必须核同租户、同 Case 或明确允许的历史范围。

Case—事件表不在首批强加指向摘要缓存的外键：摘要未生成不代表事件不存在。来源事件派生集合和显式关联集合分别输出。移走最后一个成员是否自动解除显式事件关联尚待确定，不能靠重算 members 偷删关系。

图探索保留底图来源、候选来源、节点／边引用、展开状态／过滤／布局；base_kind=run 时必须有有效原 Run，base_kind=members 时固定成员基线。新结果到来不自动替换既有探索；重置才重新选底图。协作共享／个人探索策略后定，表通过独立 id 支持，不预先用 case_id 唯一锁死。

### 4.4 活动、响应、附件和不新增的表

- **活动复用。** Case 操作写 `case_timeline_events`；状态变化可继续用 `case_status_transitions`；普通 Case 评论留 `aisoc_case_comments`。实际改派／移动／任务完成存真实 actor、subject、时间、before/after、operation_id 和范围版本。两案移动在同一事务分别记账，历史 Run 不改。
- **批量目标不靠一个会裁剪的 JSON。** 复用 audit_log 的稳定 resource/resource_id：父事件记录操作身份，逐实际目标写子事件并绑定 operation_id；为关联查询增加必要表达式索引。Case 场景也可引用已保存的完整链接／范围活动，但不得只存目标数量。审计 writer 要支持保留关联键，脱敏／裁剪规则不能删掉唯一定位；不新建通用审计框架。
- **响应复用。** 结构化 recommendation 放新结果 JSON；approval.action 保存 recommendation_ref、真实目标与 origin_refs；动作 record 继续保存实际 receipt/status。不要为了字段对齐重写旧 incident_id，也不要把批准回执当执行回执。
- **附件不扩上传系统。** 当前工件 content/blob_ref/hash/size 足以表达已有调查材料；Case 的 artifact_ids 只是引用。任意附件上传、下载权限和保留策略属另行生产接入，不因页面列表而新增通用附件服务。
- **不新增** Case 成员第二真值表、任务版本总表、全局记忆库、每页统计表、每种调查各一套 Run 表。现有 JSONB 能承载的结果结构先定版本化合同，按真实查询需求再加索引。

## 6. 迁移和历史数据处理

1. **先核实际 schema 和现有状态。** 本文附只读 SQL 可核列／约束／索引／RLS；它不查告警原文或用户业务材料。本轮未执行。各环境迁移历史和实例级 schema 尚需核实。
2. **增量增加可空列与新表。** 保持旧请求／旧报告可读；新业务入口严格写新合同。新表 tenant_id 非空，使用 RLS 和同租户关系验证；跨表只有 UUID 外键不自动保证同租户，可为父表 `(tenant_id,id)` 加唯一约束并使用组合 FK。
3. **只回填能证明的事实。** 当前成员可建立迁移基线；历史 Run 输入不改。Case 来源明确的 Run 才补 case_ref_id；未知类型保持未标注。不能自动采用旧 summary、猜会话属于哪个 Case、用任务 updated_at 猜完成时间、用原负责人猜确认人。
4. **新旧负责人／标签逐步兼容。** 可精确解析的同租户用户才写 UUID，冲突保留两原值；旧字典标签保留，列表标签从新 namespace 读。业务状态映射集中在 adapter，不改历史枚举来凑原型文案。
5. **索引和约束按真实旧数据落地。** Run 单活跃唯一约束先排查旧冲突；不把 unknown 当完成。Case 对话只给明确新绑定的行加 case_id，旧通用会话不强行归档到某案。
6. **快照与引用保持。** 旧来源、r13 报告和前四批证据不重写；新合同标版本，旧缺字段返回缺失。新增字段不会使旧空查询或报告语义自动通过。

## 8. 需要产品继续明确但不阻塞字段整理的事项

- 多次成员变化怎样合并排队，基础更新和 AI 问题谁优先；失败／取消／未知状态如何恢复。先保存版本、范围及真实执行状态，不预先写成功。
- 仅移出成员、空案首次分析、已解决案新增／最后成员移走后的事件关联策略。
- 当前判断采用人／权限、冲突处理、需要重新确认的条件；目前可确定判断必须有范围、来源、确认事实。
- **严重程度口径冲突：** PRD 4.2 说事件取成员最高，7.3 又允许管理严重程度。需要明确是事件人工覆盖、还是修改成员严重程度；不能静默新增 override 并把它当既定规则。
- Case 生命周期原六态到页面三态的写入转换、审批后自动派发策略、生产协作权限和图扩展范围。已有用户 16 项规则继续沿用，未被新版明确改变的不重问。

当前建议无需 Case 文档记忆或向量库。共享上下文的实质是明确归属、实际输入、范围、来源版本及可回查快照；先把这些字段和出口接通。
