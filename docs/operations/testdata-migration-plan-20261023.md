## 2. 本次重新设计的目标

把已迁入工具补成可重复使用的小批测试流程：**选样本→生成材料→投正式格式的隔离Kafka→观察真实处理→读取结果→对照预期。** 测试工具仍在本地运行，业务代码沿现有服务运行；不新增常驻测试平台或另一套分诊/调查实现。

与原设计相比，必要调整为：

1. 正式输入已明确走Kafka，因此补raw Kafka发送路径；原HTTP send继续作为辅助工具保留。
2. 将观察终点从Fusion扩到分诊，以及需要调查时的实际编排/Markdown交付。分阶段执行，不把每个接线样本都送模型。
3. 保留实际输入、模型可见回复、工具结果与程序采用的差别。最近调查小修未部署，测试必须记录究竟用本地候选还是线上v1，不能混写结果。
4. 补可选场景及数据范围；新批次ID不代表模板实体、时间窗和知识背景都自动独立。

## 3. 数据材料与投放设计

沿用当前`manifest + payloads + expected`结构，增量内容只放测试工具侧；不改变生产API/消息协议/数据库表。

生成器现有`--run-id`是测试批次标记，不是业务调查Run UUID。观察材料应分别记录批次标记、输入Alert ID、canonical Alert ID与实际Run ID，并通过实际持久关系关联，不能把它们当作同一个ID。

| 材料 | 计划内容与使用方式 |
| --- | --- |
| manifest | 原来源commit/hash、模板、测试租户、批次标记、发生时间；增加选定场景、实际执行版本和已声明变换。保留旧格式读取能力，扩展版本在实施时明确 |
| payloads | 当前HTTP ExistingAlert输入；标题/事实/telemetry/来源引用，不含期望结论、期望MITRE或评分字段 |
| wire | 新增直接Kafka的实际JSON及hash。明确`identity_version=source-v1`、`source_alert_id=id`、tenant/source；按现RawAlert规则计算canonical预测，仅用来核对 |
| expected | 仅供发送后的评估读取：证据支持的期望、必须保持未知的事项、不应出现的断言、适用分支。模板原期待保留其来源，不伪造TP/FP标签 |
| send-receipt | 每条开始/ACK/unknown/未发送状态与topic/partition/offset；ACK只代表broker受理 |
| observed / assessment | 从实际Alert、Run、events、artifacts读取身份、分诊、调查完成度、报告、调用与已知用量；逐条列接线结果和内容复核，不只给总分 |

当前生成器的payload**没有**`identity_version/source_alert_id`，原HTTP入口负责填充。Kafka发送器必须补齐wire转换，不能把当前payload原封不动发出后假定属于source-v1。转换复用[现合同](../integration/v1/kafka.md)与现RawAlert身份逻辑，不重新发明canonical算法。Kafka发送不经过HTTP鉴权，不能把HTTP的租户绑定测试当Kafka授权已验；发送器只用显式配置的测试tenant、目标和现有Kafka认证方式。

CLI建议沿`alert_scenarios.py`保留`generate/send`，新增有界`send-kafka`；连接较多时用同目录小模块实现。生成器补按明确template/scenario选择，现有前N个模板行为继续兼容。发送只消费payload/wire，不读取expected，不直接插PG结果、不生产fused、不创建Case或自行启动Agents。

发送前验证输入hash/tenant/数量及wire格式，先落实际wire和待发送回执。沿原1—20条上限，第一轮只用3条；逐条等待ACK，未确认即停止并标unknown，应用层不自动重发。Kafka客户端可能在一次发送内部重试，不能承诺exactly-once；后续核ACK/原消息与source-v1身份，不能用新回执重投未知结果。

## 4. 场景与证据设计

首轮只安排最少代表样本；具体材料在实施时先审输入和独立答案，再发请求。

| 阶段样本 | 计划验证点 | 不作出的结论 |
| --- | --- | --- |
| 接入组：3条固定上游场景 | 新Kafka wire、身份、原字段传递、PG首次快照及fused输出 | 不进入模型，不评价攻击识别率 |
| 功能组A：来源事实和授权资料明确的例行业务 | 实际分诊依据、置信度与原关闭/升级策略一致，结果可查 | 不因为synthetic/test标签就要求关闭；模型不符合期望时保留失败 |
| 功能组B：可疑活动但授权/后续证据不足 | 自动升级条件满足时走完实际调查，缺源保持未知，停止可交接，最终报告可读 | 不要求“必定确认攻击”，零行不等于安全；未自动升级就不能写自动调查通过 |

功能组先用2条全新输入，逐例串行。先核程序所需输入和数据源条件，不靠反复投样本“刷出”期望分支。未覆盖的分支如实列出，是否追加由实际缺口决定。

**实体与时间：** 当前run-id只改变UUID/引用/标签，模板host/user/IP仍可能与旧批相同。隔离topic和Redis前缀可隔离接入组；进入图/历史检索后仍可能读到同tenant旧实体。功能组需限定测试tenant和查询范围，必要的实体/时间替换须记录原值→测试值，保证payload、telemetry和expected一致。外层event_time不能自动代表telemetry内部所有时间；不静默改写历史日志或上游原件。

**补查数据：** 把telemetry放进raw_event不等于ClickHouse/图/厂商查询中有对应记录。第一轮明确选“仅告警材料/缺源可交接”样本。若下一轮要验证检索命中，必须列出真实可查询来源、字段、实体、绝对时间窗和受控夹具写入方式；这是另一小步的数据准备，不借此重建已暂缓的raw事件采集/检测支路。替身工具响应只能证明调用接缝，不能代称真实查询结果。

**标签与评分：** 上游合成叙述本身含攻击解释，答案文件分离也不是盲测。功能用例先评价事实采用/未知保留/动作状态与实际调用，不报总体准确率。真实分诊准确率及Replay需要经审定的结案标签与冻结上下文，另批设计；Agent Quality没有期望工具/证据集合时显示未测，工具次数多不等于调查好。

**旧探针取舍：** `probe_testdata_ingress.py`保留为历史回执入口。它依赖旧草稿中的actor、私有env/CA目录和固定24930端口，不能直接变成新工具的隐式前提。新投放/观察显式接受本批配置，复用可验证的身份/快照核对逻辑；API/Fusion/Agents均叫`app`，联测保留独立进程，不在同一解释器混装三个服务。

**调用边界：** 沿当前角色、每次completion上限、Deep六轮及原时间/token/调用预算，不因测试而提高限制。功能组预计每例一次分诊、仅升级时最多六轮Deep，2例规划上限14次业务调用轮次；实际还受现有更紧预算约束。这不是14次底层请求的承诺：当前factory仅对triage显式设置retry0，Deep的SDK重试及网关回退须在实施前核实有效配置，另列底层尝试边界；无法确认就不能标为请求总数已受控。每次调用开始/响应/失败与usage单列，可观察的重试/回退另记；未返回保持未知，停止后不补调旧输入。预算不足就停止本批并留partial。此处是后续实施计划，不是本轮已发生调用或新的运行授权。

## 6. 结果怎么判定

每条例子分别给三项结果：

1. **数据交付**：输入、ACK、canonical Alert、PG/fused能否一一对应，材料是否保持。方法调用、替身或202/ACK不能单独算全链完成。
2. **流程执行**：实际是否分诊、关闭或升级，调查是否达到既定终点，Run/步骤/报告是否可读。Run completed仅代表执行结束，调查完整性读`graph_result.completion`及实际状态；已提交记录可冷读与运行中断点续跑是两回事。本批不增加Docker重启/故障恢复专项。
3. **内容采用**：原始模型回复与最终程序采用分开，哪些来源支持哪些结论，缺源/partial是否真实表达，是否虚构动作执行。原文错误即使被程序挡住也留在评估中，不计作模型原文通过。

预期内容不符合时保留案例和原因；只有接口/字段/接线导致功能不能运行的缺陷进入最小修复。更广模型效果、事件级分析、Fusion关联算法或编排调整另讨论，不能在测试工具迁移中顺带实施。
