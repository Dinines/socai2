# V2 告警、事件、Case 功能审计

日期：2026-10-29。范围：本机 `http://127.0.0.1:4174/` 当前 V2。**本轮只审计，没有修改前端、保存浏览器业务编辑或触发真实调查。**

## 1. 结论

**主阅读链路已经接通，操作后的状态和关系还没有形成完整闭环。** 告警可进入所属事件，事件可进入相关 Case，Case 可以打开指定 Run 的工具、图谱、记录和报告。当前优先处理的不是再次填充展示数据，而是启动调查、跨来源关联、操作归属和状态保存的一致性。

本轮记录 **9 项问题：P1 四项、P2 四项、P3 一项**。P1 表示应在继续演示操作闭环前优先处理；P2 表示影响状态解释、追踪或筛选可信度；P3 表示入口体验问题。没有据此认定生产故障、安全越权或后端数据损坏。

| 编号 | 优先级 | 功能 | 已确认的问题 |
| --- | --- | --- | --- |
| F01 | P1 | 告警发起 AI 调查 | 只新增告警自己的 Pending 记录，Case 和全局调查均看不到；文案却称已启动/已排队 |
| F02 | P1 | Case 移动成员 | 允许将当前21告警移入历史20 Case，但调查读取按来源过滤，成员和调查范围不一致 |
| F03 | P1 | Case 操作活动 | 无直接 incidentId 的 Case 创建任务，会把活动记到无关的第一个样例事件 |
| F04 | P1 | 告警管理 | Unknown 状态在弹窗默认变成“新建”；只改负责人再保存也会覆盖原状态 |
| F05 | P2 | 人工判定 | 误报反馈保存后仍为“进行中”，已确认的判定与关闭语义尚未接通 |
| F06 | P2 | 解决事件 | 成员告警状态随之关闭，但告警生命周期记录未同步，部分关联 Case 也看不到这次操作 |
| F07 | P2 | Case 筛选 | 重置后显示19条，地址仍是 `data=aisoc`，刷新又变7条 |
| F08 | P2 | 时间范围 | 默认显示“最近7天”但实际未应用日期条件；告警弹窗仍默认10月24日一天 |
| F09 | P3 | 失效链接 | 不存在的告警详情静默显示全量告警列表，没有提示目标已不存在 |

F05 是对既有“实际写回和状态同步待补齐”的直接复现，不作为本轮新增回归。F01 同时包含后端未接的既有边界，以及本地两套调查记录不互通的问题。

## 2. 样本和验证方式

| 对象 | 当前数量与来源 |
| --- | --- |
| 告警 | 67：52原设计、6当前socai2、6历史AiSOC20、3历史联合调查输入 |
| 事件 | 18：12原设计、3当前socai2、3历史AiSOC20；无源事件关系的告警不补造 |
| Case | 19：12原设计、3当前流程本地集合、3历史自动调查本地集合、1已持久化历史Case |
| Run | 15：2原设计、6当前socai2、6历史AiSOC20、1历史联合调查 |
| 已保存的实际运行材料 | 13Run、192条过程、90条工具记录、108项工件目录、11份报告；目录数量不等于完整正文数量 |

六个“本地整理 Case”是展示集合，源系统没有因此创建 Case。这里的真实处理结果来自既有测试输入；本轮没有重新读取20/21线上库存或验证其当前服务。

验证分三层：

1. **浏览器代表路径**：告警列表→侧栏→完整告警→所属事件→Case→指定Run工具；切换Run后保持tools视图；进入图谱、报告；打开历史联合调查图中告警及来源材料；核Unknown管理弹窗、筛选重置/刷新、日期弹窗、Case创建占位。所有保存业务数据的动作均未在用户浏览器提交。
2. **相同源码的隔离内存副本**：载入实际index脚本顺序，调用实际渲染函数和事件处理器。覆盖858个对象/视图组合，收集1095个不同本地链接；0渲染异常、0缺目标对象链接、0生成的Case链接引用范围外Run。这里不是858次浏览器点击，也不证明所有控件可用。
3. **既有检查**：`npm run check`通过、65项测试通过，包括既有告警呈现对照。新增审计探针复现下述状态变更；不改正式测试或业务代码。已有65项测试通过不等于操作闭环已通过。

隔离操作使用新VM、空存储、无网络、无实际localStorage写入；每个问题重新载入数据，避免测试之间互相污染。CSV仅捕获内存Blob，验证AiSOC筛选导出7行数据及表头，没有下载或外发。

## 3. 按页面区域盘点

### 3.1 告警

| 区域 | 当前功能和展示 | 本轮判断 |
| --- | --- | --- |
| 列表与筛选 | 名称、等级、告警时间、资产标签、处理状态、类别、检测源、受影响资产、负责人；搜索、等级/状态/我的告警、分页、自定义列、导出 | 表格可渲染、选中条目可开侧栏；时间范围见F08。上方统计是全量口径，不能当筛选后条数 |

| 关系入口 | 所属事件、所属Case、相关告警、实体 | 主链可跳转；真实有库存ID的实体才有资产入口，资产详情仍按已确认范围占位 |
| 概况解释 | Explain正文/建议、实体/IOC、ATT&CK、相似历史 | 是已保存内容；没有触发新Explain。建议、人工判定、原AI结论应继续分开 |
| 发起 AI 调查 | 关联Case后新增本地Pending记录，转到告警响应 | F01，不可作为实际调度或Case调查闭环演示 |
| 管理告警 | 负责人、状态、评论，本地保存后影响相关列表 | 普通字段处理器存在；Unknown保护缺失见F04。认领不应被当作已启动调查 |
| 判定反馈 | 四种人工判定、理由、应用到相似历史 | 保存判定存在，关闭联动未完成见F05；不能用人工反馈覆盖原始模型材料 |
| 时间线/响应 | 生命周期、自动处理过程、已有建议与调查材料 | 直接管理有历史记录，事件批量影响缺记录见F06；告警内Run与Case Run未统一见F01 |

## 4. 问题复现与建议

以下行号指审计时版本，源码目录均为 `prototypes/security-pages-v2/`。建议是后续修复方向，本轮没有执行。

### F01 — 发起调查没有进入Case/全局Run集合（P1）

- **复现**：当前FIN告警 `4c71eec2-77da-5b81-b68a-72801d55ea24` 已在Case中；隔离调用真实表单提交，submitter为investigate。
- **实际**：告警 `detailMaterial.runs` 新增 `run-demo-*`、Pending；历史写“告警启动调查”，stop称“调查已排队”。Case Run仍2条，全局Run找不到新ID，只转告警response并提示“已添加调查记录”。
- **影响**：用户以为开始调查，进入Case却找不到进展。不是已经成功提交后端任务再丢失，本来就没有后端调用。
- **建议**：先统一本地Run引用和诚实的未执行状态；真实启动需按后续后端合同单独承接，不能仅生成成功文案。已有只读历史Run不应被改写。
- **位置**：`alert-detail.js:83,90–92`；`investigation-workspace.js:4–21`。

### F02 — 允许跨来源移动，但调查按来源过滤（P1）

- **复现**：从 `local-socai2-7bde0c0b-0d18-4abc-9382-9752f2ae5e98` 选择FIN第一条告警，移到 `local-aisoc20-1`；在VM执行save-move。
- **实际**：源Case移除该告警，目标成员2→3，提示成功；目标环境aisoc20而告警来自socai2-21。目标调查仍2条，新成员对应Run被sameSource过滤。
- **影响**：案件资料/成员与调查材料互相矛盾，容易再次被理解为“AI数据不见了”。这是本地范围规则不一致，不是后端权限验证结果。
- **建议**：先统一可关联范围，至少按已确认环境/租户限制选择与提交校验；若未来允许跨环境案例，需要显式的新聚合设计，不能默认绕过读取保护。原Case对历史Run的引用保留是正常行为，不能为修问题删掉。
- **位置**：`app.js:374,493`；`investigation-workspace.js:16–21`。告警关联弹窗同样从全Case列表取候选，应一起核查，但本轮直接复现的是移动处理器。

### F03 — Case任务活动落到无关事件（P1）

- **复现**：在历史20 FIN Case `local-aisoc20-1` 的tasks页，通过实际submitTask创建一条内存任务。
- **实际**：任务和活动caseIds属于正确Case；活动incidentId却是原设计事件 `262144`（“涉及初始访问与数据外泄的多阶段事件”）。该Case当前成员实际关联 `85b81836-be47-4ab0-8c1f-6d360c5fb0a2`。
- **原因**：Case没有直接incidentId，logActivity用 `incidentId || currentIncident().id`；当前路由是Case，currentIncident查不到后回落到第一个事件。
- **影响**：Case操作污染另一个事件的处理活动。评论/管理等共用该函数，也需要同类检查；本轮逐步执行的是任务创建。
- **建议**：Case活动不应强制填某个事件。允许无事件或按明确的成员关系关联，不能用列表第一条作默认归属。
- **位置**：`app.js:48,84–88`；`workspace-view.js` 的submitTask。

### F04 — Unknown状态被管理表单静默覆盖（P1）

- **复现**：历史告警 `b940b6ec-766f-4ab9-ade1-d6fa3767e6a5` 详情为Unknown；浏览器点“管理告警”，状态默认“新建”。只读截图已留存并取消。VM按表单默认值只改负责人后保存。
- **实际**：状态Unknown→New，负责人更新；历史甚至出现“undefined → 新建”。下拉只有New/In progress/Resolved，无当前未知值或“保持不变”。
- **影响**：用户没打算改状态也会改变数据；将“来源未记录”错误变成确定业务状态。
- **建议**：单条表单保留未知值，未主动更改的字段不写入；不要通过把Unknown全局映射成New消除空态。
- **位置**：`app.js` 的manage-alert弹窗和 `save-alerts:439–443`。

### F05 — 误报/正常反馈没有按已确认规则关闭（P2，既有待实现）

- **复现**：对当前FIN第一条告警提交false_positive及理由。
- **实际**：disposition变false_positive，status仍In progress，仅新增人工判定历史。相似历史应用也只改判定和历史。
- **依据**：[页面讨论原则](ui-discussion-principles.md)已确认误报/符合预期正常行为关闭，同时明确实际写回与状态同步待补齐。
- **建议**：按已确认语义完善状态同步，保留原模型判定；本轮不另造新的人工关闭审批方案。
- **位置**：`alert-detail.js:88–89`。

### F06 — 事件操作的跨页记录不完整（P2）

- **复现**：VM对历史20 FIN事件填写解决说明并保存Resolved。
- **实际**：事件及两条成员告警都Resolved；两条告警各自history新增关闭记录均为0。生成活动caseIds为空，切到其关联Case activities查不到本次活动。
- **原因**：关闭循环直接赋a.status；关联Case仅用 `c.incidentId===inc.id`，没有沿当前成员核关系，而该本地Case的直接incidentId为空。
- **影响**：告警详情状态与生命周期解释不一致，Case也缺少关键处理动作。不是要求事件关闭必须同时关闭Case。
- **建议**：统一事件操作影响的关系查询，记录实际受影响对象及操作原因；保留Case独立状态，不自动关闭Case。
- **位置**：`app.js:448–461`。

### F07 — 筛选与URL不一致（P2）

- **浏览器复现**：打开 `#/cases?data=aisoc` 显示7；“重置全部”变19；刷新又回7。VM独立复现同样结果。
- **原因**：clear-filters只改内存tableState，地址仍保留data=aisoc，reload的readQueueLink再次应用旧条件。
- **建议**：来源、搜索及重置统一更新URL/视图状态；明确分享链接、返回和刷新能恢复哪些条件。
- **位置**：`app.js:467` 及readQueueLink。其他query参数共享同类机制；本轮直接验证data来源筛选。

### F08 — 时间范围标签不等于实际过滤（P2）

- **复现**：新载入Case时range=7，但start/end为空，19条全部展示，包括10月21日历史Case；最新Case创建于10月29日。
- **浏览器**：AiSOC筛选仍显示“最近7天”且包含10月21日；告警点“最近7天”，弹窗默认10月24日00:00至23:59。
- **原因**：默认标签未初始化实际区间；告警/事件弹窗仍有固定日期。Case预置以最新样例日期为终点已有明确说明，问题是默认条件没有应用，不是要求一定改成系统当前时间。
- **建议**：默认要么明确全部时间，要么应用真实7天边界；标签、弹窗、筛选条件和导出必须同一范围。
- **位置**：`app.js` 的tableState/filteredRows、`caseQueueTools:246`、`date-filter:370`。
