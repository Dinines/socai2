# AiSOC 页面讨论与数据对照基本原则

更新：2026-10-25。依据本轮告警列表、侧栏、详情、真实数据核对及前端交接讨论整理，供后续调查、事件、Case等页面讨论使用。

**核心约定：以已确认的页面设计为基础，以 socai2 当前已落地流程解释数据；逐个确认业务含义、实际来源和缺口。讨论取数不等于修改页面，已有页面也不等于后台功能已经实现。**

本文件整理已有决定，不授权新的清库、重放、模型调用、后端修改或部署。告警的具体展示规则只适用于已确认范围，不自动成为事件、Case或新版调查的全部设计。

## 1. 后续讨论的方法

1. **逐页、逐区域、逐元素核对。** 列表、侧栏、详情、操作弹窗分别看；一轮只处理用户指定范围。要求盘点告警table时，不顺带重做完整详情或其他页面。
2. **先讲业务含义，再说技术来源。** 例如“负责人”是分配给谁处理，“检测源”是原始日志来自哪个厂商/产品。不能只根据字段英文名、页面名称或自己理解建立映射。
3. **设计与取数分开。** 设计阶段可用样例展示完整功能，不按现有数据能力裁剪；字段盘点阶段只更新文档，除非用户同时要求改页面。后续明确授权接真实数据时，沿已确认设计适配，保留要求保留的原样例。
4. **以21上socai2当前已落地流程为对接基线，20原版作参考。** 本地源码、线上版本、未发布方案和历史回执分别注明，不能相互替代。引用旧样例时注明日期，不能把清理前ID说成当前库存。
5. **每个字段给出可核查的来源。** 写清环境/数据库/schema/表/列或JSON路径、关联键、展示转换、空值和一条实值。多个表关联须保持同租户，不能按接近的时间随意拼接。
6. **有歧义时只提出真正需要决定的点。** 先查已有源码、表、接口和讨论记录；用真实例子说明差异，再讨论业务选择。不要重复询问已经确认的事项，也不要自行填上结论。
7. **用户要功能描述时，就说明功能及边界。** 例如相似告警、资产关联、负责人管理，后端具体算法和表设计交由对应开发处理；不擅自增加本轮实现要求。
8. **验证和汇报按实际发生的事写。** 接口成功、模型返回、程序采用、数据库落库和页面展示分开核对；不能因为“能打开页面”就宣称流程或结论正确。

## 2. 本轮用户纠正过的问题

| 曾出现的问题或误解 | 用户纠正后的口径 | 后续应遵循的原则 |
| --- | --- | --- |
| 参考文档后自行扩展，或只做一个具体详情 | 对照图片和正文；事件、Case都有列表入口；无关侧边栏只留名称 | 参考图片确定布局，正文确定交互；入口到详情要完整，范围外不发挥 |
| 数据盘点时改掉原设计、替换原样例，加上“21数据快照”等标签 | 恢复设计稿和原数据，新增可保留；缺口写进文档 | 技术核对信息不塞进产品界面，不把数据核对变成UI重设计 |
| 同名或近义信息重复堆叠 | 合并相似功能；概况删除已有页签入口和重复描述 | 同一信息有清晰主位置，避免多套入口和重复区块 |
| 用告警标签代替资产标签，把受影响账户和负责人混为一谈 | 标签取资产表，账户可作为受影响对象，负责人是被分配的处理人 | 先分清对象归属，再确定表字段 |
| 没有同名字段，就认为拿不到来源 | 检测源可以来自Fusion保存的JSON，而非必须是alerts独立列 | 检查实际数据结构；字段缺失、值为空、接口没暴露是不同问题 |
| 自动分诊、分配、启动调查和完成都混成一个状态 | 自动分诊和分配不代表进入人工处理；实际启动调查算进行中 | 状态必须反映已确认的业务流程，不能根据一个动作名称猜测 |
| 混用Fusion置信度、AiSOC分诊评分、Graph置信度 | 分诊0.85就是AiSOC评分；不能换成别的模型或上游分值 | 每个分数标清来源、量纲和含义，不用一个分数替代另一个 |
| 把Explain“未来提前生成”当成当前接入前提 | 当前按已有请求接口调用，取其返回内容 | 用当前可用方式接入；未来方向不阻塞当前，不冒充已落地 |
| 将“待核实事项”列为固定字段或必补功能 | 可能只是Explain正文的一部分，取决于实际返回结构 | 不从自然语言强拆新字段，不为填版面要求模型固定输出 |
| 给Case关联加过多常驻控件，关联已有Case还显示新名称 | 通过弹窗和两个页签选择；已有Case禁用新建 | 只呈现当前选择需要的输入，状态和可用操作一致 |
| 把模型建议、自动处理过程、响应执行混在一起 | Explain正文和建议同放“发生了什么”；响应页保留过程与响应详情 | 解释、建议、审批、执行结果分别表达；建议隔离不等于已隔离 |
| 时间线方向、表格排序标识或列宽不稳定 | 最新在上；仅告警时间和严重程度排序，时间第三列、等级第二列，列宽固定 | 保持阅读位置稳定，排序标识与实际能力一致 |
| 相关告警只有名称，缺少判断上下文 | 每条保留严重程度和时间 | 关联列表要能支持初步判断和跳转，不能只有标题 |
| 浏览器表现不同便急于改页面 | 用户指出内置浏览器和Safari正常，并判断Chrome问题可能与缓存有关 | 先确认相同地址、版本和缓存，再定位交互；不把猜测当已证实根因，不据异常表现改掉已确认设计 |

## 3. 数据缺口怎样描述

| 情况 | 正确表述 | 不应得出的结论 |
| --- | --- | --- |
| 字段有，但本条为NULL | 本条尚未分配，assigned_to_id为空 | 系统没有负责人字段 |
| 资产表有，但告警没关联到库存 | 缺资产匹配关系，原始主机/账户仍可展示 | 没有资产表；或直接伪造资产ID和标签 |
| 没有独立同名列，但JSON有值 | 记录准确JSON路径、来源语义与限制 | 完全没有检测源数据 |
| 库中有值，列表API未返回 | 后端需补响应字段或关联读取 | 前端改字段名就接通了 |
| 工具查询失败或只有摘要 | 查询失败/返回受限，完整性不足 | 没有相关活动；或已拿到完整证据 |
| 历史样例、模拟输入的真实处理结果 | 明确是测试输入及实际运行结果 | 真实攻击；或与原样例混成线上业务统计 |

缺口、空值、接口未接、待确认规则写入对照文档，标明由谁补。真实数据展示不造值；这不意味着要把原设计样例中的标签、负责人全部清空。产品正常空态可保留，不额外添加“Mock”“快照”“缺口”等工程说明标签。

## 4. 告警页已确认的具体约定

这些约定供后续保持一致；其中列顺序、展示分组、条数和布局只约束当前告警页。其他页面若表达同一业务含义应复用语义；若表达不同含义，应单独说明，而不是直接复用名字或分数。

### 列表、侧栏和字段

- 导航归属统一为“告警和事件”，告警、事件分别进入列表；Case也有独立列表入口。
- 告警主表九列：名称、严重程度、告警时间、资产标签、处理状态、类别、检测源、受影响资产、负责人。只允许严重程度和告警时间排序，列宽固定。
- 严重程度：Critical/High→高，Medium→中，Low/Inform→低；canonical中info及兼容拼写按已核对映射处理。显示分组不改写数据库原值，不把这一分组直接套到其他评分。
- 告警时间取event_time，按北京时间展示、保留原始精度排序；不静默把入库时间created_at当发生时间。列表和时间线默认最新在顶部。
- 资产标签属于关联资产，例如Windows域控、文件服务器、Web服务器；不能取告警tags替代。“类别”按MITRE战术标签理解，不是被删除的“分类”。
- 检测源的业务含义是日志原始厂商/产品。当前Fusion identity.source是可读来源标识，但测试来源或中转平台不一定能表示原始厂商，差距要明确。
- 受影响资产显示库存名字；告警中的账户名也可显示。负责人是分配给哪个用户，可暂留空，由后端管理。原始主机/账户不等于已存在的资产库存对象；有实际库存ID才跳相应资产详情，当前资产页仅大标题占位。
- 列表侧栏只保留概览；分类、相关事件/处理记录页签、查看相似告警入口已去掉。完整详情仍保留相关告警，不能因侧栏删除而全局删除。
- 快捷筛选放在筛选行，与原工具栏功能共存；包括等级、状态、全部告警/分配给我。“我”最终指当前登录用户，不能把原型固定账号当作后台身份。

### 状态、评分与对象关系

| 概念 | 已确认口径 |
| --- | --- |
| 处理状态 | new/triaging/triaged归新建或待处理；in_progress/investigating及实际启动调查归进行中；resolved/closed归完成，当前界面沿用“已解决” |
| 认领/分配 | 只分配负责人不自动改变处理状态 |
| 执行结束 | Run completed只表示本次运行结束，不等于告警关闭；调查partial不等于完整完成 |
| 判定反馈 | 认为误报、符合预期的正常或授权行为则关闭，其他不变；保留原有反馈交互，不另造“保存判定”流程。实际写回和状态同步仍待补齐 |
| 人工直接关闭 | 额外流程待定，不能把原型按钮当作最终业务审批设计 |
| 检测置信度 | 当前告警页取Fusion的alerts.confidence |
| 当前风险评分位置 | 取AiSOC分诊alerts.ai_score，例如0.85展示85；不改取上游risk_score或Graph confidence |
| 告警/事件/Case/Run | 告警应属于事件，可以没有Case；无Case也可有自动调查Run。业务Case关系与Run拥有者ID分别核对，不能仅见run.case_id就认定关联了Case |
| 创建/关联与启动 | 关联成功不自动代表调查已经启动；失败或未启动须分别说明 |

本批用graph_step证明部分告警已进入调查，是样例的取证方法，不是要求所有未来入口只能靠这个事件判定。历史未知status枚举、不同评分尺度和新的调查语义仍需按实值讨论。

### 详情、Explain与响应

- 告警完整详情为概况、时间线、原始数据、响应。原Overview有用信息迁入并合并重复项，自动处理过程放在响应中。
- Explain沿当前请求接口使用；将实际返回summary及建议动作一起放在“发生了什么”，按已有结构选取内容。无建议时留空，不固定生成动作或“待核实事项”功能。
- Explain建议与调查响应建议可以有不同来源，应标清对应内容；建议、审批要求、执行及执行结果不能混写。本批离线包只展示保存的Explain返回，不能称其会实时请求模型。
- 时间线描述发生、检测、取证、调查启动、分配、关闭等生命周期；只有已有记录才能作为真实活动展示，不造时间或补步骤。
- Case关联默认进入“关联到已有”的弹窗页签，展示最近活跃7条并可按名称/ID搜索；无Case可切换新建，新名称默认告警描述；已有Case禁用新建，不展示可编辑新名称。
- 相关告警：同主机最近发生7条，保留等级和时间。反馈中的相似历史复核：按同主机同战术、同IP/文件哈希IOC查最近5条候选。只规定候选方向和查看最近记录的功能，不在本原则中新增固定“5+5”、合并或去重规则，具体检索实现交后端；原型只覆盖已加载数据，不等于全库检索。

## 5. 进入调查、事件等页面时怎样继续

先列出该页所有区域和已有交互，复用当前视觉风格。对每个元素按下面格式讨论，先查能查到的材料，再集中提出缺口或业务歧义：

| 项目 | 每次需要说清楚的内容 |
| --- | --- |
| 页面位置 | 哪个列表列、卡片、页签或按钮，本次是否允许修改页面 |
| 业务含义 | 用户通过它要理解或执行什么 |
| 当前来源 | socai2环境、表字段/JSON路径或实际接口结构，以及必要关联 |
| 转换 | 原值如何成为文案、分组、排序、统计；量纲/时间/空值处理 |
| 操作效果 | 点击对象、目标范围、是否写回；关联、启动、审批和执行分别说明 |
| 一条实例 | 同一个真实对象的原值→页面值→关联结果，注明记录日期 |
| 缺口/歧义 | 是缺字段、缺关系、未暴露接口、未实现流程还是需用户决定 |
| 本轮结论 | 已确认/待讨论/后端待实现；不要把讨论稿记成已交付 |

在调查页尤其要核对：调查针对哪个告警/事件/Case及成员范围、哪次Run、实际查到什么、得出什么结论、为什么停止、哪些动作只建议或确实执行。**这是后续核对清单，不是本轮新定的调查页面方案。**

仍需后续细化的事项包括：事件和Case整页取数与汇总、Case成员与调查范围、负责人/资产关系的后台承接、人工关闭、反馈写回与状态同步、响应审批执行。不能把先前只要求“描述一下功能”的部分说成规则已全部确定。

## 6. 交付与依据

每轮保存最新结论、真实例子和仍待补齐的内容。文档核对不修改页面；用户要求实现时再按所定范围落实，不额外为低风险已授权修改设置确认步骤。涉及用户明确要求先讨论的后端设计/源码变动，应先说明具体变化。

前端交接保持一个可整体转发的文件夹，README说明入口和启动方式，页面、静态资源、对应字段说明和数据一起交付。区分本地交互、真实服务读回和后台写入，不能把浏览器内的操作演示称为服务端已完成。
