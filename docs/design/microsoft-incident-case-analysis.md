## 2. 产品之间是什么关系

### 2.1 Defender、Sentinel、Security Copilot

这里参考的是Microsoft Defender门户中的安全运营体验，不是Windows桌面“Windows安全中心”。Defender XDR汇集终端、身份、邮件、云应用等产品的检测与调查信息；Sentinel可以提供其他日志、检测规则、分析查询、自动化和数据湖/图能力。门户提供共同工作界面，但每项功能仍有自己的数据、许可、接入和权限条件。

例如，传统事件图的Blast radius说明使用Sentinel数据湖和图基础设施；用户异常查询选项依赖Sentinel UEBA；查看某个设备的完整资料会进入相应Defender产品的资产页面。不能因为这些按钮出现在同一页，就认为它们由同一后端或同一模型完成。

Security Copilot提供摘要、辅助查询、引导及报告等能力。普通材料列表和关系查看不必每次生成模型结果；官方也使用“when available”限定摘要等功能。页面显示的摘要不能代替告警、证据和实际执行结果。

### 2.2 Incident与Incident Case

传统Incident用于组织相关告警和调查上下文。新版Incident Case在同一安全事件处理过程中加入任务、协作、期限、结案等工作管理。该版官方文档中Incident Case仍为Preview，传统事件体验同时保留。

**不能将两种微软页面简单解释为固定的“事件→再创建Case”两级对象模型。** 官方新版Case是事件处理体验的演进，保留与相关Incident的联动。socai2的事件、Case、Run关系应按自己的业务另行确定，本轮复刻不改后台关系。

Generic Case用于一般SecOps工作，与Incident Case不同。本地保留Generic目录名称，不在本轮开发Generic模块。Cases位于Defender门户，不能把它说成Azure门户传统Sentinel事件页的相同功能。

### 2.3 四种不同的信息

| 信息 | 回答的问题 | 例子 |
| --- | --- | --- |
| 检测/观察 | 发生或检测到什么 | 邮件告警、进程执行、异常登录 |
| 关联/上下文 | 为什么把对象放在一起 | 同一用户、同一文件、相关时间和行为 |
| 判断/建议 | 如何理解、下一步做什么 | 可疑、恶意、需要进一步核查、建议隔离 |
| 操作/结果 | 实际做了什么、是否成功 | 已批准、隔离执行中、执行失败、已完成 |

本表是基于官方功能组织的产品分析。其价值在于让界面可核对，而非为模型新增固定输出字段。

## 3. 事件列表与详情

列表是选择工作对象的入口：展示名称、重要程度、状态、负责人、时间和关联材料计数，支持搜索、筛选及预览。点击行预览只查看摘要；点击标题进入完整上下文。

详情的核心是**以该事件所含告警为基础，把告警及其相关信息汇总展示，并能回到来源**。

| 区域 | 展示内容 | 用户目的 | 范围/语义 |
| --- | --- | --- | --- |
| 头部/事件资料 | ID、名称、等级、状态、负责人、分类、标签、时间与描述 | 确认正在处理哪个事件 | 事件属性不等于某条告警属性 |
| 攻击故事 | 告警序列、关系图、选中对象详情 | 理解顺序、关联与上下文 | 依据已有材料，不凭名称推定完整因果链 |
| 告警 | 所含告警、等级、来源、资产、时间、状态及关联原因（可用时） | 核对组成、进入单条详情 | 成员关系与临时筛选分开 |
| 活动 | 分配、变更、审批、自动流程、执行结果 | 看人和系统做过什么 | 是处理历史，不是攻击行为时间线 |
| 资产 | 设备、用户、邮箱、应用、云资源等 | 查看涉及的对象 | 关联对象不一律等于已被攻陷 |
| 调查 | 关联告警触发的自动调查、详情与处置状态 | 看调查工作及结果 | 没有记录不补写调查，执行结束不等于完整成功 |
| 证据与响应 | 文件、进程、IP、邮件等；判定和处置状态 | 核查依据并审阅处置 | 判定、审批、执行状态分开 |
| 建议动作 | 下一步建议、相关待处理事项 | 决定后续工作 | 建议不是已执行；产品工作负载可能有不同入口 |
| 概览 | 告警/战术分布、对象范围、时间摘要、证据和属性 | 快速掌握全貌 | 汇总必须能回到具体材料 |
| 相似事件 | 相似告警、实体或属性的其他事件 | 找相关线索、扩大调查 | 相似不是已确认同一攻击，也不是已合并 |

官方特别说明：部分Office 365调查不出现在Investigations页签中，应从关联告警进入；证据和待处理动作分别在对应页签。不能仅用某一列表为0断言“没有调查”。本地演示不接真实工作负载，不据该规则伪造调查记录。

## 4. 图谱背后的逻辑

### 4.1 图的范围与焦点

打开事件，先确定事件上下文；点击某条告警或某个实体，只改变当前聚焦对象。聚焦不等于改变事件成员。当前事件、关联事件视角、某实体的全局资产页分别有不同范围，需要在界面中保持可辨认。

官方关联文档说明，选择“This incident only / All associated incidents”会扩展可见上下文，**不改变事件分组、关联规则或合并逻辑**。被显示的其他事件仍可拥有自己的负责人、状态和生命周期。

### 4.2 节点、边与标记

| 元素 | 官方含义 | 不应解读为 |
| --- | --- | --- |
| 实体节点 | 设备、用户、IP、应用、云资源等 | 每个节点都是一条告警，或都已经被攻陷 |
| 分组节点与数字 | 多个实体的折叠表示及实体数 | 多个真实身份合并为一个，或数字必然是告警数 |
| 关系线/方向 | 特定关系，如成员、运行、权限、认证、流量等 | 所有箭头都表示攻击者已走过该路径 |
| 同一边上的数字 | 两对象可能有多个关系，侧栏可查看 | 攻击次数或风险评分 |
| 关键资产皇冠/光环 | 业务重要性分类 | 该对象已确定恶意 |
| 漏洞标记 | 对象发现了漏洞 | 攻击者已成功利用 |
| 发现来源图标 | 发现/保护该实体的产品来源 | 一定是该条告警的原始厂商 |
| 扩展标记 | 在适用图中探索更多连接对象 | 自动把扩展对象加入案件 |

“拥有访问权限”“存在网络连接”“已观察到数据传输”是不同关系，必须由具体关系详情解释。仅两节点同在某条告警中，可以表达“共同关联该告警”，不应提升为“实际进行了横向移动”。

### 4.3 按钮与点击行为

| 操作 | 可见变化 | 产品含义 | 是否改变业务对象 |
| --- | --- | --- | --- |
| 切换事件/Case | 成员及相关材料切换 | 选择另一个工作范围 | 否 |
| 点击告警 | 聚焦其相关实体并查看检测详情 | 以单条检测核对事件上下文 | 否 |
| 点击节点 | 打开实体资料/相关告警/适用动作 | 从检测视角切到对象视角 | 否 |
| 点击关系 | 查看连接语义、来源等 | 追问“为什么连在一起” | 否 |
| 所有关联事件 | 增加关联上下文 | 扩大可见范围 | 不合并、不转移告警 |
| 等级/状态/来源筛选 | 减少显示的告警与对象 | 聚焦关心的部分 | 不删除成员 |
| 实体类型显隐 | 隐藏/显示某类节点 | 降低图的复杂度 | 不排除其风险 |
| 分组/取消分组 | 折叠或展开实体 | 降低视觉负担 | 不合并身份 |
| 布局/缩放 | 位置与比例改变 | 改善阅读 | 不改变关系、评分 |
| 时间回放 | 按已记录时间显示告警/对象 | 看已有记录的先后 | 不重跑模型或攻击 |
| 查看影响范围 | 展示从选中实体到目标的可能路径 | 评估潜在影响 | 不代表实际已受影响 |
| Go hunt/进一步查询 | 查找实体相关活动或告警 | 获取更多材料 | 查询本身不自动改成员 |
| 打开完整资产页 | 查看更完整资产历史 | 离开事件局部视角 | 否 |
| 移动告警/合并 | 改变归属/事件组织 | 管理调查范围 | 是 |
| 隔离/删除/批准处置 | 提交实际响应流程 | 改变目标状态 | 是，需结果记录 |

### 4.4 攻击故事与潜在影响

事件图组织现有告警和实体上下文；Blast radius探索从选定节点到重要目标的可能传播路径。官方说明后者依赖Sentinel数据湖/图和权限，受数据覆盖、时效、已建模攻击方式与可见范围影响。没有路径可能是数据不足或范围限制，不能直接判定安全。

说明性例子（不是生产证据）：事件含钓鱼邮件、异常登录、脚本执行三条告警。点邮件告警检查邮件与收件人；点用户看其相关告警/设备；点影响范围发现该用户能够访问财务服务器。财务服务器此时是潜在目标，不能自动写成“已被攻陷”。筛掉低等级邮件告警也不能声称攻击从脚本执行才开始。

### 4.5 公开与未公开的关联逻辑

官方说明会考虑实体、工件、时间和多阶段行为，将告警加入新/已有事件，并持续发现跨事件关联。具体阈值、权重、命名和合并方向逻辑属于微软内部实现，本文不反推或仿造其算法。

Sentinel工作区关联亦有条件：所读版本描述主工作区可与Defender告警关联，其他工作区保持独立。此处用于解释功能为什么受接入条件影响，不作为socai2的新需求或当前环境事实。

## 5. Case工作区

| 区域 | 内容与功能 | 业务意义 |
| --- | --- | --- |
| 概览 | 优先级、描述、ID、时间、负责人、状态、材料概况 | 支持快速接手 |
| Summary by Copilot | 功能可用时汇总已有上下文 | 降低阅读成本，仍可回查来源 |
| Attack graph | 告警、实体、关系、时间与可用的影响范围 | 理解关联并聚焦调查 |
| Alerts | 成员告警明细、筛选、详情、移动 | 查看和管理范围 |
| Assets | 各类对象及详情 | 从对象维度调查 |
| Investigations | 自动调查及处置进度、待处理项 | 查看调查工作 |
| Evidence | 证据类型、首次发现、判定、来源、受影响对象及处置状态 | 支撑结论并追踪响应 |
| Activities | 创建/分配/状态/分类/任务/评论/自动化变化 | 审计与交接 |
| Comments & Attachments | 备注、决策、交接、支撑文件及下载 | 保存协作上下文 |
| Tasks | 责任人、状态、期限、说明、完成结果 | 把工作分成可追踪事项 |
| Manage case | 名称、责任、状态、等级、分类、标签、到期时间、结案说明等 | 管理工作生命周期；字段受租户/模板影响 |
| Agent sessions | 有条件开放的Agent会话及输入/输出/过程/报告 | 把一次执行记录关联到长期存在的案件 |

官方新版Case关闭会同步相关Incident，但**不会自动关闭关联告警**；告警保留各自状态。不能把传统事件页或历史原型的关闭联动照搬到Case。本轮本地Case管理不改告警；完整后台Incident联动仍不属于本轮。

Case不等于Run。某次调查结束后，案件仍可待处理；同一案件可以有多次调查。报告属于某次运行的交付材料，案件概览是对当前上下文的组织，两者不能互相替代。

官方正文没有充分说明Similar cases的算法/完整交互。当前仍保留目录，不自行扩成相似案件模块。Agentic playbook有Project Perception等可用性条件，当前不做可执行假按钮。

## 6. 本地原型的对齐范围

保持已确认的白色紧凑工作区、事件横向页签、Case左侧目录、原事件/Case样例和所有告警入口。新增内容属于前端演示，不证明后端具备微软能力。

1. 图谱由显式的样例关系支撑，能解释节点/边来源；实际六条告警不添加虚构材料。
2. 点击、筛选、分组、回放均保留范围语义；潜在路径单独表示；无记录正常空态。
3. 查看关联事件不改成员；相似事件按已有样例共享实体给出具体线索，不能宣称使用微软算法。
4. 调查按样例告警ID归属，执行完整性和处置状态分开；Case成员变化后重新计算相关材料。
5. Case任务与管理以本地保存实现；告警处理状态保持；评论/附件沿现有交互保留。
6. 不新增真实查询、模型、部署、消息发送或真实处置；不改告警列表、抽屉、详情的现有呈现和管理行为。

## 7. 评估结论及后续讨论

微软把安全运营分为四个连续环节：选择工作范围→查看/关联证据→开展调查与处置→跟踪协作和结果。这是本文对官方产品结构的归纳，不是微软公开的一套后台编排算法。

事件适合承载“这些告警及其上下文的汇总”；Case适合承载“如何组织这些材料和处理工作”。具体在socai2中是否保留两种独立对象、如何继承成员、何时启动调查，应按既有设计另行讨论，不由页面复刻替后端定案。

后续每个元素按“对象范围、来源、展示转换、点击效果、空态、是否写回”核对。尤其避免把关系当因果、把关联对象当已受影响、把建议当执行、把运行结束当完整调查或结案。

实施与验证记录见本轮OpenSpec `align-microsoft-incident-case-workspaces`。本文件是分析及目标范围，功能完成以执行回执为准。
