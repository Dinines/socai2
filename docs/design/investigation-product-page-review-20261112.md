# 调查产品页面功能梳理与遗漏评审

2026-11-12，产品评审稿。面向产品、设计、前端和业务后端，范围为告警、事件、Case 和调查运行。下文梳理既有设计，不新增平台模块或承诺开发排期。

**页面划分基本完整，现有功能清单对设计意图的表达还不够完整。** 主要问题是把若干独立的用户操作合并成字段读取条目，弱化了“为什么有这个页面”“点击后改变什么”“与其他页面如何衔接”。部分产品规则尚未确定，另有交付状态过时。不能把这些问题全部归为缺接口，也不能用已有表或接口说明产品功能完成。

依据为当前[产品需求](alert-incident-case-product-requirements.md)、[已确认讨论原则](ui-discussion-principles.md)、[F01至F28及跳转清单](../../deliverables/investigation-validation-20261106/frontend-feature-list.md)和[当前交接](../../FRONTEND_BACKEND_HANDOFF.md)。本轮实际查看本地原型的告警列表/详情、事件概览、Case资料/故事/概览/关系图/证据/任务、助手和单轮五个视图；其他页按需求与页面源码核对。这是产品功能审阅，没有提交业务表单或重新验收生产功能。

## 产品主线与页面分工

分析员先从告警判断是否值得跟进，再从事件理解多个告警为什么相关；需要持续核查时进入Case，组织成员、执行调查、补充人工事实并形成当前判断。每轮调查保留当时的输入和结果，供后续复核及交接。

| 工作对象 | 用户要回答的问题 | 应承担的工作 |
| --- | --- | --- |
| 告警 | 这条检测发生了什么，判定是否合理 | 阅读检测与原文、查看分诊、给人工反馈、认领或关联Case |
| 事件 | 这些告警为什么放在一起 | 展示成员、时序、共同对象和归并依据，组织处理，进入Case深入调查 |
| Case | 目前知道什么，还缺什么，接下来由谁做什么 | 维护正式范围、当前判断、调查、人工任务和协作记录 |
| 单轮调查 | 这一次具体查了什么，产出了什么 | 展示固定范围、结果、依据、过程、限制、报告及实际回执 |

资产、身份、日志和知识等是本流程使用的外部资料来源。调查页需要说明如何阅读或引用它们，不因此承担资产台账、采集、知识管理等完整平台功能。

## 列表入口

| 页面 | 有哪些功能及作用 | 为什么需要 | 产品边界 |
| --- | --- | --- | --- |
| 告警列表 | 统计概况；按名称、时间、等级、状态和负责人查找；排序、分页、列选择、导出；侧栏预览；进入详情；选择后管理 | 在大量告警中安排处理顺序，减少逐条打开的成本 | 全量指标、筛选结果和当前页数量分开；“分配给我”指当前用户；导出范围、批量操作范围须明确 |
| 事件列表 | 查看活跃、待分配、近期有新告警及高严重度事件；筛选、预览、查看成员规模和负责人；进入事件详情 | 按相关告警集合安排处理，识别需要接手或继续跟进的事件 | 事件数不能写成告警数；当前设计指标不随表格筛选变化，需有范围说明 |
| Case列表 | 待分配、处理中、高严重度、待人工跟进四指标；条件搜索、分页、预览及进入案件；设计中的创建和管理入口 | 帮负责人安排案件工作与人工跟进 | 待人工跟进按案件去重；当前服务已接队列和建案等合同，不能据此推定全部列表按钮完成 |
| 调查运行列表 | 跨主体查找已保存的调查记录；辨别父主体、类型、状态和时间；进入指定一轮 | 在不知道案件位置或需要复查某次运行时直接定位 | 需求和清单均提到该入口，但导航位置、列表字段及筛选功能未像前三个列表一样展开；属于清单待补项 |

告警列表既有九列、仅时间和严重程度排序等约定应保留；不能把产品需求中较宽泛的“标签、调查状态”等文字直接理解为又增加常驻列。需要明确默认列、可选列和详情信息分别是什么。

## 告警详情

| 页面或区域 | 功能做什么 | 为什么需要 | 操作结果与边界 |
| --- | --- | --- | --- |
| 公共页头和管理 | 展示等级、状态、负责人及分数；认领、分配或修改已允许的管理信息 | 明确处理责任和当前进度 | 告警分配不自动等于开始调查；分数要说明是检测置信度还是AI分诊置信度 |
| 概况 | 展示“发生了什么”、解释、关键依据、建议、检测规则、战术、实体和IOC、告警属性 | 让分析员先理解检测及判断理由，再决定是否深入 | 展示已有材料；建议与执行分开，缺少内容不为凑版面补造 |
| 概况中的相关告警 | 展示相关候选的名称、等级、时间和关联原因，逐条打开核查 | 判断单条告警是否属于更大的活动 | 相同对象只是关联线索；本机已加载候选与后端全库检索的范围需要区分 |
| 判定与反馈 | 选择真实威胁、误报、正常行为或需人工跟进，填写理由；选择相似历史记录复核 | 沉淀分析员判断、修正误判并交接依据 | 人工意见与原AI结论分别保留；误报/预期正常关闭告警是既有目标规则，正式告警反馈写入未完成；相似记录不能被自动批量改判 |
| 时间线 | 按真实时刻查看发生、检测、分配、调查、反馈及关闭等已有记录 | 复核处理经过，理解先后顺序 | 未发生的操作不生成条目；案件故事与单告警生命周期不同 |
| 原始数据 | 阅读收到的原文、标准化字段、来源标识及材料版本 | 核验解释是否忠于原始材料，便于调查和交接 | 回看历史调查时应定位当时版本，不能用最新原文替代 |
| 响应 | 查看已有自动处理、关联调查、建议及真实响应回执 | 从单告警追到处理结果，确认是否真正做过处置 | 没有Case也能阅读已有分诊/自动处理；没有执行回执不能写“已隔离” |
| 关联Case与准备调查 | 根据零个、一个、多个关联Case，创建/关联或选择目标案，再带入告警上下文 | 将需要继续核查的告警送入正确工作区 | “关联到”只改变关系；原型“准备调查”可能打开助手，不等于基础调查已经启动，清单须分别描述 |

## 事件详情

| 页面或区域 | 功能做什么 | 为什么需要 | 操作结果与边界 |
| --- | --- | --- | --- |
| 公共页头和管理 | 分配负责人、调整事件严重程度/状态/标签、记录解决说明；进入已有Case或创建/关联 | 让集合有明确处理责任，并衔接深入调查 | 事件分配后进入处理中；已解决事件改负责人不自动重开。这个规则与告警不同，不能共用一套默认联动 |
| 事件概览 | 展示事件说明、成员和资产范围、发生时间、战术覆盖、共同对象与告警时序；查看诊断和尝试入口 | 回答是什么、为什么相关、是否值得进一步调查 | 共同主机和时间相邻不等于确认攻击因果；已发布诊断与本次失败尝试应能分别阅读 |
| 关联分析 | 在当前事件内查看告警、实体、连线及依据；筛选、聚焦、打开详情 | 让“为什么归并”可以核查 | 固定当前事件范围，不承担跨事件探索或另建一套Case调查 |
| 成员告警 | 查看组成事件的告警及等级、时间、状态、对象，开预览或进入完整告警 | 从集合结论回到单条事实，检查是否误关联 | 使用真实成员关系，不能按相似标题拼成员 |
| 涉及对象 | 按主机、账号、IP等查看来源告警；有库存映射时进入资产详情 | 理解集合涉及哪些对象并回查来源 | 来源对象与库存资产分开；没有库存关联仍能阅读观察到的对象 |
| 处理活动 | 查看谁在何时修改了事件、成员或处理信息 | 支持交接和复核管理变化 | 与告警发生时间线、模型执行步骤分别表达 |

## Case的十个页面

公共页头保持当前案件身份、状态、负责人和关联事件，并提供添加成员、询问AI、管理等对应入口。一个按钮是否可用应取决于当前能力和案件状态，而不是因为原型上出现过就视为已完成。

| 页面 | 有哪些功能及作用 | 为什么单独存在 | 关键结果和边界 |
| --- | --- | --- | --- |
| 案件资料 | 案件背景；当前采用判断、依据、形成时间和覆盖；未解决问题；成员/对象概况；管理信息与战术覆盖；进入故事或调查 | 新接手的人先理解“这个案子是什么，目前怎么看” | 当前判断不是最后一条回答；新增成员未必被旧判断覆盖；依据变化后保留旧结论并提示需要更新 |
| 案件故事 | 按时间串联告警、调查结果和人工完成事实；搜索/筛选；选择一条或多条告警；查看详情及共同对象；围绕所选内容提问 | 解释“事情和认识怎样发展到现在”，帮助提出下一步问题 | 不是管理日志，也不只是时间排序列表；选中上下文不发送问题，历史结论保留当时范围 |
| 调查概览 | 当前执行、状态待核实、待启动下一轮；已有结果摘要；人工待办和待确认事项；准备/启动及进入历史 | 回答“现在在做什么、已经得到什么、接下来该做什么” | 待启动与运行中可并存；准备只保存记录，启动才执行；概览不应重复铺满全部历史 |
| 调查历史 | 按轮次查看目标、触发原因、输入范围、执行状态、完整性及耗时/用量；选择指定轮次 | 回答“以前每一轮做过什么，与这一轮有什么不同” | 首次基础调查、范围更新和明确保存的助手结果分别识别；聊天消息不自动成为正式调查 |
| 成员告警 | 查看正式成员；添加告警/多个事件并去重；移动所选告警到另一案；查看告警；设计中的批量管理 | 控制调查的正式业务范围 | 添加与移动不同；移动影响两案；只改当前成员和后续待更新范围，不重写历史输入 |
| 案件关系图 | 阅读当前底图；查看节点/边依据；按实体扩展、推荐线索、预览、撤销/重置、保存探索、询问所选对象、确认加入案件 | 从已有范围发现可能遗漏的关联线索 | 展开和保存探索不改变成员；只有确认加入才改变范围。探索服务尚未实现；删除未用预留表不等于取消原产品目标 |
| 对象与证据 | 默认按对象搜索/分类；查看来源告警、证据、相关调查；切换按调查阅读查询/报告/原件 | 让用户从“这台主机或这个账号有哪些依据”开始查证 | 证据计数只是其中一项功能，不能代替对象浏览器；无对象归类的调查材料仍应可找到 |
| 人工任务 | 创建、分配、设置期限、编辑、完成或取消；填写结果和明确确认范围；阅读历史版本 | 补充AI无法取得的业务事实，并落实人员责任 | 不强迫工单或附件；完成者不等于负责人；完成只提供事实，不自动更新案件判断或启动下一轮 |
| 处理活动 | 查看成员调整、管理、任务和结果发布等操作的人、时间、对象及变化 | 核查“谁改了什么”，支撑交接和追责 | 与故事中的事实及认识发展、单轮执行步骤有不同职责 |
| 评论与附件 | 留交接备注、查看已有资料、打开/下载可用附件；上传等写入按实际接入范围提供 | 保存调查结论之外的协作说明及补充材料 | 评论不自动变成已确认事实；附件列表存在不代表上传和持久保存已实现，完整服务仍待接 |

## 同案AI助手

助手是Case内共用的交互区，案件页头、故事、单轮结果和图谱节点带入不同上下文，最终进入同一个案件对话。

| 功能 | 做什么 | 为什么需要 |
| --- | --- | --- |
| 上下文选择 | 显示整案、所选告警、指定调查、对象或人工结果，可在发送前核对 | 防止回答错案或把局部事实推广到全案 |
| 建议问题 | 提供适合当前材料的问题，点击后填入输入框供编辑 | 降低提问门槛，并保持用户对执行的控制 |
| 发送与分析 | 发送后用已有资料回答，必要时做允许的查询，明确处理状态 | 围绕具体问题补查，而非要求用户先编排工具 |
| 澄清与等待人工 | 说明不明确的范围或缺少的人工事实 | 把无法自动取得的事实交给人，不编造答案 |
| 回答与引用 | 展示结论、依据、对案件的影响、未确认部分和查询限制 | 用户能判断答案是否可信、是否值得保存 |
| 保存到调查记录 | 用户确认标题和结论后，冻结问题、答复和引用材料，进入历史及故事 | 将有价值的答复沉淀为正式成果，避免所有聊天淹没调查历史 |
| 查看历史与后续问题 | 保持同案对话、回查保存时的材料，区分当前人工结果与历史引用 | 支持持续调查，同时保持复核时的原貌 |

当前Q服务尚未开放。以上是已有设计，原型中的预置回答不证明真实问答完成。**发送问题、保存答复、采用为案件当前判断是三个不同动作**；保存不重跑模型，也不自动采用。人工明确采用的具体交互仍待确定。

## 每轮调查的五个阅读视图

| 视图 | 功能做什么 | 为什么需要 | 阅读后的下一步 |
| --- | --- | --- | --- |
| 调查发现 | 先给目标、原始范围、本轮结论、发现与依据、相比之前的变化、对案件影响、限制 | 让人快速判断本轮价值，避免只有“执行完成” | 查看依据、围绕结果提问、创建人工任务 |
| AI分析 | 阅读各分析环节、采用材料、过程和查询引用；助手保存记录可回查原问题与答复 | 理解结论如何获得 | 打开具体引用，必要时进入执行明细 |
| 查询与证据 | 查看查询来源、参数、返回、失败/查空/复用情况、输入材料和原件 | 核验结论到底依据哪些实际资料 | 打开同轮原文或返回调查发现 |
| 调查关系图 | 阅读当次保存的告警/实体关系、节点/边依据及图材料 | 复原“那一轮看到的关联” | 查看来源；要继续探索则转到案件关系图 |
| 报告与响应 | 阅读和下载报告；逐项查看建议目标、理由、审批信息及真实执行记录 | 便于交接，并核对建议是否已被执行 | 阅读真实回执；处置服务未接时不显示执行成功 |

执行明细是AI分析的下钻入口，用于检查步骤、输入输出、错误和用量，不应占据分析员主阅读流程。每个视图都保持同一轮身份；切换轮次后不能残留上一轮材料。

## 功能清单应如何表达设计意图

每个可独立验收的功能，至少写明：所在页面、谁在什么情况下使用、解决的问题、用户操作、操作后的业务结果、可回查位置和当前交付状态。字段与接口作为该功能的实现关联，不能代替目的和结果。

以“完成人工确认”为例：

| 项目 | 产品表达 |
| --- | --- |
| 为什么有 | 分析员无法仅凭日志确认业务授权，需要业务人员提供明确事实 |
| 在哪里用 | Case人工任务页；调查发现也可创建任务并带入来源 |
| 用户做什么 | 填写确认结果和适用告警/对象/时间范围，确认保存 |
| 得到什么 | 保存同一任务的新版本，保留完成人、完成时间及原历史版本 |
| 会影响什么 | 后续调查可以引用该事实；不自动把整个Case判为正常、不自动启动调查或结案 |
| 下一步 | 阅读已保存结果；需要重新研判时准备并启动下一轮 |
| 如何看完成情况 | 任务写读及版本已有服务能力；故事/助手联动与完整页面体验分项标记 |

建议后续清单使用四个独立状态栏：**设计是否确定、原型是否表达、服务是否接通、页面流程是否验收**。每栏记录实际状态与证据，不用一个“已完成”覆盖四件事。这样可以保留设计师的完整想法，同时不把后置能力或原型交互误报为已实现。

本轮仅形成上述产品盘点与评审建议，未修改原产品需求、功能清单、页面代码或业务规则。下一轮可据此讨论哪些是必须补写的既定设计、哪些规则需要先明确，再选择实施范围。
