# 13 移植、测试与二次开发分期规划

> 当前职责更新（2026-10-20）：下文保留最初完整上游移植的规划分析。用户随后明确仅负责告警及后续数据处理服务端，前端不考虑；当前阶段退出标准按[模块范围](../../operations/alert-processing-scope.md)和[执行计划](../../operations/dependency-migration-plan.md)，不再以全量源码、采集检测或控制台上线为条件。

日期：2026-10-20。策略依据：用户确认“先移植测试，再稳妥二次开发”；**不以 stingAISOC 当前建设进度或现有模块架构安排本路线**。

**最新环境约定：** 用户确认21为新项目部署环境；20为已有AiSOC参考环境。21的4个旧业务容器已关闭、数据与其他服务保留；本文件中的20现状描述是参考记录，不表示新应用已部署到21。


这里的移植，是以 beenuar/AiSOC 完整源码及原有架构为起点，形成独立、可构建、可运行、可测试的版本。先保留上游功能和模块关系，在实际测试后判断哪些保留、修复、替换或重做。不是先把 AiSOC 拆成零件接回现有实现。

本文件负责阶段、范围、依赖和退出标准；[01 总览](../../anal/01-system-map.md)负责模块编号，[02—11 专题](../../anal/README.md)负责行为分析，[12](../../anal/12-end-to-end-scenarios.md)负责业务链路。之前各专题针对旧建设路线提出的“采用/不照搬”建议，作为二次开发候选，不再作为首次移植的默认裁剪决定。

## 1. 总体安排

```text
第一阶段：完整源码与运行基线移植
    ↓
第二阶段：检测、Fusion、UEBA 与上下文链路接通测试
    ↓
第三阶段：分诊、调查、知识与人员工作流接通测试
    ↓

    ↓
第六阶段：依据已测结果开展二次开发
```

前四阶段均为“迁入/接通一组能力，同时做直接相关测试”，第五阶段复用这些证据做少量整链验收，不把全部测试留到最后，也不重复跑所有组合。第六阶段才集中调整产品流程、内部架构和功能策略。

| --- | --- | --- | --- |

## 2. 第一阶段：完整源码与运行基线移植

### 目标

拿到一个自己能够维护和构建的 AiSOC 版本，保持上游默认功能关系，先解决版本、环境与依赖，不先重写业务流程。

### 迁移内容

1. 固定上游 revision `34ca18c57dd4175539e5c6dd3d04a72dc057306b`，保存来源、许可、依赖与镜像版本。先不在测试中途追随上游升级。
2. 建立独立移植开发副本；本仓库 `opensource/AiSOC` 继续保持只读参考。20的 `/home/lychee/beenuar` 作为已有参考环境核对；新部署目标21，先确认独立项目、端口与数据目录，不覆盖现有数据和配置。
3. 纳入后端服务、前端、规则产物、SQL/其他存储初始化、测试、构建和部署文件；仅复制几个服务文件不算完整源码移植。
4. 跑通关键服务从固定源码构建/加载并启动的路径，保留源码与镜像的对应证据。官方镜像可作为对照，不能只部署官方镜像就宣称开发版本已可复现构建。
5. 核对 PostgreSQL、Redis、Kafka、Qdrant 等底座。后续确实依赖的 ClickHouse、Neo4j、OpenSearch、Enrichment、独立 UEBA 分批启用，不把 full profile 所有服务一次上线当作唯一办法。
6. 参考已经验证的43对话路由和20嵌入模型指纹，在21实际复现/绑定并验证；20仅loopback/容器网络的embedding地址不能直接供21调用。检查实际角色别名、模型、向量维度和集合。现有本地嵌入适配作为有来源的部署补丁保留，不偷偷算成原版行为。
7. 准备独立认证、测试 tenant、配置模板和凭据位置说明。先验证登录、API、前端同源代理和基本服务认证。

### 测试与退出标准

- 固定源码能构建/运行关键服务，启动命令与配置可复用；源码、镜像、overlay 可以对应。
- 页面可登录、基本 API 可读，重要服务 readiness 能反映真实依赖/消费者状态。
- Chat 和 embedding 分别测试；只做必要连通性和结构输出检查，不宣称模型质量通过。
- 保存一个最小输入→Fusion 告警→API 读取的 smoke。已有 20 golden 证据符合相同版本/配置时直接复用，不机械重跑。
- 已有持久数据保留；测试输入有明确标记和隔离，恢复到前一运行版本的方法清楚。

**20 目前的定位：** 已有 CORE、登录、Fusion golden、模型连通和三条嵌入 smoke，可作为本阶段起点；独立 UEBA、完整调查、真实响应等尚不能据此记为已验。具体已有证据见[部署记录](../../../deploy/aisoc20/README.md)。

### 暂不做

不统一所有状态模型，不更换数据库架构，不合并三套调查编排，不重写 UI，不删除尚未测试的上游模块，也不做现有 stingAISOC 的融合迁移。

## 3. 第二阶段：检测、Fusion、UEBA 与上下文链路

### 目标

让采集之后的数据真正进入检测、行为分析、融合和上下文查询。重点验证“输入发生了什么、为什么产生这条告警、其他相关信息能否查到”。

| 子批 | 迁移/接通内容 | 直接测试 | 预期产物 |
| --- | --- | --- | --- |
| 2A 事件/告警入口 | M00 输入；M01 单事件、窗口、序列；M21 session/lake 的实际使用路径 | 一条厂商 finding；一组普通活动事件；非法输入 | 来源坐标/ID、命中规则、普通事件与告警分流、session/历史材料 |
| 2B Fusion 与风险 | M02 去重关联/落库/发布；M17 confidence/RBA/priority | 重投、真实不同发生、同实体关联、跨 tenant | Alert、Incident 摘要、来源关系、评分解释、Kafka/API 一致性 |
| 2C 行为分析 | M13 CORE first-seen/baseline；独立 UEBA 服务与信号联动 | 冷启动、已知数值基线、一个偏离点、实体映射 | 实际增长的 baseline、anomaly、来源与 Fusion 加权解释 |
| 2D 上下文与增强 | M14 一组资产/账号/漏洞数据；M15 一个可用增强来源；M18 业务规则 | 有数据/合法无数据/依赖失败；规则命中/未命中 | 实体上下文、来源时间、partial、规则 before/after 与版本 |
| 2E 管理面生效 | M16 rule enabled/threshold/overlay 实际进入运行面 | 保存一条调整→加载→相同事件处理 | 配置与运行采用版本对应，其他 tenant 不受影响 |

### UEBA 的具体验收

分别记录 CORE 与独立 UEBA，不把两者混作一个服务：实体从哪来、提取什么特征、多少样本可评分、z=None 如何表达、个人/peer 更新顺序、异常是否发布、Fusion 是否实际使用。至少核对一次 PG/Redis 中的真实值变化，不能只检查 processed 数字。

当前代码中的累计 Welford、peer member_count、时间无关 Alert 指纹等行为先通过定向输入确认，再记为现状/问题；不会为对齐旧架构在测试前先替换实现。若缺陷直接导致测试无结果或不受控副作用，做最小修正并保留修正前后证据。

### 数据源处理

采集器开发不在本轮默认范围，直接使用既有规范化入口、可回链的脱敏样本和隔离合成数据。资产/身份可先导入有来源的有限测试集；不能把导入样本说成真实生产库存。没有商业情报 key 时，不宣称该渠道通过，用一个实际可用来源验证调用合同即可。

### 退出标准

能从固定测试输入解释检测、UEBA、Fusion、风险和上下文各自的结果；来源/tenant/时间/关系可查；增强失败与无命中区分。每个子批有直接相关正常场景和关键边界，缺失组件明确标记。此阶段不要求模型完成调查或执行响应。

## 4. 第三阶段：分诊、调查、知识与人员工作流

### 目标

由真实告警或分析员入口启动调查，实际查询材料和知识，得到能审阅、能回查的结果，并在原版工作台/Case 中完成基本操作。

| 子批 | 迁移/接通内容 | 关键测试 | 退出产物 |
| --- | --- | --- | --- |
| 3A 自动分诊 | M04 Kafka worker、规则/历史上下文、M08 角色路由与成本 | 明显恶意、真实误报、合法触发；模型不可用 | verdict、依据、tier、Run 与实际调用记录；没有误写执行成功 |
| 3B 默认 Case 调查 | M11 Case 关联告警；M05 默认 Recon/Forensic/Responder/Report | Case 真实告警材料进入 Prompt；工具返回进入分析 | Case→Run→工具/模型→结构结果/报告关系 |
| 3C 工具与知识 | M06 后端枚举/只读查询；M07 ATT&CK/TI/memory/KB | 每条准备使用的路径做入库/查询/实际消费；失败与空结果 | 真实查询回执、知识来源/引用、模型实际看见的片段 |
| 3D 其他调查入口 | 自动升级 graph、Router、Deep/M20 的源码已有入口 | 分别核入口选择、工具绑定、预算、流事件 | 各路径能力矩阵；不把默认 Case 成功外推到全部编排 |
| 3E 人员界面与交付 | M03 队列认领/分派；M11 状态；M12 轮询/实时/回放/导出 | 从页面走一次；结果与持久账本对照；隔离基本对象 | 分析员能找到告警、发起调查、查看证据和报告 |

### 调查先保留上游路径，再比较

默认 Case 调查先作为主要验收路径；自动升级、Router、Deep 分别列出“未接通/可启动/已完成代表验证/已知限制”。暂不在测试前把它们合并，也不因为有三套就默认都要长期保留。

知识要分开检查：ATT&CK 语义函数能检索，不代表调查有调用方；全文 KB 与 semantic memory 不是同一条链。某条准备投入使用的路径只有“索引成功”时，必须继续验证它如何进入实际调查；没有消费入口就明确登记缺口。

### 退出标准

至少一条主调查路径从告警/Case 到报告有完整同 Run 证据；实际模型、工具、输入视图、输出和成本来源可查；没有有效证据时输出未确认/不足，而非凭空完成。原版页面基本可用，Case、调查执行和响应状态分别展示。其他路径未通过的项不假装删除，也不阻止一个已限定主路径的交付。

## 5. 第四阶段：剧本、审批响应与反馈

### 目标

把调查结果接到上游已有的受控处理功能，验证建议、审批、执行、效果、结案和反馈的不同事实。

| 子批 | 迁移/接通内容 | 最小验证 | 交付 |
| --- | --- | --- | --- |
| 4A 剧本预览 | M09 匹配、条件/引用、dry-run、执行开关 | 实际 trigger 命中；未允许 live 时无厂商写调用 | Playbook Run、步骤和预览结果 |
| 4B 审批 | M10 请求身份、审批人、目标参数、API→Actions | 同意、拒绝、越权/自批；参数不丢失 | 审批与 action 关联、真实 dispatch 状态 |
| 4C 动作与回读 | 一种已配置能力/测试目标，区分两类 Actions API | dry-run；条件具备时做一次受控实际执行和效果回读 | operation/回执、verification 或 unverified/unknown |
| 4D 暂停/继续 | 剧本审批 pause/resume 与必要 wait/verification | 批准后仅继续对应步骤；拒绝停止 | 暂停与恢复记录、步骤结果 |
| 4E 结案与反馈 | M11 人工结案/重开；M19 override/经验；M16 调优提案 | 一次结案和理由回查；合法触发不计 FP；调优停在待审 | Case 结论、反馈来源、记忆/提案与实际生效边界 |

先保持真实响应默认关闭；测试 dry-run 与审批路径。真实执行仅针对明确的受控目标和可用凭据，不随“完整移植”自动对生产资产隔离、停账号或封禁。缺测试条件时保留“执行器未做真机验收”，不把 simulation 算实测成功。

### 退出标准

原版响应链可解释地运行：未批准不执行；批准参数与执行参数一致；HTTP 200 内的业务失败可见；执行回执与效果状态分开；Case 结案与反馈不改写原调查事实。至少完成一个剧本/审批/dry-run 代表；真执行未具备条件时，对应能力仍不得称已验可用。

## 6. 第五阶段：整链验收与可用基线冻结

### 验收范围

复用第二至四阶段有效证据，选少量覆盖不同分支的业务场景。以同一案例、同一组输入、同一版本证明跨模块衔接，不把多个 Run 的局部成功拼成一条成功链。

| 场景 | 覆盖路径 | 主要最终判据 |
| --- | --- | --- |
| 厂商直接发现 | finding→Fusion→队列→分诊→Case 调查→报告→处理→结案 | 输入来源、Case/Run/证据/建议/处置记录能对应；动作可先 dry-run |
| 普通事件组合 | 事件→窗口/序列与行为信号→Fusion→调查 | 实际规则/基线/实体与来源关系可解释，不把统计偏离当恶意证明 |
| 合法触发/误关联反例 | 授权扫描或相似但无实际关系事件→分诊/调查/反馈 | 不凭同 IP/相邻时间确认攻击链；BTP 与 FP 分开，反馈不静默禁规则 |
| 直接受影响失败 | 一个来源不可用或模型结构输出失败 | 保留 partial/unknown 与实际错误范围，不把故障解释为安全 |

不是四个场景都要强行使用每个模块；每个测试注明启用路径。已有场景足以证明某个模块时，复用其证据，只补衔接缺口。

### 冻结内容

1. 源码 revision、移植修改、构建/依赖/镜像版本、配置模板与规则版本。
2. 数据库/向量/图/湖的实际 schema 与启用范围，测试数据来源和模型指纹。
3. 主入口、辅助入口、测试样本/期望值、运行命令和结果证据索引。
4. 模块状态清单：**代码已迁入 / 依赖已启动 / 路径已接通 / 代表测试通过 / 未接通 / 已知缺陷**分别记录，不用一个“完成”覆盖全部状态。
5. 缺陷表：输入、复现步骤、实际/预期、中间产物、业务影响、临时限制、后续处理阶段。

### 退出门槛

选定主流程可复现、重要结果有来源；已开放功能没有已知越权或不可控副作用；核心阻塞已解决；尚未完成的能力在 UI/文档/配置中有真实边界。**可用基线不等于生产验收，也不要求先解决所有工程优化与所有厂商兼容。**

第三方系统未配、未完成的辅助调查路线可以作为明确缺口保留；如果缺的是本次承诺主流程的真实取证、结果交付或审批门禁，则不能靠登记缺口把主流程验收标过。

## 7. 第六阶段：基于已测版本二次开发

### 改什么，由什么决定

| 优先级 | 依据 | 典型工作 |
| --- | --- | --- |
| D1 业务正确性缺陷 | 第五阶段或模块测试的可复现问题 | 真正的新发生被永久折叠、来源失败当成功、错误结论、状态与事实不一致、越权/审批绕过 |
| D2 调查可用性与质量 | 实际案例的缺证据/问题未回答/引用不可靠 | 实际补查、结构化输出、支持与反证、知识实际消费、覆盖和报告一致性 |
| D3 人员流程与产品化 | 分析员使用过程的实际阻塞 | 队列、Case 协作、审批界面、报告呈现、反馈管理 |
| D4 能力扩展 | 明确业务需要且已有数据/测试条件 | 新厂商、更多知识、UEBA 特征、检测规则、狩猎及关系分析 |
| D5 架构与工程优化 | 已测维护成本、重复路径或规模瓶颈 | 编排收敛、存储边界调整、性能、可恢复性、部署强化 |

每次只处理一个可验收问题或纵向场景：先固定原基线和回归样本，再改实现、验证直接影响并更新可用版本。可以直接删改不再需要的旧路径，不建设长期双轨兼容；实际历史证据仍保持不变。

合并调查编排、统一知识模型、调整 Redis/PG 权威边界、换前端/框架等都放在这一阶段按证据决定，不因为分析文档里提出过建议就在第一次移植时全部实施。

安全微调、正式检索/调查质量评测、完整平台需求和生产部署需各自定义交付物，不能用“基线已经跑通”替代。这里没有删除任何产品需求，也不承诺首次移植覆盖全平台所有要求。
