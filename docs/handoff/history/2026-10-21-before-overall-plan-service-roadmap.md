# 告警处理服务端迁移路线

## 2026-10-21优先级修订

本路线以完整功能和正常业务结果正确为退出重点。所有一体模块可整体原样迁入，不额外修改或独立测试；冗余设计、服务可用性相关测试及修复登记后置。只做本次功能改动所需的最少代表验证，复用既有证据；不以重构、全依赖专项、故障恢复/压力矩阵作前置。源码保留不等于未测能力已通过。

完整告警/调查（含自动分诊、自动关闭和自动升级）为当前功能目标；review_only不再定义最终交付上限。当前按[完整性评估与修复规划](../../openspec/changes/restore-alert-investigation-integrity/proposal.md)核入口、身份、分诊→调查阶段/usage、融合合同与实际工具/知识/报告。仅规划，未启运行，原自治质量失败不变。

六阶段编号保留：第三阶段补全上述功能；第四阶段playbook/反馈专项暂缓，一体实现保留，不额外改测；第五阶段当前告警/调查功能验收聚焦告警→分诊→按策略关闭或升级→调查证据/报告及查询关系，不再要求先完成playbook/反馈或R02启动/退出/恢复专项。下文旧review_only/R02和第四阶段全闭环要求按当时计划保留，当前优先级由本节替代。运维恢复/备份等专项登记后置，不作为本次功能验收前置；必要业务正确性、tenant和结果交付仍需核对。审批/厂商响应实现不删除，真实副作用授权约束不变。

## 一、依赖与服务基线

从固定版本本地AiSOC参考复制范围内服务及其直接构建输入，按依赖逐批迁移、逐批验收。执行顺序为1B PG/Redis → 1C Kafka → 1F告警/Fusion/API最小数据链 → 1D向量/嵌入 → 1E模型网关 → 1G调查/响应服务基线。先确认非模型数据链，再增加模型/知识依赖；按需选用TI和上下文适配，不以迁完整仓或启动所有profile为目标。具体源码落点、开关、直接验收和恢复方法只在[批次执行卡](dependency-migration-plan.md#实际执行顺序)维护。

退出标准：

- 范围内关键服务能从固定源码构建、启动，源码、依赖、镜像和适配对应。
- 一个有标记的已有告警，经受控入口、Kafka/Fusion、数据库后，可由API读取；输入、实际中间结果及最终关系可查。
- 服务认证、tenant归属、基本角色授权和非法输入拒绝有直接证据；不依赖页面登录。
- 模型与embedding分别验证连通、结构和实际调用，不将连通性视为研判或检索质量通过。
- 21复用数据服务，项目对象与旧业务隔离，配置受控，启动/回退方法明确；不覆盖旧卷或现有业务数据。

## 二、告警归并、风险与上下文

接通M00/M02/M17/M18及范围内M13/M14/M15/M16/M21的消费能力。输入始终是已有告警；UEBA、资产、身份、漏洞和历史日志作为已有材料读取。

退出标准：重投与真实不同发生有明确结果；去重/关联、风险和策略可以解释；查询有数据、合法无数据与依赖失败可区分；tenant、来源、时间及告警关系可回查。普通事件检测、行为基线生产、资产扫描和通用日志采集不纳入本阶段。

| 子批 | 输入/实际中间产品 | 通过与恢复边界 |
| --- | --- | --- |
| 2A 去重/关联 | 同一投递重发、相同特征但不同发生、同实体不同告警、另一tenant → Fusion decision、PG来源关系、Redis关联与fused消息 | 每条输入有可解释最终行/关系；先记录原版指纹/去重语义，不为过测试先换算法。真实不同发生丢失或串tenant记阻塞缺陷；暂停输入/消费者并保留现场 |
| 2B 风险/处理规则 | 已知告警与已有实体材料 → 实际评分组成、优先级、例外/路由配置版本及运行采用版本 | 相同输入的变化能回链到配置/材料；另一tenant不受影响。恢复前一配置版本只影响后续处理，不改原结果 |
| 2C 上下文/增强 | 一组有来源的资产/账号/漏洞/已有UEBA/历史日志，及一条实际可用IOC来源 → 实际查询参数/回执、时间、引用 | 有数据、无匹配、依赖失败分别可查，材料真正进入告警处理。缺外部服务时标partial/未接，停止该适配不伪造空结果；不以新建库存、基线或数据湖替代外部合同 |

源码从对应Fusion/API路径及必要上下文客户端按调用关系迁入；优先使用[已有分析](../anal/README.md)中的定位和测试。只有直接阻塞本批结果的缺陷进入最小修复，其他风险保留问题单。

## 三、分诊、调查、知识与Case数据

接通M03—M08、M11/M12及当前告警相关的M20只读补查。优先验收一条主要调查路径，其他上游编排入口分别记录可用性，不在测试前先合并架构。

退出标准：由真实告警/Case发起的同一个Run，具有实际工具/模型调用、检索消费、证据引用、结构化结论和报告；服务端能查询状态、结果、失败、unknown和调用统计。Case状态与Run状态分开；无有效证据时保留未确认，不伪造完成。所有验收通过API、消息或持久记录进行。

| 子批 | 输入/调用/输出 | 直接验收 |
| --- | --- | --- |
| 3A 分诊（自治/人审分开） | 2A告警与来源材料 → 逐批启用Kafka worker → 真实模型调用/解析 → verdict、依据、升级决定与Run；限定基线计划另见[review_only_v1](c03-review-only-profile-plan.md)：原模型建议与effective needs_review/人工队列分列 | 旧自治质量门保留：一个明显恶意、一个有授权背景、一个材料不足样例，加模型失败边界；核实际送入材料、角色、usage、ledger。先禁自动graph升级，分诊稳定后再选定入口升级，不混成一个测试；人审profile另验R01代码隔离和R02有限main worker准入，不能写成原质量门通过 |
| 3B 默认Case调查 | 同一Case关联实际告警 → 主要调查编排 → 实际只读工具/模型 → 结构结果与报告 | Case/Alert/Run/步骤/证据/引用一致；保存真实模型可见材料及截断范围。队列查询、认领/分派、状态转换通过API验；他租户不可读，服务重启后已完成结果可回查 |
| 3C 知识与记忆消费 | 按[复用计划](knowledge-data-reuse-plan.md)使用已有及旧SOCAI知识，比较0.6B/4B并允许20/21分担；固定有来源的ATT&CK/TI片段和一条测试经验 → 入库/索引 → 查询 → 实际进入调查调用 | 索引成功、检索命中和模型消费分别取证；同/跨tenant、空结果、嵌入/检索失败有区别。先选所需路径，不把14条内置ATT&CK当全量知识；自动写回另测后才启用 |
| 3D 补查/其他入口/交付 | 当前告警的历史补查、按需其他编排入口 → 实际工具结果 → ledger/结果查询、报告导出与必要消息 | 每个准备开放的入口独立标“未接/可启动/代表验证通过/已知限制”；不用一个Case成功外推全部graph/router/deep。无前端/Realtime时主结果不丢失 |

迁入范围以1G服务为基础，补对应的模型/检索/工具调用实现及直接测试。准备一个固定小型样例集，按“证据支持、反证、材料不足”人工核对结果，不以单个READY或关键词自一致性当质量通过。每条实际调用记录usage；使用真实厂商/生产数据前单独核授权和脱敏，不要求同时接全渠道。

失败时停止新Run受理/自动worker并保留已受理Run、调用和原结果；仅在明确可恢复状态下继续，不通过覆盖结论或重新执行整条调查掩盖失败。样例集、模型、提示、工具和知识版本保留指纹，后续只回归本批影响面。

限定profile只收敛模型自治权，不删除三阶段的Case/Run/工具/检索/证据引用/必要报告质量和持久交付条件。模型建议默认unreviewed，人工依据真实证据形成结论；空、截断或无据报告不能因advisory标签通过。

## 四、剧本、审批响应与反馈

接通M09/M10/M19，并使用Case、账本和处理策略记录。先做dry-run和审批链测试；真实执行另需明确受控目标、凭据及审批，不因“迁移完整”而自动启用。

退出标准：提案、审批、dispatch、执行回执、效果验证和结案反馈分别有记录并能关联；未批准不产生真实写动作；unknown不自动重发副作用操作；反馈形成经验/待审提案，不自动向外部检测系统发布规则。

| 子批 | 输入/实际记录 | 通过与边界 |
| --- | --- | --- |
| 4A 剧本dry-run | 一条已验告警/调查结果及匹配剧本 → trigger、条件、步骤引用、预览Run | 命中理由和每步数据可查；真实厂商写调用计数为0；不建设可视化编排器 |
| 4B 审批/暂停继续 | 显式提案、目标参数、请求人/审批人 → approval、policy、pause/resume、dispatch | 允许、拒绝、越权/自批、参数被修改等直接边界；只有对应批准继续对应步骤。两类Actions入口分别核身份与tenant，不用一个入口通过替另一个背书 |
| 4C 受控动作与效果 | 具备明确测试目标/授权时的一种动作 → operation ID/厂商回执 → 独立read-back | executed与verified分别存；未知不重发。没有厂商条件则保留dry-run/替身证据，并明确真机未验；不宣称真实响应能力通过 |
| 4D 结案/反馈 | 同Case的调查结论、残余风险、响应/验证结果和人工理由 → closure、经验/待审调优提案 | Run与Case状态分离，原判断/证据不覆盖；合法触发不当误报。反馈不直接发布外部检测规则 |

响应副作用不能靠回退镜像撤销。恢复先停止后续dispatch，保留operation/approval/回执并核实际目标状态；是否补偿或逆操作必须另有明确目标和授权。只读调查服务可在响应链未通过时保留已验能力，但对应真实执行入口保持不可用并公开其限制。

## 五、限定范围整链验收与冻结

使用同一组有标记的告警/Case/Run贯穿数据链，复用前四阶段有效证据，只补直接缺口。通过API/消息检查最终数据、状态和证据关系，记录外部依赖缺失、未验厂商能力和不可用入口。

退出标准：可使用的告警处理服务基线已明确范围、固定版本、配置/镜像/补丁、测试证据、已知问题与回退方法。不以控制台、可视化、完整UEBA/检测平台或所有商业插件验收为条件；也不把这些范围外能力标成已完成。

若最终选择review_only_v1，完成名称必须限定为“人审profile告警处理服务端迁移基线”；须R01/R02及后续同链验收/独审通过。原自治分类/理由质量继续未过，自动关闭/QA/graph/自动playbook/审批提案/记忆写回/真实响应均不由此开放。有限R02窗口不授权日后持续常驻，C11必须另写准入租户、预算、输入边界和人工复核责任；主链、身份、持久与批准控制缺口仍阻止冻结。

冻结交付包至少包含以下内容，缺一项则仍为测试中版本：

- 版本对应：本项目源码/来源文件hash、依赖锁、镜像digest、overlay、启用开关、模型与向量空间指纹。
- 接口合同：告警受理与拒绝回执、查询/状态、Case/Run关系、审批/动作、结果schema和必要消息；标明兼容版本和tenant/权限来源。
- 验收索引：每批输入→真实中间调用/行/消息坐标→最终结果与关系，明确替身/基础设施/模型/厂商各层。
- 能力清单：每个开放入口的可用范围、直接关键边界、未接依赖、不可用项和风险；主链、身份隔离、持久结果或批准控制有缺口时不能用整体“通过”覆盖。
- 运维恢复：启动/停止、消费者暂停/继续、凭据受控位置、数据库备份/恢复的直接验证，以及对unknown动作的人工核查步骤。

只做一组跨模块整链场景及尚未覆盖的关键边界，复用版本/配置相符的批次证据。只有来源版本和输入合同相符时复用20记录；原20 ingest/控制台golden不能代替本服务新的告警受理和无前端交付验收。

## 六、依据实测问题二次开发

按前五阶段的缺陷及服务需要，小批改进并做直接相关回归。业务改动先限定目标、输入输出和验收；必要的删除/修改先讨论。是否调整编排、存储或共享模型依实测决定，不自动扩展到采集、检测或前端建设。

每项二开以一条已复现问题或明确需求进入：现状证据→目标行为→最小改动→直接验证→版本/问题表更新。架构调整必须说明替代范围、兼容与数据恢复，不将待考虑建议当作已决定任务。
