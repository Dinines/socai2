**结论：保留总体架构；确认1项P2实现缺陷，另有2项集成前须确定的合同边界。当前可以认可有限来源核对底座，不能认可完整智能调查已经正确有效。** 旧四角色与graph/Deep/Router融合、告警与Case分层、固定查询改由程序执行，均有明确设计修订和采纳依据，没有发现未经批准的整体方向偏离。下一步先修接缝、冻结完成语义，再完成最小交付闭环；扩展Case前必须验证实际调查收益。

## 1 确认的实现缺陷

### A1 P2 地址归一化不一致导致有效查询结果被拒绝

合法已核Alert使用IPv4映射的IPv6地址`::ffff:c000:246`和`::ffff:c633:6446`，能正常通过M1范围构造。API在替身CH返回下输出`ok/1行`，将地址规范为`192.0.2.70`和`198.51.100.70`；真实caller随后返回`error/query_response_contract_mismatch`。同一响应配原生IPv4 scope则为`ok`。反例没有篡改内部dataclass，也没有使用真实网络。

原因链为[scope.py](../../services/agents/app/investigation_v2/scope.py)第98行保留mapped IPv6表示，[records.py](../../services/api/app/investigation_v2/records.py)第93/102行转IPv4，[activity_records.py](../../services/agents/app/investigation_v2/activity_records.py)第59—64行对回执参数逐字符串比较；[evidence_view.py](../../services/agents/app/investigation_v2/evidence_view.py)第169—174行也作字符串匹配。因此只修caller仍会在下一层失败。

这是已承诺查询路径的功能正确性缺陷，会丢失有效结果；进入持久gate时还会消耗一次工具尝试。当前表现为保守误拒，不是越权。**应修复，且在扩大M6.2接线前完成。** 先固定scope/API/caller/证据层的地址等价与规范化合同，保留原字段出处，再逐层直接验证IPv4、mapped IPv6、原生IPv6及确实不同地址的拒绝对照。不得修改旧版本工具来顺带解决。

## 2 已复现的边界及设计裁定

### A2 P2 子窗口命中后的ready含义需要钉死

冻结范围5分钟，只查询其中1微秒且命中1条合法记录，当前M6.1返回`scope_readiness=ready`、`limited_objective_answered`、`blocking_gaps=[]`、`review_required=false`。实际查询窗口仍保存在coverage里。

此结果**不列为确认的既有实现缺陷**：查询准入允许子窗口，Q1问来源实际记录什么；存在性事实不要求先穷尽全窗口，当前精确规格也未要求固定路径必须查满整个窗口。主设计的`conclusion_scope`则是承诺回答的目标及事件窗口，下一层若将ready显示为“整个范围调查完成”，就会扩大承诺。相关位置：[scope.py](../../services/agents/app/investigation_v2/scope.py)第220/242/372行、[evidence_view.py](../../services/agents/app/investigation_v2/evidence_view.py)第353行、[fixed_recon.py](../../services/agents/app/investigation_v2/fixed_recon.py)第111行，以及[主设计第2.1节](../architecture/investigation-planning-design.md#21-结论覆盖与关联补查分开)。

**建议合同：** 固定路径默认查询完整冻结窗口；确需子窗口时分别保存目标范围、实际查询范围及未覆盖部分。只有政策明确以存在性来源核对为目标时，才允许有限ready；仍不代表全窗穷尽、恶意/授权裁决、关闭告警或免人工处理。M6.2实施前写清，M7验证最终展示。

### A3 P2 无模型路径依赖模型视图形成材料处理限制

当前M6.1必须消费合法EvidenceView。10条记录各带512字节ASCII正文时，视图11722字节，可得到有限ready；每条改为512个引号或反斜杠后，单项摘录仍合法，但JSON转义令整体超限，builder抛`complete_model_view_exceeds_byte_limit`。513字节Alert文本在视图构建时抛`data_only_excerpt_exceeds_byte_limit`。这样，完全不调用模型的程序路径也会被模型投影限制挡住。

这是确认的耦合限制，**不是I1/I2回归或安全绕过**：I1明确保留Alert原界限，I2选择超限阻断且未承诺10条可消费；M6.1精确输入也只是合法EvidenceView。关联位置：[evidence_view.py](../../services/agents/app/investigation_v2/evidence_view.py)第125/325/374行、[fixed_recon.py](../../services/agents/app/investigation_v2/fixed_recon.py)第43/59行。

**建议合同：** M6.2先确保身份/hash/scope已核材料的大小或可消费性投影阻断能持久交付`material_projection_blocked/partial`，保全部已提交材料/查询引用、限制原因和下一步，不能把已有材料说成来源不可用，也不能只传None而丢引用。再以小块拆开“核验后的来源材料”与“给模型的有界视图”，复用身份/hash/scope校验，程序事实读取前者，模型任务受12KiB完整messages合同控制。未读正文可能含反证，仍须按命题保缺口，不提高上限或静默删材料。

第6步的场景定义可在第2步提前做，实际模型试验仍按模块前置、独立身份和单Run额度推进。若首目标必须回答“为何可疑、是否批准、是否升级”，第6步的语义场景应优先于入口扩展；当前网络有限政策不能承担这个承诺。

**两张价值场景卡：** 一张给充分的来源/授权正反证，检验主分析能否独立回答性质、授权与不确定性；另一张初始输入缺少决定性事实，第一次查询结果确实决定下一次查询，检验Deep是否有增量。expected与业务输入隔离；同时设缺源、冲突、指令污染对照，分别评价模型原文、程序采用和最终交付。同目标/材料对照程序基线与模型，用有效答案、未支持断言、引用、调用/成本/时延评价；有效答案为零不能凭全partial放行。

当前[共同场景卡](scenarios/network-observation.v1.json)的告警telemetry已含匹配事件，只证明身份/范围/留存接缝，继续保留作回归。可以先以替身完成M5循环接缝，再让首个付费真实场景兼顾分支接线与增量价值；须先修订当步规格，不再为固定已知参数单独付费证明“模型会选唯一工具”。

正式M8前必须确定持久启动与唯一writer责任；Case整体分析前必须确定跨组材料与综合；自动政策前必须确定升级阈值与新Run额度准入。这些是各阶段放行条件，未完本身不算现有纯合同违约。IOC OpenSearch、持续增量调查、自动合并、通用恢复平台及真实响应继续后置。

每小步仍采用：**预期样例/输入输出 → 活动spec严格校验 → 仅实现本块 → 直接测试 → 必要的独立新版真实接缝 → 回执与未参与实现者复核 → 阶段提交/推送。** 失败先定位；历史失败/unknown不清除、不自动重放。本轮仅审计和规划，不因此部署、合main或勾选tasks2.2/2.3。
