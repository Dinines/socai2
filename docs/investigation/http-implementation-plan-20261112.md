## 2. 建议实施顺序

| 批次 | 完整交付范围 | 原因与边界 |
| --- | --- | --- |
| 1（已发布） | 告警人工判定、告警／事件单条管理和批量管理 | E48–E53，两端服务与Swagger已同步 |
| 2（列表已发布） | 三类列表筛选／排序／分页和完整结果导出完成；同范围事件归并统计本批完成 | E02/E26/E27及E54–E56；E57已实现，统一只读范围 |
| 3 | 采用已有调查结果、Case 评论、补充附件引用 | 补结果交接和人工补充材料；采用已有合格结果不必等待助手实现 |
| 4 | 同案助手发送／读取／追问／保存，以及故事中的相关记录与搜索 | 一次完成提问到保存后读回；保存与采用分开，不扩到全局助手 |
| 5 | 相似告警／探索候选查询，再做确有需要的探索保存 | 先解决“能找到真实候选”，再做画布保存；正式加入仍复用现有成员关联 |
| 后置既有 change | 新材料及人工反馈后的自动更新／接续 | 继续按“先固定流程、后更新／流式”的已确认顺序，不在本轮启用自动消费 |

这是接口工作的顺序。现有固定调查流程的真实结论质量继续在原任务中收口；独立的管理、查询等功能不因模型质量问题重复停做。每批实施时明确一个 OpenSpec 交付范围，完成输入→处理→保存→读取和独立结束审计后，再按获准范围统一发布服务、Swagger 和交接文档。

## 3. 第一批已交付接口

下列路径统一加 `/api/v1/socai2`。现有告警／事件详情已经返回负责人、状态、版本等信息，直接用于表单回填，不重复建设管理读取接口。

| 已实现操作 | 输入 | 保存及返回结果 | 保存后怎么确认 |
| --- | --- | --- | --- |
| `POST /alerts/{alert_id}/feedback` | 告警 ID、`operation_key`、`expected_row_version`、人工判定 `disposition`、理由 `reason` | 追加人工反馈，返回反馈 ID、判定、处理状态、告警新版本和活动引用；模型分诊保留 | E28 告警详情读最新人工反馈；E30 `activities` 读操作记录；关联事件／Case 提示变化但不改其结论 |
| `POST /alerts/feedback-batch` | 明确的告警ID／版本列表`items`、操作key、共用判定及理由 | 整批校验和保存；返回各项反馈回执及`changed_count` | E28/E30逐条读回；任何一项失败整批不写入 |
| `PATCH /alerts/{alert_id}/management` | ID、操作 key、预期版本；实际修改的负责人 `owner_id`、标签 `tags`、处理状态 `handling_status`；人工关闭理由 | 返回保存后完整`facts`、`changed`和活动引用 | E28 和告警活动读回；仅分配不改变处理状态，人工关闭不改判定 |
| `POST /alerts/management-batch` | 明确的告警 ID／预期版本列表、操作 key、共用`changes`及必要理由 | 按配置限制批量（当前100），整批校验后一次保存；返回逐项回执 | 逐条详情和活动读回；只处理勾选对象，不按文字相似批量改判 |
| `PATCH /incidents/{incident_id}/management` | ID、操作 key、预期版本；负责人、标签、状态、严重程度覆盖及对应理由 | 返回保存后完整`facts`、`changed`和活动引用；有效等级及来源在详情`derived`读取 | E29 事件详情及 E30 事件活动读回；不修改成员等级 |
| `POST /incidents/management-batch` | 明确的事件 ID／预期版本列表、操作 key、共用`changes`及必要理由 | 与单条相同规则；整批校验、一次保存，返回逐项回执 | 只检查所选事件，未选事件和所属 Case 状态保持 |

六操作编号分别为E48/E49单条／批量反馈、E50/E51告警管理、E52/E53事件管理。完整DTO、逐字段返回和错误见[Swagger](http://192.168.1.21:18080/)及[操作指南](../integration/backend-test-guide.md#告警人工判定与告警事件管理)。

第一批沿用的业务规则：

- 告警判定复用已有四个值：`true_positive`、`false_positive`、`benign`、`needs_review`。误报／正常关闭；已关闭告警改为真实威胁／需跟进时，带理由恢复处理中；其他反馈不自动改状态。告警关闭为 `completed`，事件解决为 `resolved`，不混用枚举。
- 事件按现有设计：分配后进入处理中，已解决事件仅改负责人不重开；人工解决需说明，严重程度覆盖保留理由，不改成员等级。事件、Case 和告警不级联结案。
- 操作者和时间由服务端记录；用户提交负责人 ID，不提交显示姓名代替身份。负责人／资产目录继续由业务后端维护。
- 局部修改中，省略字段表示不改，允许清空的字段用 `null`；标签用明确的完整列表替换。具体可清空范围按当前字段合同列明，不将缺值当清空。
- 同一操作 key、同一内容重试返回原回执；同 key 改内容、版本过期或状态冲突返回 `409`；主体不存在返回 `404`；枚举／理由／人员引用／批量范围无效返回 `422`。失败不得留下部分写入，未知执行先查详情和回执。

### 告警冻结字段核对

本批已核对 `latest_feedback_id`、`disposition`、`handling_status`、关闭／恢复字段、负责人／分配字段、`tags`、`row_version` 与 `business_updated_at` 的写入来源和读回位置；复用现有字段、表和D02，没有迁移。原47操作及106个Schema保持，模型分诊及材料版本不被覆盖。

已有规则不重新征求确认；若详细设计确需改告警字段名、类型、空值／枚举含义、关联或 GET 合同，则按 [AGENTS](../../AGENTS.md#调查数据库-v1-与人工确认)先提交具体差异、影响页面与兼容方案给负责人确认。新增写入实现不能顺便重定义旧字段。

直接验收只覆盖这一批：人工反馈保存→详情／活动读回；误报关闭与反向改判恢复；人工管理不覆盖原判定；事件分配／解决／严重度覆盖；批量仅改所选对象；重复提交／版本冲突不多写。不为本批建立全仓回归或新测试框架。
