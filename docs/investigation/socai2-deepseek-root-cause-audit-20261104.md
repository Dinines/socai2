# 调查失败归因：先确认设计、输入和校验，再评估模型

本轮按用户最新要求重新归因。不能再把失败统称为小模型能力不足，也不能将模型服务更换后仍失败直接解释成新模型不好。此次核对 r4 的 4 次和 r5 的 3 次真实 DeepSeek 原答，逐项对照数据库冻结材料、实际模型输入、发出的 Schema、供应商回显、输出原文及本地解析器。离线核对新增模型调用为 0，未修改原答、未绕过线上校验、未发布回放结果。

结论是：已经定位到我们自己的契约不一致、输入取舍、可见性语义和失败处理问题；另外存在一个供应商 Schema 约束未生效的实测现象，以及一处明确的模型语义越界。没有证据据此归因为 DeepSeek 参数量不足。

## 输入缺口的离线对照

对同一份 r4 冻结输入重建，事件模型视图与实际请求逐值一致，排除了“拿当前数据库替代旧输入”的误差。进程分诊不在模型输入，原因明确是顺序和空间，不是 guard 拒绝、原数据缺失或模型漏读。

只做一个排布实验：保留原 19 个 observation 字段和两份同次分诊，后移两条完整检测标签对象，视图为 7901 字节，可进入原 `8192-256` 预留线；没有增加额度或模型调用。r5 同类实验也能在原额度内保留 18 个 observation 字段与两份分诊。**该实验用于证明输入取舍可以调整，不是建议直接删除检测字段上线。** 正式修法应先确定必需字段、合并重复元数据、预留每个成员的同次分诊位置，再明确哪些可选项省略及原因。

这也解释了 r4 I 为什么看到旧网络分诊 `benign`：r4 A1 失败，成功指针仍指向 r3 A1；r4 I 读取的是这条已保存旧判断，并明确质疑它的依据。不能把“复述并质疑旧判断”误记成 DeepSeek 自己再次认定良性。存储新鲜度为 current 也不证明旧判断正确，最新尝试失败与历史成功结果需要区分展示。

## 本批模型运行设置及评估边界

当前新服务直接调用官方 `deepseek-flash` Responses；原 LiteLLM 与原配置保持。请求显式使用 `reasoning.effort=none`、3000 输出 tokens 和既有总额度。这是本次适配时为了保持原额度采用的运行策略，并不是对模型完整能力的评测，不能据此宣布模型达到能力上限。思考配置是否适合完整调查，需要与流程需求、耗时和预算一起设计，不能偷偷调高再拿不同条件比较。

本次 7 份原答均正常结束，没有输出截断。r4 C3 实际输出 1699 tokens，低于 3000 上限；本批首轮停止的直接原因是契约校验，不是输出 tokens 耗尽。也没有证据表明前述输入缺失来自 Fusion 前置数据。

## 后续顺序

1. 先确定 A/I/C 的模型输入合同：每成员必需事实、同次已有判断、来源状态与真实可见性分开；在原预算下核对取舍，不能靠提示弥补缺失输入。
2. 对齐输出合同和所有后置规则，尤其成员/事件背景的引用范围；把格式、引用、事实和交付状态分层。身份/来源越界继续阻止采纳，格式处理不能偷偷改事实或删不利证据。
3. 用这 7 份固定原件离线回放，逐规则核对，不增加模型调用寻找已可离线发现的问题。只有确认设计和实现一致后，再固定新候选做一批完整链验收。
