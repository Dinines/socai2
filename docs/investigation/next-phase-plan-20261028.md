## 业务范围与已有基础

告警保存来源、分诊及处理过程；事件汇总同组告警、展示AI概况；Case负责深入调查；Run记录一次具体执行；Tool提供查询能力；证据和报告使结果可追溯。事件沿用已有汇总与AI概况，不另建深入分析循环。

| 模块 | 已有基础 | 后续主要缺口 |
| --- | --- | --- |
| 告警 | 原详情、处理上下文、分诊/解释及旧Run读取；F4按告警查询Case关联 | 告警到新版Case Run的完整处理视图与准确覆盖关系 |
| 事件 | F1成员/分诊汇总，F2首次/手动AI概况及过期标记 | 相关Case、调查进展、结论摘要和跳转；概况尚未引用Case结果 |
| Case | 材料预览、成员/窗口选择、分析/查询循环、步骤、报告、历史、追加问题 | 多告警关联与成员覆盖的明确结果结构，更多可查材料 |
| Tool | 进程和网络两个事件湖工具；旧路径存在其他产品适配能力 | 产品HTTP能力尚未进入当前Case模型的实际schema与执行分派 |
| 调查公共能力 | 原ledger，Case步骤与报告读回，旧fixed/program独立读接口 | 各入口一致的执行索引、证据跳转和历史关系，不能把旧结果强行当作新版 |
| 应用接入 | 独立API v2 factory；替身直接功能验证 | 告警→事件→Case→报告完整接入与一次真实配置下的基本运行确认 |

当前实现详情见[Case初版](case-first-version-20261028.md)、[接口合同](interface-contracts-20261027.md)、[F4成员关联](case-linking-20261028.md)。表中的已有代码不代表已部署，也不代表真实模型判断质量已经验证。

## 开发顺序与每批完成标准

### 1. 告警处理与调查关联

- 复用现有告警处理上下文和分诊记录，在新版查询入口补齐所属事件、关联Case、与该告警实际有关的Run及跳转链接。
- 区分来源告警内容、分诊判断、当前人工处置、Case调查结论；即使没有发起调查，也能看到已保存的处理信息。
- Run是否覆盖该告警以Run固定的selected_member_ids为准；只在同一个Case里，不能算该告警已被本次调查覆盖。无可靠关联的旧Run继续走原入口。
- **完成标准：** 从一条告警可查到事件、分诊、相关Case及实际覆盖它的调查记录；没有调查时明确显示没有记录，不凭关联猜原因。
- **直接验证：** 一个有调查的告警和一个只有分诊的告警，检查输入输出和跳转即可。

### 2. 事件汇总接入已有调查结果

- 在事件读取中提供关联Case和Run的简要状态、结论摘要、覆盖成员/窗口及结果链接；完整证据仍在对应Run下读取。
- 当前结构化数据随读取更新，AI概况保持首次生成、后续手动刷新；手动刷新时可引用已有Case报告摘要，保留来源Run和覆盖范围。
- 新告警加入事件后，原Run范围保持不变；事件显示新增成员尚未被原Run覆盖。Run结束不等于事件已解决。
- **完成标准：** 事件能回答“有哪些告警、各自如何处理、哪些被调查、结论在哪里”，AI概况可注明采用了哪些已有报告。
- **直接验证：** 一个三告警事件中仅两条被调查，再加入第四条；核对覆盖范围、摘要来源和链接。普通GET不触发模型。

### 3. 接入第一个产品HTTP Tool

- 优先补现有工具确实缺少的材料，例如进程父子关系或产品告警详情；实际首个能力依据可用产品接口确定，不虚构字段。
- 按告警来源connector绑定产品实例；服务端负责地址、凭据、租户和固定范围，模型只提交业务查询参数。
- 让能力真正进入当前CaseTools的定义、选择、HTTP调用、返回解析、Tool消息、证据保存及报告引用整条路径。复用已有产品适配器能解决的问题不重新建设平台。
- 模拟服务只用于提供清晰的请求/响应示例；实现规模限于该能力，不建设通用模拟器或插件管理平台。
- **完成标准：** 模型可见工具定义，程序发出正确HTTP请求，记录保留来源ID/request_id，结果正确回传并可在步骤和报告中追溯。
- **直接验证：** 正常、空结果、查询失败三个基本场景。新Tool写法及映射遵循[接入指南](tool-onboarding-and-flow-verification.md)。

### 4. 完善Case的多告警综合分析

- 在现有循环上补明确的成员覆盖、跨告警关联、行为时间线与未决问题；不用再建第二套调查执行器。
- 区分“时间相近/实体相同”与“证据支持因果”，说明哪些成员支持结论、哪些只是背景、哪些缺少材料；read_member_ids不当作逐成员已完成分析的证明。
- 按具体问题选择可用Tool补查；追加问题继续形成关联的新Run，保留历史结果和查询来源。
- 专项Deep或领域解释只有在普通Tool循环确有功能缺口时接入；输出回到同一Case报告，不强制每次调用所有角色。
- **完成标准：** 多成员Case能输出带成员/来源引用的关联判断、反证和缺口，而非只复述告警摘要。
- **直接验证：** 两条相关告警加一条无关告警的固定例子，检查关联依据及未解决项；只修改实际影响功能的提示、字段或调用逻辑。

### 5. 补齐公共调查查询与证据跳转

- 提供可按告警、事件、Case查找的调查执行索引，明确Run类型、执行状态、结果完整度和原生详情地址。
- 串起发现→证据编号→Tool调用→来源记录；追加调查可回到前次Run，下载报告与所选Run一致。
- 复用现有步骤/报告能力，统一的是查询入口和关系表达，不重写所有历史Run格式；无法确定归属时保留未知。
- **完成标准：** 从任一业务入口进入同一Run时，看到相同范围和报告，并能继续查看证据来源。
- **直接验证：** 用前面已有样例从三个入口读同一Run，不另建回放或兼容性测试工程。

### 6. 完成应用接入和基本运行

- 整理一个明确的新调查API组合入口及必要配置；不因为旧fixed/program能力未配置而阻塞已经可用的告警、事件、Case功能。
- 给调用方固定输入输出及跳转路径；有现有界面时按这些接口接入告警详情、事件概况、Case调查和报告查看，前端仓库/入口需以实际项目为准。
- 在选定开发配置中，用一个已有Case及确定的数据源走通真实模型和查询；只确认基本运行与实际字段，不启动生产部署或大规模质量评测。
- **完成标准：** 调用方能走完告警→事件→Case调查→报告→追加问题，接口配置、数据保存、结果读取一致；明确记录哪些真实依赖已验证。
- **直接验证：** 一条完整业务路径，修复阻断功能的实际问题。真实配置未就绪时继续完成独立功能，不把环境准备拆成长期前置审计。

## 执行原则与边界

- 每批以功能交付为单位：必要的接口细化→实现→少量直接验证→更新调用说明→下一批。已通过且未改变的部分不反复测试。
- 不开展权限、可用性、压力、恢复、故障注入专项，不引入大规模测试辅助代码或逐层审批门。
- Case触发/自动匹配政策仍不作为功能开发前置项；F5旧自动入口接线暂不加入这六批，后续需要接入时再按明确规则办理。
- 事件不增加深入分析循环，报告建议不自动执行隔离、封禁或其他响应动作。
- 规划当轮只更新文档；后续按用户“持续推进”实施上述功能。真实调用、迁移与部署状态单独按实际记录，不因代码完成而宣称已上线。

**第1、2项已完成代码；下一批第3项：接入首个产品HTTP Tool，优先补来源connector绑定和实际返回内容，再接当前Case模型调用链。** 后续按第4–6项推进，不把“整个调查模块”缩减为Case内部API，也不重做已有功能。
