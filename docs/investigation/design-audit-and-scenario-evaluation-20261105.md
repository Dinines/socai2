## 第一轮：设计合理性审计

### 1. 应当保留的设计

| 设计 | 判断与理由 | 必须保留的边界 |

### 2. 需要处理的四项问题

本文 P1 指直接阻断核心调查交付，P2 指影响设计一致性或产品闭环；优先级用于建议排序，不表示本轮已经修改实现。

#### D1 · P1 · 只预留最终模型调用次数，没有预留最终综合所需的容量

**性质：已有实证的功能阻断，属于已知未解决项。** C 全轮共享 4 次模型、4 次 Tool、24000 tokens 和 120 秒。执行器为 C6 预留 1 次模型，但明确没有独立保留 tokens 或时间。C3/Deep 能合法消耗前面的资源，留下“还有一次调用次数，但最终请求已放不进去”的状态。

这不是仅由大案触发的理论风险。[当前修复证据](current-investigation-audit-20261105.md)中的三个固定 C6 包，必要材料已完整保留，模型数据视图分别为 7943/7966/7894 B；完整请求仍为 16527/17262/17939 B，超过扣除已报告 usage 与输出预留后的请求允许量 13458/9314/13274 B。最终调用被阻断，不能形成新的有效案件结论。视图小于 8 KiB 并不能证明整轮预算足够。

**最小建议：** 保留共享硬上限；在分配 C3 和 Deep 之前，按完整请求（包含提示、Schema、材料和输出预留）为 C6 留出可解释的最低容量，同时定义可完成的输入规模。补查应在剩余容量内按关键问题选择，容量不足应明确交接。不能以删掉必要 H、反证、原计划或重置 usage 来制造通过。具体额度需要后续实施与新样本验证，本审计不直接建议放大上限或更换模型。

证据定位：[执行计划](../../services/api/app/socai2/baseline_executor.py)的 `final_model_calls_reserved` / `call_slot_only_tokens_and_deadline_still_shared`；[预算函数](../../services/api/app/socai2/baseline_analysis.py)的 `budget_reason`；[固定 C6 回执](../operations/evidence/current-investigation-audit-20261105/fix-validation-20261105T023329/validation.json)。字节在当前预算门中作为保守输入计量使用，以上差额不是实测 tokens，也不证明精简同等字节必然足够。

#### D2 · P2 · “程序直接查询”在主设计中存在，在完整执行器中没有对应路线

**性质：设计与实现不一致。** 主设计第 4 节区分“参数明确时程序直接查 Tool”和“根据返回继续决定下一步的 Deep”。当前 `Followup` 虽有 `mode=query/deep`，却没有直接查询绑定字段；完整执行器把两者都交给同一个问题级 `deepen`。Deep 先调用模型选择绑定，查完后再次循环决定答案或下一查。

因此，一项确定查询也可能占用两次 Deep 模型调用：C3 一次 + Deep 两次 + C6 一次，已用完 4 次额度。第二个不同问题随后只能因最终调用预留而停止。现实现按 C3 返回顺序、每个问题至多启动一次 Deep；没有独立的优先级或成本字段。这里的“两次”是可出现的场景，不是每个 Deep 都必然调用两次；预算停止会留痕，并非偷偷跳过。

**最小建议：** 先统一合同。若保留直接查询，就让服务端从已验证的问题、对象和工具绑定生成一次确定查询，无需再次让模型选择，结果交 C6 综合；动态取证才进入 Deep。若决定当前阶段全部走 Deep，则应修改主设计的承诺，明确能处理的问题数量和分配规则。无论哪条路线，都应先处理最影响结论的证据缺口；本轮不增加新 Agent 或自主循环。

证据定位：[主设计 C4](../architecture/investigation-planning-design.md)、[Followup 合同](../../services/api/app/socai2/baseline_analysis_contract.py)、[执行器路由](../../services/api/app/socai2/baseline_executor.py)、[Deep 查询循环](../../services/api/app/socai2/baseline_deep.py)。

#### D3 · P2 · 页面与服务端尚未形成同一条可操作流程

**性质：已声明的实现缺口，不是本轮发现的后端回归。** 页面目前仍由本地数据和 `localStorage` 驱动，新 `socai2` 服务端已经有版本化 H、pending Run、输入新鲜度和采用规则，但页面尚未读取这些合同。只改字段名称或给页面接一个结果接口，不能完成对接。

两个直接例子：① H 服务要求完成结果有显式 `result_scope`，修改结果会重新记录完成者和完成时间；原型使用可选 `referenceContext`，保存同一个本地任务，已有 `completedAt` 可以沿用。② 服务端允许“执行中 + 下一 pending”，而原型的活跃状态集合还包括 pending/queued，直接映射会混淆正在运行与等待启动。Case 列表和统计也没有新的独立集合 GET 出口；告警/事件列表现有出口仅固定分页，交互筛选和管理写入未覆盖。

**最小建议：** 保留已确认布局，先接通 Case 当前判断/范围 → pending 准备与启动 → 历史结果 → H 确认 → 再准备/启动这一条闭环。明确等待、执行、unknown、部分交付、过期各自文案和按钮条件。Q、响应执行等后置能力继续如实标明，不作为已完成的验收项。

证据定位：[原型数据保存](../../prototypes/security-pages-v2/app.js)、[任务表单与保存](../../prototypes/security-pages-v2/case-workflow.js)、[原型 Run/判断投影](../../prototypes/security-pages-v2/investigation-workspace.js)、[Case DTO](../../services/api/app/socai2/case_contracts.py)、[H 合同](socai2-human-tasks-20261104.md)、[页面读取边界](socai2-page-reader-20261104.md)、[当前 OpenAPI](../design/socai2-independent-api-v2.openapi.json)。

#### D4 · P2 · 活动设计文档对输入更新是否阻止采用有相反表述

**性质：当前文档自相矛盾。** `complete-socai2-investigation-chain/design.md` 的“C 并发规则”第 44 行已写明 125 检查材料、判断指针和 H 语义，过期输入不采用；紧邻第 46 行仍写“相同成员的材料或 H 后来更新……不会自动阻止该冻结轮结果采用”。后一句与当前迁移函数和读取合同相反，且没有标为历史。

**最小建议：** 后续修订该段为：冻结轮保留；受跟踪输入在采用前变化，则拒绝自动采用；已采用判断不删，但读取时可以显示 stale；用户显式准备并启动新轮。外部湖、库存和 TI 的所有变化并不都在 125 检查范围内。本文按源码及最新审计解释，不改写原设计正文或历史回执。

依据：[冲突段落](../../openspec/changes/complete-socai2-investigation-chain/design.md)、[125 迁移](../../services/api/migrations/125_socai2_baseline_input_freshness.sql)、[当前审计 A01](current-investigation-audit-20261105.md)。

### 4. 已知约束，不应误报为新的设计缺陷

- **输入容量：** 主设计已明确 200 成员是存储上限，不保证能在 8 KiB 视图和固定输出内完成；不应再说设计完全没定义这个限制。尚缺的是经过验证、可告知用户的实际可完成范围，属于 D1 的验收工作。
- **四领域能力：** 当前主要是 C3 中四个领域的适用性和发现表达；C4 可查认证/进程/网络及受限产品日志，不能由“四领域”推出云、邮件、身份平台均有完整原生取证。仅有用户对象、没有主机绑定时，也不能假定现有主机查询能查完整认证历史。
- **新鲜度：** 125 检查成员范围、材料/分诊/反馈指针、事件诊断/成员和已完成 H 语义。仅外部湖新增日志、资产或 TI 更新，不必然使 `input_freshness` 变 stale；`current` 的含义必须限定在这组已跟踪输入。
- **身份与查询：** `source_namespace` 不是原始业务环境名称。现有湖查询按租户、主机、事件类型和窗口限定，不由命名空间额外证明某条上下文记录就是某告警的因果证据。
- **不确定执行：** unknown 占槽、不自动重试是当前已选边界；明确 400/422 Schema 拒绝可以失败收口。当前未提供通用恢复流程，影响无人值守使用范围，但本轮不把恢复框架追加为核心功能前置。
- **部分采用：** 同范围、新鲜且通过门控的部分结果可以采用；可能只覆盖部分成员，不承诺覆盖比上一判断更多。旧判断及来源保留，页面必须让覆盖变化可见；是否另外增加采用策略需单独产品决定，不能在本次审计中替用户改规则。

第一轮判断：保留分层、冻结、证据身份、手动多轮和 H 版本设计；优先处理 D1、统一 D2，并以 D3 的最小页面闭环作为交付边界。D4 应在后续设计修订时消除，避免实现者依据相反规则开发。

### 5. 场景推演

以案件 X 的成员 A、B 为例；第二案 Y 初始有 C。所有例子均是假设输入，不代表新增了业务记录。

| 场景 | 推演路径与应有结果 | 当前判断与证据 |
| --- | --- | --- |
| S01 两成员首次完整调查 | 创建 X(A,B) → pending → 用户启动 → 冻结 A/B → C2/C3/补证/C5/C6 → 有效结果才采用 | 流程责任清楚；完整执行已有替身验证，真实最终 C 验收仍未通过，不能评为完整可用。D1 是直接阻断项。[执行账本](current-execution-ledger.md)、[既有真实结果](kafka-to-conclusion-validation-20261105.md) |
| S02 启动前连续添加成员 | pending(A,B) 后加入 C，再加入 D → 更新同一未领取 pending → 启动时冻结最新四成员 | 规则成立，避免每次点击都生成执行轮；页面须呈现等待启动。[成员合同与隔离验证](socai2-case-relations-20261104.md) |

### 6. 本轮离线核验及历史证据的含义

### 8. 建议的下一轮顺序与验收重点

1. **先修完整 C 的资源分配，并统一 query/Deep 合同。** 用小范围、必要事实齐全的输入确认 C3/补证/C6 各自可完成；完整请求和实际 usage 都进入核算，必要材料不能静默丢失。同步消除 D4 的相反说明。
2. **再验证“C → 明确范围的 H → 下一 C”。** 检查新证据是否真正进入最终请求及结论、人工确认的事实/授权是否保持声明范围、与上轮比较是否准确；同时允许说明该事实对整案解释的影响。缺源仍可合理输出未决或部分交付，不要求强行定性。新批才产生新实测结论，旧失败和 unknown 保留。
3. **接通最小页面闭环。** Case 队列/详情、当前判断覆盖与新鲜度、真实 pending/start、历史结果及 H 版本共用服务端合同；验证执行中同时存在下一 pending 的展示，避免“保存 H 就已更新结论”的误导。

质量评估应逐项核对事实、引用、授权范围和结论变化。`needs_review` 或证据不足不自动算误判；没有独立真值不报告准确率。无需为了本轮设计评估调用用户提供的 API token，也无需新增模型、表或 Agent 框架。
